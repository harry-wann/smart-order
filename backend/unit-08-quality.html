單元 08 · NORTHWIND LAB

驗證、例外與測試：讓錯誤也有規格

沿用 Northwind 商品 API，從負價格、查不到商品，到可重複執行的測試。

Spring Boot 4 主線有差異再看 Boot 36 個閱讀步驟

先備觀念：已學過請求資料、狀態碼、資料查詢與交易；還不需要先寫完第 10 單元。

讀完能做到：分清輸入驗證、業務例外與測試，各用一個小例子看見成功和失敗。

01 · 格式驗證與業務規則分開

@NotNull 要求有值，@DecimalMin 限定最低金額，@Digits 限制整數與小數位數。它們來自 jakarta.validation.constraints，需要 spring-boot-starter-validation。先知道規則，再看它們貼在哪些欄位。

Validation（資料驗證）先檢查資料形狀：名稱不能空白、價格不能負數。業務規則則包括「分類必須存在」、「已下單商品不可直接刪除」。前者放在請求 DTO，後者由 Service 與資料庫限制共同處理。DTO 是 Data Transfer Object（資料傳輸物件）。

@NotNull 要求有值；@DecimalMin 設最低值；@Digits 限制小數位數。這些來自 jakarta.validation.constraints，搭配 spring-boot-starter-validation。@DecimalMin 本身不會拒絕 null，所以要加 @NotNull。

02 · 讓 Controller 真的啟動驗證

前一節把規則寫在請求物件上，這一節才啟動檢查。@RequestBody 先把 JSON 轉成物件，@Valid 再要求驗證規則；不是寫了規則就會在所有普通 Java 呼叫中自動執行。

@RequestBody 將 JSON 請求本文轉成 DTO；JSON 是 JavaScript Object Notation（JavaScript 物件表示法）。@Valid 觸發 Jakarta Validation 檢查。若價格 -1，請求應在進入 Service 前回 400。

這段先展示請求入口，ProductView 是 05 定義的回應形狀。完整修改方法會在 10B 串上資料庫；目前只追蹤：合法輸入進 Service，負價格先回 400。

03 · 不存在與資料衝突要分得開

Exception（例外）是程式以特殊方式回報處理失敗。普通 Java 例外不會自己變成 HTTP 狀態碼；@ExceptionHandler 指定例外要由哪個方法轉成回應。@RestControllerAdvice 把這種處理集中到一個類別。

ResponseEntity 可以設定 HTTP 狀態與回應內容；ProblemDetail 是 Spring 提供的錯誤資料物件。下面先定義查不到商品的例外，再示範如何回 404。

@RestControllerAdvice 可以集中處理不同 Controller 的例外。ProblemDetail 是 Spring 提供的標準問題回應物件，包含 status、title、detail 等欄位。最終實作使用同樣風格，並加上 400／409。

不要把 SQL、資料庫密碼或整段堆疊回傳給前端。資料庫外鍵阻擋刪除可回 409；未知失敗記錄在伺服器後回一般錯誤訊息。

04 · 先用已知的例子理解單元測試

Unit Test（單元測試）驗證一小段功能。JUnit 是 Java 測試框架；@Test 標示一個測試方法；assertEquals 表示「實際值應等於預期值」，不相等就算失敗。

@Test 來自 org.junit.jupiter.api.Test；assertEquals 以 static import 匯入 org.junit.jupiter.api.Assertions.assertEquals。這段放在測試類別內，且需要 03A 的 ProductCatalog、TrainingCatalog、ProductLabel 同套件類別。

你在 03A 已經手動看過輸出；現在把「看到的結果要是什麼」交給工具反覆檢查。未來有人把標籤格式改壞，就能在測試時發現。這裡不需要資料庫，也不用測試替身框架。

05 · 然後才測網路入口

Web 測試要確認的不只是方法結果，而是請求進入 Controller 後，有沒有轉成對的 HTTP 狀態與資料。MockMvc 是 Spring 模擬這條處理流程的測試工具。

送什麼要檢查什麼
PATCH 價格 -1回 400，而且不執行修改
GET 不存在的商品回 404，而不是 200 搭配錯誤文字
POST 合法商品回 201，並提供新商品位置

此時先讀懂測試目標。10D 會在 Controller、Service 與例外處理都寫完之後，提供可直接放進專案的兩份完整測試，避免現在突然引用尚未出現的類別。

06 · 什麼時候才需要資料庫測試？

Integration Test（整合測試）確認 Repository、實際 SQL 與 SQL Server 能共同工作。E2E 是 End-to-End（端對端），從真正網路入口驗證完整流程。用 SQL Server 的測試副本驗證外鍵、money 型別與原生 SQL，不能只靠測試替身。

停一下，自己想想

Controller 測試全綠，是否代表查詢 SQL 一定正確？

看解釋

不是。這裡把 Service 換成替身；真正資料庫行為要在整合測試或最後單元的人工驗收檢查。
