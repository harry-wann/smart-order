01 · 查不到商品，和輸入錯誤不同

先定義兩種錯誤物件，再讓 Service 使用。RuntimeException 是 Java 執行期例外的基底類別；extends 表示繼承，super(...) 把訊息交給父類別的建構子。這裡還不決定網頁回應，下一頁才轉成 404／400。

RuntimeException 是執行期例外。稍後集中把 ProductNotFound 轉成 404、InvalidInput 轉成 400；這裡不處理 HTTP 回應，讓業務邏輯與傳輸方式分開。

02 · 更新沒有 save，回想單元 07A

required 查找受管理的實體；apply 查分類並更新五個欄位；在交易內轉成回應。Hibernate 在交易提交時同步修改，所以這裡不必再呼叫 save。找不到商品就回 404，本課 PUT 不做「不存在就新增」。

03 · 展開前，先讀懂三種 Java 寫法

完整檔案把重複步驟抽成小方法：required(id) 負責找到商品，找不到就丟出例外；apply(product, input) 負責查分類並套用輸入。它們是本課自己命名的方法，不是 Spring 特殊語法。

寫法先用白話理解
Optional<Product>Optional 是 Java 的容器型別，表示可能有商品，也可能查無商品；不是 Spring Bean 容器。findById 的結果就是它。
orElseThrow(() -> new ProductNotFound(id))有商品就取出；沒有才建立並丟出例外。() -> 是 Lambda（匿名函式）寫法，這裡表示一段尚未執行、沒有參數的動作。
PageRequest.of(page, size, Sort.by("id").ascending())PageRequest 是 Spring Data 的分頁條件，指定第幾頁、每頁幾筆、按照哪個 Java 屬性遞增排序。
stream().map(ProductView::from).toList()Stream 是 Java 的逐筆資料處理介面。map 對每筆資料做轉換；ProductView::from 是方法參照，意思是對每筆商品呼叫 ProductView.from；toList 收集回清單。

04 · 完整 Service

展開完整範例 · ProductService.java

類別預設 readOnly=true，寫入方法再用 @Transactional 改為寫入交易。stream().map(...).toList() 是把每筆 Product 轉成 ProductView 的 Java 集合處理方式。

list 先限制 size 最大 100，再固定按 id 排序，避免不受限的大量查詢；page 從 0 開始。超出最後一頁回空清單，不是 404。這種分頁在資料同時新增／刪除時仍可能位移，進階需求再考慮游標分頁。

05 · Northwind 的業務限制

新增／完整更新先確認分類存在；資料庫外鍵則提供最後保障。刪除時 flush 讓外鍵違反能在方法執行期間浮現，交給全域例外處理回 409。不要為了刪除商品而連帶清空歷史訂單明細。

本課的庫存欄位是管理者設定存量，不是扣庫存系統。如果要實作多人同時下單，需加入條件式更新或鎖定，避免兩個請求覆蓋彼此；不能把這份 replace 當成已完成併發庫存控制。

Optimistic Locking（樂觀鎖）常用版本欄位偵測並行修改，但經典 Northwind 沒有對應欄位，不能只加 @Version 就期待能用。需要先規劃資料庫結構變更，這列為後續延伸。
