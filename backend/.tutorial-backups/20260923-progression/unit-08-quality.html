驗證、例外與測試：讓錯誤也有規格

沿用 Northwind 商品 API，從負價格、查不到商品，到可重複執行的測試。

01 · 格式驗證與業務規則分開

Validation（資料驗證）先檢查資料形狀：名稱不能空白、價格不能負數。業務規則則包括「分類必須存在」、「已下單商品不可直接刪除」。前者放在請求 DTO，後者由 Service 與資料庫限制共同處理。DTO 是 Data Transfer Object（資料傳輸物件）。

@NotNull 要求有值；@DecimalMin 設最低值；@Digits 限制小數位數。這些來自 jakarta.validation.constraints，搭配 spring-boot-starter-validation。@DecimalMin 本身不會拒絕 null，所以要加 @NotNull。

02 · 讓 Controller 真的啟動驗證

@RequestBody 將 JSON 請求本文轉成 DTO；JSON 是 JavaScript Object Notation（JavaScript 物件表示法）。@Valid 觸發 Jakarta Validation 檢查。若價格 -1，請求應在進入 Service 前回 400。

03 · 不存在與資料衝突要分得開

@RestControllerAdvice 可以集中處理不同 Controller 的例外。ProblemDetail 是 Spring 提供的標準問題回應物件，包含 status、title、detail 等欄位。最終實作使用同樣風格，並加上 400／409。

不要把 SQL、資料庫密碼或整段堆疊回傳給前端。資料庫外鍵阻擋刪除可回 409；未知失敗記錄在伺服器後回一般錯誤訊息。

04 · 單元測試：不用啟動資料庫

JUnit 是 Java 測試框架；@Test 宣告測試。Mockito 是測試替身工具，mock 產生替身，when 定義回應，verify 確認互動。這就是建構子 DI（Dependency Injection，依賴注入）的價值：直接傳入替身即可。

05 · Web 測試：檢查 HTTP 合約

展開完整範例 · 完整測試 · ProductControllerTest.java，主線 Boot 4

HTTP 是 Hypertext Transfer Protocol（超文字傳輸協定）。MockMvc 模擬 Spring MVC 請求，不啟動真正伺服器；@WebMvcTest 只載入 Web 測試範圍。這兩個測試接到最終實作的 Controller 與例外處理，不驗證 SQL Server 的外鍵行為。

Boot 3 對照

本例 Boot 4 使用 spring-boot-starter-webmvc-test。Boot 3 的 @WebMvcTest import 是 org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest，使用 spring-boot-starter-test。Boot 3.5 可直接用 @MockitoBean；較早 Boot 3 專案可能仍用 @MockBean。若已加安全設定，寫入測試還要帶登入身分與 CSRF token，不要靠關掉安全測試通過。

06 · 什麼時候才需要資料庫測試？

Integration Test（整合測試）確認 Repository、實際 SQL 與 SQL Server 能共同工作。E2E 是 End-to-End（端對端），從真正網路入口驗證完整流程。用 SQL Server 的測試副本驗證外鍵、money 型別與原生 SQL，不能只靠測試替身。

停一下，自己想想

Controller 測試全綠，是否代表查詢 SQL 一定正確？

看解釋

不是。這裡把 Service 換成替身；真正資料庫行為要在整合測試或最後單元的人工驗收檢查。
