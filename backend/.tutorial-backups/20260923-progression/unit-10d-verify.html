實作四：從新增到刪除，逐步驗收

01 · 啟動與測試前提

確認 10～10C 的檔案完成、三個連線環境變數已設定，且 SQL Server 練習副本可連線。單元 08 的兩個測試可以先執行；Initializr 產生的 contextLoads 全應用測試會需要資料庫設定。

第一行只執行單元 08 的兩個測試；第二行啟動伺服器，會持續佔用終端機。另開一個終端機做下面的請求；完成後用 Control + C 停止伺服器。

curl 是傳送網路請求的命令列工具。-i 顯示標頭與狀態碼；-H 設定標頭；-d 提供本文。這裡沒有加入單元 09 的登入設定，若你已加入，需依安全單元帶登入 Cookie 與 CSRF token。

02 · GET：清單與單筆

兩者預期 200。清單包含 items、page、size、totalElements；單筆包含 id、productName、unitPrice、unitsInStock、discontinued、categoryId。未修改的經典資料中，商品 1 是 Chai。

03 · POST：新增自己的練習商品

預期 201 Created，Location 為 /api/products/新編號，本文回傳剛建立的商品。新編號由資料庫產生，不保證是 78，也不保證連續。

後續命令中的 $PRODUCT_ID 會使用你輸入的編號。每個練習只改你剛新增的 Training Tea，避免混淆原始 Northwind 商品。

04 · PUT：替換全部可寫欄位

預期 200，回應與資料庫都變成新名稱、25 元、庫存 12。若漏 discontinued 或 categoryId，預期 400；不存在的商品則是 404，不偷偷新增。

05 · PATCH：只改單價

預期 200，單價變成 26，名稱仍是 Training Green Tea、庫存仍是 12。這是固定只改價格的合約；傳 productName 會因未知欄位設定回 400。不是所有任意 JSON 都能當作這個 PATCH 的內容。

06 · HEAD／OPTIONS：確認協定行為

HEAD 預期 200，沒有回應本文。OPTIONS 預期成功，Allow 包含 GET、HEAD、PUT、PATCH、DELETE、OPTIONS 等可用方法；標頭順序依框架而定。這不代表已開放跨來源請求。

07 · DELETE：204 代表沒有內容

第一次預期 204 No Content，而且沒有 JSON 本文。後面的 GET 預期 404。若再 DELETE 一次，本課也回 404：資源仍不存在，符合刪除的冪等語意。

08 · 刻意送錯，才知道合約有沒有做好

三者預期都是 400。第三個案例驗證未知欄位與缺少價格會被拒絕，不會修改原始商品。再以未使用的正整數編號查商品，可驗證 404。

你要測什麼如何做預期
無效分類POST 合法五欄位，但 categoryId 用已確認不存在的編號400，分類不存在
刪除衝突僅在自己的副本：先確認某商品被 Order Details 引用，再請求 DELETE409，商品與訂單仍保留
庫存超界POST unitsInStock=32768400
null 單價PATCH {"unitPrice":null}400
資料持久化在第 05 步之後、刪除前重啟應用，再 GET 新商品仍為 26 元，不是只存在記憶體

09 · 你可以拿去說明的作品重點

  • 能解釋 GET／POST／PUT／PATCH／DELETE 的合約與冪等。
  • 用建構子注入，把 Controller、Service、Repository 分工清楚。
  • 知道 Entity 與 DTO 的差異，更新在交易中完成。
  • 能展示負價格 400、不存在 404、外鍵衝突 409。
  • 能說明目前尚未包含登入、多人扣庫存與正式部署；下一步先接單元 09 的安全設定。
