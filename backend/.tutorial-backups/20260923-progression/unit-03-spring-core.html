IoC 與 DI：到底是誰在 new 物件？

以 Northwind 商品目錄為例，從自己建立依賴、手動注入，到交給 Spring 管理。一次比較一個變化。

01 · 原本：商品服務自己決定資料來源

IoC 是 Inversion of Control（控制反轉）；DI 是 Dependency Injection（依賴注入）。先不背定義，觀察下面的依賴是誰建立的。DAO 是 Data Access Object（資料存取物件）。

呼叫 productName 的人不必管 DAO，但 ProductService 被綁定到 SqlProductDao。想在測試時不用資料庫，就得改 Service 本身。問題是建立依賴與使用依賴綁在同一處，不是 new 這個關鍵字不好。

02 · 先不用 Spring，也能做到 DI

建構子（Constructor）是建立物件時執行的方法。現在 Service 只要求「能查商品名稱的物件」，不再挑選具體實作。呼叫端負責把依賴交進來，這就已經是 DI。

id -> "Chai" 是 Lambda（匿名函式），用簡短方式提供介面的實作。這裡是固定回應的測試替身，不是正式資料庫邏輯。

03 · 加上 Spring：由容器負責組裝

@Component 表示交由 Spring 管理的元件；@Service 表示服務層元件。這些 @ 開頭的標記叫 Annotation（註解），供框架辨認用途。它們的 imports 分別來自 org.springframework.stereotype。

啟動時，Spring 掃描這些類別、建立 DemoProductCatalog，再把它傳進 ProductService 的建構子。只有一個建構子時，不必額外加 @Autowired。Bean 是被 Spring 管理的物件；ApplicationContext 是 Spring 的物件管理容器。

上面 A、B、C 是三個替代版本，不要一起貼進同一專案。類別也必須位在啟動類別所在套件或其子套件，才會被預設掃描到。

控制反轉是把組裝責任交出去；依賴注入是實現這件事的方式之一。你學 Servlet 時也接觸過類似概念：由 Tomcat 建立 Servlet 並呼叫 doGet，不是你自己寫迴圈等待每個請求。

它把依賴列在建構子參數，由建立 Service 的人提供；在 Spring 專案中，這個建立者通常是容器。

05 · 工作中會遇到的兩個問題

如果同一介面有兩個 Bean，Spring 可能不知道要注入哪個。可以用 @Primary 指定預設候選，或用 @Qualifier 指定名稱。這是候選選擇問題，不代表 DI 失效。

Spring Bean 預設通常是 singleton（同一容器共用一個實例）。Service 不要用成員變數保存「這次請求的商品編號」；多位使用者同時呼叫時會互相干擾。用方法參數與區域變數承接每次請求。

第三方類別不能加 @Component 時，可在 @Configuration 設定類別中用 @Bean 方法建立它；物件仍由容器接手管理。
