# 模組 7：訂位

**難易度** ★★★★☆　**里程碑** 第 4 週

## 這個模組在做什麼

客人線上選時間、選人數，系統自動配一張合適的桌。到店報到就直接開桌。

**這個模組是「排程」技術的主戰場**——區間重疊演算法、併發控制、以及六個定時任務都在這裡。

## 難易度為什麼是四顆星

| 難點 | 為什麼難 |
|---|---|
| **區間重疊判斷** | 一條判斷式，但很容易寫成 `<=` 導致誤判 |
| **併發控制** | 兩個人同時訂同一桌，跟超賣是同一類問題 |
| **狀態機複雜** | 五種狀態，加上排程會自動轉移 |
| **時間處理** | 緩衝時間、跨午夜、時區 |

## 問題思考與解決思路

### 問題 1：怎麼知道這張桌這個時間有沒有空

**情境**
A03 桌今天已有訂位 18:00–19:55。客人想訂 19:00–20:55。

**直覺會這樣寫**
把一天切成固定時段（11:30 / 13:30 / 17:30 / 19:30 / 21:00），每桌每時段只能有一筆。用 `UNIQUE(table_id, date, time_slot)` 防重複。

- 優點：實作最簡單
- 缺點：客人只能選那五個時間；而且**學不到真實訂位系統的模型**

**正確做法：區間重疊檢查** ← 我們選這個

存完整的開始與結束時間，判斷式是：

```
A.開始 < B.結束  且  B.開始 < A.結束
```

套進去：`18:00 < 20:55` ✅ 且 `19:00 < 19:55` ✅ → **重疊，不行**。

SQL：

```sql
SELECT t.* FROM dining_table t
WHERE t.active = 1 AND t.reservable = 1 AND t.seats >= :partySize
  AND NOT EXISTS (
      SELECT 1 FROM reservation r
      WHERE r.table_id = t.id
        AND r.status IN ('PENDING', 'CONFIRMED')
        AND r.start_time < :newEnd
        AND :newStart   < r.end_time
  )
ORDER BY t.seats ASC
LIMIT 1;
```

**三個細節**：

1. **用 `<` 不是 `<=`**——18:00–19:55 和 19:55–21:50 是「剛好接續」，不算衝突。用 `<=` 會白白浪費位子。
2. **排除已取消的**——不然位子永遠訂不到。
3. **`ORDER BY seats ASC` = best-fit**——2 個人不要佔 8 人桌，把大桌留給大團。

### 問題 2：清桌時間怎麼算進去

**情境**
上一組 19:40 走，下一組 19:40 到。服務生來不及收拾。

**正確做法：把緩衝加進 `end_time`**

```
end_time = start_time + 用餐時長(100 分) + 清桌緩衝(15 分)
18:00 + 100 + 15 = 19:55
```

存進資料庫時就存這個。**判斷式完全不用改。**

這是個很優雅的設計：把「業務規則」轉換成「資料」，演算法就不用知道緩衝的存在。

### 問題 3：兩個人同時訂同一桌

**情境**

```
客人 A：查詢 → A03 有空 ──→ 寫入訂位
客人 B：    查詢 → A03 有空 ──→ 寫入訂位
                                 兩筆都成功
```

跟 [超賣](../../tech/database/28-鎖與併發.md) 是同一類問題。

**但這次不能用條件式 UPDATE**，因為配桌要做區間計算，沒辦法壓成一句 SQL。

**正確做法：悲觀鎖 + 資料庫約束（兩層保護）**

```java
@Transactional
public ReservationDto create(CreateReservationRequest req) {
    LocalDateTime start = req.startTime();
    LocalDateTime end   = start.plusMinutes(DINING_MINUTES + BUFFER_MINUTES);

    // ① 鎖住候選桌（依 id 排序，避免死鎖）
    List<DiningTable> candidates = tableRepo.findReservableBySeatsForUpdate(req.partySize());

    // ② 在鎖的保護下做重疊檢查 + best-fit
    DiningTable picked = candidates.stream()
        .filter(t -> !reservationRepo.existsOverlap(t.getId(), start, end))
        .findFirst()
        .orElseThrow(() -> new BusinessException("SLOT_UNAVAILABLE", "這個時段已經客滿了", CONFLICT));

    return toDto(reservationRepo.save(Reservation.of(picked, start, end, req)));
}
```

```sql
-- ③ 資料庫層的保險
CREATE UNIQUE INDEX uk_reservation_table_start ON reservation (table_id, start_time);
```

**「應用層 + 資料庫層」雙重保護**是正確的做法。就算程式有 bug，資料庫也擋得住。

### 問題 4：訂了位沒來怎麼辦

**情境**
19:00 的訂位，19:25 了人還沒到。桌子空著，後面的客人乾等。

**直覺會這樣寫**
櫃檯自己記得，過一陣子手動標記。

**為什麼不好**
尖峰時櫃檯忙不過來，一定會忘記。而且「過了多久算 NO_SHOW」沒有一致標準。

**正確做法：排程自動處理**

```java
@Scheduled(cron = "0 */5 * * * *", zone = "Asia/Taipei")
public void markNoShow() {
    try {
        LocalDateTime deadline = LocalDateTime.now().minusMinutes(20);
        int n = reservationService.markNoShowBefore(deadline);
        if (n > 0) log.info("{} 筆訂位標記為 NO_SHOW", n);
    } catch (Exception e) {
        log.error("NO_SHOW 檢查失敗", e);
    }
}
```

標記為 `NO_SHOW` 後，桌位自動轉回 `AVAILABLE`，現場客人就能用了。

**★ 一定要配一支手動觸發的 API**，不然 demo 時你要真的等 20 分鐘。

```java
@PostMapping("/api/admin/scheduler/mark-no-show")
@PreAuthorize("hasRole('MANAGER')")
public Map<String, Object> trigger() {
    return Map.of("marked", reservationService.markNoShowBefore(LocalDateTime.now().minusMinutes(20)));
}
```

**做法**：排程方法只負責呼叫 Service + 記日誌，邏輯全在 Service，這樣排程和手動 API 共用同一段程式碼。

### 問題 5：取消的訂位還算不算佔位

**情境**
客人取消了 A03 桌 19:00 的訂位。別人現在訂得到嗎？

**如果 `status` 沒納入判斷**
取消的訂位還在表裡，重疊檢查會撞到它 → **位子永遠訂不到**。

**但如果直接刪掉**
沒有紀錄，無法統計取消率，客人也查不到自己取消過。

**正確做法：保留紀錄，但查詢時排除**

```sql
AND r.status IN ('PENDING', 'CONFIRMED')     -- 只有這兩種算佔位
```

`CANCELLED` / `NO_SHOW` / `SEATED`（已入座，桌況由 dining_session 管）都不算。

**注意唯一約束的衝突**：`UNIQUE(table_id, start_time)` 會讓「取消後同一時段再訂」失敗。

兩種解法：

- **A**：取消時把 `table_id` 設為 NULL（保留紀錄但釋放約束）
- **B**：取消的搬到 `reservation_cancelled` 歷史表

**我們選 A**，比較單純。

## 常見卡關

| 卡點 | 解法 |
|---|---|
| **明明有位卻說客滿** | 判斷式用了 `<=`，或沒排除已取消的 |
| **出現重複訂位** | 沒加悲觀鎖，或候選桌沒排序導致死鎖 |
| **`Duplicate entry for uk_reservation_table_start`** | 這是保險生效了，回 409 給前端就對 |
| **排程沒跑** | 忘了 `@EnableScheduling`，或類別沒貼 `@Component` |
| **時間差 8 小時** | 沒設 `zone = "Asia/Taipei"` |
| **跨午夜的訂位出錯** | 用 `DATETIME` 存完整時間，不要拆成日期+時間兩欄 |
| **demo 時等不到排程** | 做手動觸發 API |

## 驗收 Demo 腳本

1. 顧客端訂位：選明天 18:00、4 位 → **顯示「將為您安排 4 人桌」**
2. 再訂一次同樣時間 4 位 → 系統配到另一張桌
3. 一直訂到那個時段客滿 → 顯示「這個時段已經客滿了」
4. 訂 19:55（剛好接在第一筆之後）→ **可以訂**（證明 `<` 不是 `<=`）
5. 店家端訂位管理：看到明天的訂位清單
6. **手動觸發「預留轉換」排程** → 該桌狀態變 `RESERVED`
7. 按「報到」→ 直接開桌，人數自動帶入，桌況變「用餐中」
8. 另一筆訂位過時未到 → **手動觸發 NO_SHOW 排程** → 標記為 NO_SHOW，桌位釋放
9. 取消一筆訂位 → 那個時段又可以訂了
