# 模組 2：桌位、開桌與候位

**難易度** ★★★☆☆　**里程碑** 第 1～2 週 stub＋畫面、第 3 週開桌與桌況、第 4 週候位

## 這個模組在做什麼

管理「客人坐在哪」。桌位主檔、桌上那張永遠不變的 QR code、開桌、桌況總覽、還有尖峰時的現場候位。

**這個模組決定了系統的定位**：QR code 固定貼在桌上，但**櫃檯控制要不要開桌**。客人掃了碼，如果櫃檯還沒開桌，他只會看到「請洽櫃檯帶位」。

這就是「半輔助工具」的具體樣貌——**櫃檯仍然是主導者，系統是延伸。**

## 難易度為什麼是三顆星

單純的桌位 CRUD 只有一顆星。難的是兩件事：

1. **開桌的併發控制**——兩支手機同時對同一張桌開桌，會產生兩張帳單
2. **狀態機**——桌位有三種狀態，什麼時候該轉到什麼狀態，規則要想清楚；再加上一個**算出來的**「預約保留」，不能存成第四種狀態（問題 5）

## 問題思考與解決思路

### 問題 1：QR code 要不要每次換？

**情境**
客人要掃碼點餐，但不能讓路過的人隨便開桌。

**做法 A：每次開桌產生新的 QR**
每次開桌 → 系統產生一次性 QR → 列印小卡給客人。

- 優點：安全性最高
- 缺點：**每次都要印紙**、要有印表機、客人弄丟就麻煩

**做法 B：固定 QR + 櫃檯控制開桌** ← 我們選這個

QR 內容固定是 `/t/A03`，貼上去永不換。掃碼後系統查桌位狀態：

| 桌位狀態 | 客人看到 |
|---|---|
| `AVAILABLE` | 「請洽櫃檯帶位」，**不能自己開桌** |
| `OCCUPIED` | 直接進入點餐 |
| `CLEANING` | 「整理中」 |

- 優點：不用印、櫃檯掌握帶位、人數由櫃檯輸入比較準
- 風險：隔壁桌的人也能掃到 → 但**中高價位有服務生帶位，而且要走到那張桌才掃得到**，風險可接受

**我們的決定**：做法 B。原本還想加一道可開關的開桌碼當第二層，後來拿掉了 ——
有服務生帶位，人要走到那張桌前才掃得到，多一道四碼輸入只是讓正常客人多按幾下。

### 問題 2：兩支手機同時對同一桌開桌會怎樣？

**情境**
服務生在店家端按開桌的同時，客人也掃碼想開桌。

**直覺會這樣寫**

```java
DiningTable table = tableRepo.findByTableNo("A03");
if (table.getStatus() == AVAILABLE) {
    table.setStatus(OCCUPIED);
    sessionRepo.save(new DiningSession(table, ...));
}
```

**為什麼會壞**
跟 [超賣](../../tech/database/28-鎖與併發.md) 是同一個問題：兩邊的「查」都在對方的「改」之前，結果**產生兩張 `dining_session`**。客人和服務生各自看到不同的帳單，點的東西對不起來。

**正確做法：悲觀鎖**

```java
@Transactional
public DiningSessionDto open(String tableNo, int adults, int children) {
    // SELECT ... FOR UPDATE，把這一列鎖住
    DiningTable table = tableRepo.findByTableNoForUpdate(tableNo)
        .orElseThrow(() -> new BusinessException("NOT_FOUND", "查無此桌", NOT_FOUND));

    if (table.getStatus() != TableStatus.AVAILABLE) {
        throw new BusinessException("TABLE_OCCUPIED", "此桌已在使用中", CONFLICT);
    }
    holdService.findHolding(table, LocalDateTime.now()).ifPresent(r -> {   // 預約保留是算出來的，鎖住之後再算一次（問題 5）
        throw new BusinessException("TABLE_RESERVED",
            "這張桌保留給 " + r.getContactName() + " " + r.getStartTime().toLocalTime() + "，客人來電取消的話請到預約管理取消訂位", CONFLICT);
    });

    table.setStatus(TableStatus.OCCUPIED);
    DiningSession session = sessionRepo.save(DiningSession.open(table, adults, children));
    return toDto(session);
}
```

**為什麼不用條件式 UPDATE？** 因為開桌要做的不只是改一個數字，還要建立 session、產生 token。這種「要做好幾件事」的情況適合悲觀鎖。

### 問題 3：客人走了之後 token 還有效嗎？

**情境**
A03 桌結帳離開，下一組客人坐進來。上一組客人的手機還開著點餐頁面。

**如果不處理**
他還能繼續點餐，而且會點到新客人的帳單上。

**正確做法：token 綁 session，session 一進終態就全部失效**

```java
public DiningSession validate(String token) {
    DiningSession s = sessionRepo.findByToken(token)
        .orElseThrow(() -> new BusinessException("INVALID_SESSION_TOKEN", "連線已失效", UNAUTHORIZED));

    if (s.getStatus() == PAID || s.getStatus() == CANCELLED) {
        throw new BusinessException("INVALID_SESSION_TOKEN", "本次用餐已結束", UNAUTHORIZED);
    }
    return s;
}
```

前端收到 `401 INVALID_SESSION_TOKEN` → 清掉 `localStorage` 的用餐權杖 → 導到 C-00 首頁（`/`）。
客人再掃桌上的 QR，C-01 就照桌位狀態顯示（剛結清是「整理中，請稍候」），不另外做「本次用餐已結束」的分支。

**取消該次用餐**（2.14）也是終態，但手機的反應不一樣：收到 `SESSION_CLOSED` 的 `reason: CANCELLED` 時**不顯示任何面板**，
清掉權杖直接回 C-00；只有 `reason: PAID` 才顯示「已結帳」面板。

**這條規則一定要寫進文件並驗收**，不然 demo 時很容易被問倒。

### 問題 4：候位叫號之後沒人來怎麼辦？

**情境**
叫了 A012 號，但那組客人跑去逛街了。桌子空著等他們，後面的人乾等。

**直覺會這樣寫**
櫃檯自己記得，過一陣子手動標記過號。

**為什麼不好**
尖峰時櫃檯忙不過來，一定會忘記。而且「過了多久」沒有一致的標準。

**正確做法：排程自動處理**

```java
@Scheduled(cron = "0 * * * * *", zone = "Asia/Taipei")   // 每分鐘
public void expireCalledWaitlist() {
    try {
        LocalDateTime deadline = LocalDateTime.now().minusMinutes(10);
        int n = waitlistService.expireCalledBefore(deadline);
        if (n > 0) log.info("{} 組候位過號", n);
    } catch (Exception e) {
        log.error("候位過號檢查失敗", e);
    }
}
```

搭配一支手動觸發的管理 API，demo 時不用真的等 10 分鐘。

**延伸**：進階版可以做「過號後自動叫下一組」，但基礎版只標記，讓櫃檯決定。

### 問題 5：訂位要不要把桌位先「鎖起來」

**情境**
A08 今晚 18:30 有一筆 4 位的線上訂位（陳怡君）。現在 18:05，一組現場客人走進來，A08 剛好空著。

**直覺會這樣寫**
寫一支排程，訂位前 30 分鐘把 `dining_table.status` 改成 `RESERVED`；客人報到、取消或 NO_SHOW 時再改回來。
（舊版就是這樣做的，後來整條拿掉。）

**為什麼會壞**

1. **兩份資料要同步。** 「這張桌被誰訂走」本來就存在 `reservation`（有 `table_id` 和 `start_time`）。
   複製一份到 `dining_table.status` 之後，兩邊就得靠 cron 維持一致。排程晚跑一輪、伺服器剛好重啟、
   或訂位被取消而狀態沒轉回去，就會出現**「畫面顯示空桌，按開桌卻被擋」**，或反過來「早就沒人訂了，桌子還鎖著」——
   這是最難查的那種 bug，因為畫面本身沒有錯誤訊息。
2. **每一條「轉回去」的路都要記得寫。** 取消訂位、NO_SHOW、報到、櫃檯改帶別張桌……漏一條就卡住一張桌。
3. **時間不準。** 排程每幾分鐘跑一次，18:00 整該鎖的桌可能 18:04 才鎖，這幾分鐘剛好被開走。

**但「完全不鎖」也不行**（2026-09-16 定案）
使用者的決定是：**線上訂位就會預先保留桌位，該桌位會鎖住。**
客人線上訂到位、準時到店，卻發現桌子被現場客人坐走了，這比讓現場客人多等一下更傷。

後來再收斂一次：桌子會被鎖，**只有兩種來源**——①訂位的預約保留（算出來的）②用餐中／待清理（桌位欄位）。
**候位不鎖桌**：叫號只是通知，客人到櫃檯時才在 S-10b／S-02c 選桌開桌；客人說不吃了，就在 S-10 按「放棄」
（`DELETE /api/admin/waitlist/{id}` → `ABANDONED`），本來就沒鎖桌，沒有東西要解鎖。
能解開的只有①，而**解開的方法就是取消那筆訂位**（櫃檯代客取消，見下面），沒有「訂位留著、只解除保留」這種中間狀態。

**正確做法：保留是算出來的，不存狀態、不靠排程** ← 我們選這個（M7 7.10）

`dining_table.status` 仍然只有 `AVAILABLE`／`OCCUPIED`／`CLEANING` 三種，**什麼都不多存**。
查桌況的時候才順便判斷要不要顯示「預約保留」：

```java
// 每次查桌況都現算，什麼都不寫回資料庫
TableDisplayStatus displayStatus(DiningTable t, LocalDateTime now) {
    if (t.getStatus() == OCCUPIED) return TableDisplayStatus.OCCUPIED;   // 優先順序：用餐中
    if (t.getStatus() == CLEANING) return TableDisplayStatus.CLEANING;   //         ＞ 待清理
    boolean held = reservationRepo.findHolding(t.getId(),                //         ＞ 預約保留
            now.minusMinutes(holdAfterMinutes),     // start_time 最早：now − 10 分
            now.plusMinutes(holdBeforeMinutes))     // start_time 最晚：now + 30 分
        .isPresent();
    return held ? TableDisplayStatus.RESERVED : TableDisplayStatus.AVAILABLE;   // ＞ 空桌
}
```

```sql
-- findHolding：這張桌現在被哪筆訂位保留
-- 「現在落在 start − 30 ～ start + 10」換成查 start_time，就是「start_time 落在 now − 10 ～ now + 30」
SELECT * FROM reservation
 WHERE table_id = :tableId
   AND status = 'CONFIRMED'
   AND start_time BETWEEN :fromStart AND :toStart
 ORDER BY start_time
 LIMIT 1;
```

兩個數字放 `application.yml`：

```yaml
reservation:
  hold-before-minutes: 30   # 最早可報到的時間，保留從這裡開始
  hold-after-minutes: 10    # 訂位保留時間，過了就是 NO_SHOW，保留也到這裡結束
```

**為什麼這樣就沒有舊 `RESERVED` 的不同步問題**

| | 舊做法（排程寫進桌位欄位） | 現在（查詢時算） |
|---|---|---|
| 資料有幾份 | `dining_table.status` 和 `reservation` 兩份 | 只有 `reservation` 一份，桌況是從它推出來的 |
| 排程沒跑、晚跑、伺服器重啟 | 桌態跟訂位對不上 | 沒有排程可以漏，每次查詢都是當下的答案 |
| 訂位取消／NO_SHOW／報到 | 每條路都要記得把桌態改回去 | 訂位一離開 `CONFIRMED`，條件就不成立，保留自己消失 |
| 時間到了 | 要等排程下一輪才轉 | 時間窗寫在查詢條件裡，18:00:00 一到就算保留 |
| 櫃檯要解鎖 | 改桌態，還要防排程又把它鎖回去 | 櫃檯代客取消訂位（轉 `CANCELLED`、`table_id` 設 `NULL`），條件不成立，保留自己消失 |

一句話：**能從別的資料算出來的狀態，就不要另外存一份。** 存一份就得同步，同步就會漏。

**擋在哪裡**

| 動作 | 目標桌正在保留中 |
|---|---|
| 現場開桌 `POST /api/admin/tables/{id}/open` | `409 TABLE_RESERVED`「這張桌保留給 陳怡君 18:30，客人來電取消的話請到預約管理取消訂位」 |
| 候位入座 `POST /api/admin/waitlist/{id}/seat` | 同上 |
| 預約報到 `POST /api/admin/reservations/{id}/seat` | 保留給**別筆**訂位 → `409 TABLE_RESERVED`；是**自己的**保留桌 → 正常開桌 |
| 一鍵開桌清單 `GET /api/admin/tables/available` | 保留中的桌不列；從預約報到時，自己的保留桌排第一、標「原保留桌」 |

檢查要放在開桌那個交易裡、`FOR UPDATE` 鎖住桌位**之後**再算一次，不要相信畫面上的顏色。

**要解鎖，就是櫃檯代客取消訂位**（M7 7.18）：客人來電說不來了，櫃檯在 S-07 或 S-02d 按「取消訂位」→
`POST /api/admin/reservations/{id}/cancel`。**隨時可以取消**（不受任何期限），只要訂位還是 `CONFIRMED`；
其他狀態回 `409 RESERVATION_NOT_CANCELLABLE`。訂位轉 `CANCELLED`、`table_id` 設 `NULL`、記下 `cancelled_by_staff_id` 與 `cancel_source = STAFF`，
保留條件不成立，**桌子與那個時段的名額一起釋出**；交易提交後推 `TABLE_STATUS`，正在保留中的 A08 立刻變回空桌。
**取消是單向的，不能恢復**，所以前端一定要二次確認「確定要取消 陳怡君 18:30 的訂位嗎？通常是客人來電取消。取消後 A08 會變回空桌，這筆訂位無法恢復。」

為什麼不另外做一顆「只解除保留、訂位照留」：那會多出「訂位有效、桌子卻不保留」的中間狀態，
名額要不要照算、S-07b 要不要排第一、客人到了坐哪，全部要多想一輪；而現場真正會遇到的情況幾乎都是「客人不來了」。
客人自己線上取消只到**訂位時間前 30 分鐘**（`409 CANCEL_DEADLINE_PASSED`），剛好就是預約保留開始的時間，
所以**保留開始之後只剩櫃檯能取消**。

**兩個邊界**

1. **配到的桌到時間還在用餐中** → 顯示「用餐中」，不顯示保留（優先順序）。陳怡君到了，櫃檯從 S-07b 幫她選別張桌。
2. **還沒進保留窗、但快了**（例如 19:30 才有訂位、現在 18:00）→ 不鎖，但要**強烈提醒**。
   判斷的窗是**現在 ～ 現在 + 115 分**（用餐 100 分＋清桌 15 分：現在開下去，這組大概吃到這時候），
   這段時間內有**別筆** `CONFIRMED` 訂位要在這張桌開始，開桌頁就回 `upcomingOnThisTable`（S-07b／S-10b 的清單是 `upcomingReservationAt`）。
   畫面用醒目的警示條（`--danger` 系淺底＋深字＋警示圖示）：「A05 在 19:30 有訂位（陳小姐 4 位）。現在開桌，客人可能還沒吃完訂位就到了。」
   開桌主按鈕改成「仍要開桌」，按下去再跳確認框（標題「確定要開 A05？」、「確定開桌」／「換一張桌」）。
   **只提醒、不擋**，後端不回錯誤：窗外的調度仍然留給現場判斷（客人可能只吃一小時）。所有開桌入口都一樣（S-02b、S-02c、S-02d、S-07b、S-10b）。

**代價要講清楚**：保留窗開始或結束的那一刻沒有任何事件可以推（沒有排程），所以桌況頁除了收 WebSocket，
還要每 60 秒重抓一次 `GET /api/admin/tables`，最多晚一分鐘才換色。按開桌時後端會重算，不會因為畫面舊而開錯。

**開桌有兩個入口，後端是同一組 API。**

| 從哪裡出發 | 畫面 | 怎麼選 |
|---|---|---|
| 從桌子出發 | S-02 點空桌 → S-02b／S-02c／S-02d；點保留中的桌 → S-02d 預約頁籤、這筆置頂 | 桌已經定了，選來源（現場／候位／預約） |
| 從人出發 | S-07 預約管理／S-10 候位管理按「報到開桌」→ S-07b／S-10b | 人已經定了，從 `GET /api/admin/tables/available?partySize=` 列出的空桌挑一張 |

開桌頁要的清單都是即時查的：

```java
// 開桌頁要的清單，都是即時查 reservation / waitlist，不存狀態
List<ReservationDto> arrivals = reservationRepo.findSeatable(
        tableId, now.minusMinutes(10), now.plusMinutes(30), table.getSeats());   // −10 保留時間、+30 最早報到
Optional<ReservationDto> heldFor  = reservationRepo.findHolding(tableId, now.minusMinutes(10), now.plusMinutes(30));
Optional<ReservationDto> upcoming = reservationRepo.findUpcomingOnTable(               // 115 分內要開始的別筆訂位，強烈提醒、不擋
        tableId, now, now.plusMinutes(diningMinutes + bufferMinutes));
```

S-07b／S-10b 的清單只列 `AVAILABLE`、`seats ≥ 人數`、**沒有保留中**的桌，依座位數由小到大、再依桌號排
（從預約報到時，自己的保留桌排第一）；
這張桌 115 分鐘內有別筆訂位，卡片上用紅字標「19:30 有訂位」，而且**排在沒有衝突的桌後面**（排序：原保留桌 → 沒有衝突的桌 → 有衝突的桌，各組內再依座位數、桌號）；
選了這種桌一樣要按「仍要開桌」再確認一次（只提醒不擋，跟開桌頁一致）。
選好之後呼叫 `POST /api/admin/reservations/{id}/seat` 或 `POST /api/admin/waitlist/{id}/seat`（帶 `tableId`），
收尾跟開桌頁完全一樣。兩個櫃檯同時搶同一張桌 → 開桌本來就有 `FOR UPDATE`，後到的拿 `409 TABLE_OCCUPIED`，對話框重新載入清單。
沒有坐得下的空桌 → 空狀態「目前沒有坐得下的空桌」＋「清潔完成或有桌結帳後再試一次」。

---

**只有訂位會鎖桌，候位不鎖桌。**

原本規劃過一個延伸功能 2.E5（櫃檯按一下，把空桌鎖給某組候位或寫一行備註），2026-09-16 已刪除。
理由：候位叫號只是通知，客人真的走到櫃檯才選桌開桌，中間不需要鎖；客人不吃了就按「放棄」，也不用解鎖。
少一個桌態、少幾個欄位、少兩支 API，桌況也只剩四種顏色（其中「預約保留」還是算出來的）。

## 六週切分

| 週 | 這個模組要交出什麼 |
|---|---|
| **W1** | Flyway 建好 `dining_table` / `dining_session`；種子資料 12 張桌；桌位狀態 enum 定義完成 |
| **W2** | `POST /api/admin/tables/{id}/open` 開桌（含悲觀鎖）；`POST /api/dining-sessions/join` 加入；`GET /api/tables/{no}/status`；用餐權杖驗證 filter |
| **W3** | 店家端桌況總覽頁；開桌／關桌；取消用餐（`SESSION_HAS_ORDERS`、`reason: CANCELLED`、桌位直接回空桌）；`dining_session_guest` 與 `X-Device-Id`；**掃碼進入頁（顧客端）**；QR code 產生 |
| **W4** | 候位登記、清單、叫號、報到；候位過號排程；`GET /api/admin/tables/available` 與 S-07b／S-10b 選桌對話框；**預約保留**（桌況 `displayStatus`／`heldFor`、開桌三支的 `TABLE_RESERVED`、第四種色塊，跟 M7 7.10 一起做）；**開桌強烈提醒**（`upcomingOnThisTable`／`upcomingReservationAt` 用 115 分鐘窗、「仍要開桌」二次確認、選桌清單把有衝突的桌排後面） |
| **W5** | 桌況與候位的 WebSocket 推播；用餐超時提醒排程；座位管理後台 |
| **W6** | 不寫新功能。測 token 失效、測併發開桌 |

## 常見卡關

| 卡點 | 解法 |
|---|---|
| **`SELECT ... FOR UPDATE` 不會寫** | 用 `@Lock(LockModeType.PESSIMISTIC_WRITE)` 加在 Repository 方法上 |
| **桌況更新不即時** | 先確認 WebSocket 通了；桌況頁也要保留一個「重新整理」按鈕當備援 |
| **狀態轉移寫得到處都是** | 集中在一個 `TableStatusService`，所有轉移都經過它 |
| **候位表的狀態跟排程對不上** | 只有 `CALLED` 狀態會被排程標成 `EXPIRED`，`WAITING` 不會 |
| **想把預約保留存進 `dining_table.status`** | 不要。它是算出來的顯示狀態，存了就要同步（問題 5） |
| **保留中的桌還是被開走了** | 開桌交易裡鎖住桌位之後要重算一次保留，不能只看前端顏色 |
| **預約保留晚了一陣子才出現在桌況上** | 保留窗開始沒有事件可推，桌況頁要每 60 秒重抓 |
| **19:30 有訂位，18:00 開這張桌卻沒有任何提醒** | `upcomingOnThisTable` 的窗要用「現在～現在 + 115 分」，不是只看保留窗 |
| **按了「仍要開桌」後端回錯誤** | 強烈提醒只在前端，後端不擋；會擋的只有保留中的桌（`TABLE_RESERVED`） |
| **取消用餐後手機停在「已結帳」面板** | `SESSION_CLOSED` 要看 `reason`，`CANCELLED` 直接回 C-00 |

## 驗收 Demo 腳本

1. 手機掃 A03 的 QR → 顯示「請洽櫃檯帶位」
2. 店家端對 A03 開桌（2 大 1 小）→ 桌況變紅色「用餐中」
3. 手機重新掃同一個 QR → **這次直接進入點餐**
4. 第二支手機掃同一個 QR → 也能進入（同桌共享）
5. 櫃檯在 S-03 按「現金」、倒數到 0 結帳完成 → 桌況變「待清理」→ **手機即時變成「已結帳」；按「回到首頁」回到 C-00，再掃同一個 QR 顯示「整理中，請稍候」**
6. 候位登記一組 → 叫號 → 候位螢幕即時顯示 → S-10 按「報到開桌」→ **只列出坐得下的空桌** → 選一張 → 開桌
7. 把空桌都開掉再按一次「報到開桌」→ 顯示「目前沒有坐得下的空桌」
8. 種子資料裡 30 分鐘內要到的訂位 → 它配到的桌（例如 A08）在桌況上是暖黃「預約保留」，格內「18:30 陳○君 4 位」，統計列「預約保留 1」
9. 點 A08 → 開桌頁的預約頁籤，這筆置頂；切到現場頁籤 → 頂部暖黃條「這張桌保留給 陳怡君 18:30（4 位）。客人來電取消的話，請到預約管理取消訂位」、開桌按鈕停用；用 Postman 直接打現場開桌 → `409 TABLE_RESERVED`
10. 假裝陳怡君來電取消：切回預約頁籤，按置頂那筆的「取消訂位」→ 二次確認「確定要取消 陳怡君 18:30 的訂位嗎？通常是客人來電取消。取消後 A08 會變回空桌，這筆訂位無法恢復。」→ A08 變回空桌，S-07 那筆變成「已取消」＋小字「店家代取消・小美」（按的那位員工）
11. 種子資料裡約 1 小時後有訂位的那張桌（例如 A05）→ 點它 → 現場頁籤頂部是醒目的紅色警示條「A05 在 19:30 有訂位（陳小姐 4 位）。現在開桌，客人可能還沒吃完訂位就到了。」，主按鈕是「仍要開桌」→ 按下跳「確定要開 A05？」→ 按「換一張桌」關掉，不開桌；
    S-10 對一組 4 位候位按「報到開桌」→ S-10b 清單裡 A05 標紅字「19:30 有訂位」、排在其他空桌後面
12. 另開一張桌、不點餐 → 店長在 S-03 按「取消該次用餐」→ 桌位**直接回空桌**，**手機不顯示面板、直接回到 C-00**；
    對點過餐的桌按取消 → 「已經有點餐紀錄，請改用結帳」
