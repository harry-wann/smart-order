# 模組 3：點餐與服務鈴

**難易度** ★★★★☆　**里程碑** 第 3 週主流程全綠燈

> **這是整個專案最核心、也最難的模組。** 不論之後怎麼分工，這個模組的送出點餐交易一定要有第二個人 review。

## 這個模組在做什麼

客人從菜單挑東西、放進**整桌共用的購物車**（同桌每支手機看到同一份，每列標出是誰加的），按下「送出整桌點餐」，然後在自己手機上看到全桌點了什麼、哪些出了。另外還有一顆呼叫服務生的按鈕。

**「送出點餐」那一支 API 是整個系統技術含量最高的地方**：它要在一個交易裡完成讀整桌購物車、驗證、扣庫存、建立三層資料、清空購物車、更新金額，任何一步失敗全部回滾。

## 難易度為什麼是四顆星

| 難點 | 為什麼難 |
|---|---|
| **併發扣庫存** | 兩個人同時點最後一份，寫錯不會報錯，只會默默超賣 |
| **交易邊界** | 鎖列、讀購物車、驗證、扣庫存、寫單、清購物車要綁在一起，中間任何一步失敗都要乾淨回滾 |
| **三層資料結構** | `dining_session → order_ticket → order_item → order_item_option` |
| **多裝置同步** | 購物車存後端、整桌共用；WebSocket + 斷線重連，收到事件就重抓 |
| **選項驗證** | 必選有沒有選齊、複選有沒有超過上限 |

## 問題思考與解決思路

### 問題 1：兩個人同時點最後一份牛五花

> **這是全專案最重要的一題。五個人都要能講。**

**情境**
牛五花庫存剩 1 份。你和朋友幾乎同時按下「送出點餐」。

**直覺會這樣寫**

```java
int stock = inventoryRepo.findQuantity(12);   // 查
if (stock >= 1) {                             // 判斷
    inventoryRepo.decrease(12, 1);            // 扣
}
```

**為什麼會壞**

```
時間 →
你：    查(=1) ─→ 判斷 1>=1 ✓ ─→ 扣 ─→ 0
朋友：      查(=1) ─→ 判斷 1>=1 ✓ ─→ 扣 ─→ -1
```

兩個人的「查」都發生在對方的「扣」之前。**兩份都賣掉了，但只有一份貨。**

而且這個 bug **單人測試永遠測不出來**。

**正確做法：把條件寫進 UPDATE**

```sql
UPDATE inventory_item
   SET quantity = quantity - :qty
 WHERE menu_item_id = :itemId
   AND quantity >= :qty;
```

```java
int affected = inventoryRepo.decreaseIfEnough(itemId, qty);
if (affected == 0) {
    throw new BusinessException("ITEM_SOLD_OUT", name + " 已售完", CONFLICT);
}
```

資料庫保證同一時間只有一個交易能改同一列。第二個人執行時庫存已經是 0，條件不成立，**影響筆數是 0**。

**判斷成敗看「影響筆數」，不是看有沒有報錯。**

**延伸**：多台伺服器時這招仍然有效（因為是資料庫在把關）。要鎖資料庫以外的東西才需要 [Redis 分散式鎖](../../tech/realtime/44-Redis.md)。

### 問題 2：扣到第三項時發現庫存不夠

**情境**
一張單有五個品項。扣到第三項時庫存不足。

**如果沒有交易**
前兩項的庫存已經扣掉了，但訂單沒成立。**庫存憑空少了兩份，而且沒有人會發現。**

**正確做法**

```java
@Transactional                         // ← 整個方法綁在一起
public OrderTicketDto submitOrder(String token, String deviceId) {   // 不收品項：送出的是整桌購物車
    DiningSession session = sessionService.lockOrderable(token);  // FOR UPDATE，不是 OPEN → 409 SESSION_CLOSED
    DiningSessionGuest guest = guestService.find(session, deviceId);   // 誰按的送出

    List<CartItem> cart = cartRepo.findBySessionId(session.getId());   // 拿到鎖之後才讀（問題 7）
    if (cart.isEmpty()) {
        throw new BusinessException("CART_EMPTY", "購物車是空的，可能同桌已經送出了", CONFLICT);   // 409：同桌剛送出，是狀態衝突
    }

    validateSoupBaseRule(session, cart);       // ① 鍋底規則
    validateOptions(cart);                     // ② 必選／上限

    // ③ 依 id 排序後逐項扣庫存（避免死鎖）
    cart.stream()
        .sorted(comparing(CartItem::getMenuItemId))
        .forEach(this::decreaseStockOrThrow);  // 任一項失敗 → 例外 → 全部回滾（購物車也原封不動）

    OrderTicket ticket = buildTicketWithSnapshots(session, guest, cart);  // ④⑤⑥ 以菜單現價重算、存快照
    cartRepo.deleteAll(cart);                                            // ⑦ 同一個交易裡清空購物車
    session.recalculate();                                               // ⑧

    return toDto(ticket);
}
```

**推 WebSocket 要放在交易「之後」**，否則交易還沒 commit 前端就收到通知，去查卻查不到資料。

**延伸**：為什麼要依 id 排序？因為兩個交易如果用不同順序鎖資料，會[死鎖](../../tech/database/28-鎖與併發.md)。統一順序就不會。

### 問題 3：同桌兩支手機怎麼同步？

**情境**
你和朋友各自拿手機。你加了一盤牛五花，他的手機要看到。

**做法 A：輪詢**
每 3 秒問一次「有新的嗎」。

- 優點：簡單、容錯性天然就好
- 缺點：多數請求是白問的；最慢晚 3 秒

**做法 B：WebSocket** ← 我們選這個

你一送出，後端直接推到訂閱 `/topic/session/{id}` 的所有裝置。

- 優點：真的即時（<1 秒）、省請求
- 缺點：要處理斷線、部署要支援協定升級

**關鍵：WebSocket 不保證不漏**

手機切到別的 App、進電梯、Wi-Fi 換 4G——連線就斷了，**斷線期間推的東西全部收不到**。

所以：

```js
onConnect: () => {
  subscribe(`/topic/session/${sessionId}`, handleEvent);
  refetchAll();          // ★ 每次（重新）連上都重抓一次完整資料
}
```

**這一行讓你同時拿到「即時」和「不會錯」。** 就算 WebSocket 完全掛掉，只要使用者重新整理，資料還是對的。

**購物車也走同一條路**：誰加了東西，後端推 `CART_UPDATED`，其他手機收到就重抓 `GET /api/dining-sessions/me/cart`。
不要拿事件內容自己去拼購物車——事件只拿來跳通知條「陳小美 加了 安格斯霜降牛五花 ×1・全份」（`itemName`、`quantity`、`optionSummary`），內容一律以後端為準。

### 問題 4：客人連按三下送出

**情境**
網路有點慢，客人以為沒反應，連按三下。

**如果不處理**
成立三張一模一樣的單，廚房做三份。

**做法 A：前端擋**

```jsx
<Button disabled={submitting} loading={submitting} onClick={handleSubmit}>
  送出整桌點餐
</Button>
```

必要，但**不夠**——[前端的檢查不算數](../../tech/web/06-前端後端在做什麼.md)。

**做法 B：後端也擋（冪等鍵）**

前端每次送出時產生一個唯一的 `requestId`，後端在短時間內收到相同的就直接回上一次的結果。

**我們的決定**：基礎版做 A（前端停用按鈕），並在文件標明 B 是進階項。理由是我們的 API 是「建立新單」，重複送出的後果是多一張單而不是金額錯誤，且櫃檯可以取消。**但要在簡報時說明你們知道這個限制。**

> 購物車搬到後端之後，這個限制小了很多：第一次送出成功就把購物車清空了，第二、三下拿到的是空購物車（`409 CART_EMPTY`），
> 不會再成立一張。同桌**兩個人**同時按也是同一個道理，見問題 7。

### 問題 5：服務鈴要不要存資料庫？

**情境**
客人按「加湯」，櫃檯要看到。

**做法 A：只推 WebSocket，不存**
最省事。

**為什麼不好**
- 櫃檯重新整理頁面，未處理的呼叫就不見了
- 沒辦法統計
- 沒辦法標記「已處理」

**做法 B：存表 + 推 WebSocket** ← 我們選這個

```sql
service_call (
  id, dining_session_id, table_id,
  type    VARCHAR(20),   -- SERVICE / SOUP / POT_CLEAN（沒有結帳，結帳請到櫃檯）
  status  VARCHAR(20),   -- PENDING / ACKNOWLEDGED / DONE
  created_at, acknowledged_at, staff_id
)
```

成本只多一點點，但櫃檯體驗完全不同。

### 問題 6：購物車要放在哪裡

**情境**
陳小美和王大明同桌。陳小美加了一盤牛五花，王大明的手機要看得到；而且不管誰按送出，兩個人加的都要一起送出去。

**做法 A：前端 state／localStorage**（舊版就是這樣）
每支手機各一份。同桌看不到彼此加了什麼，兩個人各送各的，鍋底還可能各點一份。

**做法 B：HTTP session**
還是每支手機各一份（session 跟著各自瀏覽器的 cookie 走），伺服器重啟就消失。

**做法 C：Redis**
可以整桌共用，但送出時要「寫 `order_ticket`＋清購物車」一起成功或一起失敗，跨 Redis 和 MySQL 做不到同一個交易。

**做法 D：存 MySQL，整桌一份** ← 我們選這個

`cart_item` 掛在 `dining_session` 底下，不分手機。送出時在同一個交易裡搬進 `order_ticket` 再刪掉（問題 2 的第 ⑦ 步）。

**「誰加的」怎麼知道？** 同一桌只有一個 `session_token`，分不出是哪支手機。所以：

1. 前端第一次開啟時產生一個 UUID，存 localStorage，每個請求用 `X-Device-Id` 帶上來
2. 加入用餐時，後端在 `dining_session_guest` 建一筆（有登入會員用暱稱，否則依加入順序「客人 1」「客人 2」…），同一個 UUID 重複加入拿到同一筆
3. `cart_item.added_by_guest_id`、`order_ticket.submitted_by_guest_id` 都指向它

> **`device_id` 不是身分驗證**，驗證仍然靠 `session_token`。有人偽造 `X-Device-Id`，頂多讓購物車上顯示錯的名字，拿不到別桌的東西。

**前端怎麼配合**：購物車內容以後端為準，`useState` 只放畫面狀態（例如哪一列展開了）；收到 `CART_UPDATED` 或 `NEW_TICKET` 就重抓。
`cart_item.unit_price` 只給畫面顯示，送單時一律用菜單現價重算——加進購物車之後老闆改價，以送出那一刻為準。

**自己的動作不通知自己**：`CART_UPDATED` 與 `NEW_TICKET` 都帶 `byGuestId`，前端跟 join 時拿到的 `guest.id` 比對，相同就只重抓、不跳通知條。
不要拿 `byGuest` 名稱比——兩個會員暱稱一樣就會互相吃掉通知。

**不經過整桌購物車的兩種單**

| 情境 | 怎麼送 | 同桌看到什麼 |
|---|---|---|
| 櫃檯代客加點（S-03） | 店員直接帶品項出單（`POST /api/admin/dining-sessions/{id}/orders`，`source = STAFF`），跟送出購物車共用驗證、扣庫存、寫單那一段 | `NEW_TICKET` 的 `byGuest` 是「櫃檯」、`byGuestId` 是 `null` →「櫃檯 送出 2 項」；客人購物車不受影響 |
| C-17 預先點餐（A2） | 還沒有用餐紀錄，購物車只存在那支手機，送出是整批 `PUT /api/reservations/{id}/preorder` | 沒有同桌、沒有「誰加的」 |

**結帳或取消時還沒送出的品項直接捨棄**：session 進終態的同一個交易裡刪掉整桌 `cart_item`，不算錢；
**櫃檯不用管購物車**（S-03 不顯示購物車的任何提示），已結帳的 C-04／C-06 購物車列直接消失。客人要的東西，要在結帳前自己送出。

### 問題 7：兩個人同時按「送出整桌點餐」

**情境**
購物車裡有 6 項。陳小美和王大明幾乎同時按下送出。

**如果不處理**
兩個請求都讀到同一份 6 項，各建一張單 → 廚房做兩份、庫存扣兩次、帳單多一倍。

**正確做法：列鎖讓兩筆排隊，讀購物車放在拿到鎖之後**

送出點餐一開頭就 `SELECT ... FOR UPDATE` 鎖住 `dining_session`（本來就為了擋「結帳時加點」而鎖，見 [M6 問題 1](M6-結帳.md)），
這把鎖順便讓同桌的兩次送出排隊：

```
時間 →
王大明：鎖 session ─→ 讀到 6 項 ─→ 扣庫存、建單、刪購物車 ─→ 提交、放鎖
陳小美：   等鎖 ·································································→ 拿到鎖 ─→ 讀到 0 項 ─→ 409 CART_EMPTY
```

陳小美的手機顯示「購物車是空的，可能同桌已經送出了」，同時也會收到 `NEW_TICKET`（通知條「王大明 送出 6 項」），重抓本桌訂單就看到了。

> **讀購物車一定要在鎖之後。** 先讀再鎖的話，兩邊讀到的都是 6 項，鎖只是讓它們排隊各建一張單。

## 常見卡關

| 卡點 | 解法 |
|---|---|
| **交易沒生效** | 同一個類別內部呼叫 `@Transactional` 方法無效，見 [交易](../../tech/database/27-交易Transaction.md) |
| **推播推出去但前端查不到資料** | 推播寫在交易裡了，搬到交易外 |
| **前端收到事件但畫面沒更新** | 直接改了 state，要用 `setTickets(prev => [...prev, x])` |
| **WebSocket 一直斷線重連** | `useEffect` 依賴陣列裡有每次都變的物件 |
| **超賣測不出來** | 要寫多執行緒測試，見 [單元測試](../../tech/quality/47-單元測試.md) |
| **送出後金額對不上** | 用了 `double`，改 `BigDecimal`；或拿了 `cart_item.unit_price` 算錢，要用菜單現價重算 |
| **同桌兩支手機的購物車不一樣** | 購物車還放在前端 state；改成以 `GET /me/cart` 為準，收到 `CART_UPDATED` 就重抓 |
| **同時按送出變成兩張單** | 讀購物車寫在鎖之前了，見問題 7 |
| **自己加的東西，自己的手機也跳通知** | 比的是 `byGuest` 名稱而不是 `byGuestId`，或忘了把 join 回來的 `guest.id` 存起來 |
| **購物車每列都顯示同一個人／名字一直變** | 前端沒帶 `X-Device-Id`，或每次重整都重新產生 UUID（要存 localStorage） |

## 驗收 Demo 腳本

> **這就是第 3 週里程碑的驗收內容，也是最終 demo 的主線。**

1. 兩支手機掃同一桌的 QR，都進到菜單
2. 手機 A 把「鴛鴦鍋底」（左麻辣、右昆布）加進購物車 → **手機 B 跳出「客人 1 加了 鴛鴦鍋底 ×1・麻辣・昆布」，購物車角標同步變成 1**（手機 A 自己不跳）
3. 手機 B 加牛五花 ×1（全份、加蔥花）→ 手機 A 跳「客人 2 加了 牛五花 ×1・全份・加蔥花」，**兩支手機的購物車都是兩列、角標 2**，各自標「客人 1 加的」「客人 2 加的」；手機 A 把牛五花改成 2 份，**兩支手機的角標都變成 3**（數量算份數，不算列數）
4. 手機 A 按「送出整桌點餐」→ **手機 B 在 1 秒內看到「第 1 單」出現、購物車清空，通知條「客人 1 送出 3 項」**（鴛鴦鍋底 1 份＋牛五花 2 份；手機 A 自己不跳）
5. 廚房看板同時跳出這張單
6. 手機 B 加點高麗菜 → 送出 → **手機 A 看到「第 2 單」**
7. 兩支手機都加一樣東西，**同時按送出** → **只成立一張單**，另一支顯示「購物車是空的，可能同桌已經送出了」
8. 廚房勾選「鴛鴦鍋底已出餐」→ **兩支手機同時看到狀態變成「已出餐」**
9. 手機 A 按「服務鈴 → 加湯」→ **櫃檯畫面立刻跳出提示**
10. 手機 A 先把一個品項加進購物車，再用 SQL 把它的庫存設成 0（模擬剛被別桌點完）→ 送出 → **顯示「已售完」並標紅那一項，整張單沒有成立，購物車原封不動**
11. 本桌還沒點鍋底時，送出一份沒有鍋底的購物車 → **顯示「這桌還沒點鍋底，共鍋至少要一份」**，整張單沒有成立
12. 手機 B 加一樣東西但不送出 → 櫃檯打開 S-03，**看不到任何購物車提示**，合計也不含它（櫃檯只看已送出的單）
13. 櫃檯在 S-03 結帳 → **兩支手機同時變成「已結帳」**，菜單變暗、購物車列換成「這桌已經結帳完成」，剛剛沒送出的那一項不算錢
