# 模組 3：點餐與服務鈴

**難易度** ★★★★☆　**里程碑** 第 3 週主流程全綠燈

> **這是整個專案最核心、也最難的模組。** 不論之後怎麼分工，這個模組的送出點餐交易一定要有第二個人 review。

## 這個模組在做什麼

客人從菜單挑東西、放進購物車、按下「送出點餐」，然後在自己手機上看到全桌點了什麼、哪些出了。另外還有一顆呼叫服務生的按鈕。

**「送出點餐」那一支 API 是整個系統技術含量最高的地方**：它要在一個交易裡完成驗證、扣庫存、建立三層資料、更新金額，任何一步失敗全部回滾。

## 難易度為什麼是四顆星

| 難點 | 為什麼難 |
|---|---|
| **併發扣庫存** | 兩個人同時點最後一份，寫錯不會報錯，只會默默超賣 |
| **交易邊界** | 九個步驟要綁在一起，中間任何一步失敗都要乾淨回滾 |
| **三層資料結構** | `dining_session → order_ticket → order_item → order_item_option` |
| **多裝置同步** | WebSocket + 斷線重連 + 前端狀態合併 |
| **選項驗證** | 必選有沒有選齊、複選有沒有超過上限 |

## 問題思考與解決思路

### 問題 1：兩個人同時點最後一份牛五花

> **這是全專案最重要的一題。五個人都要能講。**

**情境**
牛五花庫存剩 1 份。你和朋友幾乎同時按下「送出點餐」。

**直覺會這樣寫**

```java
int stock = inventoryRepo.findQuantity(12);   // 查
if (stock >= 1) {                             // 判斷
    inventoryRepo.decrease(12, 1);            // 扣
}
```

**為什麼會壞**

```
時間 →
你：    查(=1) ─→ 判斷 1>=1 ✓ ─→ 扣 ─→ 0
朋友：      查(=1) ─→ 判斷 1>=1 ✓ ─→ 扣 ─→ -1
```

兩個人的「查」都發生在對方的「扣」之前。**兩份都賣掉了，但只有一份貨。**

而且這個 bug **單人測試永遠測不出來**。

**正確做法：把條件寫進 UPDATE**

```sql
UPDATE inventory_item
   SET quantity = quantity - :qty
 WHERE menu_item_id = :itemId
   AND quantity >= :qty;
```

```java
int affected = inventoryRepo.decreaseIfEnough(itemId, qty);
if (affected == 0) {
    throw new BusinessException("ITEM_SOLD_OUT", name + " 已售完", CONFLICT);
}
```

資料庫保證同一時間只有一個交易能改同一列。第二個人執行時庫存已經是 0，條件不成立，**影響筆數是 0**。

**判斷成敗看「影響筆數」，不是看有沒有報錯。**

**延伸**：多台伺服器時這招仍然有效（因為是資料庫在把關）。要鎖資料庫以外的東西才需要 [Redis 分散式鎖](../../tech/realtime/44-Redis.md)。

### 問題 2：扣到第三項時發現庫存不夠

**情境**
一張單有五個品項。扣到第三項時庫存不足。

**如果沒有交易**
前兩項的庫存已經扣掉了，但訂單沒成立。**庫存憑空少了兩份，而且沒有人會發現。**

**正確做法**

```java
@Transactional                         // ← 整個方法綁在一起
public OrderTicketDto submitOrder(String token, SubmitOrderRequest req) {
    DiningSession session = sessionService.lockOrderable(token);  // FOR UPDATE，不是 OPEN → 409 SESSION_CLOSED

    validateSoupBaseRule(session, req);        // ① 鍋底規則
    validateOptions(req);                      // ② 必選／上限

    // ③ 依 id 排序後逐項扣庫存（避免死鎖）
    req.items().stream()
       .sorted(comparing(OrderItemRequest::menuItemId))
       .forEach(this::decreaseStockOrThrow);   // 任一項失敗 → 例外 → 全部回滾

    OrderTicket ticket = buildTicketWithSnapshots(session, req);  // ④⑤⑥
    session.recalculate();                                        // ⑦

    return toDto(ticket);
}
```

**推 WebSocket 要放在交易「之後」**，否則交易還沒 commit 前端就收到通知，去查卻查不到資料。

**延伸**：為什麼要依 id 排序？因為兩個交易如果用不同順序鎖資料，會[死鎖](../../tech/database/28-鎖與併發.md)。統一順序就不會。

### 問題 3：同桌兩支手機怎麼同步？

**情境**
你和朋友各自拿手機。你加了一盤牛五花，他的手機要看到。

**做法 A：輪詢**
每 3 秒問一次「有新的嗎」。

- 優點：簡單、容錯性天然就好
- 缺點：多數請求是白問的；最慢晚 3 秒

**做法 B：WebSocket** ← 我們選這個

你一送出，後端直接推到訂閱 `/topic/session/{id}` 的所有裝置。

- 優點：真的即時（<1 秒）、省請求
- 缺點：要處理斷線、部署要支援協定升級

**關鍵：WebSocket 不保證不漏**

手機切到別的 App、進電梯、Wi-Fi 換 4G——連線就斷了，**斷線期間推的東西全部收不到**。

所以：

```js
onConnect: () => {
  subscribe(`/topic/session/${sessionId}`, handleEvent);
  refetchAll();          // ★ 每次（重新）連上都重抓一次完整資料
}
```

**這一行讓你同時拿到「即時」和「不會錯」。** 就算 WebSocket 完全掛掉，只要使用者重新整理，資料還是對的。

### 問題 4：客人連按三下送出

**情境**
網路有點慢，客人以為沒反應，連按三下。

**如果不處理**
成立三張一模一樣的單，廚房做三份。

**做法 A：前端擋**

```jsx
<Button disabled={submitting} loading={submitting} onClick={handleSubmit}>
  送出點餐
</Button>
```

必要，但**不夠**——[前端的檢查不算數](../../tech/web/06-前端後端在做什麼.md)。

**做法 B：後端也擋（冪等鍵）**

前端每次送出時產生一個唯一的 `requestId`，後端在短時間內收到相同的就直接回上一次的結果。

**我們的決定**：基礎版做 A（前端停用按鈕），並在文件標明 B 是進階項。理由是我們的 API 是「建立新單」，重複送出的後果是多一張單而不是金額錯誤，且櫃檯可以取消。**但要在簡報時說明你們知道這個限制。**

### 問題 5：服務鈴要不要存資料庫？

**情境**
客人按「加湯」，櫃檯要看到。

**做法 A：只推 WebSocket，不存**
最省事。

**為什麼不好**
- 櫃檯重新整理頁面，未處理的呼叫就不見了
- 沒辦法統計
- 沒辦法標記「已處理」

**做法 B：存表 + 推 WebSocket** ← 我們選這個

```sql
service_call (
  id, dining_session_id, table_id,
  type    VARCHAR(20),   -- SERVICE / SOUP / POT_CLEAN（沒有結帳，結帳請到櫃檯）
  status  VARCHAR(20),   -- PENDING / ACKNOWLEDGED / DONE
  created_at, acknowledged_at, staff_id
)
```

成本只多一點點，但櫃檯體驗完全不同。

| 週 | 這個模組要交出什麼 |
|---|---|
| **W1** | Flyway 建好 `order_ticket` / `order_item` / `order_item_option`；Entity 三層關聯設定完成 |
| **W2** | **`POST /orders` 送出點餐**（交易＋防超賣＋快照＋驗證）；`GET /orders` 查詢；顧客端菜單頁、品項詳情頁、購物車頁 |
| **W3** | ★ 本桌訂單頁 + **WebSocket 同桌同步**；取消單品；結帳後不可加點（`SESSION_CLOSED`，跟 M6 對好同一把鎖）；**完整主流程走通** |
| **W4** | 服務鈴（後端表 + 前端按鈕 + 櫃檯推播）；人氣推薦 API |
| **W5** | 錯誤流程補完（售完標紅、斷線提示）；三態處理；RWD |
| **W6** | 不寫新功能。**寫多執行緒防超賣測試**、跑 demo 腳本 |

## 常見卡關

| 卡點 | 解法 |
|---|---|
| **交易沒生效** | 同一個類別內部呼叫 `@Transactional` 方法無效，見 [交易](../../tech/database/27-交易Transaction.md) |
| **推播推出去但前端查不到資料** | 推播寫在交易裡了，搬到交易外 |
| **前端收到事件但畫面沒更新** | 直接改了 state，要用 `setTickets(prev => [...prev, x])` |
| **WebSocket 一直斷線重連** | `useEffect` 依賴陣列裡有每次都變的物件 |
| **超賣測不出來** | 要寫多執行緒測試，見 [單元測試](../../tech/quality/47-單元測試.md) |
| **送出後金額對不上** | 用了 `double`，改 `BigDecimal` |

## 驗收 Demo 腳本

> **這就是第 3 週里程碑的驗收內容，也是最終 demo 的主線。**

1. 兩支手機掃同一桌的 QR，都進到菜單
2. 手機 A 選「鴛鴦鍋底」（左麻辣、右昆布）+ 牛五花（全份、加蔥花）→ 送出
3. **手機 B 在 1 秒內看到「第 1 單」出現**
4. 廚房看板同時跳出這張單
5. 手機 B 加點高麗菜 → 送出 → **手機 A 看到「第 2 單」**
6. 廚房勾選「鴛鴦鍋底已出餐」→ **兩支手機同時看到狀態變成「已出餐」**
7. 手機 A 按「服務鈴 → 加湯」→ **櫃檯畫面立刻跳出提示**
8. 手機 A 點一個庫存 0 的品項 → 送出 → **顯示「已售完」並標紅那一項，整張單沒有成立**
9. 本桌還沒點鍋底時，送出一張沒有鍋底的單 → **顯示「這桌還沒點鍋底，共鍋至少要一份」**，整張單沒有成立
10. 櫃檯在 S-03 標記已結清 → **兩支手機同時變成「已結帳」**，菜單變暗、購物車列換成「這桌已經結帳完成」
