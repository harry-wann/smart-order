# 05 開發流程與時程

> **工作分配（基礎功能）切成五個工作包 A～E，見 §1.4**，人選開會認領；技術地基 L0 由 Harry 負責，不列入工作包。
> 進階 A1～A7 等基礎全綠燈後再分。開發順序是**後端先出 stub、前端一律接真的 API**，見 §1.4.4 與 §3。

## 1. 工作分配

### 1.1 我們的分工方法：以功能切分

> **一個人負責一個功能的前後端**，從資料表 → API → 畫面全部自己走一遍。
> **不切前端組／後端組。**

| | 水平切（前端組／後端組） | **功能切（我們用這個）** |
|---|---|---|
| 一個人做什麼 | 所有功能的某一層 | **一個功能的所有層** |
| 學到什麼 | 一層很熟，其他層沒碰過 | 一條完整的路 |
| 介面對不上時 | 「一定是你 API 的問題」 | 自己兩邊都改 |
| 面試能講什麼 | 「我負責寫前端」 | **「我做了訂位，遇到了區間重疊和併發問題，我這樣解」** |
| 代價 | 學習成本低 | **每個人前後端都要學** |

代價是真的存在的：每個人都要學 React、也要學 Spring Boot。這正是為什麼 [技術總表](../tech/00-技術總表.md) 安排了**必修八頁**——那是全員的共同語言，先讀完再開工。

### 1.2 分配的時候要注意什麼

等規格定稿後分配時，建議照這幾條：

1. **難易度要平均**。八大模組的難易度是 ★★☆☆☆ 到 ★★★★☆，不要讓一個人拿到兩個四星模組
2. **相依性高的模組給同一個人或相鄰的人**。例如 M3 點餐和 M5 庫存共用「送出點餐」那段交易，分開做會很痛
3. **技術地基（L0）由 Harry 專門負責**，不算進工作包——他卡住全隊都會卡住，所以範圍另外列（§1.4.1）
4. **每個模組要有第二個人能 review**，尤其是 M3、M5、M7 這三個有併發問題的
5. **共用檔案要有唯一負責人**（見 §2.4）

#### 1.4.4 開發順序：先前端、後後端

**假資料放在後端，前端一律當成真的**（2026-09-20 定案）

前端**沒有任何 mock 機制**——沒有 `mock/` 資料夾、沒有 `VITE_USE_MOCK` 開關、
也沒有假的 WebSocket。畫面一律打真的 HTTP、連真的 WebSocket。

需要假資料的時候，假在**後端**：API 先寫成回傳寫死的 JSON、不真的查資料庫，
之後再把實作填進去。對前端來說那就是一支正常的 API，後端換成真實查詢時**前端一行都不用改**。

**為什麼這樣選：**

- 前端不用寫兩套（一套 mock、一套真的），也不會有「mock 跟 04 對不上、換的時候要改畫面」這個經典問題——那原本是 §5 風險表上的高風險項
- API 合約從第一天就被真的跑過一次：CORS、權杖、錯誤碼、JSON 欄位名、日期格式全是真的，不會到整合那天才發現對不上
- 不用擔心假資料混進 production build
- 三態裡的「錯誤」可以請後端真的回 409，比前端自己假造可信

**規矩**（五包都一樣）：

| 規矩 | 做法 |
|---|---|
| 格式照 04 | 後端回傳的欄位、型別、錯誤碼**逐字照 [04-API規格](04-API規格.md) 的範例**，不自己發明；04 沒寫的先問 Harry 再補進 04 |
| 放哪裡 | 後端各模組的 Controller。前端只有 `src/services/api/<模組>.js` 一層，不分真假 |
| 假到什麼程度 | Controller 直接 `return` 寫死的 DTO，不碰 Repository。之後把查詢填進去，回傳型別不變 |
| 模擬延遲 | 要看骨架屏就在後端 `Thread.sleep(300~800)`，**不要在前端假造**；填實作時記得拿掉 |
| 模擬錯誤 | 錯誤態（`CART_EMPTY`、`BILL_CHANGED`、`TABLE_RESERVED`、`CANCEL_DEADLINE_PASSED`）請後端真的回 400／409，前端才測得到真的錯誤處理路徑 |
| 即時事件 | WebSocket 也是真的。要演即時效果，後端開一支開發用端點手動觸發推播，payload 照 04 §3.4 |
| 換成真的 | 後端把寫死的 JSON 換成真的查詢，**前端不改**；如果前端需要改才接得上，代表回傳跟 04 不一致，先修後端或修 04 |

**誰寫什麼**（2026-09-20 定案）

| | 做什麼 | 什麼時候 |
|---|---|---|
| **L0（Harry）** | Spring Boot 骨架、Docker Compose、Flyway＋種子、統一回應、全域例外、CORS、Swagger | **第 1 週開工前就要能跑** |
| **各包 A～E** | 自己模組的 API 自己寫：第 1 週先出 stub，第 3～4 週填實作 | 見 §3 |

> **stub 是什麼**：簽名是真的、裡面是假的空殼函式。
>
> ```java
> @GetMapping("/menu")
> public List<MenuItemDto> getMenu() {
>     // 第 1 週：回寫死的，不碰 Repository
>     return List.of(new MenuItemDto(101, "麻辣鍋", 180, false));
>     // 第 3 週：改成 menuRepository.findAll()，網址與回傳型別完全不變
> }
> ```
>
> 重點是**外面從第一天就是最終版**——網址、回傳型別、欄位名、錯誤碼都照 04。
> 填實作的時候前端一行都不用改。

> ★ **這條流程的單點風險**：所有人第一天就要打後端，
> 所以 L0 的骨架沒好，五個人一起卡住。這是新流程最需要盯的地方。

**資料夾長這樣**（2026-09-20 定案，資料夾已經建好在 `frontend/src/services/`）：

```
src/services/          ← 跟外面講話的東西全部放這裡，元件不直接 fetch 也不直接 new WebSocket
│
├── api/               ← HTTP：一問一答
│   ├── client.js          fetch 封裝。權杖、錯誤碼、base URL 只寫在這一個地方
│   └── <模組>.js          menu.js / cart.js / tables.js …畫面唯一會呼叫的層
│
└── realtime/          ← WebSocket：後端主動推
    └── socket.js          連線、重連、訂閱頻道
```

**哪個東西放哪裡，判斷方法是「誰先開口」：**

| 情況 | 放哪 | 例子 |
|---|---|---|
| 前端問一次、後端答一次 | `services/api/` | 拿菜單、加入購物車、送出點餐、結帳 |
| 後端主動推給前端 | `services/realtime/` | 同桌有人加了什麼、KDS 來新單、桌況變了、服務鈴 |

兩邊常常配成一對：收到 `CART_UPDATED` 推播後，**不要**直接把推播的 payload 塞進畫面，
而是回頭呼叫 `api/cart.js` 重抓一次。推播只當「該更新了」的信號，資料以 API 為準，
這樣兩支手機看到的內容一定一致。

> **為什麼多包一層 `services/`**：`frontend/src/` 的資料夾結構（commit `9bd1a58`）建的是
> `services/`，這份文件原本寫的是 `src/api/` 與 `src/realtime/`。2026-09-20 決定兩者合併——
> `services/` 保留當資料層的總稱，底下再用 `api/` 與 `realtime/` 把兩個概念分開。
> 好處是 `src/` 頂層少一個資料夾，而且「所有對外通訊都在 services/ 底下」這句話講得完整。
> **不要再把 `api/` 或 `realtime/` 搬回 `src/` 頂層。**

## 2. Git 協作規範

> 不熟悉的人先看 [Git 是什麼](../tech/team/02-Git是什麼.md)、[分支與合併](../tech/team/03-分支與合併.md)、[GitHub 與 PR](../tech/team/04-GitHub與PR.md)。

### 2.1 分支策略

```
main          ← 隨時可部署。只接受來自 develop 的 PR
  └ develop   ← 整合分支
      ├ feature/menu-option-group
      ├ feature/order-submit
      ├ feature/reservation-overlap
      └ fix/kds-websocket-reconnect
```

**三條鐵律**

1. **禁止直接 push 到 `main` 和 `develop`**（GitHub 設 branch protection）
2. 分支命名：`feature/<模組>-<簡述>`、`fix/<簡述>`、`docs/<簡述>`
3. 每個 PR 至少 **1 人 review**，且 **CI 必須綠燈**才能合併

### 2.2 Commit 訊息

```
feat: 新增送出點餐 API
fix: 修正 KDS 斷線後未重抓資料
docs: 更新 API 規格的 WebSocket 事件表
refactor: 抽出金額計算邏輯
test: 補上防超賣的多執行緒測試
chore: 升級 Spring Boot 版本
```

### 2.3 最容易出事的地方

| 風險 | 預防 |
|---|---|
| 兩人同時寫 Flyway migration，版本號撞號 | **指定唯一負責人**，其他人開 issue |
| 有人改了已合併的 migration | Flyway 會拒絕啟動。**已 push 的絕不修改，寫新的一支** |
| `package-lock.json` 衝突 | 不要手動解，刪掉重跑 `npm install` |
| Entity 改欄位沒通知 | PR 標題加 `[BREAKING]`，群組 @所有人 |
| 有人 `git push -f` 到共用分支 | **禁止** |
| 密碼被 commit 上去 | 第一天就設好 `.gitignore` |

### 2.4 共用檔案的唯一負責人

這些檔案動到就會影響所有人，**每一個都要有唯一 owner**：

| 項目 | 負責人 | 為什麼要唯一負責人 |
|---|---|---|
| `db/migration/` 下的 Flyway 檔案 | L0（Harry） | 版本號會撞、改了別人跑不起來 |
| Entity 定義 | L0（Harry） | 改欄位所有人都要跟著改 |
| 種子資料程式 | L0（Harry） | |
| `pom.xml` | L0（Harry） | 最容易衝突的檔案之一 |
| `docker-compose.yml` | L0（Harry） | 環境設定 |
| WebSocket 設定與事件型別 | L0（Harry） | 事件格式是前後端的合約 |
| `04-API規格.md` | L0（Harry） | 同上 |
| `frontend/package.json` | L0（Harry） | 前端只有一份，五個人都會受影響；要加套件先在群組說 |

## 7. 給整合負責人的三個提醒

不管最後誰擔任這個角色，這三件事要有人做：

1. **主要工作不是寫最多程式碼，是讓其他四個人不被卡住。** 把共用層做好、環境弄順、衝突解掉，比自己多寫一個功能有價值。
2. **第 4 週結束時要誠實評估。** 如果主流程還沒通，立刻砍掉第 5 週的一半功能。**砍範圍不丟臉，交不出來才丟臉。**
3. **每週五一定要整體跑一次。** 不要等到第 6 週才第一次把所有人的東西合起來——那時候才發現介面對不上就來不及了。
