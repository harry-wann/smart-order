# 05 開發流程與時程

> **工作分配（基礎功能）已切成五個工作包 A～E，見 §1.4**，人選開會認領。進階 A1～A7 等基礎全綠燈後再分。
> 協作規範與六週時程跟誰做什麼無關，照 §2、§3 走。

## 1. 工作分配

### 1.1 我們的分工方法：以功能切分

> **一個人負責一個功能的前後端**，從資料表 → API → 畫面全部自己走一遍。
> **不切前端組／後端組。**

| | 水平切（前端組／後端組） | **功能切（我們用這個）** |
|---|---|---|
| 一個人做什麼 | 所有功能的某一層 | **一個功能的所有層** |
| 學到什麼 | 一層很熟，其他層沒碰過 | 一條完整的路 |
| 介面對不上時 | 「一定是你 API 的問題」 | 自己兩邊都改 |
| 面試能講什麼 | 「我負責寫前端」 | **「我做了訂位，遇到了區間重疊和併發問題，我這樣解」** |
| 代價 | 學習成本低 | **每個人前後端都要學** |

代價是真的存在的：每個人都要學 React、也要學 Spring Boot。這正是為什麼 [技術總表](../tech/00-技術總表.md) 安排了**必修八頁**——那是全員的共同語言，先讀完再開工。

### 1.2 分配的時候要注意什麼

等規格定稿後分配時，建議照這幾條：

1. **難易度要平均**。八大模組的難易度是 ★★☆☆☆ 到 ★★★★☆，不要讓一個人拿到兩個四星模組
2. **相依性高的模組給同一個人或相鄰的人**。例如 M3 點餐和 M5 庫存共用「送出點餐」那段交易，分開做會很痛
3. **技術地基（L0）要有人專門負責**，而且他的功能模組要少一點——因為他卡住全隊都會卡住
4. **每個模組要有第二個人能 review**，尤其是 M3、M5、M7 這三個有併發問題的
5. **共用檔案要有唯一負責人**（見 §2.4）

#### 1.4.3 包與包之間的接點

跨包的地方先把**介面**講好，各自寫自己那側：

| 接點 | 提供方 → 使用方 | 約定 |
|---|---|---|
| Entity、Flyway、種子資料 | A → 全部 | 要加欄位開 issue 給 A，不要自己寫 migration |
| 用餐權杖、`X-Device-Id`、guest | D（join API）＋ A（filter）→ C | D 發權杖與 guest，A 的 filter 驗，C 的購物車拿 `guestId` 用 |
| 菜單品項與選項 | B → C | C 送出點餐時呼叫 B 的選項驗證（1.5），不自己再寫一份 |
| `NEW_TICKET` 與出餐事件 | C 發 `NEW_TICKET` → B 的 KDS／C-08 | 事件格式照 [04 §3.4](04-API規格.md)，A 維護型別 |
| 售完 | C 發 `MENU_SOLD_OUT` → B 的 C-04 標灰 | |
| C-04 上的疊層 | C 的元件 → B 的頁面 | 購物車列、C-04b／C-04c、已結帳面板 |
| 桌位狀態轉換 | C（結清 → `CLEANING`、取消 → `AVAILABLE`）→ D | C 呼叫 D 的 `TableService`，不直接改 `dining_table` |
| 預約保留 | E 的 `ReservationHoldService` → D 的 `GET /api/admin/tables` 與開桌三支 | D 只問「這桌現在保留中嗎」，判斷邏輯全在 E |
| 開桌 | D 的開桌 Service → E 的報到 | E 報到時呼叫 D 開桌，D 開完回頭把來源轉 `SEATED` |
| 選桌對話框 | D（S-10b 元件）→ E（S-07b） | |
| 服務鈴面板位置 | D 的後台版型 → A 的 S-11 | D 在版面右上留位置 |
| 訂位表單資料 | A（C-16b）→ E（C-16c） | 用 router state 帶姓名、手機、信箱 |

## 2. Git 協作規範

> 不熟悉的人先看 [Git 是什麼](../tech/team/02-Git是什麼.md)、[分支與合併](../tech/team/03-分支與合併.md)、[GitHub 與 PR](../tech/team/04-GitHub與PR.md)。

### 2.1 分支策略

```
main          ← 隨時可部署。只接受來自 develop 的 PR
  └ develop   ← 整合分支
      ├ feature/menu-option-group
      ├ feature/order-submit
      ├ feature/reservation-overlap
      └ fix/kds-websocket-reconnect
```

**三條鐵律**

1. **禁止直接 push 到 `main` 和 `develop`**（GitHub 設 branch protection）
2. 分支命名：`feature/<模組>-<簡述>`、`fix/<簡述>`、`docs/<簡述>`
3. 每個 PR 至少 **1 人 review**，且 **CI 必須綠燈**才能合併

### 2.2 Commit 訊息

```
feat: 新增送出點餐 API
fix: 修正 KDS 斷線後未重抓資料
docs: 更新 API 規格的 WebSocket 事件表
refactor: 抽出金額計算邏輯
test: 補上防超賣的多執行緒測試
chore: 升級 Spring Boot 版本
```

### 2.3 最容易出事的地方

| 風險 | 預防 |
|---|---|
| 兩人同時寫 Flyway migration，版本號撞號 | **指定唯一負責人**，其他人開 issue |
| 有人改了已合併的 migration | Flyway 會拒絕啟動。**已 push 的絕不修改，寫新的一支** |
| `package-lock.json` 衝突 | 不要手動解，刪掉重跑 `npm install` |
| Entity 改欄位沒通知 | PR 標題加 `[BREAKING]`，群組 @所有人 |
| 有人 `git push -f` 到共用分支 | **禁止** |
| 密碼被 commit 上去 | 第一天就設好 `.gitignore` |

### 2.4 共用檔案的唯一負責人

這些檔案動到就會影響所有人，**每一個都要有唯一 owner**：

| 項目 | 負責工作包 | 為什麼要唯一負責人 |
|---|---|---|
| `db/migration/` 下的 Flyway 檔案 | A | 版本號會撞、改了別人跑不起來 |
| Entity 定義 | A | 改欄位所有人都要跟著改 |
| 種子資料程式 | A | |
| `pom.xml` | A | 最容易衝突的檔案之一 |
| `docker-compose.yml` | A | 環境設定 |
| WebSocket 設定與事件型別 | A | 事件格式是前後端的合約 |
| `04-API規格.md` | A | 同上 |
| `frontend-customer/package.json` | B | |
| `frontend-admin/package.json` | D | |
| Tailwind 設定與共用元件 | 顧客端 B、店家端 D | 改了全站樣式都會變 |
| Figma 檔 | B | |

> **★ 本週是整個專案最關鍵的里程碑**：

## 4. 每日／每週節奏

| 時間 | 活動 | 時長 |
|---|---|---|
| 每天早上 | 站立會：昨天做了什麼／今天要做什麼／卡在哪 | **15 分鐘，站著講** |
| 每天結束 | 各自 push 到 feature 分支（**不要囤積本機程式碼**） | — |
| 每週三 | 中期檢查：本週里程碑會不會達成？不會的話現在就砍範圍 | 30 分鐘 |
| 每週五 | 收斂會：合併 PR、整體跑一次、更新 [02-需求規格](02-需求規格.md) 的狀態欄 | 60 分鐘 |

**「卡住 30 分鐘就要開口」原則**：新手最常見的時間殺手是一個人默默卡 3 小時。規定卡住 30 分鐘沒進展就在群組貼出來。**這條規則能省掉整個專案 20% 的時間。**

## 7. 給整合負責人的三個提醒

不管最後誰擔任這個角色，這三件事要有人做：

1. **主要工作不是寫最多程式碼，是讓其他四個人不被卡住。** 把共用層做好、環境弄順、衝突解掉，比自己多寫一個功能有價值。
2. **第 3 週結束時要誠實評估。** 如果主流程還沒通，立刻砍掉第 4、5 週的一半功能。**砍範圍不丟臉，交不出來才丟臉。**
3. **每週五一定要整體跑一次。** 不要等到第 6 週才第一次把所有人的東西合起來——那時候才發現介面對不上就來不及了。
