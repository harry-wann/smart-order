鎖與併發（防超賣）

難度 ★★★★☆　用在哪些模組 M2、M3、M5、M6、M7（全員都該懂）　哪幾週 第 3～4 週

一句話

當兩個人同時做同一件事，要有辦法保證只有一個人成功。

這一頁是整個專案技術含量最高、面試最愛問的一頁。五個人都要能講。

想像一下

牛五花庫存剩 1 份。你和朋友幾乎同時按下「送出點餐」。

直覺的寫法：

int stock = inventoryRepo.findQuantity(12);    // 查庫存
if (stock >= 1) {                              // 夠嗎？
    inventoryRepo.decrease(12, 1);             // 扣掉
}

看起來沒問題。但把時間軸攤開：

時間 →
你：    查庫存(=1) ──→ 判斷 1>=1 ✓ ──→ 扣掉 ──→ 庫存 0
朋友：       查庫存(=1) ──→ 判斷 1>=1 ✓ ──→ 扣掉 ──→ 庫存 -1

兩個人的「查」都發生在對方的「扣」之前，所以兩邊查到的都是 1，兩邊都通過檢查，兩邊都扣。

結果：賣出兩份，但只有一份貨。庫存變成 -1。

這叫超賣。電商、演唱會售票、餐廳庫存——全部都要處理這個問題。

為什麼不能「加個判斷」解決

很多人的第一反應是「那我扣完再檢查一次不就好了」。不行，因為問題的根源是：

「查」和「扣」是兩個分開的動作，中間有空隙讓別人插進來。

只要是兩個動作，就一定有空隙。解法是讓它變成一個動作。

解法一：把條件寫進 UPDATE（我們用這個）

UPDATE inventory_item
   SET quantity = quantity - :qty,
       updated_at = NOW(3)
 WHERE menu_item_id = :itemId
   AND quantity >= :qty;          -- ← 關鍵在這一行

int affected = inventoryRepo.decreaseIfEnough(itemId, qty);
if (affected == 0) {
    throw new BusinessException("ITEM_SOLD_OUT", item.getName() + " 已售完", CONFLICT);
}

為什麼這樣就安全？

資料庫保證：同一時間只有一個交易能修改同一列。第二個人的 UPDATE 會排隊等，等到執行時庫存已經是 0，quantity >= 1 不成立，影響筆數是 0。

一句 SQL，沒有鎖的概念要學，效能也最好。

判斷成敗看「影響筆數」，不是看有沒有報錯。 這點很多人會漏掉。

解法二：悲觀鎖

「我先把這一列鎖住，誰都不准動，等我做完再說。」

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT i FROM InventoryItem i WHERE i.menuItem.id = :id")
Optional<InventoryItem> findByMenuItemIdForUpdate(@Param("id") Long id);

底下對應的 SQL 是 SELECT ... FOR UPDATE。

  • 優點：拿到鎖之後你可以放心做任何複雜判斷
  • 缺點：別人要排隊等，高併發時會慢；而且有死鎖風險

我們在訂位配桌時用這個，因為配桌要做區間重疊計算，沒辦法寫成一句 UPDATE。 送出點餐也會用到：先鎖住這桌的 dining_session 那一列，再讀整桌購物車（見下面的場景表）。

解法三：樂觀鎖

「我先假設沒人會跟我搶。真的撞到了再重試。」

@Entity
public class InventoryItem {
    @Version                 // ← 加這個欄位
    private Long version;
}

JPA 會自動在更新時帶上版本號：

UPDATE inventory_item SET quantity = ?, version = version + 1
WHERE id = ? AND version = ?     -- 版本對不上就更新 0 筆

版本對不上 → 丟 OptimisticLockException → 你可以捕捉後重試。

  • 優點：不用等，效能好
  • 缺點：要自己寫重試邏輯

三種解法怎麼選

情況 用什麼
單純的加減（扣庫存） 條件式 UPDATE ← 最簡單最好
要複雜判斷（訂位配桌） 悲觀鎖
衝突機率低、不想等 樂觀鎖
多台伺服器且要鎖的不是資料庫的東西 Redis 分散式鎖

我們專案的五個併發場景

場景 會發生什麼 解法
兩人同時點最後一份牛五花 超賣 條件式 UPDATE
兩人同時訂同一時段同一桌 重複預約 悲觀鎖 + 唯一約束
兩個櫃檯同時對同一桌開桌 出現兩張帳單 悲觀鎖 SELECT ... FOR UPDATE，後到的回 409 TABLE_OCCUPIED
同桌兩個人同時按「送出整桌點餐」 同一份購物車被送兩次，變成兩張一樣的單 送出時先鎖這桌的 dining_session（SELECT ... FOR UPDATE），兩筆排隊；先到的讀購物車 → 扣庫存 → 寫單 → 清購物車，後到的讀到空購物車，回 409 CART_EMPTY
櫃檯正在結清，同桌客人又送出加點 收的錢跟帳單對不上 結清和送出點餐都先鎖同一筆 dining_session；結清時帶畫面上的合計 expectedTotal，重算不相等回 409 BILL_CHANGED，已結清後才到的加點回 409 SESSION_CLOSED；結清的同一個交易也把整桌還沒送出的購物車刪掉

同桌兩人同時送出，時間軸長這樣

時間 →
小美：鎖住 A03 的 dining_session → 讀購物車（6 項）→ 扣庫存、寫單、清購物車 → 提交，放開鎖
大明：    想鎖同一列（排隊等小美）………………………………………………→ 拿到鎖 → 讀購物車（0 項）→ 409 CART_EMPTY

關鍵是「先鎖，再讀購物車」。 順序反過來（還沒鎖就先讀購物車），大明手上拿的是過期的 6 項，就有機會再送出一次。 大明的手機收到 CART_EMPTY，提示「購物車是空的，可能同桌已經送出了」並重抓購物車；同時也會收到小美送單的通知。

所以同一桌的人不會互相超賣——他們在排隊。超賣發生在不同桌同時搶最後一份庫存，那是上面的條件式 UPDATE 在擋的。

死鎖是什麼

兩個交易互相等對方的鎖：

交易 A：鎖住品項 1 → 想鎖品項 2（但 2 被 B 鎖著，等）
交易 B：鎖住品項 2 → 想鎖品項 1（但 1 被 A 鎖著，等）

兩邊永遠等下去。MySQL 會偵測到，隨機殺掉一個並回 Deadlock found。

怎麼避免：永遠用同樣的順序鎖東西。我們的做法是扣庫存前先把品項 id 排序：

List<Long> sortedIds = itemIds.stream().sorted().toList();
for (Long id : sortedIds) { decreaseStock(id, ...); }

這樣所有交易都按 id 由小到大鎖，就不會互相等。

15 分鐘動手小練習

親手製造一次超賣。

  1. 建一張表 stock(id, quantity)，塞一筆 quantity = 1
  2. 寫一個 Service 方法：先查、判斷、再扣（故意用錯的寫法），中間加 Thread.sleep(100) 放大空隙
  3. 寫一個測試，用 10 條執行緒同時呼叫：
ExecutorService pool = Executors.newFixedThreadPool(10);
CountDownLatch latch = new CountDownLatch(10);
for (int i = 0; i < 10; i++) {
    pool.submit(() -> { try { service.buy(1L, 1); } catch (Exception ignored) {} finally { latch.countDown(); } });
}
latch.await();
  1. 去資料庫看 quantity ——會是負的
  2. 把 Service 改成條件式 UPDATE，再跑一次 ——這次是 0，而且只有 1 個人成功

這個練習是本專案最有價值的 15 分鐘。 做完你在面試時可以完整講一個故事。

你會遇到的坑

① 先查再改 本頁的核心。

② 在程式裡用 synchronized 只鎖得住同一台伺服器。部署兩台就失效。而且資料庫層的問題要在資料庫層解。

③ 忘記檢查影響筆數 條件式 UPDATE 不會報錯，它只是「更新了 0 筆」。你不檢查就等於沒防護。

④ 交易太長 鎖住的時間越久，別人等越久，越容易死鎖。

⑤ 沒有測試 這種問題單人測試永遠測不出來。必須寫多執行緒測試。

你會看到 中文意思 怎麼修
