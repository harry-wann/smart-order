資料表設計

難度 ★★★☆☆　用在哪些模組 技術地基 L0　哪幾週 第 1 週（L0）、第 3 週

一句話

資料表設計就是決定哪些東西要分開記、彼此怎麼指來指去。

想像一下

你要記錄火鍋店的訂單。最直覺的做法是一張大表：

帳單ID 桌號 座位數 客人姓名 電話 品項 單價 數量
1 A03 4 王小明 0912... 牛五花 280 2
1 A03 4 王小明 0912... 高麗菜 80 1
1 A03 4 王小明 0912... 麻辣鍋底 480 1

看出問題了嗎？

  • 桌號、座位數、姓名、電話重複了三次——同一筆資料存三份，很浪費，而且改電話要改三個地方
  • 改到一半改錯，同一張帳單出現兩個不同的電話
  • A03 桌今天沒客人，那它就完全不存在於這張表裡，你沒辦法管理它

正確的做法是拆開：桌位一張表、會員一張表、帳單一張表、品項一張表，然後用「指過去」的方式連起來。

三個核心概念

① 主鍵（Primary Key）—— 這一列的身分證

每張表都要有一個唯一的識別。我們統一用：

id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT

AUTO_INCREMENT = 自動編號，你不用管。

② 外鍵（Foreign Key）—— 指向別張表

CREATE TABLE dining_session (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  table_id BIGINT NOT NULL,
  FOREIGN KEY (table_id) REFERENCES dining_table(id)
);

這條外鍵保證：你不可能建立一筆指向不存在桌位的帳單。資料庫會幫你擋。

③ 三種關聯

關聯 意思 我們的例子 怎麼做
一對多 一個 A 有很多 B 一次用餐有多張點餐單 B 表上放 a_id 外鍵
一對一 一個 A 對一個 B 一個品項一筆庫存 外鍵 + UNIQUE
多對多 互相都可以有很多 品項 ↔ 選項群組 中間再開一張表

多對多的中間表長這樣：

CREATE TABLE menu_item_option_group (
  menu_item_id BIGINT,
  option_group_id BIGINT,
  sort_order INT,
  PRIMARY KEY (menu_item_id, option_group_id)
);

這樣「辣度」這個選項群組就能同時掛在 20 個品項上，不用重複建 20 次。

我們專案最重要的設計決定

三層結構

dining_session（一次用餐 = 一張帳單）
  └── order_ticket（一次送出購物車 = 出單機印一張）
        └── order_item（單一品項）
              └── order_item_option（這個品項選了什麼）

為什麼要三層？ 因為火鍋店是「開桌 → 加點好幾次 → 結一次帳」。

  • 如果只用一張 order 表，加點時要不要開新訂單？結帳要結哪一張？
  • 三層分開後：結帳算 dining_session，出單機印 order_ticket，廚房勾 order_item

這個設計如果搞錯，第 4 週要打掉重來。

快照欄位

order_item (
  menu_item_id BIGINT,              -- 指向菜單
  item_name_snapshot VARCHAR(100),  -- 但同時存一份當下的名稱
  unit_price_snapshot DECIMAL(10,2) -- 和當下的價格
)

為什麼要重複存？ 因為菜單價格會改。

如果不存快照，老闆把牛五花從 280 調到 320，那三個月前的帳單金額會跟著變成 320。歷史帳單必須凍結在當下的價格。

這是少數「故意重複存資料」是對的情況。

購物車也是一張表

我們的購物車是整桌共用的：同桌每支手機看到同一份，誰都能加、改、刪，按「送出整桌點餐」就整份變成一張 order_ticket。

dining_session
  ├── dining_session_guest（同桌的「誰」：一支手機一筆，顯示「陳小美 加的」用）
  ├── cart_item（還沒送出的品項，記下 added_by_guest_id）
  │     └── cart_item_option（選了哪些選項，只記 option_value_id）
  └── order_ticket（送出時從 cart_item 搬過來，同一個交易裡刪掉那些 cart_item）
  • 為什麼不放前端或 HTTP session？ 那都是「每支手機各一份」，同桌看不到彼此加了什麼；伺服器重開還會不見。
  • 為什麼不放 Redis？ 送出時購物車要跟寫單在同一個交易裡搬進 order_ticket，放在同一個資料庫最單純（見 交易 Transaction）。
  • dining_session_guest 的 UNIQUE(dining_session_id, device_id)：同一支手機在同一桌只算一個人，重新掃碼也不會變成「客人 3」。device_id 只拿來標示誰加的，不是身分驗證。

cart_item 也有一個 unit_price（加入當下的價格），但它只給畫面顯示——送出時還是用菜單現價重算，再寫進 order_item 的快照。 選項也一樣：購物車階段不快照，送出時才快照名稱與價差。快照只在「成交」那一刻做。

命名規定

東西 規定 例子
資料表 單數、底線 menu_item、dining_session
欄位 底線 created_at、is_soup_base
主鍵 一律 id
外鍵 <表名>_id menu_item_id
布林 TINYINT(1) active、sold_out
金額 DECIMAL(10,2) 絕對不要用 FLOAT
時間 DATETIME(3) created_at、updated_at
列舉 VARCHAR(20) 存字串 比 MySQL 的 ENUM 好改

每張表都要有 created_at 和 updated_at。 出事的時候這兩個欄位會救你。

15 分鐘動手小練習

把開頭那張「大表」拆開。試著畫出：

  1. 需要幾張表？
  2. 每張表有什麼欄位？
  3. 外鍵放在哪一張表上？

自己畫完再對照我們的 03-資料庫設計。差多少？

（提示：至少需要 桌位、會員、帳單、點餐單、單品、菜單品項 六張。）

你會遇到的坑

① 一張大表裝全部 初期很方便，後期改到崩潰。

② 沒有外鍵約束 「我在程式裡檢查就好」——然後某天資料庫裡出現指向不存在桌位的帳單，而且你不知道是誰寫進去的。

③ 用 FLOAT 存金額 帳單差一塊錢，找一整天。

④ 沒存快照 改一次菜單價格，所有歷史帳單金額全變了。

⑤ 五個人各自改表 所以我們用 Flyway，而且 schema 只有 A 能改。

⑥ 一開始就過度設計 把所有可能的功能都建表。做不完的東西不要先建表。

常見錯誤訊息對照

你會看到 中文意思 怎麼修
foreign key constraint fails 外鍵指向的資料不存在 先建父資料，或檢查 id 對不對
Cannot delete or update a parent row 有子資料還指著它 先刪子資料，或設 ON DELETE 行為
Duplicate entry for key 'PRIMARY' 主鍵重複 通常是手動指定了 id
Field 'xxx' doesn't have a default value 必填欄位沒給值 補上，或設預設值

術語對照表

白話 正式名稱
這一列的身分證 主鍵 Primary Key
指向別張表 外鍵 Foreign Key
不重複 唯一鍵 Unique Key
把重複的拆開 正規化 Normalization
故意重複存 反正規化 / 快照 snapshot
多對多的中間表 關聯表 / junction table
