區間重疊：訂位排程的演算法

難度 ★★★★☆　用在哪些模組 M7　哪幾週 第 4 週

一句話

判斷「這張桌子在這個時間有沒有被占用」，其實就是一條兩個時間區間有沒有重疊的判斷式。

想像一下

A03 桌明天已經有一組訂位：18:00 ～ 19:40。

現在有客人想訂明天的 19:00 ～ 20:40。可以嗎？

畫在時間軸上：

        18:00      19:00      19:40      20:40
          |----------已訂-------|
                     |----------想訂--------|
                     └── 重疊 40 分鐘 ──┘

重疊了，不行。

我們的線上訂位只能訂明天以後（明天起 30 天內），當天不接線上訂位，所以這頁的例子都是在訂未來的某一天。

那條判斷式

兩個區間重疊的條件是：

A.開始 < B.結束  且  B.開始 < A.結束

套進去：18:00 < 20:40 ✅ 而且 19:00 < 19:40 ✅ → 重疊。

換一組：已訂 18:00–19:40，想訂 20:00–21:40。 18:00 < 21:40 ✅ 但 20:00 < 19:40 ❌ → 不重疊，可以訂。

就這麼一條。 所有訂位系統的核心都是它。

為什麼是 < 不是 <=？ 因為 18:00–19:40 和 19:40–21:20 是「剛好接續」，不算重疊。用 <= 的話會誤判成衝突。

加上清桌緩衝

現實中一組客人走了之後要收拾。所以把緩衝時間加進「結束時間」裡：

實際占用結束 = 開始時間 + 用餐時長 + 清桌緩衝
             = 18:00   + 100 分鐘  + 15 分鐘  = 19:55

存進資料庫時就存 start_time = 18:00、end_time = 19:55。判斷式完全不用改。

SQL 怎麼寫

找出某個時段還有空的桌子：

SELECT t.*
FROM dining_table t
WHERE t.active = 1
  AND t.reservable = 1
  AND t.seats >= :partySize
  AND NOT EXISTS (
      SELECT 1
      FROM reservation r
      WHERE r.table_id = t.id
        AND ( r.status = 'CONFIRMED'           -- ← 還沒到的
              OR (r.status = 'SEATED'          -- ← 已經入座、而且還沒結帳的
                  AND EXISTS (SELECT 1 FROM dining_session ds
                               WHERE ds.reservation_id = r.id
                                 AND ds.status = 'OPEN')) )
        AND r.start_time < :newEnd            -- ← 重疊判斷
        AND :newStart   < r.end_time
  )
ORDER BY t.seats ASC                          -- ← best-fit：先給剛好夠坐的
LIMIT 1;

三個重點：

  1. NOT EXISTS ＋ 重疊條件 = 「這張桌在這段時間沒有衝突的訂位」
  2. 狀態條件 — 還沒到的（CONFIRMED）算佔用；已經報到入座的（SEATED）只在那筆用餐紀錄還沒結帳（dining_session.status = 'OPEN'）時算，結帳或取消用餐後就不算，不用等到 end_time；取消（CANCELLED）和逾時未到（NO_SHOW）不算。訂位送出就直接是 CONFIRMED，沒有 PENDING 這種狀態。 注意 OR 外面那層括號不能少：AND 比 OR 先算，少了括號會變成「CONFIRMED 那一段不比時間、SEATED 那一段不比桌號」
  3. ORDER BY seats ASC — best-fit：2 個人不要佔 8 人桌

為什麼 SEATED 也要算、又只算到結帳？ 如果只算 CONFIRMED，客人一報到，這筆就不算了——18:00 那組人明明還坐著吃， 系統卻以為那張桌 18:30 空出來了，容量少算一組。反過來，如果 SEATED 一律算到 end_time，客人 19:10 就吃完結帳走了， 那張桌到 19:55 還被當成佔用，名額白白卡住。所以用「那筆用餐紀錄還是 OPEN」來判斷人還在不在。

線上訂位只能訂明天以後，所以這條主要影響的是「同一天之後的訂位保留」與容量報表的正確性，不會出現當天被線上搶訂的情況。 桌位本身照舊走「結清 → 待清理 → 清潔完成 → 空桌」，這跟名額算不算是兩回事。

客人現場被安排到別張桌時，reservation.table_id 也不跟著改：佔用算的是「訂位當下配的那張」，容量才不會跟著現場調度亂跳。

best-fit 為什麼重要

假設你有 4 人桌和 8 人桌各一張，來了一組 2 人。

  • 如果隨便給了 8 人桌 → 等一下來 6 人就沒位子了
  • 給 4 人桌 → 8 人桌留著，兩組都能接

一行 ORDER BY seats ASC 就做到了。 這是真實訂位系統都有的邏輯，成本幾乎為零。

併發問題

兩個客人同時訂同一張桌的同一個時段會怎樣？

客人A：查詢 → A03 有空 ──→ 寫入訂位
客人B：    查詢 → A03 有空 ──→ 寫入訂位
                              兩筆都成功！重複訂位

跟 防超賣 是同一類問題：查和寫中間有空隙。

但這次沒辦法寫成一句 UPDATE（因為要做區間計算），所以用悲觀鎖：

@Transactional
public ReservationDto create(CreateReservationRequest req) {
    LocalDateTime start = req.startTime();
    LocalDateTime end   = start.plusMinutes(DINING_MINUTES + BUFFER_MINUTES);

    // ① 先鎖住所有可能的候選桌（依 id 排序，避免死鎖）
    List<DiningTable> candidates =
        tableRepo.findReservableBySeatsForUpdate(req.partySize());

    // ② 在鎖的保護下做重疊檢查
    DiningTable picked = candidates.stream()
        .filter(t -> !reservationRepo.existsOverlap(t.getId(), start, end))
        .findFirst()
        .orElseThrow(() -> new BusinessException("SLOT_UNAVAILABLE",
            "這個時段已經客滿了", HttpStatus.CONFLICT));

    // ③ 寫入
    return toDto(reservationRepo.save(Reservation.of(picked, start, end, req)));
}

加一層保險：資料庫約束

-- 同一桌、同一個開始時間不能有兩筆
CREATE UNIQUE INDEX uk_reservation_table_start
  ON reservation (table_id, start_time);

就算程式有 bug，資料庫也會擋下來。「應用層 + 資料庫層」雙重保護是正確的做法。

取消訂位時要把 table_id 設成 NULL，不然這個唯一索引會擋住「取消之後，同一時段重新訂同一桌」。 客人線上取消（只到訂位時間前 30 分鐘）和櫃檯代客取消（隨時）都一樣要清。

查詢可訂時段

前端要顯示「哪些時間還能訂」，做法是把營業時間切成 30 分鐘一格，每格跑一次重疊檢查：

public List<SlotAvailability> checkAvailability(LocalDate date, int partySize) {
    List<SlotAvailability> result = new ArrayList<>();
    LocalDateTime cursor = date.atTime(OPEN_TIME);
    LocalDateTime closing = date.atTime(LAST_ORDER_TIME);

    while (!cursor.isAfter(closing)) {
        LocalDateTime end = cursor.plusMinutes(DINING_MINUTES + BUFFER_MINUTES);
        int available = tableRepo.countAvailable(partySize, cursor, end);
        result.add(new SlotAvailability(cursor.toLocalTime(), available > 0, available));
        cursor = cursor.plusMinutes(30);
    }
    return result;
}

一天大約 20 格，每格一次查詢——資料量小的時候完全沒問題。

訂位保留桌位：算出來的鎖定，不是排程

線上訂位成立後，配到的那張桌會在用餐時間前後鎖住，不讓櫃檯開給現場或候位的客人（M7 的 7.10）。鎖住的這段叫保留窗：

            開始前 30 分              開始              開始後 10 分
   ────────────|═══════════════════════|══════════════════|──────────→
               └──────── 保留窗：桌況顯示「預約保留」 ────────┘
          最早可以來報到                              超過就算逾時未到
  • 30 分＝最早可以提前報到的時間；10 分＝保留時間。兩個都放 application.yml：reservation.hold-before-minutes: 30、reservation.hold-after-minutes: 10
  • 要解開保留，就是取消那筆訂位：客人來電說不來了，櫃檯按「取消訂位」（POST /api/admin/reservations/{id}/cancel），訂位轉 CANCELLED、table_id 設 NULL，下面的條件就對不到它了，桌子與名額一起釋出。沒有「訂位照留、只解除保留」這種操作
  • 櫃檯代客取消隨時可以按，不受期限；只有 CONFIRMED 能取消，其他狀態回 409 RESERVATION_NOT_CANCELLABLE。取消是單向的，前端的二次確認要寫明「這筆訂位無法恢復」
  • 客人線上取消只到開始前 30 分（回 409 CANCEL_DEADLINE_PASSED）——剛好就是保留窗的開頭，所以保留開始之後只剩櫃檯能取消

保留是查詢的時候算出來的，不是排程。 dining_table.status 仍然只有 AVAILABLE／OCCUPIED／CLEANING 三種，沒有人會去把欄位改成 RESERVED：

-- 桌況總覽：每張桌的「顯示狀態」
SELECT t.id, t.table_no, t.status,
       CASE
         WHEN t.status <> 'AVAILABLE' THEN t.status      -- 用餐中、待清理優先
         WHEN r.id IS NOT NULL        THEN 'RESERVED'    -- 空桌、但落在保留窗內 → 預約保留
         ELSE 'AVAILABLE'
       END AS display_status,
       r.id AS hold_reservation_id, r.reservation_no, r.contact_name, r.party_size, r.start_time
FROM dining_table t
LEFT JOIN reservation r
       ON r.table_id = t.id
      AND r.status = 'CONFIRMED'
      AND r.start_time - INTERVAL 30 MINUTE <= NOW()
      AND NOW() <= r.start_time + INTERVAL 10 MINUTE
WHERE t.active = 1
ORDER BY t.table_no;

幾個重點：

  1. 優先順序：用餐中 ＞ 待清理 ＞ 預約保留 ＞ 空桌。 配到的桌到時間還有人在吃，就照樣顯示用餐中；客人到了，櫃檯從報到對話框（S-07b）幫他選別張桌
  2. 用 LEFT JOIN：大部分桌子沒有保留，用 JOIN 的話它們會整列消失（見 關聯式資料庫與 SQL）
  3. 不會對到兩筆：同一張桌的兩筆訂位至少隔 115 分鐘（上面的區間重疊擋掉了），保留窗只有 40 分鐘寬，不會撞在一起
  4. 範例把 30、10 寫死是為了好讀，實作時從 application.yml 讀進來當參數；NOW() 也建議改成傳 :now 進去，寫測試時才能指定「現在是 18:05」

開桌前也要用同一個條件檢查：

// 現場開桌、候位開桌：目標桌正在保留中 → 擋下來
reservationRepo.findActiveHold(tableId, now).ifPresent(hold -> {
    throw new BusinessException("TABLE_RESERVED",
        "這張桌保留給 " + hold.getContactName() + " " + hold.getStartTime().toLocalTime() + "，客人來電取消的話請到預約管理取消訂位",
        HttpStatus.CONFLICT);
});

預約報到開桌也一樣檢查，只是「保留給自己這筆」的桌可以直接開，被別筆訂位保留的才回 409 TABLE_RESERVED。 還沒到開始前 30 分就來報到，回 409 RESERVATION_TOO_EARLY；超過開始後 10 分，回 409 RESERVATION_EXPIRED。

還沒進保留窗、但快到了的桌：只提醒、不擋。 現在 18:00 要開 A05，A05 19:30 有訂位——保留窗還沒開始，後端不擋； 但現在開下去，這組大概要吃到 18:00 + 100 分 + 清桌 15 分 = 19:55，訂位的客人到了桌子還沒空。所以開桌頁要查「現在 ～ 現在 + 115 分」內有沒有別筆訂位要開始：

-- 開桌強烈提醒：這張桌 115 分鐘內要開始的別筆訂位（保留中的那筆已經另外處理）
SELECT r.id, r.contact_name, r.party_size, r.start_time
FROM reservation r
WHERE r.table_id = :tableId
  AND r.status = 'CONFIRMED'
  AND r.start_time >  :now + INTERVAL 30 MINUTE     -- 30 分內的已經是保留窗，會直接擋
  AND r.start_time <= :now + INTERVAL 115 MINUTE    -- 用餐 100 + 清桌 15
ORDER BY r.start_time
LIMIT 1;

查到就回 upcomingOnThisTable（選桌清單是 upcomingReservationAt），前端顯示醒目警示、主按鈕改「仍要開桌」並再確認一次；選桌清單把這種桌排在沒有衝突的桌後面。 115 一樣不要寫死，用 application.yml 的用餐時長＋清桌緩衝相加。

為什麼不用排程在 18:00 把桌子改成 RESERVED？ 那等於把訂位複製一份到桌位上，還要靠排程同步： 排程晚跑幾分鐘、伺服器剛好重開、訂位取消了桌子卻沒被排程改回來……畫面就會出現「顯示空桌、按開桌卻被擋」這種最難查的 bug。 算得出來的東西就不要存，每次查的時候算，永遠跟訂位資料一致。（排程仍然是九支，見 排程任務與 Cron。）

索引

CREATE INDEX idx_reservation_table_time
  ON reservation (table_id, start_time, end_time);

重疊檢查每次都用 table_id + 時間範圍，這個索引是必要的。 SEATED 那一段靠 dining_session.reservation_id 找用餐紀錄；它是外鍵，MySQL 會自動幫它建索引，不用另外加。

15 分鐘動手小練習

先用紙筆做，不要寫程式。

已訂：A03: 18:00–19:55、A03: 20:00–21:55

判斷這三個新請求可不可以（用 A.start < B.end AND B.start < A.end）：

  1. 19:30–21:25
  2. 19:55–21:50
  3. 17:00–18:55
答案 1. **不行**。跟第一筆：`18:00 < 21:25` ✅ 且 `19:30 < 19:55` ✅ → 重疊 2. **可以**。跟第一筆：`19:55 < 19:55` ❌ → 不重疊（剛好接續）。跟第二筆：`20:00 < 21:50` ✅ 且 `19:55 < 21:55` ✅ → **等等，重疊了**！所以答案是**不行** 3. **不行**。`17:00 < 19:55` ✅ 且 `18:00 < 18:55` ✅ → 重疊

第 2 題故意設計成會讓人答錯，因為只檢查了第一筆就下結論。每一筆既有訂位都要檢查。

做完紙筆練習再寫 SQL，會清楚很多。

你會遇到的坑

① 用 <= 而不是 < 「剛好接續」被誤判成衝突，位子白白浪費。

② 忘記排除已取消的訂位 取消的還算數 → 位子永遠訂不到。

③ 沒有併發保護 兩個人同時訂到同一桌。

④ 忘記緩衝時間 上一組 19:40 走，下一組 19:40 到，服務生來不及收拾。

⑤ 跨午夜的訂位 23:30 開始、用餐 100 分鐘 → 隔天 01:10。用 DATETIME 存完整時間就沒問題，如果只存「日期 + 時間」兩個欄位就會出錯。

⑥ 時區 統一用 Asia/Taipei。

⑦ 客人一報到就不算佔用，或結帳走了還在佔用 重疊檢查只算 CONFIRMED，報到後那組人還在吃，容量卻少算一組；反過來 SEATED 一律算到 end_time，客人提早結帳走了名額還卡著。 → SEATED 要算，但只算到那筆 dining_session 結帳（或取消用餐）為止。

⑧ 用排程去改桌位狀態做保留 → 保留是查詢時算出來的，見上面「訂位保留桌位」。
