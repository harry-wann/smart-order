HTTP 狀態碼

難度 ★☆☆☆☆　用在哪些模組 全員　哪幾週 第 1 週

一句話

狀態碼就是後端用三位數字回答「這件事成功了嗎」。

想像一下

你去櫃檯問事情，店員的回答大概有這幾種：

  • 「好的，這是您要的。」→ 2xx 成功
  • 「這櫃檯搬到旁邊那間了。」→ 3xx 轉址
  • 「您這樣講我聽不懂 / 您沒有會員卡 / 沒有這個東西。」→ 4xx 你的問題
  • 「不好意思，我們系統壞了。」→ 5xx 我的問題

記住這個分法就好：

開頭 意思 誰的問題
2xx 成功 —
3xx 你要找的東西在別的地方 —
4xx 你（前端） 送的東西有問題 前端
5xx 我（後端） 壞掉了 後端

4 開頭看前端、5 開頭看後端——這一句話能省掉你們很多互相甩鍋的時間。

我們專案會用到的

碼 名稱 什麼時候回 前端該怎麼辦
200 OK 查詢成功 正常顯示
201 Created 新增成功（送出點餐、建立預約） 顯示成功畫面
204 No Content 成功但沒東西要回（刪除成功） 不用解析 body
400 Bad Request 欄位填錯、格式不對 在欄位下顯示錯誤訊息
401 Unauthorized 還沒登入，或 token 過期 導回登入頁
403 Forbidden 登入了但你沒權限 顯示「權限不足」
404 Not Found 找不到這筆資料 顯示「查無資料」
409 Conflict 狀態衝突——品項售完、桌子已被使用、時段被訂走 顯示具體原因，讓使用者調整
422 Unprocessable 格式對但邏輯不通過（付款失敗） 顯示原因 + 重試
429 Too Many Requests 太頻繁（驗證碼一直要） 顯示倒數
500 Internal Server Error 後端爆了 顯示通用錯誤，去看後端日誌

最容易搞混的三組

401 vs 403 - 401：我不知道你是誰（沒登入、token 過期）→ 去登入 - 403：我知道你是誰，但你不能做這件事（廚房人員想改菜單）→ 登入也沒用

404 vs 409 - 404：這個東西不存在 - 409：東西存在，但現在的狀態不允許你這樣做（品項存在，但賣完了）

400 vs 422 - 400：你送的東西我看不懂（少欄位、格式錯） - 422：我看得懂，但業務上不通過（付款被銀行拒絕）

在我們的火鍋店裡

送出點餐 → 201  第 2 單已送出
送出點餐 → 409  ITEM_SOLD_OUT  牛五花已售完
掃碼開桌 → 409  TABLE_OCCUPIED 這桌已經在使用中
結帳中加點 → 409  SESSION_LOCKED 結帳中無法加點
廚房人員想改菜單 → 403 FORBIDDEN
用餐結束後還拿舊 token → 401 INVALID_SESSION_TOKEN

409 在我們的系統裡特別常用，因為火鍋店有大量「狀態不對」的情況。

15 分鐘動手小練習

用瀏覽器直接試：

  1. 打開一個存在的網頁 → F12 Network → 狀態碼是 200
  2. 網址後面亂加一段（例如 google.com/asdfghjkl）→ 狀態碼是 404
  3. 後端起來之後，用 Swagger 打一支需要登入的 API 但不給 token → 應該回 401
  4. 故意少傳一個必填欄位 → 應該回 400

你會遇到的坑

① 全部都回 200 有些新手不管成功失敗都回 200，然後在 body 裡放 {"success": false}。 → 不要這樣。 前端會沒辦法用統一的方式處理錯誤，而且 HTTP 本來就有這個機制。

② 全部都回 500 沒做 全域例外處理，任何錯誤都變成 500 加一長串英文。前端完全不知道發生什麼事。

③ 401 和 403 亂用 前端會不知道該導去登入頁還是顯示權限不足。

④ 錯誤沒有具體訊息 回 409 但不說是哪個品項售完，使用者只能一個一個猜。
