三層架構：Controller / Service / Repository

難度 ★★☆☆☆　用在哪些模組 所有後端工作　哪幾週 第 1 週（L0）、第 3 週

一句話

把後端分成接單的、做菜的、拿食材的三層，各做各的事。

想像一下

火鍋店的分工：

角色 做什麼 不做什麼
服務生 接單、確認客人講清楚了、把菜端出去 不煮菜、不進冰箱
廚師 真正決定怎麼煮、幾分熟、要不要加料 不接待客人、不管冰箱怎麼擺
備料員 從冰箱拿食材、放回去 不決定要煮什麼

如果服務生一邊接單一邊煮菜一邊翻冰箱，整間店會亂掉。

後端也一樣：

層 對應 負責 絕對不做
Controller 服務生 接請求、檢查格式、回傳結果 不寫商業邏輯、不碰資料庫
Service 廚師 商業規則、計算、交易邊界 不知道 HTTP 存在
Repository 備料員 對資料庫讀寫 不做判斷

三層長什麼樣

Controller —— 薄薄一層

@RestController
@RequestMapping("/api/dining-sessions")
@RequiredArgsConstructor
public class OrderController {

    private final OrderService orderService;

    @PostMapping("/me/orders")                        // 不帶 body：整桌購物車就是這張單的內容
    public OrderTicketDto submit(@RequestHeader("X-Session-Token") String token,
                                 @RequestHeader("X-Device-Id") String deviceId) {
        return orderService.submitOrder(token, deviceId);
    }
}

就這樣，三行。 Controller 的工作只有：拿參數、丟給 Service、回傳結果。

Service —— 真正的重點

@Service
@RequiredArgsConstructor
public class OrderService {

    private final DiningSessionRepository sessionRepo;
    private final CartItemRepository cartItemRepo;
    private final OrderTicketRepository ticketRepo;
    private final InventoryService inventoryService;

    @Transactional
    public OrderTicketDto submitOrder(String token, String deviceId) {
        DiningSession session = sessionRepo.findByTokenForUpdate(token)   // 鎖住這一列，跟櫃檯結清、同桌其他人的送出搶同一把鎖
            .orElseThrow(() -> new BusinessException("INVALID_SESSION_TOKEN", "用餐權杖已失效", HttpStatus.UNAUTHORIZED));

        if (session.getStatus() != SessionStatus.OPEN) {
            throw new BusinessException("SESSION_CLOSED", "這桌已經結帳，不能再加點", HttpStatus.CONFLICT)
                .with("reason", session.getStatus().name());   // PAID 或 CANCELLED（見全域例外處理）
        }

        // 鎖到了才讀整桌購物車；空的通常是同桌另一個人剛送出
        List<CartItem> cart = cartItemRepo.findByDiningSessionId(session.getId());
        if (cart.isEmpty()) {
            throw new BusinessException("CART_EMPTY", "購物車是空的，可能同桌已經送出了", HttpStatus.CONFLICT);
        }

        // 檢查必選選項、檢查鍋底、扣庫存、建立點餐單（記下 deviceId 對到的同桌客人）、算金額 ...
        cartItemRepo.deleteAll(cart);                   // 同一個交易裡清空購物車
        // ... 回傳 OrderTicketDto
    }
}

Repository —— Spring 幫你寫好

public interface OrderTicketRepository extends JpaRepository<OrderTicket, Long> {
    List<OrderTicket> findByDiningSessionIdOrderBySequenceNo(Long sessionId);
}

你只要宣告方法名字，Spring Data JPA 會自動幫你產生 SQL。（詳見 ORM 與 JPA）

為什麼要分

好處 說明
找得到東西 五個人協作，「金額怎麼算的」一定在 Service，不用全專案搜尋
可以測試 Service 不依賴 HTTP，可以直接寫單元測試
交易邊界清楚 @Transactional 貼在 Service，一個方法就是一個交易
可以重用 顧客送出整桌購物車、櫃檯代客加點（不經過購物車，body 直接帶品項，source = STAFF），共用同一段「驗證、扣庫存、寫單」的 Service 邏輯

資料在三層之間怎麼傳

前端 --JSON--> Controller --Request DTO--> Service --Entity--> Repository --SQL--> 資料庫
前端 <--JSON-- Controller <--Response DTO-- Service <--Entity-- Repository <--

重點：Controller 對外用 DTO，Repository 對內用 Entity。Service 負責在中間轉換。

絕對不要把 Entity 直接回傳給前端——原因見下一頁。

15 分鐘動手小練習

把你的 Hello 專案改成三層：

  1. GreetingRepository（先假裝有資料庫，回傳固定字串）
  2. GreetingService（決定早上說早安、晚上說晚安）
  3. GreetingController（只負責接請求）
@Repository
public class GreetingRepository {
    public String findStoreName() { return "老石頭火鍋"; }
}

@Service
@RequiredArgsConstructor
public class GreetingService {
    private final GreetingRepository repo;
    public String greet(String name) {
        String prefix = LocalTime.now().getHour() < 12 ? "早安" : "午安";
        return prefix + "，" + name + "！歡迎光臨" + repo.findStoreName();
    }
}

練習重點：時間判斷的邏輯放在 Service，不是 Controller。這個習慣要從第一天養成。

你會遇到的坑

① Controller 裡寫邏輯 最常見。一開始只是加個 if，三週後 Controller 變成 300 行。 → Controller 超過 10 行就該檢討。

② Service 裡出現 HttpServletRequest 代表你的 Service 被 HTTP 綁死了，不能重用也不好測試。

③ Repository 裡做判斷 Repository 只負責拿資料，不判斷。

④ 把 Entity 直接回傳 會出現 lazy loading 錯誤、洩漏不該給前端的欄位、改資料庫就打壞 API。

⑤ 一個 Service 一千行 Service 也可以拆。OrderService、OrderValidationService、OrderPricingService。

常見錯誤訊息對照

你會看到 中文意思 怎麼修
failed to lazily initialize a collection Entity 離開交易後才被讀取 在 Service 裡轉成 DTO，不要把 Entity 丟給 Controller
Infinite recursion (StackOverflowError) 兩個 Entity 互相參照，轉 JSON 時無限循環 同上，用 DTO
No property 'xxx' found for type Repository 方法名字拼錯 方法名要對應 Entity 的欄位名

術語對照表

白話 正式名稱
服務生層 Controller / Presentation Layer
廚師層 Service / Business Layer
備料層 Repository / Data Access Layer（DAO）
對外的資料格式 DTO
對應資料表的物件 Entity
