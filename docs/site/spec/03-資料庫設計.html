03 資料庫設計

MySQL 8.0 ／ utf8mb4 ／ utf8mb4_unicode_ci ER 圖見 06-圖表總覽。本文件是欄位層級的定義，建表以此為準。 所有建表與改表都透過 Flyway，ddl-auto 設為 validate。

0. 通用約定

約定 內容
主鍵 一律 id BIGINT UNSIGNED AUTO_INCREMENT
命名 資料表單數 snake_case（menu_item），Java 端 MenuItem
時間 created_at / updated_at 全表皆有，DATETIME(3)
金額 DECIMAL(10,2)，絕對不要用 FLOAT/DOUBLE
布林 TINYINT(1)
列舉 Java 用 enum + @Enumerated(STRING)；DB 用 VARCHAR(20)
軟刪除 只有 menu_item、menu_category、dining_table 用 active 旗標
快照 訂單相關的名稱與價格必須存快照，否則改菜單會讓歷史帳單金額跟著變

Flyway 檔案規劃

db/migration/
├── V1__create_account_tables.sql       member, verification_code, staff
├── V2__create_menu_tables.sql          menu_category, menu_item, option_group, option_value, menu_item_option_group
├── V3__create_dining_tables.sql        dining_table, dining_session, order_ticket, order_item, order_item_option
├── V4__create_inventory_tables.sql     inventory_item, inventory_log
├── V5__create_payment_tables.sql       payment
├── V6__create_reservation_tables.sql   reservation
├── V7__create_service_and_waitlist.sql service_call, waitlist
└── V8__create_member_benefit_tables.sql point_transaction, coupon, member_coupon   （進階）

migration 檔案要指定唯一負責人（工作分配定案後指派），其他人要改表就開 issue 請他加。 已經合併進 develop 的檔案永遠不能修改——別人的資料庫已經跑過那一版了，改了 Flyway 會拒絕啟動。要改就寫一支新的。

1. 帳號與權限

member 會員

欄位 型別 約束 說明
id BIGINT PK
phone VARCHAR(20) UNIQUE, NOT NULL 登入帳號 09xxxxxxxx
nickname VARCHAR(50) NULL 匿名轉會員時可為空，之後補
gender VARCHAR(10) NULL MALE/FEMALE/OTHER，供屬性推薦
birth_date DATE NULL 供年齡層推薦
points INT DEFAULT 0 點數餘額（快取欄位）
profile_completed TINYINT(1) DEFAULT 0 是否已補完資料
status VARCHAR(20) ACTIVE/SUSPENDED
created_at, updated_at DATETIME(3)

索引：UNIQUE(phone)

nickname 可為 NULL 是刻意的：匿名客人在結帳頁輸入手機就綁定，這時只有手機號碼。等他真的想看紀錄時再補資料。

verification_code 手機驗證碼

欄位 型別 說明
id BIGINT PK
phone VARCHAR(20) NOT NULL
code VARCHAR(6) NOT NULL
attempt_count INT DEFAULT 0 滿 3 次作廢
expires_at DATETIME(3) 建立 +5 分鐘
used_at DATETIME(3) NULL
created_at DATETIME(3)

索引：INDEX(phone, created_at)

建議改用 Redis（SET otp:<phone> <code> EX 300），天生有 TTL，不用寫清理排程。這張表是還沒導入 Redis 時的後備方案。

staff 員工

欄位 型別 說明
id BIGINT PK
username VARCHAR(50) UNIQUE
password_hash VARCHAR(100) BCrypt
display_name VARCHAR(50)
role VARCHAR(20) COUNTER/KITCHEN/MANAGER
active TINYINT(1) DEFAULT 1

種子資料建三個帳號：counter/1234、kitchen/1234、manager/1234，並寫進 README，面試官才能登入看。

2. 菜單

menu_category 分類

id、name、sort_order、active

種子：鍋底／肉品／海鮮／蔬菜／火鍋料／主食／飲料／酒 共 8 類。

menu_item 品項

欄位 型別 說明
id BIGINT PK
category_id BIGINT FK
name VARCHAR(100)
description VARCHAR(255)
price DECIMAL(10,2) 基礎價
image_url VARCHAR(500)
is_soup_base TINYINT(1) DEFAULT 0 是否為鍋底
is_required_on_open TINYINT(1) DEFAULT 0 每桌至少一份（共鍋，非每人一份）
track_inventory TINYINT(1) DEFAULT 1 false = 免費續加品，不扣庫存
is_refill TINYINT(1) DEFAULT 0 菜單上歸類到「免費續加」區塊
suitable_for VARCHAR(20) ALL/ADULT/CHILD
spicy_level TINYINT 0–3
is_vegetarian TINYINT(1) DEFAULT 0 素食標示
contains_beef TINYINT(1) DEFAULT 0 不吃牛的客人用
sold_out TINYINT(1) DEFAULT 0 由庫存自動維護
sort_order INT
active TINYINT(1) DEFAULT 1 下架用

索引：INDEX(category_id, active, sort_order)

鍋底的種子資料（共鍋 + 鴛鴦）

麻辣鍋底      price 480  is_soup_base=1  is_required_on_open=1
酸菜白肉鍋底  price 420  is_soup_base=1  is_required_on_open=1
昆布鍋底      price 380  is_soup_base=1  is_required_on_open=1
鴛鴦鍋底      price 0    is_soup_base=1  is_required_on_open=1
  掛兩個群組：「左鍋湯底」「右鍋湯底」，各 min=1 max=1
  選項價差：麻辣 +260 / 酸菜 +230 / 昆布 +210（約單鍋的 55%）

鴛鴦不需要額外資料表。 「一桌幾個鍋」也不建模——想點兩鍋就點兩份。

option_group 選項群組

欄位 說明
id, name 「份量」「辣度」「左鍋湯底」「加點配料」
min_select 0 = 非必選
max_select 1 = 單選；>1 = 可複選
sort_order

群組不綁死在單一品項上，透過下面的關聯表共用。「辣度」建立一次可掛在 20 個品項上。

menu_item_option_group 品項 ↔ 群組（多對多）

menu_item_id、option_group_id、sort_order 主鍵：PRIMARY KEY(menu_item_id, option_group_id)

不要用 @ManyToMany，因為中間表有 sort_order。做成獨立 Entity，見 JPA 關聯對應。

option_value 選項

id、option_group_id FK、name、price_delta DECIMAL(10,2)、sort_order、active

3. 桌位、用餐與點餐

dining_table 桌位

欄位 型別 說明
id BIGINT PK
table_no VARCHAR(10) UNIQUE A01、A02、B01…
seats INT 2／4／6／8
area VARCHAR(20) 「大廳」「包廂」
status VARCHAR(20) AVAILABLE/RESERVED/OCCUPIED/CLEANING
reservable TINYINT(1) DEFAULT 1 開放線上訂位（保留 30% 給現場）
active TINYINT(1) DEFAULT 1

種子：12 張桌（2 人 ×2、4 人 ×6、6 人 ×2、8 人 ×2），其中 8 張 reservable = 1。

dining_session 用餐紀錄（＝帳單）★核心

欄位 型別 說明
id BIGINT PK
table_id BIGINT FK
member_id BIGINT FK NULL 匿名點餐時為 NULL
reservation_id BIGINT FK NULL 由訂位而來時填
waitlist_id BIGINT FK NULL 由候位而來時填
session_code CHAR(4) NULL 開桌碼，預設不使用故可為 NULL
session_token VARCHAR(64) UNIQUE 顧客端 API 憑證
adult_count / child_count INT 不參與金額計算（見下方說明）
status VARCHAR(20) OPEN/CHECKOUT_PENDING/PAID/CANCELLED
subtotal DECIMAL(10,2) 品項小計
service_fee DECIMAL(10,2) 小計 × 10%
discount DECIMAL(10,2) DEFAULT 0 優惠券（進階）
total DECIMAL(10,2) 合計
opened_at / closed_at DATETIME(3)

索引：INDEX(table_id, status)、INDEX(member_id, opened_at)、UNIQUE(session_token)

人數為什麼不參與金額計算？ 我們的計價是「一鍋一價 + 單點」、無低消。人數的用途是：座位安排、分帳均分的參考值、兒童友善推薦、客單價統計。 這點一定要寫清楚，不然會有人自己加一個人頭費進去。

一張桌同時只能有一筆 status = OPEN 的 session。 MySQL 沒有部分唯一索引，這條規則在 Service 層用 SELECT ... FOR UPDATE 保證（見 M2 問題 2）。

status VARCHAR(20) PENDING/PREPARING/SERVED/CANCELLED
is_preorder TINYINT(1) DEFAULT 0 訂位時先點的單，KDS 排最前
source VARCHAR(20) CUSTOMER／STAFF（櫃檯代點）
placed_at DATETIME(3) 預約單用「開桌時間」而非「線上點餐時間」
cancel_reason VARCHAR(100) NULL
updated_at DATETIME(3)

索引：INDEX(dining_session_id, sequence_no)、INDEX(status, placed_at)

order_item 單品 ★核心

欄位 型別 說明
id BIGINT PK
order_ticket_id BIGINT FK
menu_item_id BIGINT FK 供統計與推薦
item_name_snapshot VARCHAR(100) 下單當下的名稱
unit_price_snapshot DECIMAL(10,2) 下單當下的基礎價
options_price DECIMAL(10,2) DEFAULT 0 所有選項價差合計

索引：INDEX(order_ticket_id)、INDEX(menu_item_id)（推薦查詢會大量用到）

order_item_option 單品選項快照

id、order_item_id FK、group_name_snapshot、value_name_snapshot、price_delta

選項也要存快照，否則刪掉一個選項後歷史訂單會顯示空白。

service_call 服務鈴 ★新增

dining_session_id BIGINT FK

為什麼要存表而不是只推 WebSocket？ 櫃檯重新整理後還看得到未處理的、可以統計、可以標記已處理。

5. 訂位

reservation

欄位 型別 說明
id BIGINT PK
member_id BIGINT FK NULL 非會員也能訂
contact_name VARCHAR(50)
contact_phone VARCHAR(20)
start_time DATETIME(3) NOT NULL 用餐開始
end_time DATETIME(3) NOT NULL = start + 100 分 + 15 分緩衝
adult_count / child_count INT
party_size INT
table_id BIGINT FK NULL 建立時指派；取消時設為 NULL 以釋放唯一約束
status VARCHAR(20) PENDING/CONFIRMED/SEATED/CANCELLED/NO_SHOW
preorder_session_id BIGINT FK NULL 預先點餐（進階）
created_at / cancelled_at DATETIME(3)

關鍵索引

-- 資料庫層的保險：同一桌、同一開始時間不能有兩筆
CREATE UNIQUE INDEX uk_reservation_table_start ON reservation (table_id, start_time);

-- 區間重疊檢查用
CREATE INDEX idx_reservation_table_time ON reservation (table_id, start_time, end_time);
CREATE INDEX idx_reservation_start ON reservation (start_time, status);
CREATE INDEX idx_reservation_phone ON reservation (contact_phone);

重疊判斷式：existing.start_time < :newEnd AND :newStart < existing.end_time 用 < 不是 <=，因為「剛好接續」不算衝突。詳見 區間重疊與訂位排程。

取消時把 table_id 設為 NULL，這樣唯一約束就不會擋住「取消後同一時段重新訂」。狀態紀錄仍然保留。

6. 付款

payment

欄位 型別 說明
id BIGINT PK
dining_session_id BIGINT FK NULL 現場結帳
reservation_id BIGINT FK NULL 訂位預付（進階）
method VARCHAR(20) APPLE_PAY/GOOGLE_PAY/LINE_PAY/CASH

7. 庫存

inventory_item

欄位 型別 說明
id BIGINT PK
menu_item_id BIGINT FK UNIQUE 品項層級庫存（1:1）
quantity INT NOT NULL 防超賣的關鍵欄位
unit VARCHAR(10) 「份」「盤」「碗」
low_threshold INT 低於此值警示
updated_at DATETIME(3)

扣庫存的唯一正確寫法

UPDATE inventory_item
   SET quantity = quantity - :qty, updated_at = NOW(3)
 WHERE menu_item_id = :itemId
   AND quantity >= :qty;
-- 影響筆數 0 → 庫存不足，整張點餐單回滾並回 409

不要先 SELECT 檢查再 UPDATE。 兩個人同時點最後一份時，兩邊的 SELECT 都會通過。 這是整個專案最能展現「有想過並行問題」的地方，每位成員都要會講。詳見 鎖與併發。

track_inventory = false 的品項（免費續加）跳過這段，不扣也不會被標售完。

inventory_log

id、inventory_item_id FK、change_qty（正負）、quantity_after、reason（ORDER/RESTOCK/ADJUST/CANCEL/WASTE）、ref_id、operator、created_at

「叫貨統計」（進階）＝ 這張表依 reason='ORDER' 依日期／品項 group by，不需要額外資料表。

8. 會員權益（進階）

point_transaction

id、member_id、dining_session_id NULL、change_amount（正負）、balance_after、type（EARN/REDEEM/EXPIRE/ADJUST）、created_at

member.points 是快取欄位，真實來源是這張表的 SUM(change_amount)。

coupon / member_coupon

coupon：code、name、type（AMOUNT/PERCENT）、value、min_spend、valid_from、valid_to、active member_coupon：member_id、coupon_id、status（UNUSED/USED/EXPIRED）、used_at、dining_session_id

10. 種子資料策略 ★第 1 週必做

最容易被忽略、但最容易在 demo 當天翻車的一件事。 推薦、報表、備貨預測在空資料庫上全是空白。

資料 數量 備註
分類 8 鍋底／肉品／海鮮／蔬菜／火鍋料／主食／飲料／酒
品項 約 60 含 4 種鍋底（3 單味 + 1 鴛鴦）、3～4 個免費續加品
選項群組 6～7 組 份量、辣度、熟度、加點配料、左鍋湯底、右鍋湯底、冰塊
桌位 12 張 2×2、4×6、6×2、8×2；其中 8 張 reservable=1
員工 3 counter / kitchen / manager
會員 40 性別各半、年齡分佈 20～65 歲（否則屬性推薦看不出效果）
歷史用餐 約 400 場（過去 90 天） 平日／假日量要有差異
歷史點餐單 約 1200 張 平均每場 3 張
歷史單品 約 5000 筆 要有明顯的熱門／冷門差異
庫存 每品項 20～100 刻意留 2～3 個品項庫存 = 0 用來 demo 售完
未來訂位 未來 7 天約 20 筆
候位 3～5 筆等待中

實作建議

  • 表結構用 Flyway（V 開頭）
  • 種子資料用程式產生（CommandLineRunner + @Profile("local")），不要手寫 SQL——5000 筆手寫不完
  • 亂數要有規律：週五六人多、每桌必定至少一份鍋底、肉品機率高於甜點
  • 保留一組「乾淨的 demo 桌」（例如 A01）

Demo 前的重置腳本

準備 reset-demo.sh：清掉當日的 session 與 order，保留歷史資料與菜單。Demo 前 10 分鐘跑一次。 這個腳本救過很多組。
