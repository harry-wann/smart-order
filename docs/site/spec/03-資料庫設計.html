03 資料庫設計

MySQL 8.0 ／ utf8mb4 ／ utf8mb4_unicode_ci ER 圖見 06-圖表總覽。本文件是欄位層級的定義，建表以此為準。 所有建表與改表都透過 Flyway，ddl-auto 設為 validate。

0. 通用約定

約定 內容
主鍵 一律 id BIGINT UNSIGNED AUTO_INCREMENT
命名 資料表單數 snake_case（menu_item），Java 端 MenuItem
時間 created_at / updated_at 全表皆有，DATETIME(3)
金額 DECIMAL(10,2)，絕對不要用 FLOAT/DOUBLE
布林 TINYINT(1)
列舉 Java 用 enum + @Enumerated(STRING)；DB 用 VARCHAR(20)
軟刪除 只有 menu_item、menu_category、dining_table 用 active 旗標
快照 訂單相關的名稱與價格必須存快照，否則改菜單會讓歷史帳單金額跟著變

3. 桌位、用餐與點餐

dining_table 桌位

欄位 型別 說明
id BIGINT PK
table_no VARCHAR(10) UNIQUE A01、A02、B01…
seats INT 2／4／6／8
area VARCHAR(20) 「大廳」「包廂」
status VARCHAR(20) AVAILABLE/OCCUPIED/CLEANING
reservable TINYINT(1) DEFAULT 1 開放線上訂位（保留 30% 給現場）
active TINYINT(1) DEFAULT 1

種子：12 張桌（2 人 ×2、4 人 ×6、6 人 ×2、8 人 ×2），其中 8 張 reservable = 1。

桌位狀態只有三種，而且只反映現場當下。 這個欄位不存「預約保留」。

預約保留（M7 7.10）是查詢時算出來的顯示狀態。 AVAILABLE 的桌如果有一筆訂位同時符合 配到這張桌、CONFIRMED、現在落在 start_time − 30 分 ～ start_time + 10 分， 桌況 API 就回 displayStatus = RESERVED。所以訂位會在時間窗內鎖住配到的桌；候位不鎖桌。 要解開預約保留，就是取消那筆訂位（status → CANCELLED、table_id 設 NULL），條件自然不成立，桌位欄位什麼都不用改。 另一個接點照舊：開桌成功時，把來源那筆訂位或候位轉成已報到。

舊版也有一個 RESERVED，但它存在這個欄位裡，由排程在訂位前 30 分鐘自動轉入——那等於把 reservation 複製一份到桌位上、還要靠 cron 同步，一旦不同步就會出現 「畫面顯示空桌、按開桌卻被擋」這種最難查的狀況。那個做法已經移除； 現在每次查詢現算，不存、不靠排程，就沒有同步這件事（見 M2 問題 5）。

-- 這張桌現在被哪筆訂位保留（查不到就是沒保留）
-- 「現在落在 start − 30 ～ start + 10」換成查 start_time，就是「start_time 落在 now − 10 ～ now + 30」
SELECT * FROM reservation
 WHERE table_id = :tableId
   AND status = 'CONFIRMED'
   AND start_time BETWEEN :now - INTERVAL 10 MINUTE AND :now + INTERVAL 30 MINUTE
 ORDER BY start_time
 LIMIT 1;

30、10 兩個數字從 application.yml 讀（reservation.hold-before-minutes、reservation.hold-after-minutes），上面寫死只是好讀。 idx_reservation_table_time (table_id, start_time, end_time) 可以直接用上（先比 table_id，再掃 start_time 的範圍）。

只有訂位會鎖桌，候位不鎖桌。 桌子會被鎖只有兩種來源：預約保留（上面算出來的）與用餐中／待清理（這個欄位）。 候位叫號只是通知，客人到櫃檯才選桌開桌，所以 dining_table 沒有任何「保留給誰」的欄位，status 也只有三種。 （原本規劃過一個「櫃檯自己把空桌鎖起來」的延伸功能與對應的狀態、欄位，已經刪除，見 M2 問題 5。）

欄位 型別 說明
id BIGINT PK
table_id BIGINT FK
member_id BIGINT FK NULL 匿名點餐時為 NULL；綁會員（進階 8.10）有兩個入口：C-09 線上登入、S-03 櫃檯結清時帶 memberId（同一個交易寫入）
reservation_id BIGINT FK NULL 由訂位而來時填
waitlist_id BIGINT FK NULL 由候位而來時填
session_token VARCHAR(64) UNIQUE 顧客端 API 憑證
adult_count / child_count INT 不參與金額計算（見下方說明）
status VARCHAR(20) OPEN/PAID/CANCELLED（沒有「結帳中」，見下方說明）
subtotal DECIMAL(10,2) 品項小計
service_fee DECIMAL(10,2) 小計 × 10%
discount DECIMAL(10,2) DEFAULT 0 優惠券＋點數折抵合計（可以同時用），進階 A6 才用，基礎永遠是 0
total DECIMAL(10,2) 合計
cart_version BIGINT NOT NULL DEFAULT 0 購物車版本號。購物車每次異動（加／改／刪／送出後清空）就 +1，跟著 CART_UPDATED 推給同桌，前端用它擋掉亂序或過期的推播（見 04 §3.4）

索引：INDEX(table_id, status)、INDEX(member_id, opened_at)、UNIQUE(session_token)、INDEX(reservation_id)（外鍵本來就會自動建；訂位的區間重疊要靠它找「這筆報到的用餐紀錄結帳了沒」）

cart_version 為什麼不用時間戳？ 購物車是 cart_item 的多列集合，不是單一列，所以沒有一個現成的「整份購物車的時間」可用。 拿 MAX(updated_at) 會在刪除時出錯——被刪的那列消失了，MAX 可能反而變小， 於是「刪除」這個事件看起來比它前一個事件還舊，會被前端當成過期丟掉。 DATETIME(3) 只到毫秒也會碰撞：同桌兩支手機同一毫秒各加一樣東西，兩個事件的時間戳相同，分不出先後。 單調遞增的版本號兩個問題都沒有，而且就是 JPA 樂觀鎖的 @Version（見 鎖與併發），Hibernate 可以自動維護。

人數為什麼不參與金額計算？ 我們的計價是「一鍋一價 + 單點」、無低消。人數的用途是：座位安排、分帳均分的參考值、兒童友善推薦、客單價統計。 這點一定要寫清楚，不然會有人自己加一個人頭費進去。

一張桌同時只能有一筆 status = OPEN 的 session。 MySQL 沒有部分唯一索引，這條規則在 Service 層用 SELECT ... FOR UPDATE 保證（見 M2 問題 2）。

為什麼沒有 CHECKOUT_PENDING？ 舊版要求結帳時會把 session 鎖成「結帳中」、不能加點。 現在基礎是客人到櫃檯結帳，改成金額比對 + 列鎖：送出點餐、櫃檯結清、（進階）線上付款 三個地方都在交易裡 SELECT ... FOR UPDATE 這一列；結清／付款帶 expectedTotal， 重算不相等回 409 BILL_CHANGED，已經不是 OPEN 回 409 SESSION_CLOSED。 所以這張表不需要額外的鎖定欄位，詳見 M6 問題 1。

為什麼存 DB，不放前端、HTTP session 或 Redis？

放哪裡 問題
前端 state／localStorage 每支手機各一份，同桌看不到彼此加了什麼
HTTP session 一樣是每支手機各一份，伺服器重啟也會消失
Redis 送出時要「寫 order_ticket＋刪購物車」一起成功或一起失敗，跨 Redis 和 MySQL 做不到同一個交易

送出點餐時：鎖 dining_session 那列 → 讀整桌 cart_item → 驗證、扣庫存、快照 → 寫 order_ticket／order_item → 刪掉這些 cart_item， 全部在同一個交易裡（見 04 §4.5）。 session 進終態（PAID 或 CANCELLED）時，整桌購物車在同一個交易裡刪掉——還沒送出的東西直接捨棄，不算錢。 櫃檯代客加點（source = STAFF）與預先點餐（reservation_preorder_item）都不經過這張表。

5. 訂位

reservation

欄位 型別 說明
id BIGINT PK
reservation_no VARCHAR(20) UNIQUE 預約編號，格式 R-YYMMDD-流水號（用餐日期＋id 補零到 4 位，例 R-260920-0442）；insert 拿到 id 後在同一個交易裡填上。C-18 大字顯示、客人報到或來電查詢用

contact_email VARCHAR(100) NULL 匿名訂位選填（C-16b）；只存不寄，寄確認信是延伸（見 M7）

end_time DATETIME(3) NOT NULL = start + 100 分 + 15 分緩衝
adult_count / child_count INT
party_size INT
table_id BIGINT FK NULL 訂位當下 best-fit 配到的桌；取消時設為 NULL 以釋放唯一約束
status VARCHAR(20) CONFIRMED/SEATED/CANCELLED/NO_SHOW
access_token VARCHAR(64) UNIQUE 匿名訂位用來回來查詢與改單的憑證
preorder_updated_at DATETIME(3) NULL 最後一次預點異動時間；NULL = 沒預點（進階）
created_at DATETIME(3)
cancelled_at DATETIME(3) NULL 取消的時間（客人線上取消或櫃檯代客取消）；沒取消是 NULL
cancelled_by_staff_id BIGINT FK NULL → staff，櫃檯代客取消時是哪個員工；客人自己取消時為 NULL
cancel_source VARCHAR(10) NULL CUSTOMER（客人線上取消，M7 7.8）/ STAFF（櫃檯代客取消，M7 7.18）；沒取消是 NULL。STAFF 時 cancelled_by_staff_id 一定有值

狀態只有四種，沒有 PENDING。 舊流程是「先建訂位 → 預付成功才確認」， 所以需要一個中間狀態。現在選完時段送出就直接是 CONFIRMED，沒有任何路徑會產生 PENDING， 留著只會讓人猜。之後要做訂金（M7 的 7.E7）再加回來。

access_token 是給匿名客人的。 會員靠 JWT 就能存取自己的訂位； 匿名沒有帳號，但一樣要能回來看訂位、改預點內容。作法跟 dining_session.session_token 完全一樣：建立時發一個隨機字串，前端存 localStorage。 沒有它的話，只要猜到 reservation.id 就能改別人的單。

預約保留不另外存狀態。 保不保留由 table_id、status、start_time 當場算出來（見上面 dining_table 的說明）。 要解開保留就是取消訂位：status 改 CANCELLED、填 cancelled_at／cancel_source（櫃檯取消再加 cancelled_by_staff_id）、table_id 設 NULL。 沒有「訂位照留、只解除保留」的欄位。

取消有兩個入口，期限不同：客人線上取消只到訂位時間前 30 分鐘（之後回 409 CANCEL_DEADLINE_PASSED）； 櫃檯代客取消隨時可以。兩者都只能取消 CONFIRMED 的訂位（其他回 409 RESERVATION_NOT_CANCELLABLE）。 櫃檯取消時 body 可帶的 reason 只寫日誌，不存欄位。

關鍵索引

-- 資料庫層的保險：同一桌、同一開始時間不能有兩筆
CREATE UNIQUE INDEX uk_reservation_table_start ON reservation (table_id, start_time);

-- 區間重疊檢查用
CREATE INDEX idx_reservation_table_time ON reservation (table_id, start_time, end_time);
CREATE INDEX idx_reservation_start ON reservation (start_time, status);
CREATE INDEX idx_reservation_phone ON reservation (contact_phone);

重疊判斷式：existing.start_time < :newEnd AND :newStart < existing.end_time，而且只看 CONFIRMED，以及 SEATED 而且那筆用餐紀錄還沒結帳的： status = 'CONFIRMED' OR (status = 'SEATED' AND EXISTS (SELECT 1 FROM dining_session ds WHERE ds.reservation_id = r.id AND ds.status = 'OPEN')) ——客人還坐著就算佔用；結帳（PAID）或取消用餐之後名額立刻釋出，不用等到原本的 end_time。 線上訂位只能訂明天以後，所以這條主要影響的是「同一天之後的訂位保留」與容量報表的正確性，不會出現當天被線上搶訂的情況。 用 < 不是 <=，因為「剛好接續」不算衝突。詳見 區間重疊與訂位排程。

取消時把 table_id 設為 NULL，這樣唯一約束就不會擋住「取消後同一時段重新訂」。狀態紀錄仍然保留。

reservation.table_id 是「訂位當下配的桌」，不是「客人實際坐的桌」。 它的用途有兩個：容量與區間重疊判斷——這個時段還有沒有位子可以再賣； 以及訂位時間窗內保留那張桌（7.10）。

客人到店後實際坐哪一張，由 dining_session.table_id 與 dining_session.reservation_id 這一組記錄。開桌時不回頭改 reservation.table_id，因為那會讓區間重疊的歷史資料 跟著現場調度一起變動，訂位容量就算不準了。

兩個欄位回答兩個不同的問題，不要想合併：

問題 看哪裡
19:00 這個時段還能不能再接訂位 reservation.table_id + start_time / end_time
18:30 的訂位現在該不該鎖住 A08 reservation.table_id + start_time + status
陳小姐今天實際坐哪一桌、消費多少 dining_session（它的 reservation_id 指回來）

dining_session_id 與 reservation_id 恰有一個不為 NULL，在 Service 層檢查。 所有付款都是模擬的，不串接任何真實金流 API。 櫃檯結清（POST /api/admin/dining-sessions/{id}/settle）也寫一筆 status = SUCCESS 的紀錄， 報表才分得出現金、信用卡、條碼；櫃檯結清不做失敗機率，PENDING／FAILED 只有 A5 線上付款會出現。

為什麼不直接借用 order_ticket / order_item？ order_ticket 的語意是「送出即定案，進 KDS、扣庫存、不可改」， 但預點在報到前必須能反覆修改，兩個語意會打架； 而且訂位時還沒有桌、沒有 dining_session，硬要先開一筆會讓 「今天有幾桌在用餐」這種查詢全部要多過濾條件。 所以預點自己一組表，報到開桌時逐筆複製成 order_item（欄位幾乎一樣，轉換很單純）。 完整推導見 M7 問題 6。

欄位 型別 說明

扣庫存的唯一正確寫法

UPDATE inventory_item
   SET quantity = quantity - :qty, updated_at = NOW(3)
 WHERE menu_item_id = :itemId
   AND quantity >= :qty;
-- 影響筆數 0 → 庫存不足，整張點餐單回滾並回 409

不要先 SELECT 檢查再 UPDATE。 兩個人同時點最後一份時，兩邊的 SELECT 都會通過。 這是整個專案最能展現「有想過並行問題」的地方，每位成員都要會講。詳見 鎖與併發。

track_inventory = false 的品項（免費續加）跳過這段，不扣也不會被標售完。
