模組 2：桌位、開桌與候位

難易度 ★★★☆☆　里程碑 第 2 週開桌、第 3 週桌況、第 4 週候位

這個模組在做什麼

管理「客人坐在哪」。桌位主檔、桌上那張永遠不變的 QR code、櫃檯開桌、桌況總覽、還有尖峰時的現場候位。

這個模組決定了系統的定位：QR code 固定貼在桌上，但櫃檯控制要不要開桌。客人掃了碼，如果櫃檯還沒開桌，他只會看到「請洽櫃檯帶位」。

這就是「半輔助工具」的具體樣貌——櫃檯仍然是主導者，系統是延伸。

難易度為什麼是三顆星

單純的桌位 CRUD 只有一顆星。難的是兩件事：

  1. 開桌的併發控制——兩支手機同時對同一張桌開桌，會產生兩張帳單
  2. 狀態機——桌位有四種狀態，什麼時候該轉到什麼狀態，規則要想清楚

問題思考與解決思路

問題 1：QR code 要不要每次換？

情境 客人要掃碼點餐，但不能讓路過的人隨便開桌。

做法 A：每次開桌產生新的 QR 櫃檯開桌 → 系統產生一次性 QR → 列印小卡給客人。

  • 優點：安全性最高
  • 缺點：每次都要印紙、要有印表機、客人弄丟就麻煩

做法 B：固定 QR + 櫃檯控制開桌 ← 我們選這個

QR 內容固定是 /t/A03，貼上去永不換。掃碼後系統查桌位狀態：

桌位狀態 客人看到
AVAILABLE 「請洽櫃檯帶位」，不能自己開桌
OCCUPIED 直接進入點餐
CLEANING 「整理中」
  • 優點：不用印、櫃檯掌握帶位、人數由櫃檯輸入比較準
  • 風險：隔壁桌的人也能掃到 → 但中高價位有服務生帶位，而且要走到那張桌才掃得到，風險可接受

我們的決定：做法 B。原本還想加一道可開關的開桌碼當第二層，後來拿掉了 —— 有服務生帶位，人要走到那張桌前才掃得到，多一道四碼輸入只是讓正常客人多按幾下。

問題 2：兩支手機同時對同一桌開桌會怎樣？

情境 服務生在店家端按開桌的同時，客人也掃碼想開桌。

直覺會這樣寫

DiningTable table = tableRepo.findByTableNo("A03");
if (table.getStatus() == AVAILABLE) {
    table.setStatus(OCCUPIED);
    sessionRepo.save(new DiningSession(table, ...));
}

為什麼會壞 跟 超賣 是同一個問題：兩邊的「查」都在對方的「改」之前，結果產生兩張 dining_session。客人和服務生各自看到不同的帳單，點的東西對不起來。

正確做法：悲觀鎖

@Transactional
public DiningSessionDto open(String tableNo, int adults, int children) {
    // SELECT ... FOR UPDATE，把這一列鎖住
    DiningTable table = tableRepo.findByTableNoForUpdate(tableNo)
        .orElseThrow(() -> new BusinessException("NOT_FOUND", "查無此桌", NOT_FOUND));

    if (table.getStatus() != TableStatus.AVAILABLE) {
        throw new BusinessException("TABLE_OCCUPIED", "此桌已在使用中", CONFLICT);
    }

    table.setStatus(TableStatus.OCCUPIED);
    DiningSession session = sessionRepo.save(DiningSession.open(table, adults, children));
    return toDto(session);
}

為什麼不用條件式 UPDATE？ 因為開桌要做的不只是改一個數字，還要建立 session、產生 token。這種「要做好幾件事」的情況適合悲觀鎖。

問題 3：客人走了之後 token 還有效嗎？

情境 A03 桌結帳離開，下一組客人坐進來。上一組客人的手機還開著點餐頁面。

如果不處理 他還能繼續點餐，而且會點到新客人的帳單上。

正確做法：token 綁 session，session 一進終態就全部失效

public DiningSession validate(String token) {
    DiningSession s = sessionRepo.findByToken(token)
        .orElseThrow(() -> new BusinessException("INVALID_SESSION_TOKEN", "連線已失效", UNAUTHORIZED));

    if (s.getStatus() == PAID || s.getStatus() == CANCELLED) {
        throw new BusinessException("INVALID_SESSION_TOKEN", "本次用餐已結束", UNAUTHORIZED);
    }
    return s;
}

前端收到 401 INVALID_SESSION_TOKEN → 清掉 localStorage → 導回掃碼頁。

這條規則一定要寫進文件並驗收，不然 demo 時很容易被問倒。

問題 4：候位叫號之後沒人來怎麼辦？

情境 叫了 A012 號，但那組客人跑去逛街了。桌子空著等他們，後面的人乾等。

直覺會這樣寫 櫃檯自己記得，過一陣子手動標記過號。

為什麼不好 尖峰時櫃檯忙不過來，一定會忘記。而且「過了多久」沒有一致的標準。

正確做法：排程自動處理

@Scheduled(cron = "0 * * * * *", zone = "Asia/Taipei")   // 每分鐘
public void expireCalledWaitlist() {
    try {
        LocalDateTime deadline = LocalDateTime.now().minusMinutes(10);
        int n = waitlistService.expireCalledBefore(deadline);
        if (n > 0) log.info("{} 組候位過號", n);
    } catch (Exception e) {
        log.error("候位過號檢查失敗", e);
    }
}

搭配一支手動觸發的管理 API，demo 時不用真的等 10 分鐘。

延伸：進階版可以做「過號後自動叫下一組」，但基礎版只標記，讓櫃檯決定。

六週切分

週 這個模組要交出什麼
W1 Flyway 建好 dining_table / dining_session；種子資料 12 張桌；桌位狀態 enum 定義完成
W2 POST /api/dining-sessions 開桌（含悲觀鎖）；POST /join 加入；GET /api/tables/{no}/status；用餐權杖驗證 filter
W3 店家端桌況總覽頁；開桌／關桌／取消用餐；掃碼進入頁（顧客端）；QR code 產生
W4 候位登記、清單、叫號、報到；候位過號排程
W5 桌況與候位的 WebSocket 推播；用餐超時提醒排程；座位管理後台
W6 不寫新功能。測 token 失效、測併發開桌

常見卡關

卡點 解法
SELECT ... FOR UPDATE 不會寫 用 @Lock(LockModeType.PESSIMISTIC_WRITE) 加在 Repository 方法上
桌況更新不即時 先確認 WebSocket 通了；桌況頁也要保留一個「重新整理」按鈕當備援
狀態轉移寫得到處都是 集中在一個 TableStatusService，所有轉移都經過它
候位表的狀態跟排程對不上 只有 CALLED 狀態會被排程標成 EXPIRED，WAITING 不會

驗收 Demo 腳本

  1. 手機掃 A03 的 QR → 顯示「請洽櫃檯帶位」
  2. 店家端對 A03 開桌（2 大 1 小）→ 桌況變紅色「用餐中」
  3. 手機重新掃同一個 QR → 這次直接進入點餐
  4. 第二支手機掃同一個 QR → 也能進入（同桌共享）
  5. 店家端結帳 → 桌況變「待清理」→ 手機重新整理，顯示「本次用餐已結束」
  6. 候位登記一組 → 叫號 → 候位螢幕即時顯示 → 報到 → 自動開桌
