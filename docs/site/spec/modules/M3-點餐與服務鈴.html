模組 3：點餐

難易度 ★★★★☆　里程碑 第 4 週主流程全綠燈

這是整個專案最核心、也最難的模組。 不論之後怎麼分工，這個模組的送出點餐交易一定要有第二個人 review。

這個模組在做什麼

客人從菜單挑東西、放進整桌共用的購物車（每位同桌客人都能查看全桌內容，每列標出加入者），但每位客人只能修改或刪除自己加入的列。客人按「送出我的點餐」時，只把自己加入的列建立成一張點餐單；同桌其他人的列仍留在購物車，供本人查看、修改與送出。

「送出點餐」那一支 API 是整個系統技術含量最高的地方：它要在一個交易裡鎖定用餐紀錄、讀取目前客人自己的列、驗證、扣庫存、建立三層資料、刪除已送出的列並更新帳單。任何一步失敗都要回滾；同桌其他人的購物車列不受影響。

難易度為什麼是四顆星

難點 為什麼難
併發扣庫存 兩個人同時點最後一份，寫錯不會報錯，只會默默超賣
交易邊界 鎖用餐紀錄、讀本人購物車列、驗證、扣庫存、寫單、刪除本人已送列與更新帳單要綁在一起；中間任何一步失敗都要乾淨回滾
三層資料結構 dining_session → order_ticket → order_item → order_item_option
多裝置同步 購物車存後端、整桌可讀；WebSocket 推全桌快照與版本號，各裝置依 guest 身分標記 isOwnItem／canEdit，斷線重連與回前景補抓
選項驗證 必選有沒有選齊、複選有沒有超過上限

基礎必做功能

# 功能 驗收條件 狀態
3.1 購物車（整桌共用、全桌可讀） 存後端（cart_item），每位 guest 都能查看全桌列；GET /me/cart 依目前 guest 回傳每列的 isOwnItem 與 canEdit，只有加入者可改數量／備註或刪除（其他 guest 收到 403 CART_ITEM_FORBIDDEN）。畫面將本人區放上方、同桌其他人唯讀區放下方；小計只計本人列，並明確標示全桌內容僅供查看。每次加入都是新的一列，不跨 guest 合併同品項。加入／修改／刪除後 cart_version +1 並推 CART_UPDATED（帶不含個人權限欄位的全桌快照，見 04 §3.4.1），同桌手機 1 秒內同步；各裝置依 guest 身分標記本人列，加入時其他手機跳通知條，自己的動作不跳；已結帳 → 409 SESSION_CLOSED ☐

3.5 庫存扣減 條件式 UPDATE，任一項不足整張單回滾，回 409 ☐
3.6 快照寫入 品項名稱、單價、選項名稱與價差都存當下的值 ☐
3.7 多次加點 同一次用餐可送出多張單；session 鎖保護 sequence_no 與帳單重算，每張成功建立的單依序遞增 ☐
3.8 本桌訂單查詢 依點餐單分組，含每個品項的出餐狀態 ☐
3.9 多裝置即時同步 一支手機送出自己的列後，其他手機 1 秒內看到新單；各 guest 的送單互不清除 ☐
3.10 取消單品／整單 記錄原因，庫存回補 ☐
3.11 結帳後不可加點 送出點餐時在交易裡 SELECT ... FOR UPDATE 鎖住 dining_session，不是 OPEN → 409 SESSION_CLOSED（跟 M6 結清搶同一把鎖） ☐
3.13 防重複送出 送出中按鈕停用；同一 guest 同時送出兩次時，只建立一張單，第二次因本人已無待送列而回 409 CART_EMPTY。不同 guest 各有待送列時，兩張單都成立，session 鎖保護單號與帳單（見問題 7） ☐

問題思考與解決思路

問題 1：兩個人同時點最後一份牛五花

這是全專案最重要的一題。五個人都要能講。

情境 牛五花庫存剩 1 份。你和朋友幾乎同時按下「送出點餐」。

直覺會這樣寫

int stock = inventoryRepo.findQuantity(12);   // 查
if (stock >= 1) {                             // 判斷
    inventoryRepo.decrease(12, 1);            // 扣
}

為什麼會壞

時間 →
你：    查(=1) ─→ 判斷 1>=1 ✓ ─→ 扣 ─→ 0
朋友：      查(=1) ─→ 判斷 1>=1 ✓ ─→ 扣 ─→ -1

兩個人的「查」都發生在對方的「扣」之前。兩份都賣掉了，但只有一份貨。

而且這個 bug 單人測試永遠測不出來。

正確做法：把條件寫進 UPDATE

UPDATE inventory_item
   SET quantity = quantity - :qty
 WHERE menu_item_id = :itemId
   AND quantity >= :qty;

int affected = inventoryRepo.decreaseIfEnough(itemId, qty);
if (affected == 0) {
    throw new BusinessException("ITEM_SOLD_OUT", name + " 已售完", CONFLICT);
}

資料庫保證同一時間只有一個交易能改同一列。第二個人執行時庫存已經是 0，條件不成立，影響筆數是 0。

判斷成敗看「影響筆數」，不是看有沒有報錯。

延伸：多台伺服器時這招仍然有效（因為是資料庫在把關）。要鎖資料庫以外的東西才需要 Redis 分散式鎖。

問題 2：扣到第三項時發現庫存不夠

情境 一張單有五個品項。扣到第三項時庫存不足。

如果沒有交易 前兩項的庫存已經扣掉了，但訂單沒成立。庫存憑空少了兩份，而且沒有人會發現。

正確做法

@Transactional                         // ← 整個方法綁在一起
public OrderTicketDto submitOrder(String sessionToken, String guestToken) {   // 不收品項：只送目前 guest 自己加入的列
    DiningSession session = sessionService.lockOrderable(sessionToken);  // FOR UPDATE，不是 OPEN → 409 SESSION_CLOSED
    DiningSessionGuest guest = guestService.validateToken(session, guestToken);   // token 必須屬於本桌；記錄誰按的送出

    List<CartItem> cart = cartRepo.findBySessionIdAndAddedByGuestId(session.getId(), guest.getId()); // 拿到鎖之後讀本人列（問題 7）
    if (cart.isEmpty()) {
        throw new BusinessException("CART_EMPTY", "你目前沒有待送出的品項", CONFLICT); // 409：只看本人是否還有待送列
    }

    validateSoupBaseRule(session, cart);       // ① 鍋底規則
    validateOptions(cart);                     // ② 必選／上限

    // ③ 依 id 排序後逐項扣庫存（避免死鎖）
    cart.stream()
        .sorted(comparing(CartItem::getMenuItemId))
        .forEach(this::decreaseStockOrThrow);  // 任一項失敗 → 例外 → 全部回滾（購物車也原封不動）

    OrderTicket ticket = buildTicketWithSnapshots(session, guest, cart);  // ④⑤⑥ 以菜單現價重算、存快照；鎖保護單號
    cartRepo.deleteAll(cart);                                            // ⑦ 同一個交易裡只刪除本人已送列
    session.incrementCartVersion();                                      // 清車也必須 +1，否則 GET 空車會被本機舊版丟棄
    session.recalculate();                                               // ⑧ 在同一把 session 鎖內更新帳單

    return toDto(ticket);
}

推 WebSocket 要放在交易「之後」，否則交易還沒 commit 前端就收到通知，去查卻查不到資料。

延伸：為什麼要依 id 排序？因為兩個交易如果用不同順序鎖資料，會死鎖。統一順序就不會。

問題 3：同桌兩支手機怎麼同步？

情境 你和朋友各自拿手機。你加了一盤牛五花，他的手機要看到。

做法 A：輪詢 每 3 秒問一次「有新的嗎」。

  • 優點：簡單、容錯性天然就好
  • 缺點：多數請求是白問的；最慢晚 3 秒

做法 B：WebSocket ← 我們選這個

你一送出，後端直接推給這桌每位客人的個人信箱 /user/queue/cart-updates（見 04 §3.2）。

  • 優點：真的即時（<1 秒）、省請求
  • 缺點：要處理斷線、部署要支援協定升級

關鍵：WebSocket 不保證不漏

手機切到別的 App、進電梯、Wi-Fi 換 4G——連線就斷了，斷線期間推的東西全部收不到。

所以：

onConnect: () => {
  subscribe('/user/queue/cart-updates', handleEvent);
  refetchAll();          // ★ 每次（重新）連上都重抓一次完整資料
}

這一行讓你同時拿到「即時」和「不會錯」。 就算 WebSocket 完全掛掉，只要使用者重新整理，資料還是對的。

購物車也走同一條路：誰加了東西，後端推 CART_UPDATED，payload 帶全桌快照與版本號，其他手機比對版本後套用，再依自己的 guest 身分標記本人與唯讀列（見 04 §3.4.1）。個人化的權限欄位與本人小計以 GET /me/cart 為準。 不要拿事件內容自己去拼購物車——事件只拿來跳通知條「陳小美 加了 安格斯霜降牛五花 ×1・全份」（itemName、quantity、optionSummary），內容一律以後端為準。

問題 4：客人連按三下送出

情境 網路有點慢，客人以為沒反應，連按三下。

如果不處理 成立三張一模一樣的單，廚房做三份。

做法 A：前端擋

<Button disabled={submitting} loading={submitting} onClick={handleSubmit}>
  送出我的點餐
</Button>

必要，但不夠——前端的檢查不算數。

做法 B：後端也擋（冪等鍵）

前端每次送出時產生一個唯一的 requestId，後端在短時間內收到相同的就直接回上一次的結果。

我們的決定：基礎版做 A（前端停用按鈕），並在文件標明 B 是進階項。理由是我們的 API 是「建立新單」，重複送出的後果是多一張單而不是金額錯誤，且櫃檯可以取消。但要在簡報時說明你們知道這個限制。

同一 guest 快速重送時，第一次成功會刪掉該 guest 自己的列；後續請求在 session 鎖後重讀，因本人沒有待送列而回 409 CART_EMPTY，不會重複建立訂單。不同 guest 各有待送列時，都可以各自建立一張單，見問題 7。

歷史設計（已移出本次範圍）：服務鈴

以下是舊版方案，僅供理解既有設計稿與舊連結；本次不實作服務鈴，不建立資料表、不提供 API 或 WebSocket 事件，也不列入開發時程與驗收。

情境 客人按「加湯」，櫃檯要看到。

做法 A：只推 WebSocket，不存 最省事。

為什麼不好 - 櫃檯重新整理頁面，未處理的呼叫就不見了 - 沒辦法統計 - 沒辦法標記「已處理」

舊版做法 B：存表 + 推 WebSocket

service_call (
  id, dining_session_id, table_id,
  type    VARCHAR(20),   -- SERVICE / SOUP / POT_CLEAN（沒有結帳，結帳請到櫃檯）
  status  VARCHAR(20),   -- PENDING / ACKNOWLEDGED / DONE
  created_at, acknowledged_at, staff_id
)

成本只多一點點，但櫃檯體驗完全不同。

問題 6：購物車要放在哪裡

情境 陳小美和王大明同桌。陳小美加了一盤牛五花，王大明的手機要看得到；兩人各自送出時，訂單只包含各自加入的列。

做法 A：前端 state／localStorage（舊版就是這樣） 每支手機各一份。同桌看不到彼此加了什麼，兩個人各送各的，鍋底還可能各點一份。

做法 B：HTTP session 還是每支手機各一份（session 跟著各自瀏覽器的 cookie 走），伺服器重啟就消失。

做法 C：Redis 可以整桌共用，但送出時要「寫 order_ticket＋清購物車」一起成功或一起失敗，跨 Redis 和 MySQL 做不到同一個交易。

做法 D：存 MySQL，整桌共用且依加入者管理 ← 我們選這個

cart_item 掛在 dining_session 底下，不分手機；全桌可讀，每列仍記錄加入者。送出時在同一個交易裡只把目前 guest 的列搬進 order_ticket，只刪除這些列並遞增 cart_version（問題 2 的第 ⑦ 步）；同桌其他人的列保留。結清或取消用餐時若還有未送出的購物車列，才在終止交易內刪除整桌剩餘列並遞增版本；空車不需額外遞增。

「誰加的」和 owner 權限怎麼知道？ X-Session-Token 只表示這次用餐；同桌每位客人還需要自己的伺服器簽發身分：

  1. 掃碼加入時，後端建立或恢復 dining_session_guest，以安全亂數簽發 guestToken；前端保存 sessionToken 與 guestToken
  2. 後續顧客操作在 HTTPS 標頭帶 X-Session-Token；新增、修改、刪除購物車與送出點餐另外帶 X-Guest-Token
  3. 資料庫只存 guestToken 的 SHA-256 雜湊，並由 guest 列綁定 dining_session_id；後端先確認 token 屬於該 session，再把 cart_item.added_by_guest_id、order_ticket.submitted_by_guest_id 指向該 guest
  4. PATCH／DELETE 在交易內比對目標列的 added_by_guest_id；不是目前 guest 的列就回 403 CART_ITEM_FORBIDDEN

X-Device-Id 可由客戶端偽造，只是顯示提示，不參與 guest 查找、owner 判斷或授權。光有同桌共用的 X-Session-Token 不能修改別人的列。

送單範圍依加入者劃分：任何通過本桌 guest 驗證的人都能查看全桌購物車，但只能修改或刪除自己加入的列；送出時也只處理自己的列。自己的畫面將本人品項放在上方、同桌其他人放在下方並標示唯讀；小計只計本人品項，明確提示全桌其他品項僅供查看。isOwnItem 表示這列是否由目前 guest 加入，canEdit 表示目前 guest 是否可執行修改；兩者分開回傳，畫面提示不能取代後端權限檢查。

前端怎麼配合：購物車內容以後端為準，useState 只放畫面狀態（例如哪一列展開了）；CART_UPDATED 帶全桌列快照，前端依本機 guest 身分更新本人／唯讀區與本人小計，NEW_TICKET 後要重抓個人化購物車。 cart_item.unit_price 只給畫面顯示，送單時一律用菜單現價重算——加進購物車之後老闆改價，以送出那一刻為準。

自己的動作不通知自己：CART_UPDATED（在 change 裡）與 NEW_TICKET 都帶 byGuestId，前端跟 join 時拿到的 guest.id 比對，相同就只更新畫面、不跳通知條。 不要拿 byGuest 名稱比——兩個會員暱稱一樣就會互相吃掉通知。

不經過整桌購物車的兩種單

情境 怎麼送 同桌看到什麼
櫃檯代客加點（S-03） 店員直接帶品項出單（POST /api/admin/dining-sessions/{id}/orders，source = STAFF），跟送出購物車共用驗證、扣庫存、寫單那一段 NEW_TICKET 的 byGuest 是「櫃檯」、byGuestId 是 null →「櫃檯 送出 2 項」；客人購物車不受影響
C-17 預先點餐（A2） 還沒有用餐紀錄，購物車只存在那支手機，送出是整批 PUT /api/reservations/{id}/preorder 沒有同桌、沒有「誰加的」

結帳或取消時還沒送出的品項直接捨棄：session 進終態的同一個交易裡刪掉整桌 cart_item，不算錢； 櫃檯不用管購物車（S-03 不顯示購物車的任何提示），已結帳的 C-04／C-06 購物車列直接消失。客人要的東西，要在結帳前自己送出。

問題 7：同桌不同客人與同一客人同時送出

同桌 session 鎖同時保護 sequence_no 與帳單重算，並讓同桌送單交易依序執行。拿到鎖後，每個請求只讀取提交者自己的列。

情境 A：兩位 guest 各有自己的品項 王大明與陳小美各加入一列，幾乎同時送出。先取得鎖的請求建立自己的訂單並刪除自己的列；後取得鎖的請求仍讀得到另一位 guest 的列，因此也建立另一張訂單。兩張單的 sequence_no 依序增加，帳單在同一把鎖下重算，兩人的購物車都不會被對方清掉。

情境 B：同一 guest 對自己的購物車連送兩次 先取得鎖的請求建立一張訂單並刪除該 guest 的列；第二個請求拿到鎖後讀不到該 guest 的待送列，回 409 CART_EMPTY，因此只成立一張單。若該 guest 本來沒有待送列，即使同桌其他 guest 有列，也回 409 CART_EMPTY，那些列仍保留。

讀取本人購物車列一定要在鎖之後。 先讀再鎖會讓同一 guest 的兩個請求都拿到相同列，可能重複扣庫存並建立兩張單。

驗收 Demo 腳本

這就是第 4 週里程碑的驗收內容，也是最終 demo 的主線。

  1. 兩支手機掃同一桌的 QR，都進到菜單
  2. 手機 A 把「鴛鴦鍋底」（左麻辣、右昆布）加進購物車 → 手機 B 跳出「客人 1 加了 鴛鴦鍋底 ×1・麻辣・昆布」，購物車角標同步變成 1（手機 A 自己不跳）
  3. 手機 B 加牛五花 ×1（全份、加蔥花）→ 手機 A 跳「客人 2 加了 牛五花 ×1・全份・加蔥花」，兩支手機的購物車都是兩列、角標 2，各自標出 owner；手機 A 嘗試改或刪手機 B 的列 → 403 CART_ITEM_FORBIDDEN；手機 B 把自己加入的牛五花改成 2 份，兩支手機的角標都變成 3（數量算份數，不算列數）
  4. 手機 A 按「送出我的點餐」→ 只送出 A 自己加入的鴛鴦鍋底，成立第 1 單；B 的牛五花仍保留在 B 的購物車。手機 B 收到通知條「客人 1 送出 1 份鍋底」
  5. 廚房看板收到第 1 單
  6. 手機 B 送出原先加入的牛五花 → 成立第 2 單；再加高麗菜並送出 → 成立第 3 單
  7. A、B 各有自己的待送品項，同時按送出 → 各成立一張單，單號依序增加且購物車彼此保留；再以同一 guest 的兩個請求同時送出，只成立一張單，後一個回 409 CART_EMPTY
  8. 廚房勾選「鴛鴦鍋底已出餐」→ 兩支手機同時看到狀態變成「已出餐」
  9. 手機 A 先把一個品項加進購物車，再用 SQL 把它的庫存設成 0（模擬剛被別桌點完）→ 送出 → 顯示「已售完」並標紅那一項，整張單沒有成立，購物車原封不動
  10. 本桌還沒點鍋底時，送出一份沒有鍋底的購物車 → 顯示「這桌還沒點鍋底，共鍋至少要一份」，整張單沒有成立
  11. 手機 A 加一樣東西但不送出 → 櫃檯打開 S-03，看不到任何購物車提示，合計也不含它（櫃檯只看已送出的單）
  12. 櫃檯在 S-03 結帳 → 兩支手機同時變成「已結帳」，菜單變暗、購物車列換成「這桌已經結帳完成」，剛剛沒送出的那一項不算錢
