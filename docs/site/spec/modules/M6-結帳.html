模組 6：結帳

難易度 ★★☆☆☆　里程碑 第 4 週

這個模組在做什麼

算清楚這桌總共多少錢，收款，然後把桌子放回可用狀態。

基礎版是客人到櫃檯結帳：櫃檯在 S-03 桌位詳情看帳單，結帳區有三顆付款按鈕「現金／信用卡／條碼」，三顆都先跳同一個 5 秒倒數（S-03b，可取消），倒數到 0 才真的送出，成功後約 1.5 秒自動關閉。 客人在自己手機上付款（「我要結帳」→ C-09～C-11）是進階 A5（6.E7），基礎全綠燈後才動工。

這裡要記得我們的定位：半輔助工具。 系統管的是「點什麼、出到哪、坐多久」，不管錢怎麼進抽屜。所以我們不做找零、交班、日結、稽核、發票、折讓——那些留給店家原本的收銀機。

難易度為什麼只有兩顆星

沒有複雜演算法、沒有即時推播的難點，併發也只有一處（跟開桌同一招：列鎖）。主要是：

  • 金額計算要正確（用 BigDecimal）
  • 結清與加點要搶同一把列鎖，金額比對不上就擋（見問題 1）
  • 櫃檯結清只是標記；線上付款（進階 A5）也是模擬的，不串接任何真實金流

唯一要小心的是「不要把範圍做大」。 結帳很容易越做越像 POS 系統。

基礎必做功能

# 功能 驗收條件 狀態

6.4（取消結帳）刪除，空號不重編——沒有鎖定狀態，就沒有「解鎖」這件事。 原 6.5、6.6、6.8、6.12 移到 6.E7（A5 顧客線上結帳），編號留空。 客人預設到櫃檯結帳；C-08 底部只留一行「用餐完畢請到櫃檯結帳」，服務鈴也沒有「我要結帳」。 付款方式從「現金／模擬支付」改成「現金／信用卡／條碼」（2026-09-16），payment.method 沒有 MOCK_PAY 了。

S-03 結帳區的「會員（選填）」那一塊是進階 8.10 的櫃檯入口（A1／A6 的前提）：輸入手機 → 查詢 → 顯示「陳小美・1998/04/21」讓櫃檯唸給客人確認 → 「確認是本人」才把 memberId 放進 settle 的 body，同一個交易寫進 dining_session.member_id。不做 8.10 就整塊拿掉，settle 不帶 memberId。細節見 M8 8.10。

結帳時整桌購物車還有東西：結清的同一個交易裡直接捨棄、不算錢（6.10）。櫃檯不用管購物車：S-03／S-03b 不顯示任何購物車提示， GET /api/admin/dining-sessions/{id} 也不回購物車資訊，櫃檯只看已經送出的單。客人要那幾樣，就要在結帳前自己送出（或請櫃檯代客加點）。

S-03 還有一顆「取消該次用餐」（僅店長，M2 2.14），跟結帳是兩條路：沒點過餐才能取消， 點過餐就只能結帳（409 SESSION_HAS_ORDERS）。取消推的也是 SESSION_CLOSED，但 reason: CANCELLED，手機不顯示「已結帳」面板、直接回 C-00。

問題思考與解決思路

問題 1：結帳到一半有人加點

情境 櫃檯在 S-03 看到這桌合計 1562，正要按「信用卡」；同一時間，桌上的朋友在手機上又加了一盤肉。

如果不處理 櫃檯收的是 1562，實際帳單已經變成 1914。錢收了，金額卻不對。

舊做法：先鎖再付（已拿掉） 舊版有一個 CHECKOUT_PENDING 狀態：按「我要結帳」就把整桌鎖住不能加點，還要配一顆「取消結帳」解鎖。 代價是多一個狀態、兩支 API、一個 WebSocket 事件；而且基礎版客人是走去櫃檯結帳， 手機上根本沒有「開始結帳」這個時間點可以鎖。

正確做法：金額比對 + 列鎖

畫面上看到多少，就把那個數字一起送上來（expectedTotal）。 後端在同一個交易裡鎖住這筆 dining_session、重算一次，不一樣就擋下來。

@Transactional
public SettleResult settle(Long sessionId, SettleRequest req) {
    // SELECT ... FOR UPDATE：跟送出點餐搶同一列的鎖
    DiningSession session = sessionRepo.findByIdForUpdate(sessionId)
        .orElseThrow(() -> new BusinessException("NOT_FOUND", "查無此筆用餐", NOT_FOUND));

    if (session.getStatus() != SessionStatus.OPEN) {
        throw new BusinessException("SESSION_CLOSED", "這桌已經結帳，不能再加點", CONFLICT)
            .with("reason", session.getStatus().name());          // PAID 或 CANCELLED，前端靠它決定顯示什麼
    }

    CheckoutAmount amount = calculator.calculate(session);        // 重算，不相信畫面
    if (amount.total().compareTo(req.expectedTotal()) != 0) {     // 用 compareTo，見問題 2
        throw new BusinessException("BILL_CHANGED", "金額有變動，請重新確認", CONFLICT)
            .with("bill", toBillDto(session, amount));             // 附最新帳單，前端直接重畫
    }

    if (req.memberId() != null) {                                 // 進階 8.10 的櫃檯入口：客人確認是本人才會帶
        session.attachMember(req.memberId());                     // 已綁了別的會員 → 409 ALREADY_ATTACHED
    }

    paymentRepo.save(Payment.settled(session, req.method(), amount.total()));  // CASH、CARD 或 BARCODE
    closeSession(session, amount);
    return toResult(session);
}

// 收尾：櫃檯結清與（進階 A5）線上付款成功共用，兩邊不要各寫一份
private void closeSession(DiningSession session, CheckoutAmount amount) {
    session.markPaid(amount);                                     // → PAID，用餐權杖一起失效
    session.getTable().setStatus(TableStatus.CLEANING);
    cartRepo.deleteBySessionId(session.getId());                  // 還沒送出的購物車直接捨棄，不算錢
    var event = new WsEvent("SESSION_CLOSED", Map.of("sessionId", session.getId(), "reason", "PAID"));
    events.publishAfterCommit("/topic/session/" + session.getId(), event);  // 同桌手機切到「已結帳」
    events.publishAfterCommit("/topic/counter", event);                     // 櫃檯更新桌況
}

送出點餐那一邊，也在交易裡鎖同一列：

// OrderService.submitOrder()，同一個 @Transactional 裡、扣庫存之前
DiningSession session = sessionRepo.findByIdForUpdate(sessionId).orElseThrow(...);
if (session.getStatus() != SessionStatus.OPEN) {
    throw new BusinessException("SESSION_CLOSED", "這桌已經結帳，不能再加點", CONFLICT)
        .with("reason", session.getStatus().name());   // 409 回應也帶 reason（04 §1.2）
}

兩邊搶同一把鎖，所以一定一先一後：

誰先拿到鎖 結果
加點先 單成立、合計變了 → 櫃檯的結清拿到 409 BILL_CHANGED，畫面換成新金額，再按一次
結清先 這桌已是 PAID → 加點拿到 409 SESSION_CLOSED；同桌手機收到 SESSION_CLOSED，C-04 顯示「已結帳」

櫃檯結清和客人線上付款（進階 A5）同時按也是同一個道理：後到的拿 409 SESSION_CLOSED，不會收兩次錢。

只鎖一邊等於沒鎖。結清、付款、送出點餐三個地方都要 FOR UPDATE 同一筆 dining_session。

問題 2：金額算出來差一塊錢

情境 小計 1420，服務費 10%，合計應該是 1562。但系統顯示 1561.9999999。

原因 用了 double 或 float。電腦的浮點數沒辦法精確表示 0.1。

System.out.println(0.1 + 0.2);   // 0.30000000000000004

正確做法：從頭到尾用 BigDecimal

public CheckoutAmount calculate(DiningSession session) {
    BigDecimal subtotal = session.getTickets().stream()
        .filter(t -> t.getStatus() != TicketStatus.CANCELLED)
        .flatMap(t -> t.getItems().stream())
        .filter(i -> i.getStatus() != ItemStatus.CANCELLED)
        .map(OrderItem::getLineTotal)
        .reduce(BigDecimal.ZERO, BigDecimal::add);

    BigDecimal fee = subtotal.multiply(SERVICE_FEE_RATE)
                             .setScale(2, RoundingMode.HALF_UP);

    return new CheckoutAmount(subtotal, fee, subtotal.add(fee));
}

三個重點：

  1. 資料庫欄位用 DECIMAL(10,2)，不要 FLOAT
  2. 建立 BigDecimal 用字串：new BigDecimal("0.10") 不是 new BigDecimal(0.10)
  3. 每一步都 setScale(2, HALF_UP)，明確指定進位規則

比較兩個 BigDecimal 要用 compareTo，equals 會認為 142.0 和 142.00 不相等。

問題 3：模擬付款的界線在哪（進階 A5）

情境 規格寫「模擬 Apple Pay / Google Pay / LINE Pay」。

如果不寫清楚會發生什麼 一定會有組員跑去研究真的串接文件。LINE Pay 要商家申請、Apple Pay 要開發者帳號 + 正式網域——浪費三到五天，而且做不出來。

明確定義（請貼進群組）

付款 = 一個假的付款畫面 → 客人選一種方式（三顆按鈕，只是圖示不同）→ 前端顯示 2 秒處理動畫 → 後端建立一筆 payment 紀錄，隨機 95% 成功／5% 失敗 → 回傳交易編號。 不串接任何真實金流 API。不申請任何開發者帳號。

@Transactional
public PaymentDto pay(PayRequest req) {
    // 先走問題 1 的列鎖 + 狀態檢查 + expectedTotal 比對（跟櫃檯結清共用）
    DiningSession session = lockAndVerify(req.diningSessionId(), req.expectedTotal());
    CheckoutAmount amount = calculator.calculate(session);

    boolean success = random.nextInt(100) < 95;      // 95% 成功
    Payment payment = paymentRepo.save(Payment.of(session, req.method(), amount.total(),
        success ? PayStatus.SUCCESS : PayStatus.FAILED,
        "MOCK-" + LocalDate.now().format(BASIC_ISO_DATE) + "-" + nextSeq()));

    if (success) {                                    // 成功：收尾跟櫃檯結清完全一樣（04 §4.9）
        closeSession(session, amount);                // PAID、桌位 CLEANING、權杖失效、刪購物車、推 SESSION_CLOSED
    }
    return toDto(payment);   // FAILED 由 Controller 轉成 422 PAYMENT_FAILED
}

失敗不要用「丟例外」離開這個方法。 @Transactional 遇到 RuntimeException 會整個回滾， 剛存進去的 FAILED 紀錄也會一起消失，事後查不到失敗過。用回傳值表示失敗，交給 Controller 回 422。

為什麼要留 5% 失敗？ 因為 demo 時可以展示錯誤處理。一個「永遠成功」的付款流程看不出你有沒有想過失敗的情況。

付款頁要明確標示「本系統為教學專題，付款為模擬流程，不會產生實際交易」。 誠實，而且評審會欣賞。

問題 4：人數不進帳單計算，那收集人數幹嘛？

情境 我們的計價是「一鍋一價 + 單點」、無低消。所以：

小計 = Σ(品項 × 數量)
服務費 = 小計 × 10%
合計 = 小計 + 服務費

人數完全不參與金額計算。

那為什麼還要輸入大人／小孩人數？ 四個用途：

用途 說明
座位安排 櫃檯配桌、訂位的 best-fit
分帳均分 顯示「每人約 $521」（即使不做分帳功能，顯示參考值也有用）
兒童友善推薦 有小孩時把辣度 0 的品項排前面
客單價統計 營收 ÷ 人數

這點一定要寫進文件，不然組員會問「為什麼要收集人數卻不用」，或者更糟——自己加一個人頭費的計算進去。

問題 5：櫃檯按錯付款方式怎麼辦

情境 客人說要刷卡，櫃檯手滑按到「現金」。

如果一按就送出 帳就記成現金了。這一版沒有「改付款方式」也沒有退款流程，只能進資料庫改。

正確做法：倒數 5 秒，倒數中可以取消（S-03b）

點任何一顆付款按鈕，先跳同一個倒數對話框：大數字 5 → 0＋金額＋「取消」，標題跟著方式變—— 現金「收款中，請把現金放進收銀機」、信用卡「信用卡付款中」、條碼「條碼付款中」。倒數到 0 才送 settle； 倒數期間按「取消」，什麼都不會發生。成功後換成勾勾「結帳完成」，約 1.5 秒後自動關閉回 S-02，櫃檯不用多按一下。

現金也要倒數嗎？ 要（2026-09-16 定案）。三顆走同一個流程，程式只有一條路；現金的倒數剛好是「把錢放進收銀機」的時間。

// 倒數只在前端：取消不需要任何 API，因為還沒送出任何東西
useEffect(() => {
  if (!paying) return;
  if (count === 0) { settle(paying.method); return; }      // 到 0 才送，送出中按鈕停用（6.11）；成功後 setTimeout 1500 自動關閉
  const t = setTimeout(() => setCount(c => c - 1), 1000);
  return () => clearTimeout(t);                             // 按「取消」→ setPaying(null)，計時器被清掉
}, [paying, count]);

倒數途中有人加點：倒到 0 送出時照樣走問題 1 的 expectedTotal 比對，拿到 409 BILL_CHANGED → 對話框關閉、帳單刷新、提示「剛剛有人加點，金額更新了」，櫃檯再按一次。

為什麼櫃檯結帳不做失敗機率？ 櫃檯是真的收到錢、刷過卡才按的，系統只是記錄； 「付款失敗、可重試」是客人自己在手機上付款（A5）才有的情境。

週 這個模組要交出什麼
W1 Flyway 建好 payment；服務費率等設定放進 application.yml
W2 金額計算 Service（含單元測試）

常見卡關

卡點 解法
金額差一塊錢 檢查有沒有用 double；檢查 setScale 的進位規則
BigDecimal 比較不相等 用 compareTo 或 isEqualByComparingTo，不要用 equals；金額比對用 equals 會每次都回 BILL_CHANGED
取消的品項也被算進去 計算時要 filter 掉 CANCELLED
結清成功但桌位沒轉狀態 三個狀態要在同一個 @Transactional 裡改
櫃檯連按兩次結清 前端 disabled={submitting}；後端第二次會拿到 409 SESSION_CLOSED
結帳完成的對話框一直停著 成功後要自己 setTimeout 約 1.5 秒關閉並回 S-02，不是等櫃檯按
結帳後購物車的東西還在 closeSession 漏了刪 cart_item；A5 線上付款成功也走同一個 closeSession
按了取消還是結帳了 一按就送了 settle、倒數只是動畫；要倒數到 0 才送（問題 5）
取消用餐後手機顯示「已結帳」 SESSION_CLOSED 沒看 reason，CANCELLED 要直接回 C-00
結清一直回 BILL_CHANGED 前端送的是舊金額；收到 409 要用回傳的最新帳單重畫，再讓櫃檯按一次
結清時有人加點卻沒被擋 送出點餐沒有 FOR UPDATE 同一筆 dining_session，只鎖一邊等於沒鎖
付款失敗紀錄查不到（A5） 失敗時丟了例外，交易回滾把 FAILED 紀錄也收掉了，見問題 3
