模組 4：出菜看板（KDS）

難易度 ★★★☆☆　里程碑 第 4 週

這個模組在做什麼

廚房牆上那塊螢幕。客人一送出點餐，這裡立刻跳出一張卡片，上面是桌號和要做的菜。廚師做好一樣就勾一樣，全部勾完卡片自動消失。

KDS = Kitchen Display System，取代傳統的出單機紙條。

難易度為什麼是三顆星

邏輯本身不難（就是查詢 + 更新狀態）。難的是三件事：

  1. 即時性——客人送出後廚房必須馬上看到，不能等
  2. 狀態推導——order_ticket 的狀態要由旗下 order_item 自動算出來，不能手動設
  3. 可讀性設計——廚房光線強、距離遠、手可能是濕的，UI 要跟一般後台完全不同

基礎必做功能

# 功能 驗收條件 狀態

問題思考與解決思路

問題 1：單的狀態要手動設還是自動算？

情境 一張單有五個品項。廚師勾了三個。這張單現在是什麼狀態？

直覺會這樣寫 每次勾選時，前端或後端手動判斷要不要把單改成 PREPARING 或 SERVED。

為什麼會壞 - 兩個廚師同時勾不同品項，狀態可能被覆蓋成錯的 - 取消一個品項時忘記重算 - 狀態和實際內容對不起來，而且很難 debug

正確做法：由品項推導

public void refreshStatusFromItems() {
    List<ItemStatus> statuses = items.stream()
        .filter(i -> i.getStatus() != ItemStatus.CANCELLED)
        .map(OrderItem::getStatus).toList();

    if (statuses.isEmpty())                                   this.status = CANCELLED;
    else if (statuses.stream().allMatch(s -> s == SERVED))    this.status = SERVED;
    else if (statuses.stream().anyMatch(s -> s == SERVED))    this.status = PREPARING;
    else                                                      this.status = PENDING;
}

每次品項狀態改變，就呼叫這個方法重算一次。 單的狀態永遠等於「品項狀態的函數」，不可能對不起來。

面試會問：這是「單一真相來源（single source of truth）」的實際應用。

問題 2：預約先點的單怎麼排到最前面？

情境 一組客人線上訂位時就先點好菜（不先付款，到店一起結帳），賣點是「到店後優先上菜」。這是進階 A2 才有的單。

做法 A：另外開一個「預約單」看板 兩個看板，廚師要看兩邊。容易漏。

做法 B：同一個看板，排序時排前面 ← 我們選這個

SELECT ... FROM order_ticket
WHERE status IN ('PENDING', 'PREPARING')
ORDER BY is_preorder DESC, placed_at ASC

一個 ORDER BY 就解決了。 再加上視覺區隔（金色邊框 + 標籤），廚師一眼就知道要先做哪張。

關鍵細節：placed_at 要用「報到開桌的時間」而不是「客人線上點餐的時間」。否則一張三天前點的預約單，placed_at 是三天前，會被算成「等待了 4320 分鐘」，警示一直閃。

問題 3：廚房的 UI 為什麼要跟別的頁面不一樣

情境 KDS 螢幕掛在廚房牆上，廚師站在兩公尺外，手上可能是濕的。

如果照一般後台的設計 14px 的字、灰白背景、小小的勾選框——廚師根本看不清楚，也點不準。

正確做法：為場景設計

一般後台 KDS
亮色背景 #FBF7F0 深色背景 #241C18
內文 14–16px 品項 20px、桌號 32px
勾選框 16px 勾選框 40×40px
資訊密度高 一排 5 張卡，留白多
滑鼠操作 觸控操作

為什麼深色？ 廚房光線強、油煙多，深底白字的對比在遠距離最清楚，而且螢幕反光比較不影響。

這是全站唯一使用深色的頁面。 在 11-設計系統 有明確規範。

問題 4：卡片消失得太快，廚師來不及確認

情境 勾完最後一個品項，卡片立刻消失。廚師心想「我剛剛勾的是哪一桌？」

正確做法：0.5 秒的淡出動畫 + 可以看已完成的單

// 先標記，動畫跑完再從清單移除
const handleComplete = (ticketId) => {
  setFading(prev => [...prev, ticketId]);
  setTimeout(() => {
    setTickets(prev => prev.filter(t => t.ticketId !== ticketId));
    setFading(prev => prev.filter(id => id !== ticketId));
  }, 500);
};

再加一個「最近完成」的分頁，可以看剛剛出完的 10 張單。成本很低，但廚師用起來安心很多。

六週切分

週 這個模組要交出什麼
W1 （無）等 M3 的資料表建好
W2 GET /api/admin/kitchen/tickets 查詢 API；PATCH /api/admin/order-items/{id}/serve
W3 ★ KDS 看板畫面（深色、大字、勾選框）；WebSocket 即時推播；狀態自動推導；主流程全綠燈
W4 久候警示；出餐順序建議；（有做 A2 才需要）預約優先排序
W5 退菜紀錄；最近完成分頁；平板實機測試
W6 不寫新功能。在真的平板上測一次，確認兩公尺外看得清楚

常見卡關

卡點 解法
查詢 N+1 一張單要抓品項、選項，用 JOIN FETCH 或 @EntityGraph
WebSocket 推了但看板沒動 檢查訂閱的 topic 名稱有沒有打錯
狀態改了但顧客端沒同步 勾選後要同時推 /topic/kitchen 和 /topic/session/{id}
等待時間顯示錯誤 placed_at 用錯了（預約單的問題，見上面）
平板上排版跑掉 KDS 只做 ≥1024px，不用管手機

驗收 Demo 腳本

  1. KDS 看板開在平板上（或另一個瀏覽器視窗）
  2. 手機送出一張單 → 看板 1 秒內跳出卡片
  3. 卡片上桌號很大、品項清楚、選項有顯示（「全份・加蔥花」）
  4. 勾選第一個品項 → 手機端的出餐進度立刻變成「已出餐」
  5. 勾完全部 → 卡片淡出消失
  6. 一張放了 16 分鐘的單 → 紅色邊框警示 7.（有做 A2 預先點餐才演）一張預約先點的單 → 排在最前面，金色邊框 + 「預約優先」
