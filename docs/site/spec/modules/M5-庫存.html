模組 5：庫存

難易度 ★★★★☆　里程碑 第 3 週扣減、第 4 週售完推播

這個模組在做什麼

記錄每樣東西還剩幾份。客人點餐時即時扣掉，歸零時自動下架並通知所有正在點餐的手機。 店長補貨、看哪些快沒了是 S-09 庫存管理畫面，屬於進階 A3；扣庫存與防超賣是基礎。

這個模組的技術價值遠高於它的功能價值——「防超賣」是後端面試最常出現的題目之一。

難易度為什麼是四顆星

功能本身很單純（加加減減）。但「兩個人同時點最後一份」這個問題：

  • 寫錯不會報錯，只會默默把庫存變成負數
  • 單人測試永遠測不出來
  • 要理解資料庫的鎖與交易才寫得對

基礎必做功能

# 功能 驗收條件 狀態
5.1 品項層級庫存 一個品項對一筆庫存（1:1） ☐
5.2 防超賣扣減 10 個人同時搶最後 1 份，只有 1 個成功，庫存是 0 不是 -9 ☐
5.3 告罄自動下架 歸零時 menu_item.sold_out = true ☐
5.4 售完即時推播 所有正在點餐的手機 1 秒內看到「售完」 ☐
5.5 取消回補 取消點餐單時庫存加回去 ☐
5.6 續加品不扣庫存 track_inventory = false 的品項跳過扣減 ☐

5.7～5.10 移到進階 A3（S-09 庫存管理畫面），見下面的 5.E0。編號沿用不重編，驗收條件照舊：

問題思考與解決思路

問題 1：防超賣（本模組的全部重點）

已經在 M3 點餐 和 鎖與併發 詳述。這裡只放結論：

UPDATE inventory_item
   SET quantity = quantity - :qty
 WHERE menu_item_id = :itemId
   AND quantity >= :qty;

判斷成敗看影響筆數。 0 = 庫存不足，整張單回滾。

為什麼不用 synchronized？ 它只鎖得住同一台伺服器。部署兩台就失效。而且資料庫層的問題要在資料庫層解。

問題 2：庫存要記到多細？

情境 「牛五花」和「牛肉拼盤」其實共用同一批牛肉。點了拼盤，五花的庫存要不要減？

做法 A：品項層級庫存 ← 我們基礎版選這個

一個品項一筆庫存，各算各的。

  • 優點：極度單純，一張表、一個欄位
  • 缺點：共用原料的情況算不準

做法 B：BOM 配方（原料層級）

recipe: menu_item_id, ingredient_id, amount
  牛五花     → 牛肉 200g
  牛肉拼盤   → 牛肉 150g + 豬肉 150g

扣的是原料，不是品項。

  • 優點：真實、準確
  • 缺點：多兩張表、每個品項都要設定配方、換算單位很煩

我們的決定：基礎版做 A，BOM 列為進階。

在文件和簡報裡明講這個取捨。「我們知道 BOM 更準確，但評估後認為在專題時程內，把防超賣做對比把配方做出來更有價值」——這種說明在面試時是加分的，比假裝沒想過好得多。

問題 3：售完了，但客人購物車裡已經有了

情境 牛五花剛被別桌點完。你這桌的購物車裡已經加了兩份，正要按送出。

如果只靠前端推播 你的手機收到「售完」推播，把菜單上那項標成灰色。但購物車裡那兩份還在。

正確做法：兩層防護

層 做什麼 目的
前端 收到 MENU_SOLD_OUT → 菜單標灰、購物車那項標紅並提示 體驗：讓客人早點知道
後端 送出時再扣一次庫存，不足回 409 + 是哪一項 真相：真正把關

前端收到 409 之後：

case 'ITEM_SOLD_OUT':
  markSoldOut(err.details);              // 標紅那幾項
  toast.error('部分品項已售完，請調整後重新送出');
  break;

整張單不成立，讓客人自己決定要移除還是換別的。

問題 4：續加的白飯要不要扣庫存？

情境 白飯、湯底、飲料是免費無限續。

如果照一般品項處理 每次續加都扣 1，白飯庫存很快變 0 → 自動標成「售完」→ 客人看到「白飯售完」，很怪。

正確做法：加一個旗標

menu_item (
  track_inventory TINYINT(1) NOT NULL DEFAULT 1
)

track_inventory = false 的品項：

  • 不扣庫存、不會被標售完
  • 但仍然要出單給廚房（0 元不代表不用做，續湯續飯一樣要送）

這個 boolean 欄位就解決了。

問題 5：怎麼證明防超賣真的有效？

情境 你寫好了條件式 UPDATE。怎麼確認它真的有用？

手動測試沒用——你一個人按十次，那是「依序」不是「同時」。

正確做法：多執行緒測試 + 真的 MySQL

@Test
void 十個人同時搶最後一份不應超賣() throws Exception {
    Long itemId = seedItemWithStock(1);

    ExecutorService pool = Executors.newFixedThreadPool(10);
    CountDownLatch latch = new CountDownLatch(10);
    AtomicInteger success = new AtomicInteger();

    for (int i = 0; i < 10; i++) {
        pool.submit(() -> {
            try { orderService.submitOrder(token, oneItemRequest(itemId)); success.incrementAndGet(); }
            catch (BusinessException ignored) { }
            finally { latch.countDown(); }
        });
    }
    latch.await(10, TimeUnit.SECONDS);

    assertThat(success.get()).isEqualTo(1);
    assertThat(inventoryRepo.findQuantity(itemId)).isZero();
}

一定要用 Testcontainers 的真 MySQL，用 H2 測等於沒測（H2 的鎖行為跟 MySQL 不一樣）。

這個測試是整個專案最值得寫的一個。 面試時可以直接秀給對方看。

六週切分

週 這個模組要交出什麼
W1 Flyway 建好 inventory_item / inventory_log；種子資料（刻意留 2–3 個品項庫存為 0）
W2 防超賣的條件式 UPDATE（在 M3 的送出點餐裡）；取消時回補
W3 售完自動下架；track_inventory 旗標
W4 （本模組這週較空，可以先支援 M3 的送出點餐與取消回補測試）
W5 ★ 售完的 WebSocket 推播
有餘力才做 A3：店家端庫存管理頁 S-09；手動補貨；異動紀錄查詢；低水位警示；低庫存排程
W6 不寫新功能。寫多執行緒防超賣測試，這是 demo 的亮點

常見卡關

卡點 解法
庫存變負數 用了「先查再扣」，改成條件式 UPDATE
UPDATE 沒報錯但庫存沒變 忘了檢查影響筆數
取消後庫存沒回補 取消流程也要走 inventory_log，不要直接改數字
白飯顯示售完 忘了 track_inventory = false
多執行緒測試不穩定 要用 CountDownLatch 確保真的同時；要用真 MySQL
售完推播後前端沒反應 檢查 /topic/menu 有沒有訂閱

驗收 Demo 腳本

  1. 用種子資料或 SQL 把某品項庫存設為 1（有做 A3 就在 S-09 設）
  2. 兩支不同桌的手機（例如 A03、A05）各自把那個品項加進自己那桌的購物車 （同一桌的購物車是整桌共用的，兩支手機加的會進同一份，測不出搶最後一份，一定要用兩桌）
  3. 兩支同時按送出 → 一支成功，一支顯示「已售完」並標紅那一項
  4. 第三支正在看菜單的手機：那個品項自動變灰 + 「售完」標籤
  5. 點一份免費續加的白飯 → 送出 → 廚房看得到，但白飯庫存沒變 6.（加分）秀出多執行緒測試的綠燈畫面 7.（有做 A3 才演）S-09：那個品項變成 0，紅底，排在最前面 → 補貨 10 份 → 三支手機的菜單都恢復正常
