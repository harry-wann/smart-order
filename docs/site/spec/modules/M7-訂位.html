模組 7：訂位

難易度 ★★★★☆　里程碑 第 4 週

這個模組在做什麼

客人線上選時間、選人數，系統自動配一張合適的桌。選完時段按下確認，訂位當場就成立—— 不必付款、不必等店家回電。訂位成立之後才問「要不要先點餐」，到店報到就直接開桌。

這個模組是「排程」技術的主戰場——區間重疊演算法、併發控制、以及定時任務都在這裡。

動線一句話

選日期時段人數 ──► 訂位成立 ──► 問要不要先點餐 ──┬──► 先點餐（進階）
                                              └──► 到店再點
                       ▲
                       └── 我的預約：事後回來補點、改單（前一天 20:00 前）或取消（訂位時間前 30 分鐘前）

訂位不收錢，預先點餐也不收錢。 餐點金額一律到店結帳時才算。 所以「調整餐點」「取消訂位」都只是改資料，沒有任何退款流程要寫—— 這是這一版最大的簡化，也是刻意的：金流分支一多，五個人的專題會在第 4 週卡死。 想練退款的話走延伸功能 7.E7（訂金），跟主流程切乾淨。

難易度為什麼是四顆星

難點 為什麼難
區間重疊判斷 一條判斷式，但很容易寫成 <= 導致誤判
併發控制 兩個人同時訂同一桌，跟超賣是同一類問題
狀態機複雜 四種狀態，加上排程會自動轉移
時間處理 緩衝時間、保留窗（前 30 分～後 10 分）、跨午夜、時區

基礎必做功能

# 功能 驗收條件 狀態
7.1 任意時間預約 存 start_time / end_time（含清桌緩衝），非固定時段；只能訂明天起 30 天內（當天不接線上訂位，後端回 400 VALIDATION_FAILED） ☐
7.2 區間重疊檢查 A.start < B.end AND B.start < A.end，剛好接續不算衝突；算佔用的只有 CONFIRMED，以及 SEATED 而且那筆用餐紀錄還沒結帳（dining_session.status = OPEN），結帳或取消用餐後名額就釋出，不等到 end_time（見問題 5） ☐
7.3 best-fit 配桌 自動挑「座位數 ≥ 人數」中最小的那張 ☐
7.4 可訂時段查詢 回傳當日各時間點還剩幾桌 ☐
7.5 併發控制 兩人同時訂同一桌，只有一個成功 ☐
7.6 唯一約束 UNIQUE(table_id, start_time) 當資料庫層保險 ☐
7.7 可預約比例 只有 reservable = true 的桌開放線上訂（70%） ☐
7.8 取消（客人線上） C-19 可取消到訂位時間前 30 分鐘；之後 DELETE /api/reservations/{id} 回 409 CANCEL_DEADLINE_PASSED「訂位前 30 分鐘內請來電取消」，改由櫃檯代客取消（7.18）；訂位不是 CONFIRMED → 409 RESERVATION_NOT_CANCELLABLE；寫 cancelled_at、cancel_source = CUSTOMER，table_id 設 NULL ☐
7.9 報到開桌 S-07 按「報到開桌」→ S-07b 選一張坐得下的空桌（原保留桌排第一，標「原保留桌」；115 分鐘內有別筆訂位的桌紅字「19:30 有訂位」、排在沒有衝突的桌後面，選了要按「仍要開桌」再確認，只提醒不擋）→ 建立 dining_session 並帶入人數；最早提前 30 分鐘，太早 → 409 RESERVATION_TOO_EARLY「還沒到可報到時間（18:00 起）」；超過訂位時間 10 分鐘 → 409 RESERVATION_EXPIRED ☐
7.10 訂位保留桌位（算出來的鎖定，不是排程） 配到的桌在 start_time − 30 分 ～ +10 分、訂位 CONFIRMED 時，桌況顯示「預約保留」（displayStatus = RESERVED、heldFor）；現場開桌、候位入座、別筆訂位報到要開這張桌 → 409 TABLE_RESERVED；要解開保留就是櫃檯代客取消這筆訂位（7.18），沒有「只解除保留」的功能。桌位欄位不多存任何東西，見 M2 問題 5 ☐
7.11 排程：NO_SHOW 訂位時間過 10 分鐘未報到自動標記（每 5 分鐘跑一次）；訂位只保留 10 分鐘，逾時只能現場候位 ☐
7.12 排程：訂位提醒 用餐前 2 小時發通知 ☐
7.13 店家端訂位管理 依日期列出、可報到開桌／取消；「報到開桌」只在 start_time − 30 分 ～ +10 分 出現，更早的列顯示灰字「18:00 起可報到」；進入保留窗的列狀態欄多一行小字「保留 A08」；每一筆 CONFIRMED 列（不限保留窗內，明天以後的也算）都有 ghost「取消訂位」（7.18）；已取消的列狀態膠囊「已取消」，櫃檯取消的多一行小字「店家代取消・小美」；逾時未到的列顯示「逾時未到」，沒有報到按鈕，改成「登記候位」 ☐
7.14 手動觸發 API 每個排程都要能手動跑（demo 用） ☐
7.15 訂位即成立 送出後直接 CONFIRMED，回傳預約編號與配到的桌 ☐
7.16 開桌時列出可報到的預約 給 S-02d 用：用餐時間在現在 −10 ～ +30 分、坐得下的 CONFIRMED 訂位（+30 就是最早可報到的時間）；這張桌保留中時，保留的那筆置頂 ☐
7.17 報到轉 SEATED 從開桌頁選了預約 → 轉 SEATED；不動 table_id（那是容量用的配桌） ☐
7.18 櫃檯代客取消 客人來電取消時，櫃檯在 S-07 或 S-02d 按「取消訂位」→ POST /api/admin/reservations/{id}/cancel（COUNTER、MANAGER，body 可帶 { "reason": "客人來電取消" }，選填）；隨時可以取消，不受任何期限；只有 CONFIRMED 能取消，其他 → 409 RESERVATION_NOT_CANCELLABLE；寫 cancelled_at、cancelled_by_staff_id、cancel_source = STAFF，table_id 設 NULL，桌子與名額一起釋出，交易提交後推 TABLE_STATUS；按之前二次確認「確定要取消 陳怡君 18:30 的訂位嗎？通常是客人來電取消。取消後 A08 會變回空桌，這筆訂位無法恢復。」；C-19 那筆顯示「店家已代為取消」 ☐

7.10 恢復使用（2026-09-16）。 它原本是「排程：預留轉換」（訂位前 30 分鐘把 dining_table.status 改成 RESERVED）， 因為要靠 cron 同步、一沒跑就對不上，整條拿掉過、留了空號。 現在的 7.10 不是排程：桌位欄位一樣只有三種，「預約保留」是查桌況時從 reservation 算出來的， 所以排程仍然是九支，不要把舊的預留轉換排程加回來。為什麼算出來就沒有同步問題，見 M2 問題 5。

只有訂位會鎖桌，候位不鎖桌。 原本延伸功能裡「沒有訂位時櫃檯自己把空桌鎖起來」那一項已經刪除（M2 問題 5）。

7.18 是新編號（2026-09-16）：原本 7.10 裡「只解除保留、訂位照留」的按鈕整個拿掉，改成櫃檯代客取消整筆訂位。既有編號都不重編。

取消期限和預點截止是兩條線。 - 客人線上取消（7.8）：訂位時間前 30 分鐘。剛好等於預約保留開始的時間（reservation.hold-before-minutes），所以保留開始之後只剩櫃檯能取消（7.18）。 - 預點修改（7.E2，進階）：用餐日前一天 20:00，不變（廚房要有一天備料）。 - 以前兩者是同一個時間點，現在分開。預點截止維持前一天 20:00（2026-09-16 定案）：廚房要靠前一晚的預點備料，客人臨時改單會讓備料白費。

基礎這一層沒有預先點餐。 基礎要交出來的是一條完整可 demo 的線： 選時間 → 訂位成立 → 到店報到 → 開桌。預先點餐整塊在下面的延伸功能， 不做也不影響這條線跑完。

問題思考與解決思路

問題 1：怎麼知道這張桌這個時間有沒有空

情境 A03 桌明天已有訂位 18:00–19:55。客人想訂明天 19:00–20:55。（線上訂位只能訂明天以後，見 7.1）

直覺會這樣寫 把一天切成固定時段（11:30 / 13:30 / 17:30 / 19:30 / 21:00），每桌每時段只能有一筆。用 UNIQUE(table_id, date, time_slot) 防重複。

  • 優點：實作最簡單
  • 缺點：客人只能選那五個時間；而且學不到真實訂位系統的模型

正確做法：區間重疊檢查 ← 我們選這個

存完整的開始與結束時間，判斷式是：

A.開始 < B.結束  且  B.開始 < A.結束

套進去：18:00 < 20:55 ✅ 且 19:00 < 19:55 ✅ → 重疊，不行。

SQL：

SELECT t.* FROM dining_table t
WHERE t.active = 1 AND t.reservable = 1 AND t.seats >= :partySize
  AND NOT EXISTS (
      SELECT 1 FROM reservation r
      WHERE r.table_id = t.id
        AND ( r.status = 'CONFIRMED'              -- 還沒到的
              OR (r.status = 'SEATED'             -- 已報到、而且還沒結帳的（客人還坐著）
                  AND EXISTS (SELECT 1 FROM dining_session ds
                               WHERE ds.reservation_id = r.id AND ds.status = 'OPEN')) )
        AND r.start_time < :newEnd
        AND :newStart   < r.end_time
  )
ORDER BY t.seats ASC
LIMIT 1;

三個細節：

  1. 用 < 不是 <=——18:00–19:55 和 19:55–21:50 是「剛好接續」，不算衝突。用 <= 會白白浪費位子。
  2. 排除已取消與未到的；已報到的只算到結帳為止——不然位子永遠訂不到，或容量算錯（見問題 5）。
  3. ORDER BY seats ASC = best-fit——2 個人不要佔 8 人桌，把大桌留給大團。

問題 2：清桌時間怎麼算進去

情境 上一組 19:40 走，下一組 19:40 到。服務生來不及收拾。

正確做法：把緩衝加進 end_time

end_time = start_time + 用餐時長(100 分) + 清桌緩衝(15 分)
18:00 + 100 + 15 = 19:55

存進資料庫時就存這個。判斷式完全不用改。

這是個很優雅的設計：把「業務規則」轉換成「資料」，演算法就不用知道緩衝的存在。

問題 3：兩個人同時訂同一桌

情境

客人 A：查詢 → A03 有空 ──→ 寫入訂位
客人 B：    查詢 → A03 有空 ──→ 寫入訂位
                                 兩筆都成功

跟 超賣 是同一類問題。

但這次不能用條件式 UPDATE，因為配桌要做區間計算，沒辦法壓成一句 SQL。

正確做法：悲觀鎖 + 資料庫約束（兩層保護）

@Transactional
public ReservationDto create(CreateReservationRequest req) {
    LocalDateTime start = req.startTime();
    LocalDateTime end   = start.plusMinutes(DINING_MINUTES + BUFFER_MINUTES);

    // ① 鎖住候選桌（依 id 排序，避免死鎖）
    List<DiningTable> candidates = tableRepo.findReservableBySeatsForUpdate(req.partySize());

    // ② 在鎖的保護下做重疊檢查 + best-fit
    DiningTable picked = candidates.stream()
        .filter(t -> !reservationRepo.existsOverlap(t.getId(), start, end))
        .findFirst()
        .orElseThrow(() -> new BusinessException("SLOT_UNAVAILABLE", "這個時段已經客滿了", CONFLICT));

    return toDto(reservationRepo.save(Reservation.of(picked, start, end, req)));
}

-- ③ 資料庫層的保險
CREATE UNIQUE INDEX uk_reservation_table_start ON reservation (table_id, start_time);

「應用層 + 資料庫層」雙重保護是正確的做法。就算程式有 bug，資料庫也擋得住。

問題 4：訂了位沒來怎麼辦

情境 19:00 的訂位，19:15 了人還沒到。後面的客人在門口乾等，櫃檯不知道要不要把位子給別人。

直覺會這樣寫 櫃檯自己記得，過一陣子手動標記。

為什麼不好 尖峰時櫃檯忙不過來，一定會忘記。而且「過了多久算 NO_SHOW」沒有一致標準。

規則：訂位保留 10 分鐘。 過了訂位時間 10 分鐘還沒報到就視為 NO_SHOW，只能現場登記候位。 顧客端 C-18 訂位完成與 C-19 我的預約都要寫一行「訂位保留 10 分鐘，逾時視同未到，需現場候位」。 被標成 NO_SHOW 的訂位，C-19 放在「已取消」頁籤，狀態膠囊「逾時未到」＋一句「需要的話請重新訂位」，沒有按鈕。

正確做法：排程自動處理

@Scheduled(cron = "0 */5 * * * *", zone = "Asia/Taipei")
public void markNoShow() {
    try {
        LocalDateTime deadline = LocalDateTime.now().minusMinutes(10);   // status = CONFIRMED AND start_time < deadline
        int n = reservationService.markNoShowBefore(deadline);
        if (n > 0) log.info("{} 筆訂位標記為 NO_SHOW", n);
    } catch (Exception e) {
        log.error("NO_SHOW 檢查失敗", e);
    }
}

標記為 NO_SHOW 後，桌位不用動——7.10 的預約保留是算出來的，保留窗在訂位時間後 10 分鐘就自己結束了 （跟 NO_SHOW 用同一個 10 分鐘），排程晚幾分鐘才標也不影響桌況（見 M2 問題 5）。 這筆只是不再出現在開桌頁的預約清單上。有預點（A2）的也不用回補庫存，因為庫存本來就是報到才扣。

不能只靠排程。 排程每 5 分鐘跑一次，最晚要到 15 分鐘才標得到。所以：

  • 開桌頁的預約清單（open-options）自己看時間：只列 start_time 在現在 −10 ～ +30 分的
  • 報到 API（POST /api/admin/reservations/{id}/seat）自己檢查 now > start_time + 10 分 → 409 RESERVATION_EXPIRED「已超過保留時間，請改登記候位」

報到 API 也擋太早的：now < start_time − 30 分 → 409 RESERVATION_TOO_EARLY「還沒到可報到時間（18:00 起）」。 30 分就是保留窗的開頭，也是開桌清單的 +30，也是客人線上取消的期限——四個地方用同一個設定值（reservation.hold-before-minutes）。

★ 一定要配一支手動觸發的 API，不然 demo 時你要真的等 10 分鐘。

@PostMapping("/api/admin/scheduler/mark-no-show")
@PreAuthorize("hasRole('MANAGER')")
public Map<String, Object> trigger() {
    return Map.of("marked", reservationService.markNoShowBefore(LocalDateTime.now().minusMinutes(10)));
}

做法：排程方法只負責呼叫 Service + 記日誌，邏輯全在 Service，這樣排程和手動 API 共用同一段程式碼。

問題 5：取消的訂位還算不算佔位

情境 客人取消了 A03 桌 19:00 的訂位。別人現在訂得到嗎？

如果 status 沒納入判斷 取消的訂位還在表裡，重疊檢查會撞到它 → 位子永遠訂不到。

但如果直接刪掉 沒有紀錄，無法統計取消率，客人也查不到自己取消過。

正確做法：保留紀錄，但查詢時排除

AND ( r.status = 'CONFIRMED'
      OR (r.status = 'SEATED' AND EXISTS (SELECT 1 FROM dining_session ds
                                           WHERE ds.reservation_id = r.id AND ds.status = 'OPEN')) )

CANCELLED / NO_SHOW 不算。SEATED 只在那筆用餐紀錄還沒結帳（OPEN）時算：

這裡原本只算 CONFIRMED，想法是「入座後桌況改由 dining_session 管」。但這樣客人一報到， 那張桌那個時段的名額就被讓出去了——客人明明還坐著，容量卻少算一組。 後來改成 SEATED 一律佔到 end_time，又錯到另一邊：客人提早吃完、結帳走了，名額還被佔著。 所以現在是：已報到、而且 dining_session.status = OPEN 才算；結帳（PAID）或取消用餐（CANCELLED）之後這筆就不佔名額，不用等到原本的 end_time。

桌位本身照舊：結清 → 待清理 → 清潔完成 → 空桌，接著給下一筆訂位的保留（到了保留窗就顯示預約保留）或現場、候位使用。

線上訂位只能訂明天以後（7.1），所以這條主要影響的是「同一天之後的訂位保留」與容量報表的正確性，不會出現當天被線上搶訂的情況。 子查詢靠 dining_session.reservation_id 找那筆用餐紀錄（外鍵欄位，MySQL 會自動幫它建索引）。

reservation.table_id 不因為現場換桌而改：客人被帶到別張桌吃，佔的仍是當初配到那張桌的名額（容量算的是「這個時段賣出幾組」）。

原本這裡是 IN ('PENDING', 'CONFIRMED')。 PENDING 的存在理由是舊流程的 「先建訂位、預付成功才確認」；現在選完時段就直接成立，沒有任何路徑會產生 PENDING， 所以這個狀態整個拿掉了。留著一個永遠不會出現的狀態，只會讓後面接手的人一直猜它什麼時候用。 之後若要做 7.E7 訂金，再把它加回來。

注意唯一約束的衝突：UNIQUE(table_id, start_time) 會讓「取消後同一時段再訂」失敗。

兩種解法：

  • A：取消時把 table_id 設為 NULL（保留紀錄但釋放約束）
  • B：取消的搬到 reservation_cancelled 歷史表

我們選 A，比較單純。

問題 6：預先點餐的資料要存在哪裡

情境 客人三天前就先點好了鍋底跟牛五花。這時候還沒有桌、沒有開桌、沒有 dining_session。

直覺會這樣寫 訂位時就開一筆 dining_session，把 order_ticket 寫進去，reservation 用 preorder_session_id 指過去。反正點餐那一整套 API 都能重用。

為什麼不好

  1. dining_session 的語意壞掉——它現在的定義是「一次實際用餐（＝一張帳單）」。 資料庫裡會躺著一堆還沒發生、甚至永遠不會發生（NO_SHOW）的 session， 「今天有幾桌在用餐」這種查詢全部要多加條件過濾。
  2. order_ticket 送出即定案——單一旦成立就進 KDS、就扣庫存、就不能改。 但預點的單在報到前必須能反覆修改，這兩個語意直接打架。

正確做法：預點自己一張表，報到時才轉成正式的單 ← 我們選這個

reservation
  └── reservation_preorder_item        （可以隨便改，改到前一天 20:00）
        └── reservation_preorder_option

        ── 報到開桌時做一次轉換 ──►

dining_session
  └── order_ticket (is_preorder = 1)   （成立即定案，進 KDS）
        └── order_item
              └── order_item_option

兩邊欄位幾乎一樣（都存名稱與價格快照），轉換就是逐筆複製。價格照抄預點當下的快照，不重新取價—— 客人三天前看到多少就是多少，中間調價不追溯，這是對客人也對自己都好解釋的規則。

順帶解決一件事：因為預點不是正式的單，「調整餐點」就只是改自己的表， 不用去碰已經進 KDS 的東西，也不用發 WebSocket 通知廚房。

那 API 怎麼設計？ 用 PUT /api/reservations/{id}/preorder 整批覆蓋， 不要做「加一筆／減一筆」的部分更新。C-17 的購物車只存在那支手機（預點時還沒有用餐紀錄，不走店內那套整桌共用的後端購物車），把整份送上來最直覺； 後端一句 deleteByReservationId 再重建，不用寫 diff 邏輯； 重送同一份結果也一樣（冪等）。「新增預點」和「調整預點」是同一支 API。

問題 7：預先點餐什麼時候扣庫存

情境 客人三天前預點了 2 份牛五花。現在要不要馬上把庫存扣掉？

直覺會這樣寫 預點的時候就扣，跟現場點餐一樣。

為什麼不好 庫存會被鎖死三天。而且客人 NO_SHOW 的話，那 2 份就白白鎖了一整晚—— 火鍋店的肉品是當日備料，這等於是拿今天的庫存去擋三天後的單。

正確做法：報到開桌、轉成正式單的那一刻才扣

預點時    ：只寫 reservation_preorder_item，不碰庫存
報到開桌時：建立 order_ticket → 逐項扣庫存 → 扣不到的品項標記出來

代價要講清楚：客人到店時，預點的某一項可能已經賣完了。 所以報到 API 不能無聲失敗，要回一份「這幾項庫存不足」的清單給櫃檯畫面， 由櫃檯當面跟客人講。這不是 bug，是這個設計選擇的已知取捨，驗收時要能講得出來。

// 報到開桌：轉單 + 扣庫存，扣不到的挑出來回報
SeatResult seat(Long reservationId) {
    // ...建立 dining_session 之後
    List<String> soldOut = new ArrayList<>();
    for (ReservationPreorderItem pre : preorderRepo.findByReservationId(reservationId)) {
        if (inventoryService.tryDeduct(pre.getMenuItemId(), pre.getQuantity())) {
            ticket.addItem(OrderItem.copyOf(pre));   // 價格快照照抄
        } else {
            soldOut.add(pre.getItemNameSnapshot());
        }
    }
    return new SeatResult(session, soldOut);
}

只有基礎功能（不做 7.E1）的話，這一整段不存在——報到就只是開桌而已。

常見卡關

卡點 解法
明明有位卻說客滿 判斷式用了 <=，或沒排除已取消的
客人報到後還在吃，那張桌那個時段卻算成空的 區間重疊只算了 CONFIRMED；還沒結帳的 SEATED 也要算
客人早就結帳走了，那個時段還算佔用 SEATED 一律算到 end_time；要加「dining_session.status = 'OPEN'」的條件
櫃檯取消訂位被期限擋下來 7.18 不看任何期限，只看 status = CONFIRMED；期限（訂位前 30 分）只套在客人自己的 DELETE /api/reservations/{id}
訂位前 20 分鐘，用 Postman 還是取消得掉 只靠前端停用按鈕；後端要自己比 now > start_time − 30 分，回 409 CANCEL_DEADLINE_PASSED
客人早就報到了，桌況還顯示預約保留 保留條件漏了 status = 'CONFIRMED'
櫃檯取消訂位後，那張桌要等一陣子才變回空桌 交易提交後要推 TABLE_STATUS；取消時也要把 status 改 CANCELLED，保留條件才不成立
過了前一天 20:00，C-19 的取消按鈕也停用了 取消期限和預點截止是兩條線，cancellableUntil（訂位前 30 分）和 preorderEditableUntil（前一天 20:00）分開判斷
保留窗算反了（18:30 的訂位 17:50 就鎖、18:45 還鎖） 條件是「現在落在 start − 30 ～ start + 10」；改查 start_time 就是 now − 10 ～ now + 30
有人又寫了一支「預留轉換」排程 不要。7.10 是算出來的，排程只有九支
出現重複訂位 沒加悲觀鎖，或候選桌沒排序導致死鎖
Duplicate entry for uk_reservation_table_start 這是保險生效了，回 409 給前端就對
排程沒跑 忘了 @EnableScheduling，或類別沒貼 @Component
時間差 8 小時 沒設 zone = "Asia/Taipei"
跨午夜的訂位出錯 用 DATETIME 存完整時間，不要拆成日期+時間兩欄
demo 時等不到排程 做手動觸發 API
預點改不動，回 409 過了前一天 20:00 就鎖定，這是規則不是 bug；PREORDER_LOCKED 要回可讀的中文訊息
報到後預點的菜不見了 庫存不足被挑掉了（見問題 7）。報到 API 要回 soldOut 清單，櫃檯畫面一定要顯示
匿名訂位改不到自己的單 匿名沒有 JWT，要靠建立訂位時發的 access_token；前端存 localStorage
客人明明遲到 12 分鐘，還是報到成功 報到 API 只靠 NO_SHOW 排程判斷；要自己比 start_time + 10 分，回 RESERVATION_EXPIRED

驗收 Demo 腳本

基礎（一定要演完）

  1. 顧客端訂位：選明天 18:00、4 位 → 按下確認，當場跳出「訂位完成」與預約編號（不經過付款頁），畫面上寫著「訂位保留 10 分鐘」
  2. 再訂一次同樣時間 4 位 → 系統配到另一張桌
  3. 一直訂到那個時段客滿 → 顯示「這個時段已經客滿了」
  4. 訂 19:55（剛好接在第一筆之後）→ 可以訂（證明 < 不是 <=）
  5. 店家端訂位管理：看到明天的訂位清單
  6. 桌況總覽：種子資料裡今天 30 分鐘內要到的那筆訂位，它配到的桌是暖黃「預約保留」，格內「18:30 陳○君 4 位」； 用 Postman 對那張桌打現場開桌 → 409 TABLE_RESERVED
  7. 桌況總覽點一張別的空桌 → 開桌頁的「預約」頁籤上有數字，裡面列著那筆訂位（第 1 步訂的是明天，不在現在 −10～+30 分的清單裡）
  8. 按該列的「開桌」→ 直接開桌，人數自動帶入，桌況變「用餐中」；原本保留的那張桌變回空桌（訂位已轉 SEATED，保留自己消失）
  9. 回到開桌頁看別張桌 → 那筆訂位已經不在清單裡了（狀態已轉 SEATED）
  10. 另一筆 30 分鐘內要到的訂位：在 S-07 那一列看到「保留 A05」→ 按「報到開桌」→ S-07b 第一張是「A05・原保留桌」，其他保留中的桌不列 → 選 A05 → 開桌
  11. 再一筆保留中的訂位（陳怡君，A08）：先用那筆的 accessToken 打 DELETE /api/reservations/{id} → 409 CANCEL_DEADLINE_PASSED「訂位前 30 分鐘內請來電取消」（C-19 的取消按鈕也已停用）； 假裝客人來電：S-07 按「取消訂位」→ 二次確認「確定要取消 陳怡君 18:30 的訂位嗎？通常是客人來電取消。取消後 A08 會變回空桌，這筆訂位無法恢復。」→ 櫃檯代客取消：桌況 A08 立刻變回空桌，這一列變成「已取消」＋小字「店家代取消・小美」，C-19 這筆顯示「店家已代為取消」； 用 Postman 再打一次 POST /api/admin/reservations/{id}/cancel → 409 RESERVATION_NOT_CANCELLABLE 接著 S-07 切到明天：每一筆已確認的訂位都有「取消訂位」（不限保留窗內、不受期限）
  12. 一小時後的訂位 → S-07 那一列沒有報到按鈕，顯示灰字「xx:xx 起可報到」；直接打報到 API → 409 RESERVATION_TOO_EARLY
  13. 一筆訂位時間已過 10 分鐘 → S-07 那一列顯示「逾時未到」，只剩「登記候位」；直接打報到 API → 409 RESERVATION_EXPIRED
  14. 手動觸發 NO_SHOW 排程 → 那筆標記為 NO_SHOW，桌況完全沒變（保留在訂位後 10 分鐘就已經自己結束）
  15. 顧客端 C-19 取消第 2 步訂的那筆（明天的，離訂位時間還早）→ 成功，那個時段又可以訂了
  16. 第 8 步開的那桌到 S-03 結帳 → 呼叫 reservationRepo.existsOverlap(那筆原本配到的桌, 那筆的 start_time, end_time)（那張桌那段時間沒有別的訂位時）： 結帳前是 true，結帳後是 false，名額已經釋出。線上只能訂明天以後，所以這一步用 Repository 呼叫或 W2 的單元測試驗證，不是用 C-16c

有做預先點餐才加演（7.E1～7.E3）

  1. 訂位完成頁按「先點餐」→ 走一般菜單流程選好 → 送出，全程沒有付款頁
  2. 回「我的預約」→ 看得到預點內容 → 改成 3 份牛五花 → 再送出，內容更新
  3. 把系統時間調到用餐前一天 20:00 之後 → 改單停用，顯示請來電；取消訂位仍然可以按（取消期限是訂位前 30 分鐘，跟預點截止是兩條線）
  4. 櫃檯按「報到開桌」→ KDS 立刻跳出這張單，金色邊框 + 「預約優先」標籤，排在最前面
  5. 事先把某一項庫存調成 0 再報到 → 櫃檯畫面顯示「這 1 項已售完，已從單中移除」（問題 7 的取捨）
