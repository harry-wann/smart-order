模組 7：訂位

難易度 ★★★★☆　里程碑 第 4 週

這個模組在做什麼

客人線上選時間、選人數，系統自動配一張合適的桌。選完時段按下確認，訂位當場就成立—— 不必付款、不必等店家回電。訂位成立之後才問「要不要先點餐」，到店報到就直接開桌。

這個模組是「排程」技術的主戰場——區間重疊演算法、併發控制、以及定時任務都在這裡。

動線一句話

選日期時段人數 ──► 訂位成立 ──► 問要不要先點餐 ──┬──► 先點餐（進階）
                                              └──► 到店再點
                       ▲
                       └── 我的預約：事後回來補點、改單或取消（前一天 20:00 前）

訂位不收錢，預先點餐也不收錢。 餐點金額一律到店結帳時才算。 所以「調整餐點」「取消訂位」都只是改資料，沒有任何退款流程要寫—— 這是這一版最大的簡化，也是刻意的：金流分支一多，五個人的專題會在第 4 週卡死。 想練退款的話走延伸功能 7.E7（訂金），跟主流程切乾淨。

難易度為什麼是四顆星

難點 為什麼難
區間重疊判斷 一條判斷式，但很容易寫成 <= 導致誤判
併發控制 兩個人同時訂同一桌，跟超賣是同一類問題
狀態機複雜 四種狀態，加上排程會自動轉移

問題思考與解決思路

問題 1：怎麼知道這張桌這個時間有沒有空

情境 A03 桌今天已有訂位 18:00–19:55。客人想訂 19:00–20:55。

直覺會這樣寫 把一天切成固定時段（11:30 / 13:30 / 17:30 / 19:30 / 21:00），每桌每時段只能有一筆。用 UNIQUE(table_id, date, time_slot) 防重複。

  • 優點：實作最簡單
  • 缺點：客人只能選那五個時間；而且學不到真實訂位系統的模型

正確做法：區間重疊檢查 ← 我們選這個

存完整的開始與結束時間，判斷式是：

A.開始 < B.結束  且  B.開始 < A.結束

套進去：18:00 < 20:55 ✅ 且 19:00 < 19:55 ✅ → 重疊，不行。

SQL：

SELECT t.* FROM dining_table t
WHERE t.active = 1 AND t.reservable = 1 AND t.seats >= :partySize
  AND NOT EXISTS (
      SELECT 1 FROM reservation r
      WHERE r.table_id = t.id
        AND r.status = 'CONFIRMED'
        AND r.start_time < :newEnd
        AND :newStart   < r.end_time
  )
ORDER BY t.seats ASC
LIMIT 1;

三個細節：

  1. 用 < 不是 <=——18:00–19:55 和 19:55–21:50 是「剛好接續」，不算衝突。用 <= 會白白浪費位子。
  2. 排除已取消的——不然位子永遠訂不到。
  3. ORDER BY seats ASC = best-fit——2 個人不要佔 8 人桌，把大桌留給大團。

問題 2：清桌時間怎麼算進去

情境 上一組 19:40 走，下一組 19:40 到。服務生來不及收拾。

正確做法：把緩衝加進 end_time

end_time = start_time + 用餐時長(100 分) + 清桌緩衝(15 分)
18:00 + 100 + 15 = 19:55

存進資料庫時就存這個。判斷式完全不用改。

這是個很優雅的設計：把「業務規則」轉換成「資料」，演算法就不用知道緩衝的存在。

問題 3：兩個人同時訂同一桌

情境

客人 A：查詢 → A03 有空 ──→ 寫入訂位
客人 B：    查詢 → A03 有空 ──→ 寫入訂位
                                 兩筆都成功

跟 超賣 是同一類問題。

但這次不能用條件式 UPDATE，因為配桌要做區間計算，沒辦法壓成一句 SQL。

正確做法：悲觀鎖 + 資料庫約束（兩層保護）

@Transactional
public ReservationDto create(CreateReservationRequest req) {
    LocalDateTime start = req.startTime();
    LocalDateTime end   = start.plusMinutes(DINING_MINUTES + BUFFER_MINUTES);

    // ① 鎖住候選桌（依 id 排序，避免死鎖）
    List<DiningTable> candidates = tableRepo.findReservableBySeatsForUpdate(req.partySize());

    // ② 在鎖的保護下做重疊檢查 + best-fit
    DiningTable picked = candidates.stream()
        .filter(t -> !reservationRepo.existsOverlap(t.getId(), start, end))
        .findFirst()
        .orElseThrow(() -> new BusinessException("SLOT_UNAVAILABLE", "這個時段已經客滿了", CONFLICT));

    return toDto(reservationRepo.save(Reservation.of(picked, start, end, req)));
}

-- ③ 資料庫層的保險
CREATE UNIQUE INDEX uk_reservation_table_start ON reservation (table_id, start_time);

「應用層 + 資料庫層」雙重保護是正確的做法。就算程式有 bug，資料庫也擋得住。

問題 4：訂了位沒來怎麼辦

情境 19:00 的訂位，19:25 了人還沒到。桌子空著，後面的客人乾等。

直覺會這樣寫 櫃檯自己記得，過一陣子手動標記。

為什麼不好 尖峰時櫃檯忙不過來，一定會忘記。而且「過了多久算 NO_SHOW」沒有一致標準。

正確做法：排程自動處理

@Scheduled(cron = "0 */5 * * * *", zone = "Asia/Taipei")
public void markNoShow() {
    try {
        LocalDateTime deadline = LocalDateTime.now().minusMinutes(20);
        int n = reservationService.markNoShowBefore(deadline);
        if (n > 0) log.info("{} 筆訂位標記為 NO_SHOW", n);
    } catch (Exception e) {
        log.error("NO_SHOW 檢查失敗", e);
    }
}

標記為 NO_SHOW 後，桌位自動轉回 AVAILABLE，現場客人就能用了。

★ 一定要配一支手動觸發的 API，不然 demo 時你要真的等 20 分鐘。

@PostMapping("/api/admin/scheduler/mark-no-show")
@PreAuthorize("hasRole('MANAGER')")
public Map<String, Object> trigger() {
    return Map.of("marked", reservationService.markNoShowBefore(LocalDateTime.now().minusMinutes(20)));
}

做法：排程方法只負責呼叫 Service + 記日誌，邏輯全在 Service，這樣排程和手動 API 共用同一段程式碼。

問題 5：取消的訂位還算不算佔位

情境 客人取消了 A03 桌 19:00 的訂位。別人現在訂得到嗎？

如果 status 沒納入判斷 取消的訂位還在表裡，重疊檢查會撞到它 → 位子永遠訂不到。

但如果直接刪掉 沒有紀錄，無法統計取消率，客人也查不到自己取消過。

正確做法：保留紀錄，但查詢時排除

AND r.status = 'CONFIRMED'     -- 只有這一種算佔位

CANCELLED / NO_SHOW / SEATED（已入座，桌況改由 dining_session 管）都不算。

原本這裡是 IN ('PENDING', 'CONFIRMED')。 PENDING 的存在理由是舊流程的 「先建訂位、預付成功才確認」；現在選完時段就直接成立，沒有任何路徑會產生 PENDING， 所以這個狀態整個拿掉了。留著一個永遠不會出現的狀態，只會讓後面接手的人一直猜它什麼時候用。 之後若要做 7.E7 訂金，再把它加回來。

注意唯一約束的衝突：UNIQUE(table_id, start_time) 會讓「取消後同一時段再訂」失敗。

兩種解法：

  • A：取消時把 table_id 設為 NULL（保留紀錄但釋放約束）
  • B：取消的搬到 reservation_cancelled 歷史表

我們選 A，比較單純。

問題 6：預先點餐的資料要存在哪裡

情境 客人三天前就先點好了鍋底跟牛五花。這時候還沒有桌、沒有開桌、沒有 dining_session。

直覺會這樣寫 訂位時就開一筆 dining_session，把 order_ticket 寫進去，reservation 用 preorder_session_id 指過去。反正點餐那一整套 API 都能重用。

為什麼不好

  1. dining_session 的語意壞掉——它現在的定義是「一次實際用餐（＝一張帳單）」。 資料庫裡會躺著一堆還沒發生、甚至永遠不會發生（NO_SHOW）的 session， 「今天有幾桌在用餐」這種查詢全部要多加條件過濾。
  2. order_ticket 送出即定案——單一旦成立就進 KDS、就扣庫存、就不能改。 但預點的單在報到前必須能反覆修改，這兩個語意直接打架。

正確做法：預點自己一張表，報到時才轉成正式的單 ← 我們選這個

reservation
  └── reservation_preorder_item        （可以隨便改，改到前一天 20:00）
        └── reservation_preorder_option

        ── 報到開桌時做一次轉換 ──►

dining_session
  └── order_ticket (is_preorder = 1)   （成立即定案，進 KDS）
        └── order_item
              └── order_item_option

兩邊欄位幾乎一樣（都存名稱與價格快照），轉換就是逐筆複製。價格照抄預點當下的快照，不重新取價—— 客人三天前看到多少就是多少，中間調價不追溯，這是對客人也對自己都好解釋的規則。

順帶解決一件事：因為預點不是正式的單，「調整餐點」就只是改自己的表， 不用去碰已經進 KDS 的東西，也不用發 WebSocket 通知廚房。

那 API 怎麼設計？ 用 PUT /api/reservations/{id}/preorder 整批覆蓋， 不要做「加一筆／減一筆」的部分更新。前端本來就有購物車，把整份送上來最直覺； 後端一句 deleteByReservationId 再重建，不用寫 diff 邏輯； 重送同一份結果也一樣（冪等）。「新增預點」和「調整預點」是同一支 API。

問題 7：預先點餐什麼時候扣庫存

情境 客人三天前預點了 2 份牛五花。現在要不要馬上把庫存扣掉？

直覺會這樣寫 預點的時候就扣，跟現場點餐一樣。

為什麼不好 庫存會被鎖死三天。而且客人 NO_SHOW 的話，那 2 份就白白鎖了一整晚—— 火鍋店的肉品是當日備料，這等於是拿今天的庫存去擋三天後的單。

正確做法：報到開桌、轉成正式單的那一刻才扣

預點時    ：只寫 reservation_preorder_item，不碰庫存
報到開桌時：建立 order_ticket → 逐項扣庫存 → 扣不到的品項標記出來

代價要講清楚：客人到店時，預點的某一項可能已經賣完了。 所以報到 API 不能無聲失敗，要回一份「這幾項庫存不足」的清單給櫃檯畫面， 由櫃檯當面跟客人講。這不是 bug，是這個設計選擇的已知取捨，驗收時要能講得出來。

// 報到開桌：轉單 + 扣庫存，扣不到的挑出來回報
SeatResult seat(Long reservationId) {
    // ...建立 dining_session 之後
    List<String> soldOut = new ArrayList<>();
    for (ReservationPreorderItem pre : preorderRepo.findByReservationId(reservationId)) {
        if (inventoryService.tryDeduct(pre.getMenuItemId(), pre.getQuantity())) {
            ticket.addItem(OrderItem.copyOf(pre));   // 價格快照照抄
        } else {
            soldOut.add(pre.getItemNameSnapshot());
        }
    }
    return new SeatResult(session, soldOut);
}

只有基礎功能（不做 7.E1）的話，這一整段不存在——報到就只是開桌而已。

驗收 Demo 腳本

基礎（一定要演完）

  1. 顧客端訂位：選明天 18:00、4 位 → 按下確認，當場跳出「訂位完成」與預約編號（不經過付款頁）
  2. 再訂一次同樣時間 4 位 → 系統配到另一張桌
  3. 一直訂到那個時段客滿 → 顯示「這個時段已經客滿了」
  4. 訂 19:55（剛好接在第一筆之後）→ 可以訂（證明 < 不是 <=）
  5. 店家端訂位管理：看到明天的訂位清單
  6. 桌況總覽點一張空桌 → 開桌頁的「預約」頁籤上有數字，裡面列著這筆訂位
  7. 按該列的「開桌」→ 直接開桌，人數自動帶入，桌況變「用餐中」
  8. 回到開桌頁看別張桌 → 那筆訂位已經不在清單裡了（狀態已轉 SEATED）
  9. 另一筆訂位過時未到 → 手動觸發 NO_SHOW 排程 → 標記為 NO_SHOW
  10. 取消一筆訂位 → 那個時段又可以訂了

有做預先點餐才加演（7.E1～7.E3）

  1. 訂位完成頁按「先點餐」→ 走一般菜單流程選好 → 送出，全程沒有付款頁
  2. 回「我的預約」→ 看得到預點內容 → 改成 3 份牛五花 → 再送出，內容更新
  3. 把系統時間調到用餐前一天 20:00 之後 → 改單與取消都停用，顯示請來電
  4. 櫃檯按「報到開桌」→ KDS 立刻跳出這張單，金色邊框 + 「預約優先」標籤，排在最前面
  5. 事先把某一項庫存調成 0 再報到 → 櫃檯畫面顯示「這 1 項已售完，已從單中移除」（問題 7 的取捨）
