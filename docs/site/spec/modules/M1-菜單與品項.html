模組 1：菜單與品項

難易度 ★★★☆☆　里程碑 第 1 週要能查、第 3 週後台能改

這個模組在做什麼

管理「店裡賣什麼」。分類、品項、價格、照片，還有每道菜可以怎麼客製（份量、辣度、加點）。

顧客端從這裡讀資料畫出菜單；店家端從這裡改價格、上下架、標售完。

它是整個系統的地基——沒有菜單，客人連東西都點不了。所以它是第 1 週第一個要打通的模組。

難易度為什麼是三顆星

CRUD 本身只有一顆星。難的是選項群組模型：

  • 「份量」「辣度」「加點配料」看起來是三種不同的東西，其實是同一個機制
  • 如果用「在 menu_item 上加欄位」的方式做，加到第三種就做不下去
  • 多對多關聯（一個群組掛在多個品項上）對新手是個門檻

做對了，之後所有客製化需求都不用改程式。做錯了，第 3 週要重寫。

問題思考與解決思路

問題 1：「份量」「辣度」「加點」要怎麼存？

情境 牛五花要能選半份／全份（價差 80）、原味／炙燒（價差 20）、還能加蔥花蒜泥（各 10 元，可複選）。

直覺會這樣寫 在 menu_item 上加欄位：

menu_item (
  has_size BOOLEAN, half_price DECIMAL, full_price DECIMAL,
  has_doneness BOOLEAN, ...
)

為什麼會壞 第三種需求出現時你會發現：欄位無限增加、每個品項的選項都不一樣、加一種新選項要改程式加欄位、而且「可複選」根本表達不出來。

正確做法：選項群組模型

option_group「份量」 min=1 max=1
  ├─ option_value「半份」 +0
  └─ option_value「全份」 +80

option_group「加點配料」 min=0 max=5
  ├─ 加蔥花 +10
  ├─ 加蒜泥 +10
  └─ 加香菜 +10

menu_item_option_group（中間表）
  menu_item_id ↔ option_group_id + sort_order

一個模型解決全部三種需求。min_select 和 max_select 兩個數字就決定了「必選／選填」「單選／複選」。

延伸 「辣度」這個群組建立一次，可以掛在 20 個品項上。改一次，20 個品項全部生效。

面試會問：「你怎麼設計商品規格？」這題答得好會加很多分。

問題 2：鴛鴦鍋要不要另外建表？

情境 共鍋店有單味鍋，也有鴛鴦鍋（一鍋兩味）。

直覺會這樣寫 建一張 pot 表，記錄「這桌有幾個鍋、每個鍋什麼湯底、鴛鴦的話兩個湯底各是什麼」。

為什麼不好 多一張表、多一套 CRUD、多一層關聯。而且「點菜要指定下哪一鍋」在真實店家根本不會發生——菜端上桌，客人自己決定下哪鍋。

正確做法：用現有的選項群組

menu_item「麻辣鍋底」      price 480, is_soup_base=true
menu_item「酸菜白肉鍋底」  price 420, is_soup_base=true
menu_item「昆布鍋底」      price 380, is_soup_base=true
menu_item「鴛鴦鍋底」      price 0,   is_soup_base=true
  ├─ option_group「左鍋湯底」 min=1 max=1 → 麻辣 +260 / 酸菜 +230 / 昆布 +210
  └─ option_group「右鍋湯底」 min=1 max=1 → 同上

零額外資料表。 鴛鴦價 = 左半 + 右半（各約單鍋的 55%），這也是真實店家的算法。想點兩鍋就點兩份。

問題 3：改了價格，三個月前的帳單會變嗎？

情境 老闆把牛五花從 280 調到 320。

直覺會這樣寫 order_item 只存 menu_item_id，要顯示時再去 join 菜單表拿名稱和價格。

為什麼會壞 歷史帳單的金額會跟著變成 320。 客人三個月前明明付 280，報表卻顯示 320。

正確做法：存快照

order_item (
  menu_item_id BIGINT,               -- 還是要，供統計與推薦用
  item_name_snapshot VARCHAR(100),   -- 下單當下的名稱
  unit_price_snapshot DECIMAL(10,2)  -- 下單當下的價格
)

這是少數「故意重複存資料」是正確的情況。

延伸 選項也要存快照（order_item_option 的 group_name_snapshot / value_name_snapshot / price_delta），否則刪掉一個選項後，歷史訂單會顯示空白。

問題 4：售完要怎麼讓所有人立刻看到？

情境 牛五花剛剛被最後一桌點完。此時有五桌客人正在看菜單。

直覺會這樣寫 菜單 API 每次都查一次資料庫，前端每 3 秒重新抓菜單。

為什麼不好 五桌 × 每 3 秒 = 每分鐘 100 次全菜單查詢，而且客人可能已經把它加進購物車了。

正確做法：WebSocket 推播 + 送出時再驗一次

  1. 庫存歸零時，後端推 MENU_SOLD_OUT 到 /topic/menu
  2. 所有正在點餐的裝置收到，把那個品項標成售完
  3. 但這還不夠——已經在購物車裡的怎麼辦？
  4. 所以送出點餐時後端一定要再檢查一次，不夠就回 409

前端的顯示是體驗，後端的檢查才是真相。

六週切分

週 這個模組要交出什麼
W1 Flyway 建好 menu_category / menu_item / option_group / option_value / 中間表；GET /api/menu/categories 和 GET /api/menu/items 能回傳種子資料；顧客端 React 能把菜單列出來（walking skeleton）
W2 GET /api/menu/items/{id} 回傳完整選項群組；必選驗證邏輯；顧客端品項詳情頁能選規格
W3 店家端菜單管理後台（品項 CRUD、上下架、快速下架開關）；選項群組管理
W4 飲食標示、免費續加品項；人氣推薦查詢（GROUP BY + SUM）
W5 售完狀態的 WebSocket 推播；菜單快取（選配）
W6 不寫新功能。檢查售完顯示、圖片載入、RWD

常見卡關

卡點 解法
多對多關聯寫不出來 不要用 @ManyToMany，把中間表做成 Entity（見 JPA 關聯對應）
回傳品項詳情時噴 lazy 錯誤 在 Service 裡轉 DTO，或用 JOIN FETCH（見 Entity 與 DTO）
選項價差算錯 用 BigDecimal 不要用 double；單價 = 基礎價 + 所有選項價差
種子資料太少，看不出效果 60 個品項、5 個選項群組是最低限度

驗收 Demo 腳本

  1. 店家端改一個品項價格 → 顧客端重新整理 → 新價格生效
  2. 店家端把一個品項下架 → 顧客端看不到了
  3. 顧客端點「鴛鴦鍋底」→ 左右鍋各選一個湯底 → 價格正確累加
  4. 點「牛五花」→ 不選份量 → 加入購物車按鈕是停用的
  5. 一個庫存 0 的品項顯示灰階 + 售完標籤，且點不下去
