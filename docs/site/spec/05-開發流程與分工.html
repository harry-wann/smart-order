05 開發流程與時程

工作分配尚未決定。 等八大模組的規格都定稿後再分。 本文件先定下協作規範與六週時程，這兩件事跟誰做什麼無關。

1. 工作分配：原則先講，人選後定

1.1 我們的分工方法：以功能切分

一個人負責一個功能的前後端，從資料表 → API → 畫面全部自己走一遍。 不切前端組／後端組。

水平切（前端組／後端組） 功能切（我們用這個）
一個人做什麼 所有功能的某一層 一個功能的所有層
學到什麼 一層很熟，其他層沒碰過 一條完整的路
介面對不上時 「一定是你 API 的問題」 自己兩邊都改
面試能講什麼 「我負責寫前端」 「我做了訂位，遇到了區間重疊和併發問題，我這樣解」
代價 學習成本低 每個人前後端都要學

代價是真的存在的：每個人都要學 React、也要學 Spring Boot。這正是為什麼 技術總表 安排了必修八頁——那是全員的共同語言，先讀完再開工。

1.2 分配的時候要注意什麼

等規格定稿後分配時，建議照這幾條：

  1. 難易度要平均。八大模組的難易度是 ★★☆☆☆ 到 ★★★★☆，不要讓一個人拿到兩個四星模組
  2. 相依性高的模組給同一個人或相鄰的人。例如 M3 點餐和 M5 庫存共用「送出點餐」那段交易，分開做會很痛
  3. 技術地基（L0）要有人專門負責，而且他的功能模組要少一點——因為他卡住全隊都會卡住
  4. 每個模組要有第二個人能 review，尤其是 M3、M5、M7 這三個有併發問題的
  5. 共用檔案要有唯一負責人（見 §2.4）

1.3 目前已知的模組難易度

模組 難易度 主要難點
M1 菜單與品項 ★★★☆☆ 選項群組的多對多模型
M2 桌位開桌與候位 ★★★☆☆ 開桌的悲觀鎖、狀態機
M3 點餐與服務鈴 ★★★★☆ 交易邊界、防超賣、WebSocket
M4 出菜看板 ★★★☆☆ 狀態推導、即時推播
M5 庫存 ★★★★☆ 防超賣、多執行緒測試
M6 結帳 ★★☆☆☆ 金額精度、金額比對與列鎖
M7 訂位 ★★★★☆ 區間重疊演算法、併發控制、排程
M8 會員 ★★★☆☆ Spring Security 雙軌認證、JWT
技術地基 L0 ★★★☆☆ Flyway、共用層、環境、部署

2. Git 協作規範

不熟悉的人先看 Git 是什麼、分支與合併、GitHub 與 PR。

2.1 分支策略

main          ← 隨時可部署。只接受來自 develop 的 PR
  └ develop   ← 整合分支
      ├ feature/menu-option-group
      ├ feature/order-submit
      ├ feature/reservation-overlap
      └ fix/kds-websocket-reconnect

三條鐵律

  1. 禁止直接 push 到 main 和 develop（GitHub 設 branch protection）
  2. 分支命名：feature/<模組>-<簡述>、fix/<簡述>、docs/<簡述>
  3. 每個 PR 至少 1 人 review，且 CI 必須綠燈才能合併

2.2 Commit 訊息

feat: 新增送出點餐 API
fix: 修正 KDS 斷線後未重抓資料
docs: 更新 API 規格的 WebSocket 事件表
refactor: 抽出金額計算邏輯
test: 補上防超賣的多執行緒測試
chore: 升級 Spring Boot 版本

2.3 最容易出事的地方

風險 預防
兩人同時寫 Flyway migration，版本號撞號 指定唯一負責人，其他人開 issue
有人改了已合併的 migration Flyway 會拒絕啟動。已 push 的絕不修改，寫新的一支
package-lock.json 衝突 不要手動解，刪掉重跑 npm install
Entity 改欄位沒通知 PR 標題加 [BREAKING]，群組 @所有人
有人 git push -f 到共用分支 禁止
密碼被 commit 上去 第一天就設好 .gitignore

3. 六週時程

圖見 06-圖表總覽 的甘特圖。每個模組的細節見各模組頁的「六週切分」。 以下只寫「本週要交出什麼」，不指定誰做。

第 0 週（現在～開工前）

  • 全員讀完 00-架構分層與技術選型 與 技術總表 的必修八頁
  • 八大模組規格定稿 → 開會分配工作（原則見 §1）
  • 建 GitHub repo、設定分支保護、指定共用檔案的 owner
  • 每人裝好：JDK 17、IntelliJ IDEA、Node 20、Docker Desktop、DBeaver
  • 每人的機器都能跑起 Hello World Spring Boot + Vite React

第 1 週：基礎建設

要交出什麼

  • 全員做完 React 基礎練習（官方繁中「快速入門」+「描述 UI」），約 2 天
  • Spring Boot 骨架、Docker Compose（MySQL + Redis）
  • 統一回應格式、全域例外處理、CORS、Swagger
  • Flyway V1～V7 建表 + 種子資料第一版 ← 最高優先，別人才有資料可用
  • 菜單 Entity / Repository、GET /api/menu/categories、GET /api/menu/items
  • Spring Security 基礎設定 + 員工登入 API
  • Vite + Tailwind 專案初始化、共用元件雛形
  • Figma 主視覺定調（用 12-AI UI 工具與提示詞）

★ 里程碑（週五驗收）：手機瀏覽器打開顧客端，看到從後端 API 抓下來的菜單。 這叫 walking skeleton。它很醜沒關係，但整條路必須是通的：React → fetch → Spring Boot → JPA → MySQL。

第 2 週：點餐核心

  • 選項群組 API、品項詳情（含選項）
  • POST /orders 送出點餐（交易 + 防超賣 + 快照 + 鍋底規則 + 選項驗證）
  • GET /orders 本桌訂單、KDS 查詢 API
  • 開桌／加入／用餐狀態 API（含悲觀鎖）、用餐權杖 filter
  • 金額計算 Service
  • 顧客端：菜單頁（鍋底是其中一個分類頁籤）、品項詳情與選項、購物車
  • 店家端：登入、桌況總覽頁
  • CI、部署技術驗證（先跑一次 Hello World 上線，確認平台支援 WebSocket）

里程碑：用 Postman 完成「櫃檯開桌 → 掃碼加入 → 送出點餐 → 查詢本桌訂單」。

第 3 週：主流程打通 ★最關鍵

  • WebSocket 設定與握手驗證、五個頻道
  • KDS 推播、出菜勾選、狀態自動推導
  • 櫃檯結清（服務費、expectedTotal 金額比對、跟送出點餐搶同一把列鎖）、SESSION_CLOSED 推播
  • 顧客端：掃碼進入頁、本桌訂單頁 + 即時同步、C-04 的「已結帳」狀態
  • 店家端：KDS 看板（深色、大字）、桌位詳情（含結帳區）、菜單管理後台

★ 本週是整個專案最關鍵的里程碑： 用手機完整走一次「掃碼 → 加入 → 點餐（含鍋底）→ 送出 → 另一支手機 1 秒內看到 → 廚房收到 → 勾選出餐 → 手機看到已出餐 → 櫃檯結清 → 手機看到已結帳」。

這條路通了，這個專題就算成功了一半。 第 3 週結束還沒通的話，第 4 週不要開新功能，先把它補完。

第 4 週：訂位、候位、服務鈴

  • 訂位：區間重疊檢查 + 悲觀鎖 + best-fit 配桌、可訂時段查詢、取消、報到開桌
  • 服務鈴（後端表 + 推播 + 顧客端按鈕 + 櫃檯面板）
  • 候位登記、叫號、報到、過號
  • 一鍵開桌：GET /api/admin/tables/available + S-07b／S-10b 選桌對話框；訂位保留 10 分鐘（RESERVATION_EXPIRED）
  • 人氣推薦 API、出餐順序建議
  • 顧客端：訂位頁面（C-16c 選時段 → C-18 訂位完成）、服務鈴面板
  • 店家端：候位管理、訂位管理後台

里程碑：線上訂位 → 自動配到合適的桌 → 到店報到 → 選一張空桌開桌；按服務鈴櫃檯即時跳出。

第 5 週：會員、庫存、排程、部署 ★

  • 庫存：售完自動下架與推播（補貨、低水位、異動紀錄的 S-09 是進階 A3）
  • 會員：OTP + JWT + 會員中心 + 訂位自動帶入（消費歷史、匿名轉會員是進階）
  • 九支排程任務 + 對應的手動觸發 API（7.10 空號；跟著進階走的三支見 00 §3.4）
  • 單元測試補到 15～20 個
  • 前端三態處理、RWD、iOS Safari 實機測試
  • UI 一致性檢查（把 42 張畫面並排看，進階的 8 張另外標出來）
  • ★ 部署上線

里程碑：線上 demo 網址可以完整操作。 第一次部署一定會卡 CORS、環境變數、SPA 路由、WebSocket 的 wss://——絕對不能留到第 6 週。

第 6 週：收斂（★不寫新功能）

天 做什麼
一～三 修 bug、補錯誤流程、跨瀏覽器測試、寫防超賣的多執行緒測試
四 README（含線上連結與測試帳號）、架構圖、功能 GIF
五 上線最終版、demo 腳本、備援方案
六～日 簡報製作與演練（至少完整演練 3 次）

鐵則：第 6 週一行新功能都不要寫。 每年都有組在最後一週加功能然後 demo 當天炸掉。

備援清單（demo 當天保命用）： - 錄好一段 3 分鐘的完整操作影片 - 本機也能跑（docker compose up 就能起） - 資料庫備份一份乾淨的 demo 資料 - reset-demo.sh 在 demo 前 10 分鐘跑一次 - 開始前 5 分鐘先打開網站叫醒免費方案的服務 - 手機和電腦都先連好網路並測試過

4. 每日／每週節奏

時間 活動 時長
每天早上 站立會：昨天做了什麼／今天要做什麼／卡在哪 15 分鐘，站著講
每天結束 各自 push 到 feature 分支（不要囤積本機程式碼） —
每週三 中期檢查：本週里程碑會不會達成？不會的話現在就砍範圍 30 分鐘
每週五 收斂會：合併 PR、整體跑一次、更新 02-需求規格 的狀態欄 60 分鐘

「卡住 30 分鐘就要開口」原則：新手最常見的時間殺手是一個人默默卡 3 小時。規定卡住 30 分鐘沒進展就在群組貼出來。這條規則能省掉整個專案 20% 的時間。

5. 完成定義（DoD）

一個功能要標成完成，必須全部符合：

  • 已合併到 develop，且 develop 能正常啟動
  • CI 綠燈
  • API 出現在 Swagger 上，參數說明正確
  • 前端處理三種狀態：載入中、空資料、錯誤
  • 手機 375px 不破版（顧客端功能）
  • 至少一位組員 review 過 PR
  • 對應模組頁的驗收條件逐條測過
  • 沒有殘留的 console.log / System.out.println
  • 02-需求規格.md 的狀態欄已更新

6. 風險與應對

風險 可能性 影響 應對
React 學習曲線導致前端落後 高 高 第 1 週結束檢查點；落後則店家端改 Thymeleaf
送出點餐的交易 + 防超賣寫錯 中 高 一定要有第二個人 review；第 6 週寫多執行緒測試
WebSocket 部署後連不上 中 高 第 2 週就做部署技術驗證
功能切分後有人前後端都不熟，整個卡住 高 高 必修八頁先讀完；卡住 30 分鐘就開口；相依模組安排相鄰
第一次部署卡住 高 中 提前到第 5 週；第 2 週先驗證
Git 衝突導致程式碼遺失 中 高 分支保護、禁 force push、每天 push
Demo 當天網路或服務掛掉 中 高 備援清單（§3 第 6 週）
範圍蔓延 高 高 進階功能（A1～A6）一律不排進六週時程；要加必須先砍一個
種子資料沒做，推薦報表空白 中 中 第 1 週最高優先

7. 給整合負責人的三個提醒

不管最後誰擔任這個角色，這三件事要有人做：

  1. 主要工作不是寫最多程式碼，是讓其他四個人不被卡住。 把共用層做好、環境弄順、衝突解掉，比自己多寫一個功能有價值。
  2. 第 3 週結束時要誠實評估。 如果主流程還沒通，立刻砍掉第 4、5 週的一半功能。砍範圍不丟臉，交不出來才丟臉。
  3. 每週五一定要整體跑一次。 不要等到第 6 週才第一次把所有人的東西合起來——那時候才發現介面對不上就來不及了。
