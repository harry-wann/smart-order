05 開發流程與時程

工作分配（基礎功能）切成五個工作包 A～E，見 §1.4，人選開會認領；技術地基 L0 由 Harry 負責，不列入工作包。 進階 A1～A7 等基礎全綠燈後再分。開發順序是後端先出 stub、前端一律接真的 API，見 §1.4.4 與 §3。

1. 工作分配

1.1 我們的分工方法：以功能切分

一個人負責一個功能的前後端，從資料表 → API → 畫面全部自己走一遍。 不切前端組／後端組。

水平切（前端組／後端組） 功能切（我們用這個）
一個人做什麼 所有功能的某一層 一個功能的所有層
學到什麼 一層很熟，其他層沒碰過 一條完整的路
介面對不上時 「一定是你 API 的問題」 自己兩邊都改
面試能講什麼 「我負責寫前端」 「我做了訂位，遇到了區間重疊和併發問題，我這樣解」
代價 學習成本低 每個人前後端都要學

代價是真的存在的：每個人都要學 React、也要學 Spring Boot。這正是為什麼 技術總表 安排了必修八頁——那是全員的共同語言，先讀完再開工。

1.2 分配的時候要注意什麼

等規格定稿後分配時，建議照這幾條：

  1. 難易度要平均。八大模組的難易度是 ★★☆☆☆ 到 ★★★★☆，不要讓一個人拿到兩個四星模組
  2. 相依性高的模組給同一個人或相鄰的人。例如 M3 點餐和 M5 庫存共用「送出點餐」那段交易，分開做會很痛
  3. 技術地基（L0）由 Harry 專門負責，不算進工作包——他卡住全隊都會卡住，所以範圍另外列（§1.4.1）
  4. 每個模組要有第二個人能 review，尤其是 M3、M5、M7 這三個有併發問題的
  5. 共用檔案要有唯一負責人（見 §2.4）

1.4.4 開發順序：先前端、後後端

假資料放在後端，前端一律當成真的（2026-09-20 定案）

前端沒有任何 mock 機制——沒有 mock/ 資料夾、沒有 VITE_USE_MOCK 開關、 也沒有假的 WebSocket。畫面一律打真的 HTTP、連真的 WebSocket。

需要假資料的時候，假在後端：API 先寫成回傳寫死的 JSON、不真的查資料庫， 之後再把實作填進去。對前端來說那就是一支正常的 API，後端換成真實查詢時前端一行都不用改。

為什麼這樣選：

  • 前端不用寫兩套（一套 mock、一套真的），也不會有「mock 跟 04 對不上、換的時候要改畫面」這個經典問題——那原本是 §5 風險表上的高風險項
  • API 合約從第一天就被真的跑過一次：CORS、權杖、錯誤碼、JSON 欄位名、日期格式全是真的，不會到整合那天才發現對不上
  • 不用擔心假資料混進 production build
  • 三態裡的「錯誤」可以請後端真的回 409，比前端自己假造可信

規矩（五包都一樣）：

規矩 做法
格式照 04 後端回傳的欄位、型別、錯誤碼逐字照 04-API規格 的範例，不自己發明；04 沒寫的先問 Harry 再補進 04
放哪裡 後端各模組的 Controller。前端只有 src/services/api/<模組>.js 一層，不分真假
假到什麼程度 Controller 直接 return 寫死的 DTO，不碰 Repository。之後把查詢填進去，回傳型別不變
模擬延遲 要看骨架屏就在後端 Thread.sleep(300~800)，不要在前端假造；填實作時記得拿掉
模擬錯誤 錯誤態（CART_EMPTY、BILL_CHANGED、TABLE_RESERVED、CANCEL_DEADLINE_PASSED）請後端真的回 400／409，前端才測得到真的錯誤處理路徑

做什麼 什麼時候
L0（Harry） Spring Boot 骨架、Docker Compose、Flyway＋種子、統一回應、全域例外、CORS、Swagger 第 1 週開工前就要能跑
各包 A～E 自己模組的 API 自己寫：第 1 週先出 stub，第 3～4 週填實作 見 §3

stub 是什麼：簽名是真的、裡面是假的空殼函式。

java @GetMapping("/menu") public List<MenuItemDto> getMenu() { // 第 1 週：回寫死的，不碰 Repository return List.of(new MenuItemDto(101, "麻辣鍋", 180, false)); // 第 3 週：改成 menuRepository.findAll()，網址與回傳型別完全不變 }

重點是外面從第一天就是最終版——網址、回傳型別、欄位名、錯誤碼都照 04。 填實作的時候前端一行都不用改。

★ 這條流程的單點風險：所有人第一天就要打後端， 所以 L0 的骨架沒好，五個人一起卡住。這是新流程最需要盯的地方。

資料夾長這樣（2026-09-20 定案，資料夾已經建好在 frontend/src/services/）：

src/services/          ← 跟外面講話的東西全部放這裡，元件不直接 fetch 也不直接 new WebSocket
│
├── api/               ← HTTP：一問一答
│   ├── client.js          fetch 封裝。權杖、錯誤碼、base URL 只寫在這一個地方
│   └── <模組>.js          menu.js / cart.js / tables.js …畫面唯一會呼叫的層
│
└── realtime/          ← WebSocket：後端主動推
    └── socket.js          連線、重連、訂閱頻道

哪個東西放哪裡，判斷方法是「誰先開口」：

情況 放哪 例子
前端問一次、後端答一次 services/api/ 拿菜單、加入購物車、送出點餐、結帳
後端主動推給前端 services/realtime/ 同桌有人加了什麼、KDS 來新單、桌況變了、服務鈴

兩邊常常配成一對：收到 CART_UPDATED 推播後，不要直接把推播的 payload 塞進畫面， 而是回頭呼叫 api/cart.js 重抓一次。推播只當「該更新了」的信號，資料以 API 為準， 這樣兩支手機看到的內容一定一致。

為什麼多包一層 services/：frontend/src/ 的資料夾結構（commit 9bd1a58）建的是 services/，這份文件原本寫的是 src/api/ 與 src/realtime/。2026-09-20 決定兩者合併—— services/ 保留當資料層的總稱，底下再用 api/ 與 realtime/ 把兩個概念分開。 好處是 src/ 頂層少一個資料夾，而且「所有對外通訊都在 services/ 底下」這句話講得完整。 不要再把 api/ 或 realtime/ 搬回 src/ 頂層。

2. Git 協作規範

不熟悉的人先看 Git 是什麼、分支與合併、GitHub 與 PR。

2.1 分支策略

main          ← 隨時可部署。只接受來自 develop 的 PR
  └ develop   ← 整合分支
      ├ feature/menu-option-group
      ├ feature/order-submit
      ├ feature/reservation-overlap

三條鐵律

  1. 禁止直接 push 到 main 和 develop（GitHub 設 branch protection）

3. 六週時程

第 0 週（現在～開工前）

第 1 週：各包 stub API ＋第一批畫面

要交出什麼

  • 全員做完 React 基礎練習（官方繁中「快速入門」+「描述 UI」），約 2 天
  • 顧客端手機殼版型與共用元件雛形（B）、店家端側欄＋主區版型（D）

    前端專案本身已經建好了（frontend/，Vite + Tailwind + 設計系統 token + .env + services/ 骨架都在裡面）， 顧客端與店家端是同一個專案，用 src/features/customer/ 與 src/features/admin/ 分開，不是兩個專案。 所以第 1 週 B 與 D 做的是各自那一側的版型，不是初始化。

  • 各包寫自己模組的 stub API（§1.4.4）：回寫死的 DTO、不碰 Repository，欄位與錯誤碼逐字照 04-API規格
  • 各包第一批畫面接上自己的 stub：C-00、C-01、C-04、C-05、C-06、C-07、C-12、C-12b、C-13、C-16c、C-18、S-02、S-02b
  • L0（Harry，開工前就要好）：Spring Boot 骨架、Docker Compose、Flyway V1～V7 建表 + 種子資料、統一回應、全域例外處理、CORS、Swagger
  • Figma 對照確認：每個人打開自己工作包顏色的畫面，確認看得懂說明卡

里程碑（週五驗收）：手機瀏覽器打開顧客端，從入口頁一路點到菜單、購物車；店家端打開桌況總覽。 資料是後端 stub 回的寫死 JSON，但整條路徑是真的——React → fetch → Spring Boot → 回應。

第 2 週：畫面全部做完

  • 其餘基礎畫面接上各自的 stub：C-04b、C-04c、C-08、C-14、C-16、C-16b、C-19、C-21、S-01、S-02c、S-02d、S-03、S-03b、S-04、S-05、S-06、S-07、S-07b、S-08、S-10、S-10b、S-11

第 3 週：後端核心——stub 填成真的

  • 共用購物車 API（/me/cart 四支）、POST /orders 送出整桌購物車（交易 + 防超賣 + 快照 + 鍋底規則 + 選項驗證 + 清空購物車 + CART_EMPTY）、金額計算 Service
  • 會員 OTP、限流、補資料、會員中心 API
  • 區間重疊 + 單元測試、可訂時段、建立訂位 API
  • L0（Harry）：WebSocket 設定與握手驗證、五個頻道、頻道權限

里程碑：顧客端的菜單、購物車、送出點餐已經是真的查詢，不再是寫死的 JSON；用 Postman 完成「開桌 → 兩支裝置加入 → 各自加入購物車 → 送出整桌點餐 → 查詢本桌訂單」。

第 4 週：主流程打通 ★最關鍵

  • KDS 查詢與推播、出菜勾選、狀態自動推導、C-08 即時

  • 同桌購物車推播 CART_UPDATED（帶 optionSummary）、售完推播、取消單品

  • 各包把剩下的 stub 填成真的實作

★ 本週是整個專案最關鍵的里程碑： 用手機完整走一次「掃碼 → 加入 → 加進購物車（另一支手機看到誰加了什麼）→ 點餐（含鍋底）→ 送出整桌點餐 → 另一支手機 1 秒內看到 → 廚房收到 → 勾選出餐 → 手機看到已出餐 → 櫃檯結清 → 手機看到已結帳」，全程都是真實資料。

這條路通了，這個專題就算成功了一半。 第 4 週結束還沒通的話，第 5 週不要做別的，先把它補完。

  • 九支排程任務 + 對應的手動觸發 API（7.10 是算出來的預約保留、不是排程，不要把舊的預留轉換排程加回來；跟著進階走的三支見 00 §3.4）

  • 前端三態、RWD、iOS Safari 實機測試；全域搜一次確認沒有 stub 漏掉（寫死的回傳、Thread.sleep）

鐵則：第 6 週一行新功能都不要寫。 每年都有組在最後一週加功能然後 demo 當天炸掉。

備援清單（demo 當天保命用）： - 錄好一段 3 分鐘的完整操作影片 - 本機也能跑（docker compose up 就能起） - 資料庫備份一份乾淨的 demo 資料 - reset-demo.sh 在 demo 前 10 分鐘跑一次 - 開始前 5 分鐘先打開網站叫醒免費方案的服務 - 手機和電腦都先連好網路並測試過

4. 每日／每週節奏

時間 活動 時長
每天早上 站立會：昨天做了什麼／今天要做什麼／卡在哪 15 分鐘，站著講
每天結束 各自 push 到 feature 分支（不要囤積本機程式碼） —
每週三 中期檢查：本週里程碑會不會達成？不會的話現在就砍範圍 30 分鐘
每週五 收斂會：合併 PR、整體跑一次、更新 02-需求規格 的狀態欄 60 分鐘

「卡住 30 分鐘就要開口」原則：新手最常見的時間殺手是一個人默默卡 3 小時。規定卡住 30 分鐘沒進展就在群組貼出來。這條規則能省掉整個專案 20% 的時間。

5. 完成定義（DoD）

一個功能要標成完成，必須全部符合：

  • 已合併到 develop，且 develop 能正常啟動
  • CI 綠燈
  • API 出現在 Swagger 上，參數說明正確
  • 前端處理三種狀態：載入中、空資料、錯誤
  • 手機 375px 不破版（顧客端功能）
  • 至少一位組員 review 過 PR
  • 對應模組頁的驗收條件逐條測過
  • 沒有殘留的 console.log / System.out.println
  • 02-需求規格.md 的狀態欄已更新

7. 給整合負責人的三個提醒

不管最後誰擔任這個角色，這三件事要有人做：

  1. 主要工作不是寫最多程式碼，是讓其他四個人不被卡住。 把共用層做好、環境弄順、衝突解掉，比自己多寫一個功能有價值。
  2. 第 4 週結束時要誠實評估。 如果主流程還沒通，立刻砍掉第 5 週的一半功能。砍範圍不丟臉，交不出來才丟臉。
  3. 每週五一定要整體跑一次。 不要等到第 6 週才第一次把所有人的東西合起來——那時候才發現介面對不上就來不及了。
