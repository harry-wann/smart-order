00 架構分層與技術選型

全員第一篇。 這份文件說明我們怎麼切這個系統、為什麼選這些技術、以及每個選擇背後的取捨。 看完這份，你就知道自己在做的東西在整張圖的哪個位置。

1. 兩個定位

1.1 餐廳定位

中高價位、多人共鍋的台式火鍋餐廳。

這決定了幾件事：

決定 影響
共鍋（不是個人鍋） 鍋底是「每桌至少一份」，不是「每人一份」
一鍋一價 + 單點，無低消 人數完全不參與帳單計算
單味 + 鴛鴦，不限鍋數 鴛鴦用兩個選項群組表達，不建「鍋位」表
中高價位 有服務生帶位、服務鈴實用、10% 服務費
家庭與朋友聚餐為主 UI 維持台式親切感、長輩兒童友善

1.2 系統定位

這是一套「店家的半輔助工具」，不是完整的 POS 系統。

我們管 我們不管
點什麼、出到哪、坐多久 錢怎麼進抽屜
菜單、桌況、庫存、訂位 找零、交班日結、現金核對
帳單明細、櫃檯結清（線上模擬付款是進階） 發票、折讓、稽核紀錄

這個切法讓範圍乾淨，而且定位講得出來。結帳模組因此大幅簡化——客人到櫃檯結帳，系統算出金額、櫃檯結清、桌位轉待清理，錢的事情留給店家原本的收銀機。

2. 分層原則

2.1 判準：拿掉它，系統還成不成立

我們不用「時間夠不夠」來決定做什麼。用這個判準：

  • 基礎層 = 拿掉它，這套系統就沒辦法讓一家店做生意
  • 進階層 = 拿掉它，系統還是能運作，只是比較笨

2.2 兩層切法

模組層級：八大模組全部在基礎層。缺任何一個，店都開不了門。

細項層級：每個模組裡面再分「核心細項」與「進階細項」。

所以推進方式是廣度優先：

先把八個模組的核心細項全部打通成一條營運閉環，再回頭一層層加厚。 不是做完模組 A 才做模組 B。

這對五人並行開發特別有利——介面早期就定下來了，不會有人在等別人。

3. 技術選型與理由

3.1 後端

項目 選擇 為什麼
語言／框架 Java 17 + Spring Boot 3 課程延伸，Java 職缺主流
資料存取 Spring Data JPA Java 職缺主流；複雜查詢用 native query
資料庫 MySQL 8.0
版本控管 Flyway 5 人共用 schema 的唯一解
認證 Spring Security + JWT 前後端分離標準做法
即時 WebSocket + STOMP 見 §3.3
排程 @Scheduled 見 §3.4
快取／TTL Redis 驗證碼、限流、菜單快取
API 文件 springdoc-openapi 加一個依賴就有
測試 JUnit + Mockito + Testcontainers 防超賣一定要用真 MySQL 測

3.2 前端

項目 選擇 限制
框架 React 18 函式元件 + Hooks only
建置 Vite 不用 Next.js
語言 JavaScript 不用 TypeScript
樣式 Tailwind + 自建 10 個元件 不裝 MUI / Ant Design
路由 react-router-dom 只用 Routes / Link / useNavigate
狀態 useState + useContext 禁用 Redux / Zustand
資料 fetch + useEffect 禁用 React Query / SWR
即時 @stomp/stompjs

為什麼限制這麼多？ 因為五個人都沒學過 React。限制用法不是偷懶，是把風險集中在「學會 React 本身」這一件事上，不要再疊三個新概念上去。

第 1 週全員（含後端）都要做完 React 基礎練習——後端的人不寫前端，但必須看得懂，否則 debug 時會互相甩鍋。

3.3 為什麼保留 WebSocket

輪詢（polling）比較簡單，但我們選 WebSocket。

輪詢 WebSocket
實作成本 低 中
延遲 最慢 3 秒 < 1 秒
請求量 大量白問的請求 只在有事時推
學習價值 低 高
部署風險 無 平台要支援協定升級

理由：這是一個帶著學習的專題，而「同桌即時同步」正是 WebSocket 存在的理由——用輪詢是繞路。用對的技術解決對的情境，而且它是簡報和面試時很好講的一塊。

五個頻道：

頻道 訂閱者 推什麼
/topic/session/{id} 同桌所有裝置 共用購物車異動、新單、出餐狀態、金額變動、已結帳／已取消
/topic/kitchen KDS 新單、狀態變更、退菜
/topic/counter 櫃檯 桌況（含預約保留）、服務鈴、結清完成、超時提醒
/topic/menu 所有點餐中的裝置 售完／補貨
/topic/waitlist 櫃檯與候位螢幕 叫號、候位異動

最重要的工程觀念：

WebSocket 保證「快」，不保證「不漏」。 每次（重新）連上都要重抓一次完整資料。

做了這件事，你同時拿到即時性和容錯——就算 WebSocket 完全掛掉，重新整理資料還是對的。

3.4 為什麼保留排程

有些事「時間到了就該做」，沒有人會特地去點：

任務 頻率 歸屬
用餐超時掃描（>100 分） 每 1 分 M2
候位過號標記（叫號後 10 分未到） 每 1 分 M2
待清理提醒（>15 分） 每 5 分 M2
NO_SHOW 標記（訂位時間過 10 分未到） 每 5 分 M7 7.11
訂位提醒（用餐前 2 小時） 每 10 分 M7 7.12
驗證碼清理 每 10 分 M8（改用 Redis TTL 就不需要）
低庫存檢查 每小時 M5 5.10（進階 A3）
營業日結算 每日 23:30 報表快照（進階 A4）
明日備貨建議 每日 06:00 M5 5.E2（進階）

共九支。原本的第十支「桌位預留轉換」排程已刪除，不會加回來。 7.10 這個編號現在給「訂位保留桌位」用——配到的桌在訂位前 30 分～後 10 分鎖住，但那是查桌況時算出來的，不是排程（理由見 M2 問題 5）。 後三支跟著進階功能走，基礎要交的是前六支。

★ 每個排程都要配一支手動觸發的管理 API。 你不可能在 demo 時等到晚上 11:30。

做法：排程方法只負責呼叫 Service + 記日誌，邏輯全在 Service，排程和手動 API 共用同一段程式碼。

3.5 Redis 的定位

用途 值不值得
驗證碼的 TTL 最自然的切入點，天生需要自動過期
OTP 請求限流 合理且必要
菜單快取 讀多寫少，合理
共用購物車 不用。送出時購物車要跟 order_ticket 在同一個交易裡搬過去，放 MySQL 最單純（見 M3 問題 6）
分散式鎖 單台部署用不到，多台才需要
WebSocket 多實例 broker 同上

從「驗證碼 + 限流」開始，這兩個是真的比 MySQL 好，不是為了炫技。

3.6 RabbitMQ：誠實的評估

你們的規模不需要它。 一家店、十幾桌，不會有塞車問題。

如果要加，只做一個場景做深：出單機列印佇列。

理由：那是真實餐廳的痛點（卡紙、缺紙、離線），而且能完整走過訊息持久化、ack、重試、死信佇列、冪等性。比「我用 MQ 發通知」好講太多。

列為進階，基礎全綠燈且部署上線之後才碰。 簡報時要能說出「我知道這對目前規模是過度設計，但我想學這個模式」——這比假裝沒想過好得多。

4. 系統架構

見 06-圖表總覽 的「系統工程架構圖」。

五層：使用者裝置 → 靜態主機（Vercel）→ 應用伺服器（Render/Railway）→ 模擬外部服務 → 資料層（MySQL + Redis）。

三個關鍵設計：

  1. 前端拆成兩個獨立專案（顧客端／店家端），顧客端不必載入後台才用得到的程式碼，兩邊也不會互相卡住
  2. 付款與簡訊全部是本地 Mock，不申請任何外部帳號、不需要正式網域
  3. WebSocket 用 Spring 內建的 SimpleBroker，單台部署足夠

5. 不建議花時間的事

新手團隊最常見的過度工程。這些一律不做：

不做 理由
自己實作 JWT refresh token 輪替 單純的 access token + 合理效期就夠
微服務架構 你們沒有需要拆的理由
Kubernetes
手刻完整的 RBAC 權限系統 三種角色用 enum + @PreAuthorize 就夠
追求 90% 測試覆蓋率 15～20 個測到重點的測試比 200 個無意義的好
TypeScript 同時學 React + TS 風險太高；在 README 寫「已規劃遷移」即可
自建 CI/CD 伺服器 GitHub Actions 免費且夠用

6. 推進順序

Stage 內容 完成時能 demo 什麼
1 營運閉環 M1～M6 的核心細項各做最薄一層 一家店真的能用這套做完一天生意
2 即時化 WebSocket 五個頻道、庫存告罄推播、服務鈴 兩支手機同步、廚房即時、售完全場秒更新
3 排程與訂位 區間模型訂位 + 九個排程 + 算出來的預約保留 線上訂位、自動配桌、訂位前 30 分鐘鎖住配到的桌、提醒與 NO_SHOW
4 會員 OTP + JWT + 會員中心 + 訂位免填資料 登入後訂位自動帶入、查我的預約（消費紀錄、匿名轉會員、點數是進階）
5+ 各模組進階細項 每個都是獨立的加分項

每個 Stage 結束都有一個完整可 demo 的東西，而不是一堆半成品。

對應到六週的細節見 05-開發流程與時程。

7. 就業導向的補強

7.1 最重要的一件事：線上 demo

面試官不會 clone 你的 repo 然後裝 MySQL。 沒有可以點開操作的網址，這個專案在履歷上的價值大概打三折。

部署要在第 5 週跑通，不要留到最後一週。第一次部署一定會遇到 CORS、環境變數、SPA 路由這三個坑。

7.2 分工原則：以功能切分，不要切前後端

工作分配還沒決定，等八大模組的規格都定稿後再分。但原則現在就要講清楚。

  • ❌ 水平切：一人寫前端、一人寫後端、一人寫 CSS——每個人都只看到系統的一個橫切面，說不出自己做了什麼
  • ✅ 功能切（垂直切）：一個人負責一個功能的前後端，從資料表 → API → 畫面全部自己走一遍

面試的核心問題永遠是「講一個你在專題遇到的技術問題，你怎麼解的」。功能切才有完整的故事可講，而且你會真的懂那條路上每一層發生了什麼事。

代價是每個人前後端都要學。這正是為什麼 技術總表 有必修八頁——那是共同語言。

7.3 每個模組都有一個可以講的技術故事

不管最後誰做哪個模組，每個模組本身都已經內建一個值得講的題目：

模組 可以講什麼
M1 菜單 「選項群組模型怎麼用一套機制表達份量、口味、加購和鴛鴦鍋」
M2 桌位 「固定 QR + 櫃檯控制開桌的設計」／「開桌的悲觀鎖」／「預約保留為什麼用算的、不存桌態也不靠排程」
M3 點餐 「送出點餐的交易邊界怎麼切」／「整桌共用購物車，兩個人同時按送出怎麼只成立一張單」／「WebSocket 斷線重連為什麼一定要重抓」
M4 KDS 「單的狀態為什麼由品項推導而不是手動設」
M5 庫存 「防超賣的條件式 UPDATE，以及怎麼用多執行緒測試證明它有效」
M6 結帳 「為什麼算錢一定要用 BigDecimal」／「拿掉結帳中狀態後，怎麼用金額比對 + 列鎖擋住結帳時的加點」
M7 訂位 「區間重疊演算法 + 悲觀鎖 + 唯一約束的雙重保護」
M8 會員 「JWT 為什麼沒辦法真的登出」／「兩套認證機制怎麼並存」
技術地基 「Flyway 怎麼解決五個人的資料庫不同步」

第 6 週簡報演練時，逐一確認每個人都講得出自己負責模組的那一題。

8. 如果只能記住三件事

  1. 廣度優先：八個模組先各做最薄一層，把一條營運閉環打通，再回頭加厚。
  2. 三個容易做錯且改起來最痛的地方：dining_session / order_ticket / order_item 三層結構、選項群組模型、防超賣的條件式 UPDATE。
  3. 第 1 週就寫種子資料，第 5 週就部署上線，第 6 週不寫新功能。 這三個時間點是專題成敗的分水嶺。
