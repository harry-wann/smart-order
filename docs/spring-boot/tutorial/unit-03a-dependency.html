01 · 先約定能力，才有辦法換人做

Java 的 interface（介面）描述「需要提供哪些方法」，不必指定由哪個類別完成。我們把需求縮到一件事：給商品編號，能回傳名稱。

ProductCatalog 是我們自己定義的型別。它沒有查資料的內容，只要求 findName(int id) 必須回傳 String。只要遵守這個約定，就可以當成資料來源。

02 · 兩個來源，遵守同一份約定

implements 表示類別實作這個介面；@Override 是 Java 的註解，讓編譯器檢查方法是否確實覆寫介面要求的方法。它不是 Spring 的功能。

兩者接受相同的輸入 1，但分別回傳 Chai 與測試茶。現在還沒有碰標籤格式，只有資料來源不同。

03 · 標籤只依賴共同約定

只改了欄位與建構子參數的型別。text() 裡仍然呼叫 catalog.findName(1)，因為介面保證每個實作都有這個方法。

這就是依賴介面的具體意思：ProductLabel 只需要查名字的能力，不必知道是誰實作。不是每個類別都需要介面；這裡因為確實要替換來源，所以值得抽出共同約定。

06 · 下一個問題：誰來組裝整個系統？

現在只有兩個物件，手動 new 很清楚。若網站有商品、訂單、付款、庫存等服務，每個服務又需要其他物件，就會有更多「先建立誰，再交給誰」的程式。

下一頁讓 Spring 接手這個組裝工作。ProductLabel 的建構子與 text() 都可以保留；先不要把「交給 Spring」理解成所有 Java 語法都要重寫。

停一下，自己想想

新增第三個 ProductCatalog 實作，ProductLabel 要增加 if/else 判斷來源嗎？

看解釋

不需要。呼叫端選擇實作，ProductLabel 只按介面的約定呼叫方法。若每新增一個來源都得修改 ProductLabel，代表替換責任還沒有分乾淨。
