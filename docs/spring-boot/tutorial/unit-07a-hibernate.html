單元 07A · HIBERNATE

Hibernate：Entity 何時變成 SQL

Hibernate 是 ORM 實作。這一頁只理解「查出來的物件如何被管理、修改後何時寫回資料庫」。

ORMPersistence ContextTransaction

讀完能做到：知道為什麼 Service 的更新方法需要交易，也知道 Hibernate 不是資料庫。

01 · 一次查詢經過哪些角色

EntityManager 是 JPA 管理 Entity 的介面；Hibernate 實作它；JDBC 負責把 SQL 送到 MySQL。Spring Data JPA 把常用操作包成 Repository 方法。

02 · Persistence Context

Persistence Context（持久化上下文）可以先想成「目前這次資料庫操作中，JPA 正在管理的 Entity 清單」。在 Service 的 @Transactional 方法內用 Repository 查出的 Product 會受到管理；離開交易後，不應假設原物件仍會被追蹤。它不是一張資料庫表，也不是所有請求共用的 Java 清單。

狀態白話意思
Transient剛用 new Product(...) 建立，還沒有交給 JPA。
Managed已被目前的 Persistence Context 管理，欄位變化可以被追蹤。
Detached交易或 Persistence Context 結束後，物件不再被追蹤。
Removed已標記要刪除，交易提交時會執行 DELETE。

03 · Dirty Checking

Dirty Checking（髒檢查）是 Hibernate 比對受管理 Entity 前後狀態的機制。Service 查出商品、呼叫 setter 後，交易提交前 Hibernate 會同步變動；若交易回滾，修改不會寫入資料庫。

這段只顯示價格修改的原理，沒有列出 PUT 的其他必填欄位與分類檢查，不能直接取代現有 Service。完整實作請看 10B 及 ProductService.java。如果新價格與舊價格相同，也不一定需要一筆 UPDATE。

04 · 交易範例

Transaction（交易）要求一組操作全部成功，或發生錯誤時一起回滾。@Transactional 放在 Service，而不是放在 Controller，因為 Service 才知道一次業務操作包含哪些資料庫動作。

Boot 3 對照

Boot 3 與 Boot 4 都可以使用 @Transactional、Spring Data JPA 與 Hibernate；不要自行把 Hibernate 版本硬改掉，交給 Spring Boot 的 dependency management（依賴版本管理）。
