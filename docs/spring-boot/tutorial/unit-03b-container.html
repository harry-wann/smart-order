01 · 先回想自己組裝的兩行

這兩行決定建立哪個來源，再把它交給標籤。若想統一管理這種工作，就需要一個地方記得：有哪些物件、怎麼建立，以及誰要交給誰。

02 · 管理中心叫容器，被管理的物件叫 Bean

Spring 容器（Container）是 Spring 建立、保存與組裝物件的管理環境。ApplicationContext 是常用的容器介面名稱，可以先理解成你和管理中心溝通的入口。

Bean 是「由 Spring 容器管理的 Java 物件」的稱呼，不是英文縮寫。普通 Java 類別的物件，只要依設定交給容器管理，就可以是 Bean，不需要變成另一種特殊語法。

範例裡的東西現在怎麼稱呼
ProductLabel類別，描述標籤物件能做什麼
你在 main 裡自己 new 的 ProductLabel，沒有交給容器普通 Java 物件，不會因此自動成為 Spring Bean
由容器依設定建立、管理的 ProductLabel 物件一個 Spring Bean
負責保存與組裝這些物件的環境Spring 容器
Bean 這個詞描述「物件由誰管理」，不是看到某個類別名稱就能判定。單純 new 一個帶有 Spring 註解的類別，也不代表你拿到的是容器管理的實例。

03 · 先用明確的組裝設定，別急著掃描註解

Annotation（註解）是 @ 開頭、讓工具或框架辨認用途的標記。這裡先學兩個：@Configuration 標示組裝設定類別；@Bean 標示一個建立物件的方法，將它回傳的物件交給容器管理。

  • 把 AppConfig 作為組裝設定提供給容器。
  • 容器呼叫 productCatalog()，取得 NorthwindCatalog 物件並管理它。
  • 容器發現 productLabel(...) 需要 ProductCatalog，找到剛才符合型別的物件。
  • 容器把它當參數傳入 productLabel(...)，取得並管理 ProductLabel。

new 沒有消失。這次把建立方式放在設定裡，容器決定何時呼叫與如何供應參數。ProductLabel 仍只接收依賴，不自己找容器，也不自己挑來源。

04 · 誰在呼叫這些設定方法？

下面是閱讀用的 Spring 程式：需要 Spring 的 spring-context 依賴，與 03A 的類別、AppConfig 放在同一套件。它不是能直接接在「java Demo.java」後執行的純 Java 範例。Spring Boot 專案的實際啟動會在下一單元處理。

AnnotationConfigApplicationContext 來自 org.springframework.context.annotation，它依設定類別建立容器。getBean 是向容器取得已管理的物件；ProductLabel.class 表示你要的型別。try 區塊結束後關閉容器。var 是讓 Java 推斷區域變數型別的語法。

這裡刻意手動取得物件，讓你看見誰在管理。後面的 Spring Boot 範例改用 @Autowired 欄位注入，不需要到處寫 getBean。

05 · 再換一次來源：這次只改組裝設定

重新建立容器後，同樣取出 ProductLabel 並呼叫 text()，預期輸出變成「商品：測試茶」。ProductLabel 與呼叫它的程式都沒有改。差別是來源選擇集中在組裝設定。

問題手動組裝Spring 組裝
誰設定要用哪個來源？你在 main 裡選你在 AppConfig 裡選；Spring 依設定執行
誰把來源交給 ProductLabel？你呼叫 new ProductLabel(catalog)容器解析依賴，再呼叫 @Bean 方法
誰保管組裝好的物件？你的程式變數容器
ProductLabel 做的事有變嗎？用來源取得名稱並組字同樣的工作

IoC = Inversion of Control，控制反轉。在這個例子中，「建立、組裝與管理物件的控制」由散落在呼叫端的程式轉交給容器。DI 則是容器把需要的物件交進建構子的方法之一。IoC 是較廣的原則，DI 是實現方式；Spring 不是 IoC 唯一的實作。

那為什麼不一直手動組裝？只有這兩個物件時，手動寫完全合理；改用 Spring 甚至多了設定。當許多類別共用資料來源，又各有依賴時，容器會依登記資訊尋找候選、安排建立順序，並在適當時機執行初始化與關閉清理。這些從建立到結束的過程，稱為物件的「生命週期」。你仍決定類別做什麼、選什麼來源，但不用在每個呼叫端重做組裝。

可對照你學過的 Servlet：你提供 doGet，Tomcat 決定何時呼叫它；這裡你提供組裝設定，Spring 決定如何依設定建立與串接物件。兩者管理的事情不同，但都有「把部分流程交給框架安排」的想法。

06 · 理解組裝後，再看常見的簡寫

實務專案常在自己的類別加 @Component，讓 Spring 的元件掃描找到它。@Service 是表達「處理應用規則」的同類標記。這是另一種登記物件的方式，不是另一套注入原理。

@Component 和 @Service 來自 org.springframework.stereotype；@Autowired 來自 org.springframework.beans.factory.annotation。容器掃描到類別後會建立物件，再把符合型別的來源注入欄位。這裡的欄位不宣告為 final，且不能自己用 new 建立 ProductLabel 來期待自動注入。掃描範圍在下一單元配合啟動類別說明。

這是上一種 @Bean 登記方式的替代寫法。不要把兩套設定都加進相同練習，否則可能重複登記來源。03A 的 TrainingCatalog 如果沒有加註解、也沒有 @Bean 設定，就不會因為 implements 介面而自動成為候選。

07 · 先檢查理解，再看進階情況

停一下，自己想想

IoC、DI、Bean 在這個例子中各是哪件事？

看解釋

IoC：讓容器負責組裝與管理。DI：在前面的 @Bean 範例中透過建構子傳入 ProductCatalog；在元件掃描版本中，Spring 將來源注入 ProductLabel 欄位。Bean：容器管理的來源物件或標籤物件。三者不是同義詞。

停一下，自己想想

加了 @Service 的類別，自己 new ProductLabel() 就會自動注入嗎？

看解釋

不會。自己 new 出來的物件不由 Spring 管理，@Autowired 欄位不會被注入，使用時可能遇到 null。自動注入發生在 Spring 組裝物件時。

選讀：兩個來源都被登記時，以及共用物件要注意什麼

如果兩個 ProductCatalog 實作都被登記，單靠型別可能無法選出候選。@Primary 表示預設優先候選；@Qualifier 指定用哪個登記名稱。這是完成基本注入後才需要處理的選擇問題。

@Qualifier 來自 org.springframework.beans.factory.annotation。使用 @Component 時，NorthwindCatalog 的預設登記名稱通常是 northwindCatalog；使用 @Bean 時通常取方法名。名稱要與實際登記方式一致。

Spring 管理的 Bean 預設通常在同一容器內共用一個實例，稱為 singleton（單例）。不要用共用欄位保存「這次請求的商品編號」；把每次請求的資料放在方法參數或區域變數，避免不同使用者互相影響。
