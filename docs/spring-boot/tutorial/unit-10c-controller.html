01 · URL 與方法表

HTTP 方法表達「我要對資源做什麼」。同一個 /api/products/{id} 因方法不同而執行不同動作。GET 有清單與單筆兩個入口，因此總共六個方法，涵蓋五種 HTTP 動詞。

方法網址用途成功狀態
GET/api/products查詢分頁清單。200 OK
GET/api/products/{id}查詢單筆商品。200 OK
POST/api/products新增商品。201 Created
PUT/api/products/{id}完整替換可寫欄位。200 OK
PATCH/api/products/{id}只修改有傳入的欄位。200 OK
DELETE/api/products/{id}刪除商品。204 No Content

02 · Controller 共同結構

開啟 backend/src/main/java/tw/ispan/smartorder/controller/ProductController.java。@RestController 把方法回傳值轉成 HTTP 回應，@RequestMapping 設定共同網址前綴，@Autowired 由 Spring 注入 ProductService。

Controller 不自行建立 Service，也不直接寫 SQL。服務層與資料存取層的責任已在 10B 說明。下面的方法都屬於同一個類別；閱讀時可以在現有檔案逐一找到。

03 · 六個請求入口

@PathVariable 讀網址裡的 id。@RequestBody 把 JSON 轉成 DTO，@Valid 啟用 10A 的欄位驗證。清單的 page 從 0 起算，預設每頁 20 筆並按 id 排序。POST 的 Location 標頭指向新商品網址，回應本文是新增後的 ProductResponse。

PUT 與 PATCH 都回傳修改後的商品，但使用不同 DTO：PUT 欄位全部必填，PATCH 只帶要修改的欄位。DELETE 回 204，沒有 JSON 本文。以上是類別內的方法；import 和完整類別以現有檔案為準，不需再建立第二份 Controller。

04 · 錯誤與安全

ApiExceptionHandler 使用 @RestControllerAdvice 集中處理錯誤：找不到商品回 404、輸入錯誤或不存在的分類回 400、資料庫約束衝突回 409。錯誤本文包含 status、message、path、timestamp，所以 Controller 方法不用重複寫 try-catch。

目前 SecurityConfig 允許 /api/** 本機練習，並使 API 請求不受 CSRF（跨網站請求偽造）檢查影響。這是教材的環境設定；火鍋店正式功能須依專案權限規格處理登入與角色。

停一下，自己想想

POST 新增成功時為什麼用 201，而 GET 查詢用 200？

看解釋

201 表示新資源已建立，還用 Location 指出它的位置；200 表示查詢成功並回傳資料。
