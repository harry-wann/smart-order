01 · IoC 在這個專案做了什麼

IoC 是 Inversion of Control（控制反轉）：物件要用誰，不自己決定建立，而是交給 Spring 容器管理。DI 是 Dependency Injection（依賴注入）：Spring 將需要的物件傳進來。

沒有 Spring 時有 Spring IoC 時
Controller 自己 new ProductService()。Spring 建立 ProductService，Controller 只宣告需要它。
Service 自己建立資料存取物件，也要自己決定怎麼換成測試替身。Spring 把真正的 Repository 注入；測試時可以換成 mock。
每個類別都知道如何建立下一層，彼此黏死。每個類別只描述「我需要什麼」，建立與組裝交給容器。

所以 IoC 的差別不是「少打幾個 new」而已，而是把組裝責任集中到 Spring。這讓分層清楚，也讓單元測試可以替換依賴。

這兩個 @Autowired 欄位是目前程式採用的 DI 寫法。Spring 啟動時看到 @Service，就建立 ProductService，並在建立後把兩個 Repository Bean（由 Spring 容器管理的物件）注入欄位。Controller 不需要知道資料庫如何連線。欄位注入不能搭配未初始化的 final；自行 new ProductService() 也不會觸發 Spring 注入。

你在 03 學的是建構子注入；兩種寫法都屬於 DI。團隊的 依賴注入短篇以建構子注入作為新程式碼的示例，這裡保留既有欄位注入，好讓你能一行一行對照現有 ProductService.java。

03 · 五種操作的業務規則

HTTP 方法Service 做什麼成功結果
GET找商品；清單使用 Spring Data 的分頁。回傳商品 DTO。
POST先確認 categoryId 存在，再建立新 Entity。資料庫產生新 id。
PUT先找原商品，再用完整輸入替換可寫欄位。找不到不偷偷新增。
PATCH只套用 JSON 中有傳入的欄位。沒有傳的欄位保持原值。
DELETE先確認商品存在，再刪除。成功回傳 204。

Service 還會把找不到商品轉成 ProductNotFoundException，把不存在的分類轉成 CategoryNotFoundException。ApiExceptionHandler 再把它們轉成 404 或 400。注意 PATCH 的 null 在目前程式代表「不修改」，所以它不能用來把欄位清成 null；空物件 {} 會回 400。

04 · Transaction 是什麼

Transaction（交易）是一組「要嘛全部成功、要嘛全部取消」的資料庫操作。@Transactional 放在新增、更新、刪除方法上，讓讀寫在正確的資料庫交易中完成。

這裡的 save 不是每次更新都必須手動呼叫：查出的 Entity 在交易中受到 JPA 管理，欄位改變後會在提交前同步。現有 Service 類別先標 @Transactional(readOnly = true)，只有 create、replace、patch、delete 方法另標 @Transactional 開啟寫入交易。若查不到商品，先丟例外；若分類不存在，寫入不會完成。
