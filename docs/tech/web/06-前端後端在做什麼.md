# 前端與後端各在做什麼

**難度** ★☆☆☆☆　**用在哪些模組** 全員　**哪幾週** 第 0 週

## 一句話

前端是**餐廳的外場**，後端是**廚房**。

## 想像一下

你去餐廳吃飯。你看得到的是：菜單、桌子、服務生、送上來的菜。你看不到的是：廚房怎麼煮、食材放在哪個冰箱、庫存剩多少。

網站也一樣：

| | 前端 | 後端 |
|---|---|---|
| 比喻 | 外場 | 廚房 |
| 跑在哪 | **使用者的手機／電腦裡** | **遠方的伺服器上** |
| 負責 | 畫面長什麼樣、按鈕按下去有反應 | 資料存哪、計算、驗證、決定誰能看什麼 |
| 我們用 | React、Tailwind | Spring Boot、MySQL |
| 使用者看得到嗎 | 看得到，**也改得到** | 看不到 |

## 最重要的一句話

> **前端跑在使用者的電腦裡，所以前端的任何東西使用者都能看、能改。**

這句話有一個很重要的後果：

**前端做的檢查完全不算數。**

比如說你在前端寫「庫存不足就不讓他按送出」。使用者只要打開瀏覽器的開發者工具，就能把那個限制拿掉，硬是送出請求。

所以：
- 前端的檢查是**為了體驗**（讓使用者早點知道，不用等）
- 後端的檢查是**為了安全**（真正把關的那一道）

**兩邊都要做。** 前端隱藏一個按鈕，不等於後端擋住了那個功能。

## 在我們的火鍋店裡

客人按下「送出點餐」的時候，實際發生了什麼：

```
① 手機上的 React（前端）
   收集購物車內容，打包成 JSON
        ↓  透過網路送出
② 伺服器上的 Spring Boot（後端）
   檢查：這桌還能點嗎？選項有選齊嗎？庫存夠嗎？
   扣庫存 → 寫進資料庫 → 通知廚房
        ↓  回傳結果
③ 手機上的 React（前端）
   顯示「第 2 單已送出」
```

前端只負責「畫」和「問」。**所有會影響金錢、庫存、權限的判斷，一律在後端做。**

**前端的人也要懂一點後端，後端的人也要看得懂前端。** 不然出問題的時候會變成互相甩鍋：「一定是你 API 的問題」「才不是，一定是你前端沒傳對」。

## 15 分鐘動手小練習

打開任何一個網站（例如 PChome），按 F12 打開開發者工具：

1. 切到 **Elements** 分頁 → 隨便改一個商品的價格文字 → 畫面上真的變了
2. **但重新整理，價格就變回來了**
3. 切到 **Network** 分頁 → 重新整理頁面 → 看到一堆請求，那些就是前端在跟後端要資料

第 1、2 步就是「前端可以被使用者改，但改的只是他自己看到的畫面」的最好示範。做完這個練習，你永遠不會忘記為什麼後端一定要自己檢查一次。

## 你會遇到的坑

**① 以為前端檢查就夠了**
最常見也最嚴重的新手錯誤。

**② 把商業邏輯寫在前端**
像「服務費 = 小計 × 10%」如果只寫在前端，後端算出來的金額會對不上。
→ **金額一律由後端算，前端只負責顯示。**

**③ 把密鑰放在前端**
前端的程式碼使用者全都看得到，放什麼密碼都等於公開。
