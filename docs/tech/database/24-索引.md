# 索引是什麼

**難度** ★★☆☆☆　**用在哪些模組** M3、M4、M7　**哪幾週** 第 2 週

## 一句話

索引就是**書後面的那個「索引頁」**：不用從第一頁翻到最後一頁，直接查到在第幾頁。

## 想像一下

你有一本 800 頁的食譜，想找「麻婆豆腐」。

**沒有索引**：從第 1 頁開始翻，一頁一頁看，直到找到。平均要翻 400 頁。

**有索引**：翻到書後面的索引頁，按注音排序，「ㄇ」在那裡，麻婆豆腐 → 第 312 頁。三秒鐘。

資料庫完全一樣。

```sql
SELECT * FROM member WHERE phone = '0912345678';
```

- **沒索引**：從第 1 筆掃到第 10000 筆（叫 full table scan，全表掃描）
- **有索引**：直接跳到那一筆

資料量小的時候感覺不出來。**資料一多，差距是幾百倍。**

## 怎麼建

```sql
-- 一般索引
CREATE INDEX idx_order_item_menu ON order_item (menu_item_id);

-- 唯一索引（順便保證不重複）
CREATE UNIQUE INDEX uk_member_phone ON member (phone);

-- 複合索引（兩個欄位一起）
CREATE INDEX idx_session_table_status ON dining_session (table_id, status);
```

**主鍵自動就有索引**，不用另外建。

## 什麼時候該建

| 情況 | 該建嗎 |
|---|---|
| 這個欄位常出現在 `WHERE` | ✅ |
| 這個欄位是外鍵，常被 `JOIN` | ✅ |
| 這個欄位常用來 `ORDER BY` | ✅ |
| 這個欄位必須唯一（手機、桌號） | ✅ 用唯一索引 |
| 這個欄位只有兩三種值（性別、布林） | ❌ 沒意義 |
| 這張表只有幾十筆資料 | ❌ 不用 |

## 索引不是免費的

| 代價 | 說明 |
|---|---|
| **佔空間** | 索引本身也要存 |
| **寫入變慢** | 每次 INSERT／UPDATE，索引也要跟著更新 |

所以**不要每個欄位都建索引**。只建真的會用來查的。

一張表建 3～5 個索引很正常，建 15 個就有問題了。

## 複合索引的「最左前綴」規則

這是最容易搞錯的地方。

假設你建了 `INDEX (table_id, status)`：

| 查詢條件 | 用得到索引嗎 |
|---|---|
| `WHERE table_id = 3` | ✅ |
| `WHERE table_id = 3 AND status = 'OPEN'` | ✅ |
| `WHERE status = 'OPEN'` | ❌ **用不到** |

**規則**：複合索引像電話簿（先按姓排、同姓再按名排）。你可以只知道姓就查，但只知道名字沒辦法查。

所以**欄位的順序很重要**。

## 我們專案的索引

| 資料表 | 索引 | 為什麼 |
|---|---|---|
| `member` | `UNIQUE(phone)` | 登入查詢，而且不能重複 |
| `dining_table` | `UNIQUE(table_no)` | 桌號不能重複 |
| `dining_session` | `(table_id, status)` | 桌況頁每 5 秒查一次 |
| `dining_session` | `UNIQUE(session_token)` | 顧客端每次請求都要驗 |
| `order_ticket` | `(dining_session_id, sequence_no)` | 查本桌訂單 |
| `order_ticket` | `(status, placed_at)` | KDS 看板 |
| `order_item` | `(menu_item_id)` | **人氣推薦統計（進階 A7）會大量用到** |
| `reservation` | `(table_id, start_time, end_time)` | 訂位的區間重疊檢查 |
| `inventory_item` | `UNIQUE(menu_item_id)` | 一對一 |

## 怎麼知道索引有沒有用到

在 SQL 前面加 `EXPLAIN`：

```sql
EXPLAIN SELECT * FROM member WHERE phone = '0912345678';
```

看 `type` 欄位：

| type | 意思 |
|---|---|
| `const` / `eq_ref` / `ref` | 有用到索引，很好 |
| `range` | 範圍查詢用到索引，可以 |
| **`ALL`** | **全表掃描，沒用到索引** |

看到 `ALL` 而且那張表資料很多，就該想想是不是缺索引了。

## 15 分鐘動手小練習

1. 建一張測試表，塞 10 萬筆假資料（用迴圈或 `INSERT ... SELECT`）
2. `SELECT * FROM 測試表 WHERE 某欄位 = '某值';` ——記下花多久
3. `EXPLAIN` 看一下，應該是 `ALL`
4. `CREATE INDEX ...` 建索引
5. 再查一次，再 `EXPLAIN` 一次

**時間從幾百毫秒掉到幾毫秒的那一刻，你就永遠記得索引是什麼了。**

## 你會遇到的坑

**① 完全不建索引**
資料少的時候沒事，seed 了 5000 筆歷史訂單後，推薦查詢變超慢。

**② 每個欄位都建**
寫入變慢，而且很多根本用不到。

**③ 複合索引順序錯**
建了 `(status, table_id)` 但都用 `WHERE table_id = ?` 查——用不到。

**④ 在索引欄位上做運算**
```sql
WHERE DATE(created_at) = '2026-09-13'    -- ❌ 用不到索引
WHERE created_at >= '2026-09-13 00:00:00'
  AND created_at <  '2026-09-14 00:00:00' -- ✅ 用得到
```

**⑤ 用 `LIKE '%關鍵字%'`**
前面有 `%` 就用不到索引。`LIKE '關鍵字%'` 可以。
→ 我們的菜單搜尋資料量小，直接在前端過濾就好。

## 常見錯誤訊息對照

索引很少直接噴錯，比較常見的是「怎麼這麼慢」。

| 症狀 | 可能原因 |
|---|---|
| 某支 API 特別慢 | 缺索引，用 `EXPLAIN` 看 |
| `Duplicate entry for key 'uk_xxx'` | 唯一索引擋住了重複 —— 這是它的功能 |
| 寫入變慢 | 索引建太多 |

## 術語對照表

| 白話 | 正式名稱 |
|---|---|
| 書後面的索引頁 | Index 索引 |
| 從第一筆翻到最後一筆 | Full Table Scan 全表掃描 |
| 不能重複的索引 | Unique Index 唯一索引 |
| 兩個欄位一起的索引 | 複合索引 Composite Index |
| 只能從最左邊開始用 | 最左前綴原則 |
| 看查詢計畫 | `EXPLAIN` |
