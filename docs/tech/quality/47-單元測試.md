# 單元測試 JUnit + Mockito

**難度** ★★★☆☆　**用在哪些模組** 全員　**哪幾週** 第 5 週

## 一句話

單元測試就是**寫一段程式去檢查另一段程式對不對**，改東西時它會自動幫你看有沒有壞掉。

## 想像一下

你改了「服務費計算」的程式。改完之後你怎麼知道沒改壞？

**手動測**：啟動後端 → 開前端 → 櫃檯點空桌開桌 → 手機掃碼 → 加三樣進購物車、送出 → 櫃檯結帳 → 看金額對不對。**五分鐘。**

而且你只測了一種情況。有小孩的呢？有選項加價的呢？金額是 0 的呢？

**自動測**：寫好測試之後，按一個鍵，**三秒鐘測完二十種情況**。

這就是測試的價值：**不是為了證明程式是對的，是為了讓你敢改程式。**

## 一個最簡單的測試

```java
class PricingServiceTest {

    private final PricingService pricing = new PricingService();

    @Test
    void 服務費應為小計的百分之十() {
        BigDecimal subtotal = new BigDecimal("1420.00");

        BigDecimal fee = pricing.calculateServiceFee(subtotal);

        assertThat(fee).isEqualByComparingTo("142.00");
    }
}
```

三個部分（記成 **Given-When-Then**）：

| 部分 | 做什麼 |
|---|---|
| **Given** 準備 | 準備輸入資料 |
| **When** 執行 | 呼叫要測的方法 |
| **Then** 驗證 | 檢查結果對不對 |

**測試方法名可以用中文**，而且建議用——`測試1` 沒人看得懂，`服務費應為小計的百分之十` 一看就知道在測什麼。

## Mockito：假裝的依賴

`OrderService` 需要 `InventoryRepository`（會真的連資料庫）。測試時我們不想連資料庫，怎麼辦？

**做一個假的**：

```java
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock  DiningSessionRepository sessionRepo;     // 假的
    @Mock  CartItemRepository cartItemRepo;         // 假的
    @Mock  InventoryRepository inventoryRepo;       // 假的
    @Mock  OrderTicketRepository ticketRepo;        // 假的
    @InjectMocks OrderService orderService;         // 真的，但依賴是假的

    static final String TOKEN = "token-1052";
    static final String DEVICE_ID = "device-a";

    @Test
    void 庫存不足時應丟出售完例外() {
        // Given：這桌還開著，購物車裡有 2 份牛五花（id 12），但扣庫存回傳 0（表示庫存不夠）
        given(sessionRepo.findByTokenForUpdate(TOKEN)).willReturn(Optional.of(openSession(1052L)));
        given(cartItemRepo.findByDiningSessionId(1052L)).willReturn(List.of(cartItem(12L, 2)));
        given(inventoryRepo.decreaseIfEnough(12L, 2)).willReturn(0);

        // When + Then
        assertThatThrownBy(() -> orderService.submitOrder(TOKEN, DEVICE_ID))
            .isInstanceOf(BusinessException.class)
            .hasFieldOrPropertyWithValue("code", "ITEM_SOLD_OUT");
    }

    @Test
    void 購物車是空的應丟出CART_EMPTY() {
        // Given：同桌另一個人剛送出，購物車已經清空
        given(sessionRepo.findByTokenForUpdate(TOKEN)).willReturn(Optional.of(openSession(1052L)));
        given(cartItemRepo.findByDiningSessionId(1052L)).willReturn(List.of());

        assertThatThrownBy(() -> orderService.submitOrder(TOKEN, DEVICE_ID))
            .hasFieldOrPropertyWithValue("code", "CART_EMPTY");
        verifyNoInteractions(inventoryRepo);              // 沒東西就不該去扣庫存
    }

    @Test
    void 庫存足夠時應建立點餐單並清空購物車() {
        given(sessionRepo.findByTokenForUpdate(TOKEN)).willReturn(Optional.of(openSession(1052L)));
        given(cartItemRepo.findByDiningSessionId(1052L)).willReturn(List.of(cartItem(12L, 2)));
        given(inventoryRepo.decreaseIfEnough(anyLong(), anyInt())).willReturn(1);
        given(ticketRepo.save(any())).willAnswer(inv -> inv.getArgument(0));

        var result = orderService.submitOrder(TOKEN, DEVICE_ID);

        assertThat(result.status()).isEqualTo("PENDING");
        verify(inventoryRepo).decreaseIfEnough(12L, 2);   // 確認真的有扣庫存
        verify(cartItemRepo).deleteAll(anyList());        // 確認購物車有清掉
    }
}
```

（`openSession()`、`cartItem()` 是測試類別裡自己寫的小工具，專門造假資料；菜單、鍋底檢查這些依賴為了好讀先省略。）

| 東西 | 意思 |
|---|---|
| `@Mock` | 做一個假的替身 |
| `@InjectMocks` | 要測的真東西，把假的塞進去 |
| `given(...).willReturn(...)` | 「如果有人這樣呼叫，就回這個」 |
| `verify(...)` | 「確認這個方法真的被呼叫過」 |

## 該測什麼

**時間有限的話，只測這三種：**

| 優先 | 測什麼 | 例子 |
|---|---|---|
| **1** | **算錢的邏輯** | 服務費、小計、選項價差、均分 |
| **2** | **狀態轉換規則** | 已結帳不能再加點、結清時金額變了要擋、已經點過餐的桌不能取消用餐 |
| **3** | **邊界與錯誤** | 庫存剛好 0、必選沒選、數量 0、購物車是空的 |

**不要測的**：getter / setter、框架本身的功能、單純把 Entity 轉 DTO 的方法。

## 我們的目標：15～20 個測試

不是為了覆蓋率，是為了**保護最容易出錯的那幾塊**。

建議分配：

| 模組 | 幾個 |
|---|---|
| 金額計算（服務費、選項價差、均分） | 5 |
| 送出點餐（狀態檢查、空購物車、必選驗證、鍋底規則） | 5 |
| 庫存扣減（足夠／不足／回補） | 3 |
| 訂位重疊判斷（含 `SEATED` 也算佔用）、保留窗判斷 | 4 |
| 狀態機轉換 | 3 |

## 防超賣一定要寫「多執行緒測試」

[鎖與併發](../database/28-鎖與併發.md) 的問題**單執行緒永遠測不出來**：

```java
@Test
void 十桌同時搶最後一份不應超賣() throws Exception {
    // 先塞一筆庫存 = 1 的資料，再開 10 桌、每桌購物車都放 1 份這個品項
    inventoryRepo.save(new InventoryItem(menuItemId, 1));
    List<String> tokens = seedTablesWithCart(10, menuItemId, 1);

    ExecutorService pool = Executors.newFixedThreadPool(10);
    CountDownLatch latch = new CountDownLatch(10);
    AtomicInteger success = new AtomicInteger();

    for (String token : tokens) {
        pool.submit(() -> {
            try { orderService.submitOrder(token, "device-test"); success.incrementAndGet(); }
            catch (BusinessException ignored) { }
            finally { latch.countDown(); }
        });
    }
    latch.await();

    assertThat(success.get()).isEqualTo(1);                        // 只有一個成功
    assertThat(inventoryRepo.findQuantity(menuItemId)).isZero();   // 庫存是 0 不是負數
}
```

**這個測試是整個專案最值得寫的一個。** 面試官看到會眼睛一亮。

**為什麼是十桌，不是同一桌十個人？** 同一桌的送出會先鎖同一筆 `dining_session` 排隊，第一個送出後購物車就空了，後面九個拿到的是 `CART_EMPTY`，根本走不到扣庫存。超賣要「不同桌搶同一份庫存」才會發生。
（它需要真的資料庫，用 [Testcontainers](48-Testcontainers.md)。）

## 15 分鐘動手小練習

```java
// 要測的東西
@Service
public class PricingService {
    private static final BigDecimal FEE_RATE = new BigDecimal("0.10");

    public BigDecimal serviceFee(BigDecimal subtotal) {
        return subtotal.multiply(FEE_RATE).setScale(2, RoundingMode.HALF_UP);
    }

    public BigDecimal splitPerPerson(BigDecimal total, int people) {
        if (people <= 0) throw new IllegalArgumentException("人數必須大於 0");
        return total.divide(BigDecimal.valueOf(people), 2, RoundingMode.HALF_UP);
    }
}
```

寫四個測試：

1. 小計 1420 → 服務費 142.00
2. 小計 0 → 服務費 0.00
3. 總額 1562 分 3 人 → 每人 520.67
4. 人數 0 → 應該丟例外

寫完按綠色三角形，看到全綠的那一刻很爽。

## 你會遇到的坑

**① 測試依賴執行順序**
測試 A 塞了資料，測試 B 依賴它。**每個測試都要能單獨跑。**

**② 測試依賴真實時間**
`LocalDateTime.now()` 讓測試在特定時間才會過。
→ 把時間當參數傳進去，或注入 `Clock`。

**③ 只測「成功路徑」**
真正會出事的都是失敗路徑。

**④ 為了覆蓋率寫測試**
測 getter/setter 沒有任何價值。

**⑤ Mock 太多**
一個測試 mock 八個東西，代表你的類別依賴太多，該重構了。

**⑥ 用 `assertEquals` 比較 BigDecimal**
`new BigDecimal("142.0").equals(new BigDecimal("142.00"))` 是 **false**！
→ 用 `isEqualByComparingTo` 或 `compareTo`。

## 常見錯誤訊息對照

| 你會看到 | 中文意思 | 怎麼修 |
|---|---|---|
| `NullPointerException` 在 mock 上 | 沒有 `given` 那個呼叫 | 補上 stub，或用 `lenient()` |
| `UnnecessaryStubbingException` | 你 given 了但測試沒用到 | 刪掉，或用 `@MockitoSettings(strictness = LENIENT)` |
| `Wanted but not invoked` | `verify` 的方法沒被呼叫 | 檢查程式邏輯 |
| `expected: 142.0 but was: 142.00` | BigDecimal 比較方式錯 | 用 `isEqualByComparingTo` |
| `No qualifying bean` | 整合測試缺 Bean | 用 `@SpringBootTest` 或補 mock |
