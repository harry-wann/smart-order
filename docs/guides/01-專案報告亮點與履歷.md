## 0. 寫法原則

1. **一條 = 情境 + 做法 + 為什麼**。「用 React 寫頁面」沒有資訊量；「同桌多支手機改同一份購物車，用悲觀鎖讓操作排隊」才有。
2. **講取捨**：每個亮點都有「直覺會怎麼寫 → 為什麼會壞 → 我們怎麼做」，面試官最想聽的是後兩段。
3. **自己負責的寫「設計／實作」，共用的寫「參與」**。
4. **每人準備一個主打的技術故事**（下面每一包第一個亮點），1～2 分鐘講得完：問題 → 考慮過的做法 → 選擇與理由 → 怎麼驗證。

## 1. 全體共用（五人都可以寫）

### 1.1 專案一句話

一套給多人共鍋火鍋店用的**掃碼點餐系統**：顧客掃桌上 QR code，同桌多支手機共用一份購物車即時點餐；店家端有桌況與開桌、候位、訂位、菜單管理、庫存與出菜看板，櫃檯結帳。
5 人團隊，前後端分離，規格先行、依工作包平行開發。

### 1.2 技術棧

| 層 | 技術 |
|---|---|
| 前端 | React 19、TypeScript、Vite、Tailwind CSS 4、react-router、`@stomp/stompjs` |
| 後端 | Java 21、Spring Boot、Spring Data JPA、Spring Security＋JWT、WebSocket／STOMP、`@Scheduled`、springdoc-openapi |
| 資料 | MySQL、Flyway、Redis |
| 測試 | JUnit 5、Mockito、Testcontainers |
| 工具 | Docker Compose、GitHub Actions、Git／GitHub PR、Figma |

### 1.3 共同亮點

| 亮點 | 講法 |
|---|---|
| **一條完整、不會壞的交易線** | 掃碼入座 → 同桌點餐 → 扣庫存、出單到廚房 → 出菜進度 → 櫃檯結清 → 清桌，每一段都處理了併發與異常 |
| **即時同步，但不怕斷線** | 同桌手機、廚房、櫃檯都用 WebSocket／STOMP 推播；連線（重連）時一律重抓一次完整資料，所以「即時」和「不會錯」兩個都拿到（[M3 問題 3](../spec/modules/M3-點餐與服務鈴.md)） |
| **併發問題用資料庫解，不用 `synchronized`** | 防超賣用條件式 `UPDATE`、開桌與結帳用悲觀鎖、訂位用悲觀鎖＋唯一約束；`synchronized` 只鎖得住一台伺服器 |
| **依交易邊界切工作包** | 不是照前後端切，而是同一段交易、同一把鎖的東西給同一個人（例：送出點餐與結帳鎖同一筆用餐紀錄，都在 C），五個人平行開發不互相踩 |
| **規格先行** | 需求、資料表、API、每張畫面的狀態都先寫成文件，每張畫面有代號（C-04、S-02…），前後端、設計稿、文件用同一套代號溝通 |
| **規格會變，流程跟得上** | 中途把服務鈴移出範圍、購物車改成「只能改自己點的」：規格、API、資料表、設計稿（保留舊稿對照）一起改 |
| **設計系統** | 色彩、字級、間距、動畫做成 design token，共用元件有展示頁；廚房看板依場景改用深色大字 |
| **工程規範** | 功能分支 → PR → 自動指派其他四人 review；CI 跑 typecheck、lint、build、測試；Docker Compose 一鍵起 MySQL＋Redis |

### 1.4 五人都能用的履歷句子

- 5 人團隊開發火鍋店掃碼點餐系統（React 19＋TypeScript／Spring Boot＋MySQL＋Redis），涵蓋顧客點餐、廚房出菜看板、櫃檯桌況、候位、訂位與結帳。
- 以 WebSocket（STOMP）同步同桌多裝置、廚房與櫃檯畫面，重連時重抓完整狀態確保資料一致。
- 採規格先行流程，依交易邊界拆分五個工作包平行開發，透過 GitHub PR、交叉 code review 與 CI 協作。
- 共同建立 Tailwind CSS 設計系統（design token＋共用元件庫），統一顧客端與店家端介面。

## 2. 各工作包

### A　顧客入口＋會員｜Vincent Shih

**負責範圍**：C-00 入口、C-01 掃碼進入、C-12／12b／13 會員登入註冊、C-14 會員中心、C-16／16b 訂位入口與匿名訂位、S-01 員工登入畫面；後端 M8 會員（OTP 註冊登入、驗證碼、限流、會員 JWT、會員中心），以及掃碼入座的用餐權杖。

**報告亮點**

1. **主打：模擬簡訊的手機 OTP 驗證**（[M8 問題 1、2](../spec/modules/M8-會員.md)）
   - 直覺做法是跳過驗證直接用手機註冊——流程不完整，也講不出東西。
   - 我們做完整流程：6 位數驗證碼 5 分鐘效期、錯 3 次鎖定、請求限流（超過回 429），**簡訊發送用模擬的**；換成真的 Twilio 只要換一個 `SmsGateway` 實作。
   - 驗證碼存 Redis：`set(key, code, 5 分鐘)` 一行就有效期，不用建表、也不用寫清理排程——短期、會過期、掉了也沒關係的資料正是 Redis 的典型用途。
2. **匿名顧客怎麼被「認得」**：顧客不用註冊就能點餐。掃碼加入時後端用 jjwt 簽一張用餐權杖，之後每個請求經過自訂的 Security Filter 解析出這次用餐；顧客與會員是兩種不同的權杖。
3. **JWT 怎麼登出**（[M8 問題 4](../spec/modules/M8-會員.md)）：JWT 無狀態，刪掉 `localStorage` 不等於失效。我們的決定是縮短效期，並說明黑名單（Redis）與 refresh token 輪替的取捨——面試很常問。
4. **前端藏按鈕不等於安全**（[M8 問題 5](../spec/modules/M8-會員.md)）：權限一律在後端檢查，前端只負責體驗。
5. 會員與訂位的分岔：會員訂位免填資料，匿名訂位填姓名電話，兩條路接到同一個訂位流程。

**可能被追問**：Redis 掛了驗證碼怎麼辦？限流怎麼算時間窗？JWT 放 `localStorage` 和 cookie 的差別？權杖被偷了怎麼辦？

**履歷建議**

- 設計並實作手機 OTP 註冊登入：驗證碼存 Redis（TTL 5 分鐘）、錯誤 3 次鎖定、請求限流（429），簡訊發送採模擬並抽象為介面，可替換為真實服務。
- 以 jjwt 簽發會員與用餐兩種權杖，透過自訂 Spring Security Filter 驗證，讓匿名顧客免註冊即可掃碼加入用餐。
- 實作顧客入口、會員登入／註冊／驗證碼、會員中心與匿名訂位等 React 頁面。

### B　菜單＋出菜看板｜Clara

**負責範圍**：C-04 菜單主頁、C-05 品項詳情、C-08 本桌出菜進度、S-04 出菜看板 KDS、S-05 菜單管理、S-06 選項群組管理；後端 M1 菜單與品項、M4 出菜看板；顧客端版型與 Tailwind 樣式基礎。

**報告亮點**

1. **主打：「份量、辣度、加料」怎麼存**（[M1 問題 1](../spec/modules/M1-菜單與品項.md)）
   - 直覺是在品項上加欄位（`has_size`、`half_price`…），第三種需求出現就爆炸，複選也表達不出來。
   - 我們用**選項群組模型**：`option_group` 用 `min_select`／`max_select` 兩個數字表達必選／選填、單選／複選，`menu_item_option_group` 中間表做多對多。「辣度」建一次掛在 20 個品項上，改一次全部生效。
2. **鴛鴦鍋不另外建表**（[M1 問題 2](../spec/modules/M1-菜單與品項.md)）：用既有的選項群組表達左鍋、右鍋湯底，零額外資料表——不是每個需求都要多一張表。
3. **出菜狀態由品項推導**（[M4 問題 1](../spec/modules/M4-出菜看板.md)）：一張單的狀態不手動設，而是每次品項狀態改變就由品項重算（全部出完 → 已完成、部分出 → 製作中）。兩個廚師同時勾不同品項也不會把狀態蓋錯——單一真相來源。
4. **KDS 即時推播與排序**：新單、退菜即時推到廚房；預約預點的單用 `ORDER BY is_preorder DESC, placed_at ASC` 排最前面，等待時間從報到開桌算，不會誤觸久候警示（[M4 問題 2](../spec/modules/M4-出菜看板.md)）。
5. **為場景設計 UI**（[M4 問題 3、4](../spec/modules/M4-出菜看板.md)）：廚房螢幕掛在牆上、廚師手是濕的，所以全站唯一深色介面、品項 20px、勾選框 40×40；完成的卡片 0.5 秒淡出並可回看，避免「剛剛勾的是哪一桌」。
6. 售完即時推播到所有點餐中的手機，菜單立刻變灰。

**可能被追問**：多對多為什麼要中間表、中間表能放什麼欄位？品項詳情怎麼避免 N+1？狀態推導和直接存狀態的效能取捨？

**履歷建議**

- 設計可重用的選項群組資料模型（多對多＋最少／最多選擇數），支援份量、辣度、複選加料與鴛鴦鍋，新增選項類型不需改表。
- 實作廚房出菜看板（KDS）：WebSocket 即時接單、逐項勾選、單據狀態由品項自動推導、久候警示與預點優先排序。
- 實作菜單與選項群組後台管理（CRUD、上下架、售完標示），並導入 Tailwind CSS 建立樣式基礎。

### C　點餐交易＋櫃檯結帳｜YiTing

**負責範圍**：C-04b／04c 同桌通知、C-06 購物車、C-07 送出成功、S-03 桌位詳情、S-03b 櫃檯結帳；後端 M3 點餐、M5 庫存（基礎）、M6 結帳。

**報告亮點**

1. **主打：兩個人同時點最後一份牛五花**（[M3 問題 1](../spec/modules/M3-點餐與服務鈴.md)、[M5 問題 1](../spec/modules/M5-庫存.md)）
   - 先查再扣會超賣。我們用**條件式 `UPDATE`**：`SET quantity = quantity - :qty WHERE quantity >= :qty`，看影響筆數判斷成敗，0 筆就整張單回滾、回 409 告訴客人是哪一項。
   - 為什麼不用 `synchronized`：只鎖得住一台伺服器，資料庫層的問題要在資料庫層解。
   - 多品項依 id 排序再扣，避免兩筆交易用不同順序鎖而死鎖。
   - **用多執行緒＋Testcontainers 真的 MySQL 測試證明防超賣有效**（[M5 問題 5](../spec/modules/M5-庫存.md)）——手動按十次是「依序」不是「同時」。
2. **同桌兩個人同時按「送出整桌點餐」**（[M3 問題 7](../spec/modules/M3-點餐與服務鈴.md)）：送出一開頭就 `SELECT … FOR UPDATE` 鎖住這次用餐，拿到鎖之後才讀購物車；第一個人送出後購物車清空，第二個人拿到 `409 CART_EMPTY`，不會成立兩張單。
3. **結帳到一半有人加點**（[M6 問題 1](../spec/modules/M6-結帳.md)）：櫃檯把畫面上看到的金額（`expectedTotal`）一起送上來，後端在同一把鎖裡重算，對不上就回 `409 BILL_CHANGED`。結清、送出點餐搶同一把鎖，一定一先一後——不需要「鎖桌不能加點」的額外狀態。
4. **同桌多手機的購物車同步**：購物車存後端、整桌一份，只有加入者能改自己的列（他人 403）；每次異動遞增版本號並推 `CART_UPDATED`（帶整份購物車），前端只套用比本機新的版本，擋掉亂序推播；推播在**交易 commit 之後**才送，避免其他手機讀到未提交的資料。
5. **金額從頭到尾 `BigDecimal`**（[M6 問題 2](../spec/modules/M6-結帳.md)）：`DECIMAL(10,2)`、用字串建構、每步 `setScale(2, HALF_UP)`、比較用 `compareTo`；送單時快照品名與單價，日後改價不影響歷史帳單。
6. **櫃檯按錯付款方式**（[M6 問題 5](../spec/modules/M6-結帳.md)）：付款倒數到 0 才送出，倒數中可取消。

**可能被追問**：悲觀鎖和樂觀鎖怎麼選？條件式 `UPDATE` 和 `SELECT FOR UPDATE` 差在哪？為什麼推播要等 commit？`equals` 比 `BigDecimal` 會怎樣？

**履歷建議**

- 以條件式 `UPDATE` 實作庫存扣減防超賣，依品項 id 排序避免死鎖，並以多執行緒＋Testcontainers（MySQL）測試驗證併發正確性。
- 實作多裝置共用購物車與整桌送單：悲觀鎖序列化同桌操作、版本號擋亂序推播、交易提交後才以 STOMP 通知，確保同桌畫面一致。
- 實作櫃檯結帳：以 `expectedTotal` 金額比對與同一把列鎖處理「結帳中加點」，金額全程以 `BigDecimal` 計算並保存價格快照。

### D　桌位開桌＋候位｜ting chiu

**負責範圍**：S-02 桌況總覽、S-02b／02c 開桌（現場、候位）、S-08 座位管理、S-10 候位管理、S-10b 候位報到選桌（共用選桌對話框）；後端 M2 桌位（狀態機、QR code、開桌、關桌、清桌、桌況推播、用餐計時）與候位（登記、叫號、報到、過號）、三支排程；店家端後台版型。

**報告亮點**

1. **主打：兩個人同時開同一張桌**（[M2 問題 2](../spec/modules/M2-桌位開桌與候位.md)）
   - 直覺寫法「查到空桌 → 開桌」，兩邊的查都在對方的改之前，會產生兩筆用餐紀錄，兩邊看到不同帳單。
   - 我們用**悲觀鎖**：`SELECT … FOR UPDATE` 鎖住桌子，鎖住後才檢查狀態，非空桌回 409。
   - 為什麼不用條件式 `UPDATE`：開桌不只改一個欄位，還要建立用餐紀錄、發權杖——要做好幾件事的情況適合悲觀鎖。
2. **「預約保留」不存成桌位狀態，而是算出來的**（[M2 問題 5](../spec/modules/M2-桌位開桌與候位.md)）：舊設計用排程在訂位前 30 分鐘把桌子改成 `RESERVED`，結果兩份資料要靠 cron 同步，排程晚跑或漏一條「轉回去」就卡桌。改成查桌況時從訂位資料算出 `displayStatus`，桌位欄位只有三種狀態，沒有同步問題。
3. **桌位狀態機**：空桌 → 用餐中 → 待清理 → 空桌，每一步檢查前一個狀態，不合法的轉換直接拒絕；用餐一進終態，該次的用餐權杖全部失效，上一組客人的手機不能點到下一組的帳單上（[M2 問題 3](../spec/modules/M2-桌位開桌與候位.md)）。
4. **固定 QR code 的取捨**（[M2 問題 1](../spec/modules/M2-桌位開桌與候位.md)）：QR 永不換、開桌由櫃檯控制，掃到空桌只會看到「請洽櫃檯帶位」——不用每次印紙，風險靠服務生帶位控制。
5. **排程自動處理沒人記得的事**（[M2 問題 4](../spec/modules/M2-桌位開桌與候位.md)）：用餐超時、待清理提醒、候位過號三支 `@Scheduled`，每支都配手動觸發 API；排程只呼叫 Service，邏輯和手動 API 共用。
6. **桌況即時推播**：開桌、清桌、結清都推 `TABLE_STATUS`，櫃檯不用重新整理；選桌對話框做成共用元件，訂位報到（E）直接沿用。

**可能被追問**：悲觀鎖鎖住期間別人查桌況會被卡住嗎？為什麼「算出來」比「存起來」好、效能呢？排程在多台伺服器會不會重複跑？

**履歷建議**

- 以悲觀鎖（`SELECT … FOR UPDATE`）實作開桌，防止同一張桌被重複開立；設計桌位狀態機與用餐權杖失效規則。
- 將「預約保留」改為依訂位資料即時推導的顯示狀態，移除排程同步，消除桌況與訂位不一致的問題。
- 實作候位登記、叫號、報到與過號，並以 `@Scheduled` 處理用餐超時、待清理提醒與候位過號（皆提供手動觸發 API）。
- 實作店家端桌況總覽（WebSocket 即時更新）、開桌、座位管理與候位管理頁面，以及共用的選桌開桌對話框。

### E　訂位｜Harry Wang（另負責 L0 技術地基）

**負責範圍**：C-16c 選日期時段人數、C-18 訂位完成、C-19 我的預約、S-02d 開桌預約頁籤、S-07 預約管理、S-07b 預約報到；後端 M7 訂位（區間重疊、best-fit 配桌、併發控制、預約保留、取消、報到、兩支排程）。
另負責 **L0 技術地基**：Spring Boot 骨架、Docker Compose、Flyway、統一回應與全域例外處理、Spring Security＋JWT、用餐權杖 filter、WebSocket 設定與頻道權限、CI 與部署；以及前端 API client 分層、R2 圖片上傳、規格文件與分工規劃。

**報告亮點**

1. **主打：這張桌這個時間有沒有空**（[M7 問題 1、2](../spec/modules/M7-訂位.md)）
   - 直覺做法是切固定時段（11:30／13:30…），簡單但客人只能選那幾個時間，也學不到真實訂位系統的模型。
   - 我們存完整的開始、結束時間，用**區間重疊** `A.start < B.end AND B.start < A.end` 判斷；用 `<` 不是 `<=`，剛好接續不算衝突。
   - **清桌緩衝直接加進 `end_time`**（用餐 100 分＋清桌 15 分），把業務規則轉成資料，演算法完全不用知道緩衝存在。
   - `ORDER BY seats ASC LIMIT 1` 就是 **best-fit**：2 個人不佔 8 人桌，大桌留給大團。
2. **兩個人同時訂同一桌**（[M7 問題 3](../spec/modules/M7-訂位.md)）：配桌要做區間計算，壓不成一句條件式 `UPDATE`，所以用**悲觀鎖＋資料庫唯一約束 `UNIQUE(table_id, start_time)` 雙層保護**——程式有 bug，資料庫也擋得住。
3. **訂了位沒來**（[M7 問題 4](../spec/modules/M7-訂位.md)）：保留 10 分鐘，排程每 5 分鐘標 `NO_SHOW`；但**不能只靠排程**——報到 API 自己檢查時間（太早 `RESERVATION_TOO_EARLY`、太晚 `RESERVATION_EXPIRED`），保留窗、開桌清單、線上取消期限共用同一個設定值。
4. **預約保留是算出來的鎖定**：訂位前 30 分到後 10 分，桌況顯示「預約保留」，別人開這張桌回 `409 TABLE_RESERVED`；不動桌位欄位，所以取消、NO_SHOW 都不用「轉回去」（與 D 共同設計）。
5. **取消的訂位不佔位、已報到的只算到結帳**（[M7 問題 5](../spec/modules/M7-訂位.md)）：狀態納入重疊判斷，否則位子永遠訂不到或容量算錯。
6. **技術地基讓五個人能平行開發**：統一回應格式與全域例外處理（錯誤碼一致）、JWT 與用餐權杖兩條認證、WebSocket 頻道權限（只能訂閱自己那桌）、Flyway 版本化建表、Docker Compose 一鍵起環境、CI；前端 API client 分顧客端／員工端、權杖集中管理、錯誤統一成 `ApiError`。
7. **R2 圖片直傳**：後端簽 presigned URL，前端直接上傳到物件儲存，大檔不經過 Spring Boot。

**可能被追問**：區間重疊 SQL 要建什麼索引？悲觀鎖鎖的是哪一列（桌子還是訂位）？排程在多台機器重複跑怎麼辦？presigned URL 為什麼安全？為什麼選 Flyway？

**履歷建議**
