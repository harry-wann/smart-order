同桌購物車：由整桌送單改為本人送單

本篇記錄 2026-10-22 使用者提出的新規格調整。這是產品規則改變，不是原作者的程式錯誤。

規格變更重點：原規格是同一桌共用購物車、按下送單會送出全桌內容。新規格改為本人和同桌客人的內容分區；他人內容唯讀；只送出本人加入的品項；送單後保留其他人的購物車。

01 · 規格時間線

前後對照：交易範圍從整桌改成本人

左側是 develop 已合併的原規格與送單流程；右側是 2026-10-22 新規格。本次產品規則調整由 commit e323fac 實作。

原規格／原流程
  • 同一用餐場次的客人看同一份購物車。
  • 每一列保留加入者；加入者可修改自己的列。
  • 任一客人送單時，原流程會把該場次購物車整份建立成訂單。
2026-10-22 新規格
  • 畫面分出「本人」與「同桌客人」的購物車內容。
  • 本人只能修改自己的品項；同桌其他人的品項唯讀。
  • 按送單只送出本人加入的品項，其他人的內容繼續留在購物車。
為什麼這不算原作者 bug？

舊流程符合當時「送出整桌點餐」的規格。2026-10-22 使用者改了交易邊界：每位客人各自送出，且保留同桌其他人的未送內容。問題在新舊規格的行為不同，不應把原本符合規格的實作描述成作者犯錯。

02 · 實際情境

兩位客人各自加菜

以下以兩台裝置和兩位客人的操作呈現新規格要確認的行為。

  1. 裝置 A：客人 A 加入牛肉與飲料。

  2. 裝置 B：同桌客人 B 加入蔬菜與豆腐。

  3. 檢視購物車：A 能辨認自己的品項與 B 的品項；A 的區域可操作，B 的區域只能查看。

  4. A 送單：預期只有 A 的品項送出，B 的購物車仍保留。

  5. B 再檢查：B 重新查看時，自己的品項仍在；B 可以自行修改並送出。

03 · 變更範圍

規格改了哪裡

這個調整不只改按鈕文字，還改變「一次送單」包含哪些資料。

原送單範圍

原送單服務依用餐場次查出購物車列，整批建立成一張點餐單；提交者只記錄為誰按下送單，其他人的列也會一起被處理。

新送單範圍

後端用目前 guest 身分查出本人列，只把這些列建立成訂單並刪除；同桌其他人的列留在共用購物車。

修正後送單服務以 findByDiningSession_IdAndAddedByGuest_IdOrderByIdAsc(sessionId, guestId) 查詢本人列，再依序建立點餐單。這個查詢方法由 repository（集中資料庫查詢的類別）中的 Spring Data JPA（協助依方法名稱產生查詢的工具；JPA — Java Persistence API（Java 持久化介面，現稱 Jakarta Persistence））處理。命名分段：DiningSession_Id 是「哪一次用餐」，AddedByGuest_Id 是「哪位客人加入」，OrderByIdAsc 是「依購物車列編號由小到大排序」。這是依 2026-10-22 新規格調整資料範圍，不是原作者 bug。

04 · 權限邊界

「擁有者」是加入該列的客人

owner（資料擁有者）在這個情境中指加入該購物車品項的用餐客人。不是誰正在看畫面，也不是由瀏覽器任意指定的一個人。

前端：讓操作方式看得懂

畫面用 isOwnItem 把全桌品項分成本人區與他人區；本人區置頂，他人區唯讀，小計只加總本人列。實際按鈕狀態由 isOwnItem 搭配 locked 決定，前端沒有直接讀 canEdit 來控制按鈕。API（Application Programming Interface，應用程式介面）中的 canEdit 是對應的權限欄位；locked 由後端回傳，表示 session 已非 OPEN、本桌已停止點餐。單次請求處理中則由 busy 表示。隱藏或停用按鈕本身仍不能阻止直接送出請求。

後端：每次操作重新確認身分

伺服器從已驗證的用餐請求取得目前客人，再檢查品項所屬用餐場次與加入者。更新或刪除其他人的品項回 403（拒絕這次操作）；送單查詢也以目前客人的 guestId 篩選，因此只會建立本人的訂單列。不能只靠前端篩選。

前端與後端的差別

isOwnItem 表示「這列是不是目前 guest 加的」，用來分區並計算本人小計；canEdit 表示「目前是否允許編輯這列」，是 API 回傳的權限欄位。實際前端按鈕以 isOwnItem 和 locked 組合決定，沒有直接讀 canEdit。前端（瀏覽器裡的畫面）負責清楚呈現，後端（伺服器上的程式）則在每次修改、刪除與送單時再次檢查權限。前端分區方便使用，後端驗證才保護資料。

本人區 = filter(items, isOwnItem 為 true)
他人區 = filter(items, isOwnItem 為 false)
本人小計 = 加總(本人區各列的 lineTotal)

filter 是「從清單挑出符合條件的列」；lineTotal 是單列金額，等於該列單價乘上份數。這段是邏輯示意：isOwnItem 用來決定列放在哪一區及哪些金額列入本人小計；按鈕是否能操作則依實作組合本人身分與 locked 狀態。前端計算只為了畫面顯示，送單範圍由後端再次查詢並核對。

05 · 修正流程

依新規格拆解的修正流程

從客人身分、操作權限到送單後保留內容，逐段檢查同一個雙人情境。

  1. 確認目前客人：沿用伺服器驗證的 guest 身分，避免把可偽造的裝置提示當作資料擁有者。

  2. 查出本人列：repository 使用 findByDiningSession_IdAndAddedByGuest_IdOrderByIdAsc(sessionId, guestId)，同時依用餐場次和加入者查詢並依列編號排序。

  3. 分區與計算：前端依 isOwnItem 篩成本人區和他人唯讀區，以 isOwnItem 搭配 locked 控制操作按鈕，僅將本人列的金額加成本人小計。

  4. 交易只處理本人列：依序讀取本人列、建立點餐單、刪除本人已送列、更新帳單與通知；同桌其他人的購物車列保留。e323fac 的成果範圍是依 owner 篩選送單列與保留他人購物車。

  5. 保護切桌後畫面：切換桌位時遞增請求 generation（世代編號）；非同步請求帶著送出時的編號，回來時若桌位已換，就忽略舊回應，不讓舊桌結果覆蓋新桌狀態。

同桌有人同時送單時，後端以用餐場次資料列鎖（row lock）讓單號和帳單更新依序進行；交易（transaction）把相關資料庫步驟當成一組，避免只保存一半。這是在解釋整體流程中的併發保護，不是 e323fac 新增的功能範圍。

切桌 generation 是這次整合補強，目的是隔離上一桌尚未完成的請求，不應歸責原作者。確認範圍包含延遲的舊 204（成功、沒有回應內容）與舊 409（資料狀態衝突）返回後，新桌的 busy（等待處理）狀態、錯誤提示和導頁仍受保護。

06 · 手動確認

雙裝置手動確認步驟

基本操作確認（Smoke test，冒煙測試）是快速走過主要流程。實際驗證使用兩個隔離的瀏覽器身分模擬兩支手機，並搭配 HTTP（Hypertext Transfer Protocol，超文字傳輸協定）請求；不是兩台實體手機。以下步驟保留給讀者手動重做。

  1. 準備：可使用兩台手機，或兩個彼此隔離的瀏覽器身分；讓 A、B 加入同一張桌的同一個用餐場次，確認各自持有不同的客人身分。

  2. 分別加購：A 和 B 各加入不同品項，檢查雙方都看得到全桌內容，且本人區在上、他人區唯讀在下，小計只含本人列。

  3. 檢查後端權限：以 A 的身分對 B 的列發出 PATCH（更新既有資料）與 DELETE（刪除資料）請求，兩者都應回 403；測試結果為兩項皆拒絕。

  4. 分別送單：A 送出後確認訂單只有 A 的列、B 的列仍保留；再由 B 送出，B 的品項也能成立另一張單。

  5. 確認空車邊界：A 沒有本人待送列時，即使 B 還有列，A 送單仍回 409 CART_EMPTY（資料狀態衝突），不會代送 B 的品項。

  6. 確認重複請求：對同一 guest 同時送出兩個請求，確認一個回 201（成功建立），另一個回 409 CART_EMPTY；兩個不同 guest 各有品項時則各成立一張單。

  7. 確認切桌保護：在 A 的請求仍等待時切換到另一桌，讓舊桌的延遲成功與錯誤回應返回；新桌的 busy 狀態、錯誤提示與導頁不應被舊回應改寫。

08 · 驗證證據

程式提交與確認證據

Commit（版本提交）是將一組程式變更記進版本歷史，便於確認這篇說明對應哪一版程式。

修正提交

e323fac — fix(yiting): separate personal cart items and submit only owned items

代表 2026-10-22 個人購物車送單規格調整的程式提交。

操作確認

後端 clean package（清理舊建置產物後打包）與前端 build（整理成可執行或部署的產物）通過；56 項 HTTP（Hypertext Transfer Protocol，超文字傳輸協定）檢查、23 項瀏覽器檢查通過；獨立檢視修正後沒有新發現。

他人 PATCH／DELETE 為 403；只送本人列並保留他人列及選項；本人空車為 409 CART_EMPTY；同 guest 同時送兩個請求為一個 201、一個 409。

HTTP 狀態碼白話：201 表示建立成功；204 表示操作成功但沒有回應內容；403 表示目前身分不允許操作；409 表示目前資料狀態不允許這次操作。

WebSocket（雙向即時通訊）新增曾單次觀察到 129ms，這是單次量測，不是效能保證。

切桌後，延遲返回的舊 204 與舊 409 都沒有改寫新桌 busy（等待處理）、錯誤或導頁狀態。

09 · 審查建議

本次審查建議（技術前輩角度）

先保留每列加入者與後端 ownership（擁有權）檢查這項基礎，再用雙人情境定義讀取、修改、送單與保留範圍。面試時應能以 A、B 操作證明他人列可讀不可改，以及 A 送單不會清掉 B 尚未送出的購物車。

10 · 報告與面試

可說明的技術亮點

以下說法以這次已完成的規格調整與操作證據為準。

報告可說明的技術亮點

「需求從任一人送出全桌購物車，改成每位客人只送自己的列。我用 guest 身分查詢本人購物車，後端更新與刪除會驗 owner，前端則把本人可操作區和他人唯讀區分開；兩位 guest 的送單在同一 session 鎖下依序更新單號與帳單。」

可以用 A 能看 B 的品項、但不能改或刪 B 的列，以及 A 送單後 B 的購物車仍保留，說明「看得到」和「有權操作」是不同事情。

面試時可準備的追問

為什麼不能只在畫面隱藏修改按鈕？購物車品項如何知道加入者？交易中如何確保只刪除已送出的列？另一位客人送單時會看到什麼？每題都要用實際程式或確認結果回答。

12 · 名詞說明

專有名詞

API — Application Programming Interface（應用程式介面）
畫面向伺服器讀取資料或提出操作要求時使用的固定入口。
HTTP — Hypertext Transfer Protocol（超文字傳輸協定）
瀏覽器和伺服器交換請求、回應時使用的通訊規則。
owner（資料擁有者）
本案例中指加入該購物車列的用餐客人；擁有者應由伺服器驗證的身分決定。
guest（用餐客人）
加入某次用餐場次的其中一位客人；同桌每位客人各有自己的身分。
session（用餐場次）
某一桌從開桌到結帳或取消的這一次用餐紀錄。
guestToken（用餐客人權杖）
伺服器簽發或驗證的用餐身分憑證；後端用它判斷請求來自哪位客人，不應由畫面自行指定。
repository（資料查詢類別）
集中撰寫資料庫查詢與資料存取方法的程式類別，讓其他程式不必自己拼 SQL。
JPA — Java Persistence API（Java 持久化介面，現稱 Jakarta Persistence）
用 Java 物件表示資料並對應資料表的標準介面。Spring Data JPA 可依 repository 方法名稱產生常用查詢。
filter（篩選）
從一份清單挑出符合條件的資料列，例如把本人加入的購物車列挑出來。
lineTotal（單列金額）
這一列的單價乘上份數；本人小計只加總本人區各列的金額。
BigDecimal（精確十進位數字類別）
Java 用來表示金額等十進位數值的類別，避免一般二進位浮點數的近似誤差。
canEdit（是否可編輯）
API 回傳的權限欄位，描述目前是否可以編輯該列；這個畫面的按鈕實際以 isOwnItem 和 locked 組合控制。
isOwnItem（是否為本人品項）
表示購物車列是否由目前 guest 加入。前端可依它分區並計算本人小計；它回答「屬於誰」，不等同於目前一定能編輯。
addedByGuest（加入該列的客人）
購物車資料所記錄的加入者，用於把品項和客人身分對起來。
locked（本桌已停止點餐）
來自後端 CartResponse.locked；表示用餐 session 已不是 OPEN，例如本桌已結帳，因此不能再點餐。它不是單次請求的等待狀態。
busy（單次操作處理中）
前端表示某個請求尚在等待或處理中的狀態，例如送單按下後等待伺服器回應；和代表本桌已停止點餐的 locked 不同。
transaction（資料庫交易）
把多個資料庫步驟當成一組處理；成功時一起保存，失敗時可以一起取消，避免只完成一半。
row lock（資料列鎖）
暫時鎖住一筆資料，讓同一用餐場次的同時操作依序處理，避免單號或帳單互相覆蓋。
WebSocket（雙向即時通訊）
讓瀏覽器與伺服器維持連線，伺服器可即時通知同桌其他裝置購物車或訂單有變化。
build（建置）
整理並編譯程式，產生可執行或部署的檔案。
clean package（清理後打包）
先移除前一次的建置產物，再打包目前程式；用來確認乾淨狀態下仍可建置。
HTTP 201／204／403／409
201：建立成功；204：操作成功且沒有回應本文；403：不允許此身分操作；409：資料目前的狀態與請求衝突。
PATCH（部分更新）
只修改既有資料的一部分，例如購物車列的數量或備註。
DELETE（刪除）
要求移除指定資料，例如刪除自己加入的購物車列。
generation（世代編號）
切換用餐桌位時增加的流水編號。非同步請求回來時先比對編號，舊桌請求不能改動新桌畫面狀態。
Smoke test（冒煙測試）
快速走過主要操作路徑，確認基本流程能回應；它不等於完整測試。
SHA（Secure Hash Algorithm，安全雜湊演算法）
版本提交識別碼由雜湊值縮短而來；本文使用短識別碼 e323fac 對應修正提交。
