櫃檯結帳與場次安全

結帳流程 指定 HTTP API 與瀏覽器驗收通過 修正提交：b0c2432

這篇把五個已確認的結帳與訂單存取問題，整理成「發生情境 → 原因 → 修法 → 如何操作驗收」。另外說明前端如何避免舊請求覆蓋新帳單，以及場次結束通知的處理方式。

本次指定 HTTP API 冒煙驗證 156 項通過，瀏覽器驗收 27 項通過。驗證集中在已列出的流程與付款視窗，不代表所有裝置、瀏覽器或營運情境都已涵蓋。

先掌握這條結帳路徑

櫃檯畫面先讀取指定桌號目前的用餐場次，再顯示這個場次的帳單。店員選付款方式後，前端把當下看到的總額一起送給後端；後端重新計算並比對。成功後才記錄付款、關閉該場次並更新桌況。

因此，付款操作的識別對象是「場次編號」，不是單獨的桌號。桌號會重複使用，場次編號則代表一次具體的用餐。

問題一 · 權限

櫃檯明細、結帳和取消操作不能只靠藏按鈕

發生情境

沒有員工登入憑證的人，可能直接呼叫櫃檯明細或結帳網址；若取消訂單品項的路徑也沒有伺服器權限檢查，只把畫面按鈕藏起來並不能阻止直接送請求。

原程式原因

部分管理操作落在公開的 API 路徑規則之下。前端顯示與否不是安全邊界，因為使用者仍能自行組出 HTTP 請求。

目前修法與位置

backend/src/main/java/.../config/SecurityConfig.java 在公開 API 規則之前明確限制管理路徑：櫃檯明細、場次明細與結帳要求櫃檯或店長角色；單品取消依路徑規則要求櫃檯、店長或廚房角色；空場次取消只允許店長。後端服務仍會檢查場次狀態與操作條件。

控制器入口在 TableController 與 OrderSubmitController。角色名稱對照：COUNTER 是櫃檯、MANAGER 是店長、KITCHEN 是廚房。

操作驗收

  1. 不帶員工登入憑證，直接讀取 GET /api/admin/tables/{桌號}/detail，確認伺服器拒絕。
  2. 以顧客憑證呼叫管理員的結帳或單品取消路徑，確認伺服器拒絕；只隱藏畫面按鈕不算通過。
  3. 以有權限的櫃檯或店長登入，再讀取明細並執行允許的操作，確認成功。

問題二 · 顧客資料範圍

顧客訂單明細必須屬於目前登入的場次

發生情境

顧客知道或猜到另一張訂單的編號時，嘗試直接開啟那張訂單的明細。

原程式原因

若只用訂單編號查資料，沒有再確認訂單所屬場次，登入狀態本身不足以限制顧客讀取範圍。

目前修法與位置

SessionTokenFilter 驗證顧客憑證後，將其中的場次編號放入此次請求上下文。OrderSubmitController 的 GET /api/order-tickets/{id} 取得這個場次編號，再呼叫 OrderSubmitService.getOrder(ticketId, sessionId)。服務會確認訂單和場次相符，不相符就回傳找不到，避免洩漏另一桌的訂單內容。

操作驗收

  1. 用 A 場次的顧客憑證讀取 A 的訂單，確認明細可見。
  2. 沿用 A 的憑證，把網址中的訂單編號換成 B 場次的訂單編號，確認不能取得 B 的明細。
  3. 用 B 的憑證讀取 B 的同一張訂單，確認原本的顧客仍可正常查看。

問題三 · 金額確認

櫃檯看到的總額必須和實際結帳總額一致

發生情境

櫃檯打開帳單後，同桌又有人加點、取消品項或改變了帳單。店員按下付款時，畫面上的金額已經過期。

原程式原因

結帳請求只帶付款方式，後端便以請求到達時的帳單金額完成付款，沒有確認店員看到的金額是否仍相同。

目前修法與位置

TableDetail.jsx 在店員按下付款的當下，凍結場次編號、付款方式、小計、服務費與總額。services/api/table/tableApi.ts 呼叫 POST /api/admin/dining-sessions/{id}/settle，送出 { method, expectedTotal }。後端 TableService.settle(sessionId, request) 鎖定正確場次並重新計算帳單；總額不同時回傳 BILL_CHANGED 和完整的新帳單，不完成付款。前端更新畫面並要求店員再次確認，不會自動重送。

操作驗收

  1. 打開帳單並記下總額，先不要付款。
  2. 讓同桌另一位顧客新增或取消一個品項，改變場次帳單。
  3. 送出舊畫面上的付款確認，確認收到 BILL_CHANGED、顯示最新帳單並關閉付款確認視窗。
  4. 確認畫面沒有替店員自動完成第二次付款；店員重新核對並按一次付款後，才送出新的確認。

問題四 · 場次識別

桌號被重用後，舊畫面不能結掉新一桌的帳

發生情境

店員開著某桌的舊畫面。原場次結束後，桌子又接待下一組客人；如果舊畫面仍以桌號送出付款，它可能操作到新場次。

原程式原因

桌號是會重複使用的位置編號，不能單獨表示哪一次用餐。舊流程以桌號作為付款目標，缺少一次用餐的精確識別。

目前修法與位置

櫃檯明細回傳 sessionId、sessionStatus 和 hasOrderHistory。前端付款時使用當下讀到的 sessionId；管理端 API 對場次使用 /api/admin/dining-sessions/{id} 與 /settle，不再用桌號尋找付款對象。TableService.settle 鎖定該場次及其桌況，確認仍是有效的開啟場次，才繼續付款。

操作驗收

  1. 開啟桌子 A 的場次明細，保留這個櫃檯畫面。
  2. 以另一個有權限的流程結束原場次，讓桌子 A 開始新的場次。
  3. 從舊畫面送出原場次付款，確認後端不會結束新場次；新場次帳單與狀態保持完整。
  4. 重新讀取桌子 A 的明細，確認新的 sessionId 與新帳單一致。

問題五 · 操作時序

倒數必須從 5 到 0，成功後等待 1.5 秒再離開

發生情境

櫃檯操作規格要求先倒數五秒，歸零後才送出付款；成功畫面保留一小段時間，再回到桌況頁。

原程式原因

舊畫面倒數顯示與實際等待行為不一致：畫面從 3 顯示到 1，之後還會再等待約 10 秒，成功後的回頁節奏也不符合需求。

目前修法與位置

PaymentProcessing.jsx 以明確的付款階段倒數 5、4、3、2、1、0。只有歸零時可以呼叫一次付款；送出中鎖住付款和取消操作。歸零前取消只關閉流程、不送出付款。成功畫面顯示 1.5 秒後才返回桌況頁；請求失敗則顯示錯誤，不會誤顯示成功。

操作驗收

  1. 開啟付款確認，觀察畫面依序從 5 倒數到 0；在 0 之前取消，確認沒有送出結帳請求。
  2. 重新付款並等到 0，確認只出現一次結帳請求；送出期間付款與取消控制不可重複操作。
  3. 讓後端回覆錯誤，確認畫面顯示錯誤而非成功。
  4. 完成付款，確認成功畫面保留約 1.5 秒後才返回桌況頁。

付款視窗畫面紀錄

1440px 與 390px 寬度下可辨識倒數、金額和取消操作

兩張圖都來自隔離驗收資料。畫面停在倒數 5 秒時截圖，隨即按取消並確認沒有送出結帳請求；這不是實際付款。窄畫面結果只說明付款對話框在 390px 視窗內可用，不代表整個管理後台都已完成窄螢幕響應式驗收。

跨畫面時序

舊請求、金額變更和場次結束都要有明確的先後判斷

帳單刷新不讓慢回應蓋掉新資料

TableDetail.jsx 對每次帳單讀取編流水號。只有目前最新的一次讀取可以更新畫面。收到 BILL_CHANGED 時也會使先前尚未完成的讀取失效，再套用錯誤回應內附的完整帳單。如此一來，較早開始、較晚返回的舊讀取不能把新帳單蓋回去。付帳期間使用的金額則來自付款按下瞬間凍結的資料，不跟背景刷新一起變動。

場次結束有 WebSocket 通知，也有可辨認的 401 回應

後端 SessionTokenFilter 對簽章及裝置資料有效、但場次已關閉的顧客憑證，回傳 INVALID_SESSION_TOKEN，並附上 reason: PAID 或 reason: CANCELLED。真正無效的憑證沒有這個原因。customerClient 清除被拒絕的對應憑證，但保留並傳遞原錯誤，讓頁面判斷結束原因。

顧客選單與購物車的請求錯誤、連線檢查和 WebSocket 場次結束事件都交給一致的結束處理方式：PAID 顯示已結帳完成畫面；CANCELLED 清除憑證並回入口；沒有結束原因的無效憑證走重新掃碼或入口流程。購物車收到場次結束事件時不再另外發起一個可能因 401 搶先導頁的讀取。

這些事件處理會核對目前頁面仍掛載、場次編號及切換代號仍相符。若使用者已切到另一場次，舊場次的回應或通知就不能清掉新場次狀態、顯示舊錯誤或把人帶離新頁面。

操作驗收

  1. 讓舊帳單讀取延遲，再收到新帳單通知；確認舊讀取晚到時不會覆蓋新帳單。
  2. 付款按下後，在背景帳單更新期間確認付款內容仍是當時凍結的場次、付款方式和總額。
  3. 一桌完成付款後，確認顧客看到「已經結帳完成」；另一桌取消時，確認顧客回到入口。
  4. 在舊桌請求尚未回覆時切換到另一桌，再讓舊回應或舊通知到達；確認新桌畫面、錯誤狀態和導頁不受影響。

協作收尾

本次一起接齊的流程

以下是讓結帳前後能連成一條可操作流程的整合工作，不列為原作者的五項缺失。

  • 取消沒有訂單的空場次：櫃檯可提出取消確認，只有店長能呼叫 POST /api/admin/dining-sessions/{id}/cancel；後端只接受沒有訂單的場次，取消後清理購物車並釋放桌子。
  • 帳單即時更新：BillingNotifier 在資料庫交易成功提交後，才通知員工端重新讀取同一場次帳單。useBillingSocket 也會在重連、視窗返回前景或網路恢復時刷新，以補上離線期間的變更。
  • 結束事件在提交後通知：付款或空場次取消完成後，服務在交易提交後發出顧客場次結束訊息和櫃檯桌況更新。顧客端依付款或取消原因顯示對應結果。
  • 維持既有防重複機制：後端原本就有同場次結帳鎖，避免同一場次被重複結帳。本次沒有把「原本可並發雙重扣款」當成缺陷；新增的總額比對補上的是櫃檯畫面過期時的確認。

學習與表達

前輩建議：把狀態邊界和資料歸屬說清楚

這類流程的關鍵不只在按鈕能否點擊，而是每筆請求代表哪個場次、使用者是否有權讀取、金額以哪個時間點為準，以及舊回應能否影響已切換的畫面。走讀時先畫出「畫面 → API → 權限過濾器 → 服務 → 資料庫 → 通知」路徑，再逐段確認資料歸屬與失敗分支，通常比只追成功案例更快找到缺口。

驗收也要涵蓋競爭順序：舊讀取晚到、新帳單先到、場次先關閉、使用者再切桌。單看每個請求各自成功，無法證明組合時序安全。

報告可以怎麼呈現

用一張時序圖呈現店員讀帳單、顧客同時改單、付款送出與 BILL_CHANGED 的順序；再用一張權限表對照匿名、顧客、櫃檯、店長和廚房可執行的操作。這能讓讀者快速理解金額確認與角色檢查各自解決什麼問題。

結果段落要分清楚「原始程式的五項問題與本次修正」和「協作收尾接上的通知、空場次取消與整合驗證」，也應列出未涵蓋的裝置、瀏覽器或營運例外，不把局部冒煙結果寫成全面保證。本次 HTTP API 156 項及瀏覽器 27 項均有報告可查；桌面與窄螢幕兩張截圖僅驗收付款對話框。

履歷描述建議

可依實際負責範圍寫成：「修正櫃檯結帳流程的權限、顧客訂單場次隔離、金額變更確認、桌號重用與付款倒數問題；以場次識別、交易鎖、最新請求序號與結帳總額比對，避免舊畫面或過期回應影響付款；參與即時帳單更新與場次結束通知整合，並以 HTTP API 與瀏覽器操作驗收主要流程。」

若某項通知或整合由協作者完成，履歷可寫「參與整合」或「協作驗收」，不要寫成自己獨立設計或實作。可寫明本次指定驗證有 156 項 API、27 項瀏覽器檢查通過，同時說明這些數量不代表全產品測試。

新手名詞表

本文常用詞

API — Application Programming Interface（應用程式介面）
讓前端與後端依約定路徑和資料格式交換資訊的入口。
HTTP — Hypertext Transfer Protocol（超文字傳輸協定）
瀏覽器和伺服器常用的請求與回應規則；例如讀取明細或送出結帳。
JSON — JavaScript Object Notation（JavaScript 物件表示法）
常見的文字資料格式，例如付款請求中的付款方式與預期總額。
JWT — JSON Web Token（JSON 網頁權杖）
一種帶有簽章的登入憑證格式。服務端仍須檢查憑證所屬場次與目前狀態。
UI — User Interface（使用者介面）
使用者實際看到和操作的畫面。藏起按鈕不能取代後端權限檢查。
WebSocket（網頁雙向連線）
建立後可由伺服器主動推送更新的連線方式；本流程用來通知帳單或場次狀態改變。
401 未授權
伺服器表示這個請求沒有可接受的登入憑證。這次流程另用結束原因區分已付款、已取消與一般無效憑證。
409 Conflict（資源狀態衝突）
請求格式可讀，但目前資料狀態不允許照原內容完成；本流程的 BILL_CHANGED 會附上最新帳單，要求重新確認。
交易提交後通知（afterCommit）
先讓資料庫確認付款或取消已正式完成，再發送外部通知，避免通知內容和實際資料狀態不一致。
冒煙驗證（smoke test）
用少量端到端操作快速確認主要流程能工作；它有範圍限制，不能代替完整測試或所有情境驗收。
