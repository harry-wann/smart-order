01 · 哪裡錯

沿著一筆點餐，追蹤金額和狀態

1. 送單沿用加入購物車時的舊價格

修正前

客人把肉品加入購物車後菜單改價，再送單。正式訂單沿用購物車存的舊單價，帳單沒反映送單當下的菜單價格。

修正後

OrderSubmitService.submitOrder() 先呼叫 OrderValidationService.validate() 鎖定並讀取菜單現價，用它寫入 unit_price_snapshot，再加選項價差算明細金額。為什麼：購物車價格只供送單前顯示，正式訂單要固定送單那一刻的價，日後再調價也不改寫舊單。

2. 選項群組名稱快照是空白

修正前

客人選「份量：全份」「加點：蔥花」後送單，明細有選項值，群組名稱快照卻是空字串，之後看舊單無法還原選項屬於哪個群組。

修正後

validate() 讀取選項值、所屬群組名稱與價差，組成 OptionSnapshot，送單時寫進 order_item_option；同時確認所選值仍有效且屬於該品項，否則整筆送單被拒絕，交易不留半張訂單。為什麼：名稱要在送單當下存好，舊單才看得懂。

3. 服務費被取整到整數元

修正前

小計 15.00 元、服務費率 10%，服務費應是 1.50 元、總額 16.50 元，卻被取整成 2.00 元，總額變 17.00 元。

修正後

BillingCalculator.calculate() 從有效明細加總小計，以 subtotal × 0.10 加 RoundingMode.HALF_UP（四捨五入）保留兩位。送單與取消都呼叫同一個 recalculateAndStore()。為什麼：金額取整到元會多收或少收，兩條路徑共用同一套規則。

4. 取消餐點後，帳單仍是舊金額

修正前

客人只點一份 100 元餐點，帳單含 10 元服務費共 110 元。櫃檯取消後明細不再列出，帳單總額仍顯示 110 元。

修正後

cancelItem() 與 cancelTicket() 在同一筆交易內更新取消狀態、回補庫存，再呼叫 recalculateAndStore() 重算（排除已取消的單與明細），上例會回到 0.00 元。為什麼放同一筆交易：任何一步失敗就整組回復，不會留下「已取消但帳單沒變」。

5. 整張點餐單取消後，單與明細狀態不一致

修正前

廚房取消整張點餐單，單的狀態已是取消，裡面的餐點明細仍是原狀態。畫面或計算分別讀單與明細，會得到兩種答案。

修正後

cancelTicket() 逐筆把仍可取消的明細改成 CANCELLED，再把單改成 CANCELLED；先逐項取消過的明細保留原取消狀態。為什麼：單與明細要一起變，「這張單有沒有效」才只有一個答案。已出餐的整單拒絕取消，已結帳的場次也不能取消。

02 · 後續修正（整合時發現）

改了「是否追蹤庫存」之後，取消會補錯庫存

這不是原本的寫法錯。後來菜單管理讓店長可以隨時切換品項的「是否追蹤庫存」，原本的假設就不成立了：取消流程判斷「要不要補回庫存」時，看的是品項現在的設定，不是送單那一刻的設定。

修正前（實測）

不追蹤時點 3 份，店長改成追蹤、庫存設 20，再取消：庫存變 23，憑空多 3 份。反過來，追蹤時點 3 份（20 扣成 17），改成不追蹤再取消：庫存停在 17，那 3 份不見了。單品取消、整單取消都一樣。

修正後

每筆訂單明細多記一個 stock_deducted：送單時有沒有真的扣庫存。取消只看這個紀錄，有扣才補。上面兩個情境的結果都是 20。為什麼：之後可能被改、但當下的值會影響後續處理的資料，要在當下存一份，這就是快照。

  • 紀錄要跟扣庫存「同一刻」：送單時先鎖住品項（SELECT … FOR UPDATE）才讀「是否追蹤」並扣庫存，stock_deducted 也用同一個值寫入。店長要切換設定得改同一列，會被鎖擋住排隊，所以紀錄和實際扣庫存一定一致。顧客送單與櫃檯代客點餐走同一段程式。
  • 舊資料怎麼辦：升級腳本 migrate_order_item_stock_deducted.sql 先把欄位加成可空白，只替空白的列用品項現在的設定回填（舊單當時的設定已查不到，這是最好的推測），最後才改成不可空白；中途斷掉重跑也能補完。
03 · 一起接齊的流程

鍋底、選項、庫存與取消一起維持一致

以下是整合時補上的保護，不算原作者的缺失。

  • 鍋底規則：validate() 先看本次送單列是否含鍋底，沒有再查該場次是否已有未取消的鍋底明細。其他客人放在購物車、尚未送出的鍋底不算已點，不能替別人通過規則。
  • 選項有效性：送單時鎖定菜單、選項群組與選項值，重新確認品項仍上架、選項仍啟用且屬於該品項，並檢查每個群組的最少與最多選擇數。
  • 庫存競爭：先鎖用餐場次，再依品項編號排序取列鎖（固定順序可降低死結）。扣庫存用 InventoryRepository.decreaseIfEnough() 一句「庫存夠才扣」的更新，影響筆數不是 1 就是不夠，回 ITEM_SOLD_OUT，同筆交易的扣庫存、訂單、帳單、購物車變更一起回滾。
  • 取消回補：只回補 track_inventory=true 的品項；取消服務鎖用餐場次並用狀態條件更新，重複取消或同時取消都不會補第二次。已出餐的單項、整單與已結帳場次都拒絕取消。已出餐餐點的報廢屬另一套政策，後來在出菜看板補上，見 Clara 的出菜看板文章。
  • 通知時機：訂單、取消、售完狀態在資料庫交易提交後（afterCommit）才推送，交易回滾就不會先讓其他畫面收到尚未保存的狀態。

05 · 用到的技術與設計模式

本篇真的用到的

  • 悲觀鎖（SELECT … FOR UPDATE）與固定鎖順序：送單、取消先鎖用餐場次再依編號鎖品項（OrderValidationService、OrderCancellationService）。
  • 樂觀並發控制（條件式 UPDATE）：扣庫存「夠才扣」、取消用狀態條件更新（InventoryRepository）。
  • 快照：送單當下存單價、品名、選項名稱與價差、是否扣過庫存（OrderItemEntity）。
  • 單一真相來源：帳單一律由 BillingCalculator 從有效明細重算，送單與取消共用；金額用 BigDecimal（Java 精確表示十進位數的類別）。
  • 資料庫交易與回滾：@Transactional(isolation = READ_COMMITTED)，失敗整組回復。
  • 交易提交後才通知（afterCommit）：KitchenNotificationService 等通知類別。
  • JdbcTemplate 原生 SQL（Structured Query Language，結構化查詢語言）：鎖定品項、選項時用原生 SQL（OrderValidationService）。
  • 學到什麼：判斷依據要在「當下」記下來，不要事後看現在的設定；面試要能用一個案例說清楚哪一步失敗、為什麼回滾、取消後帳單怎麼從有效明細重算。
06 · 名詞說明

專有名詞

snapshot（快照）
在某個時間點複製並保存資料，例如送單時的品名與價格，舊訂單不受之後菜單修改影響。
transaction／rollback（資料庫交易／回滾）
把多個資料庫操作當一組，全部成功才保存；中途失敗就撤銷未提交的變更，一起回復。
row lock（列鎖）
暫時鎖住一筆資料，讓同時操作的交易排隊，避免互相覆寫。
deadlock（死結）
兩個交易各拿著對方要的鎖互相等待；都照固定順序上鎖可降低機率。
條件式更新
在 SQL 的更新裡加條件，例如「庫存夠才扣」，用影響的資料列數判斷成不成功。
BigDecimal／HALF_UP
Java 精確表示十進位數的類別／四捨五入規則；金額要明確規定小數位數與捨入。
afterCommit（提交後回呼）
資料庫交易成功提交後才執行的程式，用來發通知。
smoke test（冒煙測試）
快速走過最重要的操作路徑確認基本流程能運作，不能取代完整測試。
