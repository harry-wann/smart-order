02 · 價格快照

送單時沿用加入購物車的舊價格

原問題表現

客人先把一份肉品加入購物車，之後菜單價格更新，再送出點餐。原問題是正式點餐單沿用加入購物車時保存的舊單價，帳單沒有反映送單當下的菜單價格。

目前程式怎麼處理

加入購物車時會保存 cart_item.unit_price，但送單不能把它當成正式訂單價格。現在的 OrderSubmitService.submitOrder() 先呼叫 OrderValidationService.validate() 鎖定並讀取菜單當下的價格；建立明細時使用這個價格寫入 unit_price_snapshot，再以單價加選項價差計算明細金額。

目前修法：OrderValidationService.validate() 對購物車內的菜單品項逐一讀取並鎖定目前資料；OrderSubmitService.submitOrder() 以回傳的 MenuSnapshot.price() 作為正式單價，並保存品名、單價、選項價差、數量與明細總額。如此可保留送單時價格，即使之後菜單再調整也不會改寫舊單。

讀程式位置：backend/src/main/java/tw/ispan/smartorder/ordersubmitted/service/OrderSubmitService.java 的 submitOrder()；backend/src/main/java/tw/ispan/smartorder/service/OrderValidationService.java 的 validate()。

手動 smoke 步驟：價格更新後再送單
  1. 在隔離測試資料中記下某品項目前菜單價格，並由客人加入購物車。
  2. 在測試環境更新該品項菜單價格，保留購物車中已加入的那列。
  3. 送出點餐後查看新點餐單的單價與帳單金額。
  4. 確認 order_item.unit_price_snapshot 等於送單時的菜單價格，明細金額也以該快照加選項價差計算。
03 · 選項快照

有選項的明細，群組名稱快照是空白

原問題表現

客人為肉品選擇「份量：全份」或「加點：蔥花」後送單。原問題是明細雖有選項值，群組名稱快照卻是空字串；之後查看舊單時，無法從快照還原選項屬於哪個群組。

目前程式怎麼處理

審查確認的舊問題是送單快照沒有保存所屬群組名稱。現在 OrderValidationService.validate() 會讀取選項值、所屬群組名稱與價差，組成 OptionSnapshot；OrderSubmitService.submitOrder() 再將群組名稱、值名稱及價差寫入 order_item_option。

目前修法：驗證階段會確認所選值仍有效且屬於該品項，再從選項值所屬群組取名稱。送單時將 OptionSnapshot.groupName()、valueName() 與 priceDelta() 寫入快照；若選項已停用或不屬於品項，整筆送單會以用戶端錯誤回應，資料庫交易不會留下半張訂單。

讀程式位置：backend/src/main/java/tw/ispan/smartorder/service/OrderValidationService.java 的選項驗證與 OptionSnapshot；backend/src/main/java/tw/ispan/smartorder/ordersubmitted/service/OrderSubmitService.java 的選項快照保存。

手動 smoke 步驟：檢查選項群組快照
  1. 選一個有群組和選項的品項，例如指定份量或加點內容，加入購物車並送單。
  2. 在測試資料庫查看該點餐明細的選項群組快照與選項值快照。
  3. 確認群組名稱、選項值名稱及價差快照都有保存，且與送單時選擇相符。
04 · 金額精度

服務費被四捨五入到整數元

原問題表現

小計為 15.00 元、服務費率為 10% 時，服務費應是 1.50 元，總額應是 16.50 元。原問題是送單時計算曾把服務費取整到元，得到 2.00 元，總額變成 17.00 元。

目前程式怎麼處理

服務費屬於金額，取整到整數元會造成帳單多收或少收。現在金額由 BillingCalculator.calculate() 從該用餐場次仍有效的訂單明細加總，服務費率為 10%，再用 HALF_UP 捨入至小數點後兩位。

目前修法：BillingCalculator.calculate() 先把有效明細小計整理為兩位小數，再以 subtotal × 0.10 計算服務費並使用 RoundingMode.HALF_UP 保留兩位，最後計算總額。送單與取消都呼叫同一個 recalculateAndStore()，因此使用相同的金額規則。

讀程式位置：backend/src/main/java/tw/ispan/smartorder/service/BillingCalculator.java 的 calculate() 與 recalculateAndStore()；backend/src/main/java/tw/ispan/smartorder/ordersubmitted/service/OrderSubmitService.java 的 submitOrder()。

手動 smoke 步驟：核對小數金額
  1. 在隔離測試資料中準備小計正好為 15.00 元的點餐內容，服務費率使用 10%。
  2. 送出後查看服務費、小計與總額。
  3. 確認服務費為 1.50 元、總額為 16.50 元，而不是 2.00 元與 17.00 元。
05 · 取消與帳單

取消餐點後，用餐場次總額仍是舊金額

原問題表現

原問題情境是客人只點了一份 100 元餐點，帳單含 10 元服務費，總額為 110 元。櫃檯取消這份餐點後，明細不再列出它，但舊帳單總額仍顯示 110 元。

目前程式怎麼處理

審查確認的舊問題是取消狀態更新後沒有同步重算帳單。現在 OrderCancellationService.cancelItem() 與 cancelTicket() 都會在同一筆交易內呼叫 BillingCalculator.recalculateAndStore()；計算依據排除已取消的點餐單和明細。

目前修法：兩種取消方法都在資料庫交易中先鎖定仍開放點餐的用餐場次，再更新取消狀態、依規則回補庫存並重算小計、服務費和總額。若其中一步失敗，交易會回復這一組資料變更。

讀程式位置：backend/src/main/java/tw/ispan/smartorder/service/OrderCancellationService.java 的 cancelItem()、cancelTicket() 與 lockOpenSession()；金額由 BillingCalculator.recalculateAndStore() 計算。

手動 smoke 步驟：取消後重新核對帳單
  1. 在隔離測試桌只送出一份 100 元餐點，確認原帳單含 10 元服務費，總額 110 元。
  2. 從廚房看板取消該餐點，再重新載入櫃檯帳單。
  3. 確認取消列不計入有效明細；此例沒有其他餐點時，小計、服務費和總額都應回到 0.00 元。
  4. 確認送單與取消路徑的有效明細金額一致；櫃檯端後續以共用的 BillingCalculator 核算並檢查預期總額，詳見結帳文章。
06 · 狀態一致性

取消整張點餐單後，點餐單與明細狀態不一致

原問題表現

原問題情境是廚房取消一整張點餐單後，點餐單狀態已改為取消，但所包含的餐點明細仍保留原狀態。畫面或後續計算若分別讀取點餐單與明細，就會對這張單是否有效得到不同答案。

目前程式怎麼處理

審查確認的舊問題是整張取消後，點餐單與明細可能留下不同狀態。現在 cancelTicket() 會逐筆將仍可取消的明細改為 CANCELLED，再將點餐單改為 CANCELLED；若明細已先逐項取消，整張取消會保留其取消狀態並完成剩餘部分。

目前修法：整單取消只允許訂單仍在處理中，且不含已出餐明細時進行；服務以條件更新確認明細及訂單狀態仍可取消，接著回補可追蹤庫存並重算帳單。已取消的明細不會再次回補；已出餐的整單拒絕取消；已結帳的用餐場次也不能再取消。

讀程式位置：backend/src/main/java/tw/ispan/smartorder/service/OrderCancellationService.java 的 cancelTicket()、isOpenTicket()、isUnserved() 與條件式資料更新；資料模型為 OrderTicketEntity 與 OrderItemEntity。

手動 smoke 步驟：檢查整單及每筆明細
  1. 建立一張含兩筆餐點的測試點餐單，記下點餐單及兩筆明細的原始狀態。
  2. 從廚房看板執行整張取消。
  3. 重新查看點餐單和每筆明細，確認點餐單與所有未出餐明細都已取消，且不留下仍有效的明細。
  4. 再查看帳單，確認整單取消後金額只依仍有效的明細計算。
06b · 後續修正（整合時發現）

改了「是否追蹤庫存」之後，取消會補錯庫存

這不是原本的寫法錯，而是後來菜單管理讓店長可以隨時切換品項的「是否追蹤庫存」，原本的假設就不成立了。取消流程判斷「要不要補回庫存」時，看的是品項現在的設定，而不是送單那一刻的設定。

原問題表現（修正前實測）

不追蹤時點了 3 份，店長改成追蹤、庫存設 20，再取消：庫存變成 23，憑空多了 3 份。反過來，追蹤時點了 3 份（20 扣成 17），改成不追蹤再取消：庫存停在 17，那 3 份不見了。單品取消、整單取消都一樣。

目前程式怎麼處理

每筆訂單明細多記一個 stock_deducted：送單時有沒有真的扣庫存。取消時只看這個紀錄，有扣才補，不再看品項現在的設定。上面兩個情境的結果變成 20 和 20。

  • 記錄要跟扣庫存「同一刻」：送單時鎖住品項（SELECT … FOR UPDATE）後才讀「是否追蹤」並扣庫存，stock_deducted 也用同一個值寫入。店長要切換設定得改同一列，會被這把鎖擋住排隊，所以紀錄和實際扣庫存一定一致。顧客送單、櫃檯代客點餐都走同一段程式。
  • 舊資料怎麼辦：升級腳本 migrate_order_item_stock_deducted.sql 先把欄位加成可以空白，只替空白的列用品項現在的設定回填，最後才改成不可空白。舊單當時的設定已經查不到，這是最好的推測（店長沒切換過的品項，現在的值就等於當時的值）；腳本中途斷掉，重跑也能補完；只有每一列都回填好了才改成不可空白，不會把還沒回填的列默默變成 0，也不會改動舊列的更新時間。
  • 這種設計叫「快照」：跟訂單明細保存下單當時的品名與價格是同一個道理，凡是之後可能被改掉、但當下的值會影響後續處理的資料，都要在當下存一份。

07 · 一起接齊的流程

鍋底、選項、庫存與取消一起維持一致

以下是送單與取消流程的實際保護措施，補足端到端交易邊界。這些是本次一起接齊的流程，不列作原作者另外五項缺失。

鍋底規則：OrderValidationService.validate() 先看本次送單列是否含鍋底；若沒有，再查該用餐場次是否已有未取消的鍋底訂單明細。其他客人只放在購物車、尚未送出的鍋底不算已點鍋底，所以不能替另一位客人通過規則。

選項有效性：送單時會鎖定菜單、選項群組和已選選項值，重新確認品項仍上架、選項仍啟用、選項仍屬於該品項，並檢查每個群組的最少及最多選擇數。快照保存群組名稱、選項值名稱與價差。

庫存競爭：送單先鎖用餐場次，再依菜單品項編號排序取得品項列鎖；實際扣庫存由 InventoryRepository.decreaseIfEnough() 以「庫存足夠才扣」的單一更新完成。若任何品項不足，回傳 ITEM_SOLD_OUT，同筆交易已執行的扣庫存，以及後續若已執行的訂單、帳單和購物車變更都會回滾，不會留下半張訂單或只刪除部分購物車。庫存扣到零時只更新 sold_out，不會改動 active。

取消與回補：OrderCancellationService.restoreInventory() 只回補 track_inventory=true 的品項，按品項編號排序更新庫存；不追蹤庫存的免費續加不會因此增加數量。回補後依有效明細重算帳單；庫存恢復時只解除售完標記，不會自動重新上架或改動 active。

避免重複回補：取消服務鎖用餐場次，且用狀態條件更新明細和點餐單。已取消的明細或訂單再次送取消會直接結束，不再回補第二次；兩個請求同時取消時，後續請求會看到已變更狀態，不會再次成功更新。

可取消範圍：單項取消只接受尚未出餐的明細。整單取消若包含已出餐明細就拒絕，已結帳或已關閉的場次也拒絕取消。已出餐餐點的報廢或退料屬於另一套政策，本篇不處理；後來在出菜看板補上了報廢（退菜）功能，見 Clara 的出菜看板文章。

即時通知時機：訂單、取消和售完狀態的通知會透過 afterCommit 在資料庫交易成功提交後送出。若交易回滾，就不會先讓其他畫面收到一個尚未保存的狀態。

讀程式位置：backend/src/main/java/tw/ispan/smartorder/ordersubmitted/service/OrderSubmitService.java 的 submitOrder()；backend/src/main/java/tw/ispan/smartorder/service/OrderValidationService.java 的 validate()；backend/src/main/java/tw/ispan/smartorder/repository/InventoryRepository.java 的 decreaseIfEnough() 與 increase()；backend/src/main/java/tw/ispan/smartorder/service/OrderCancellationService.java 的取消、鎖定與回補方法；backend/src/main/java/tw/ispan/smartorder/service/BillingCalculator.java 的金額計算方法。

逐步核對：從購物車到取消
  1. 選有選項的品項加入購物車，再停用其中一個已選選項；送單應被拒絕，購物車保留，且不留下訂單或庫存扣減。
  2. 恢復選項後，準備含多個追蹤庫存品項的購物車，讓其中一項庫存不足再送單；確認其他品項的扣減、訂單和帳單一併回滾。
  3. 先把庫存設為 1，成功送出 1 份後確認數量為 0、sold_out 為真而 active 不變；再取消未出餐明細，確認庫存只回補 1 次並只解除售完狀態。
  4. 先逐項取消一張多品項訂單中的一項，再整單取消；確認剩餘明細、訂單狀態、庫存與有效金額都相符。
  5. 分別嘗試取消已出餐項目、含已出餐明細的整單及已結帳場次；確認操作被拒絕且庫存和帳單不變。
08 · 審查建議

本次審查建議（技術前輩角度）

以 BigDecimal（Java 用來表示十進位數值的類別）表示金額是好的起點，也要明確規定精度和捨入時機。送單、取消與後續櫃檯結帳已共用 BillingCalculator；結帳金額變更的確認方式另見櫃檯結帳與場次安全。

取消操作會同時影響點餐單、明細和用餐場次帳單。應把彼此相依的狀態更新放在正確的資料庫交易邊界，並由有效明細重算金額；發生錯誤時要能整組回滾，避免資料只更新一半。

面試時要能用一筆具體案例說明：哪一步失敗、為什麼需要回滾、訂單快照保存了什麼、取消後帳單如何從有效明細重算。只列出 BigDecimal 或資料庫交易的名稱，還不足以說明設計判斷。

09 · 報告與面試

把資料一致性說成可以追問的技術故事

報告技術亮點

沿著送單與取消兩條資料流程，說明購物車暫存價格與正式訂單快照的差別、服務費精度如何影響總額，以及取消後如何從有效明細重算。完成 smoke 與資料庫核對後，再補上具體結果和證據。

面試時可以解釋

快照讓點餐單保留送單當下的品項、選項名稱與價格，日後菜單變更不會改寫舊單內容。交易則保護一組互相依賴的更新；若更新帳單失敗，不應留下已取消的明細和未取消的帳單狀態。

一分鐘回答練習

「我會先找出金額從哪裡產生、在哪裡被保存。購物車的價格只是送單前顯示用，正式點餐單應固定送單時的菜單與選項快照。取消後則要排除已取消明細，重算帳單並確保狀態更新一起成功；若中途失敗，資料庫交易要讓整組變更回復。這次的具體工作與驗證範圍，我會依自己實際參與的修正來說明。」

11 · 名詞說明

專有名詞

API — Application Programming Interface（應用程式介面）
讓不同程式依約定呼叫功能的介面；本文的送單與取消端點就是由前端呼叫後端的介面。
HTTP — Hypertext Transfer Protocol（超文字傳輸協定）
瀏覽器、前端和伺服器常用的請求與回應規則；送單成功、庫存不足等結果會透過此協定回傳。
SQL — Structured Query Language（結構化查詢語言）
查詢或修改資料庫資料的語言；本文的明細加總、鎖定資料列和條件式庫存更新都會使用它。
DB — Database（資料庫）
集中保存程式資料的地方；本文的價格快照、點餐明細與帳單都會寫入資料庫。
JPA — Java Persistence API（Java 持久化應用程式介面；現規格名稱為 Jakarta Persistence）
Java 程式透過物件存取關聯式資料庫的標準介面；目前程式使用 Jakarta Persistence 的 EntityManager 在計算前將待寫入資料同步到資料庫連線。
transaction（資料庫交易）
把多個資料庫操作當成一組；全部成功才一起保存，中途失敗則一起回復，避免只更新部分資料。
snapshot（快照）
在一個時間點複製並保存資料，例如送單時的品名、價格和選項名稱，讓舊訂單不受之後菜單修改影響。
cart_item.unit_price
購物車列保存的單價供購物車階段使用；送單正式保存單價時，OrderSubmitService.submitOrder() 取用驗證階段讀取的菜單現價。
groupNameSnapshot
點餐選項快照記錄送單當下的群組名稱，例如「份量」或「加點」；目前由選項所屬群組提供名稱並寫入點餐單。
BigDecimal
Java 用來精確表示十進位數值的類別，適合金額；仍需搭配明確的小數位數和捨入規則，避免一般二進位浮點數的表示誤差。
scale（小數位數）
數字的小數點後保留幾位。金額欄位保留兩位時，15.00 元的 10% 服務費應保留為 1.50 元。
HALF_UP
Java 的常用捨入規則之一；遇到正好在中間的數字時，向遠離零的方向進位，例如 1.005 保留兩位為 1.01。
有效明細
目前仍應計入帳單的點餐項目；所屬訂單或明細已取消時，不再增加小計、服務費或總額。
OrderTicketEntity／OrderItemEntity
Java 程式中的資料模型，分別代表一張點餐單及其中一筆餐點明細。
列鎖（row lock）
暫時鎖住資料庫中的特定資料列，使同時操作的交易依序修改同一張桌、菜單品項或選項，避免互相覆寫。
deadlock（死結）
兩個交易各自持有對方所需的鎖並互相等待，形成無法自行前進的狀態；送單和取消按固定順序鎖資料，可降低這類競爭。
READ_COMMITTED（read committed，讀取已提交隔離級別）
交易只讀取其他交易已成功提交的資料；取消服務明確採用此隔離級別，並以用餐場次列鎖保護同桌修改。
affected rows（受影響資料列數）
資料庫更新或刪除回報實際符合條件的資料列數；例如庫存條件更新回傳 1 才代表成功扣到庫存，回傳 0 就代表庫存不足或資料不存在。
commit（交易提交／版本提交）
資料庫交易提交表示整組變更成功保存；版本提交則表示程式變更被記錄在版本控制中。
rollback（交易回滾）
交易中途失敗時，撤銷該交易尚未提交的資料變更；例如多個品項送單時有一項庫存不足，就不保留前面已扣的庫存或建立中的訂單。
afterCommit（提交後回呼）
資料庫交易成功提交後才執行的程式；目前訂單、取消與菜單狀態通知在這時送出，避免回滾交易仍通知前端更新。
smoke test（冒煙測試）
快速走過最重要的操作路徑，確認基本流程能回應；它不能取代完整測試。
