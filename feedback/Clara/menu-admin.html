工作包 B（菜單）菜單管理已驗證

Clara｜菜單管理：先把門鎖上，再把功能補齊

S-05 菜單管理是店長每天都會用的後台：新增分類、改價錢、上下架、替品項掛上「份量」「辣度」這類選項。整合時發現，這組 API 完全沒有登入檢查，沒登入的人也能新增、修改、刪除菜單。這篇說明怎麼用 Spring Security 只讓店長進來，也把規格 M1 要求、但還沒做完的分類管理與品項標示補齊。

本篇範圍

一個安全問題、兩個資料錯誤、一串補上的功能

  • P1 菜單後台誰都能改：沒登入也能新增、修改、刪除分類與品項。修正前實測，四種操作都成功。
  • 停用的分類，顧客照樣看得到：分類本身、底下的品項、品項詳情頁都還在顧客的菜單上。
  • 刪除還有品項的分類，回 500 錯誤：後端想把品項一起刪掉，被庫存資料擋下，店長只看到「伺服器錯誤」。
  • 補上的基本功能：
    • 分類可以改名、排序、停用。
    • 品項可以標示鍋底、免費續加、是否追蹤庫存、素食／含牛／辣度，並掛上選項群組。
    • 1024px 寬的平板上，看得到上架開關與編輯按鈕。
    • 菜單圖片上傳只給店長。

依據 M1 菜單與品項規格 1.1–1.11、API 規格 §2.4（菜單管理只給店長 MANAGER）與 UI 規格 S-05。規格寫的路徑是 /api/admin/menu/**，實作掛在 /api/order/admin/**；這次以實作為準，只補上權限，不搬路徑。

情境 · 店長在平板上改菜單

後台 API 每次都要回答兩個問題

任何後台請求進來，伺服器都要先回答：

  1. 你是誰？這叫認證（authentication）。員工登入後拿到一張 JWT（登入憑證），之後每個請求都帶著它。
  2. 你可以做這件事嗎？這叫授權（authorization）。JWT 裡寫著角色：店長 MANAGER、櫃檯 COUNTER、廚房 KITCHEN。API 規格 §2.4 寫明：菜單管理只給店長。櫃檯不能改價錢，廚房也不能刪品項。

在 Spring Boot 裡，這兩件事由 Spring Security 負責。專案的規則都寫在 SecurityConfig.java：一條一條由上往下比對，第一條符合的規則就決定結果。最後一條是「其他 /api/** 一律放行」，讓顧客端不用登入也能看菜單。

原本哪裡會錯

門沒鎖、停用沒用、刪除會爆

1. 菜單後台的路徑掉進了「一律放行」

SecurityConfig 裡有訂位、出菜、候位等後台路徑的規則，但沒有 /api/order/admin/**。比對到最後，它符合「其他 /api/** 一律放行」，所以誰都能呼叫。修正前在隔離環境實測，沒有帶任何憑證：

沒登入的人做得到

新增分類（200）、讀取含下架品項的後台菜單（200）、把品項上下架（200）、刪除分類（200）。

為什麼平常沒發現

選項群組頁呼叫 API 時根本沒帶員工憑證，也一樣能用。門沒鎖的時候，「沒帶鑰匙」和「有帶鑰匙」看起來完全一樣。

還有一個藏得更深的地方：負責讀員工 JWT 的過濾器 StaffJwtFilter，原本只處理 /api/admin/ 開頭的路徑。所以就算只在 SecurityConfig 加上「需要店長」的規則，伺服器也不知道這個人是店長（憑證沒被讀），結果會變成連店長都被擋掉。規則和讀憑證的地方要一起改。

菜單圖片上傳也有類似問題：原本只有一個環境變數開關 R2_ALLOW_ANONYMOUS_UPLOADS，關掉時沒人能上傳，打開時所有人都能上傳，沒有「只給店長」這個選項。

2. 停用的分類，顧客還看得到

顧客端查分類用的是 findAll()，也就是「全部拿出來」，沒有看 active（啟用）欄位。查品項時只看品項自己有沒有上架，沒有看它所屬的分類。修正前實測：把一個分類設成停用後，顧客的分類清單裡還有它，品項清單和品項詳情頁也照樣打得開。另外，新分類的排序值一律是 0，顧客端也沒有照排序值排列，店長沒辦法決定分類的先後。

3. 刪除還有品項的分類，回 500

分類實體 MenuCategoryEntity 設定了 cascade = CascadeType.ALL（連帶操作）：刪分類時，JPA 會試著把底下的品項一起刪掉。但每個品項都有一筆庫存資料指向它，Hibernate 因此丟出例外，前端只拿到 500（伺服器內部錯誤）。修正前實測：回 500，分類和品項都還在，店長不知道為什麼刪不掉。就算真的刪成功了也不對，因為那些品項可能已經出現在客人的訂單裡。

4. 平板上看不到編輯按鈕

店家端畫面規格從 1024px 起。1024px 時，扣掉側欄與分類欄，表格只剩 558px 可以顯示，但表格最小寬度是 780px，右邊有 222px 看不到，剛好是「上架狀態」和「操作」兩欄。外框又把捲軸藏起來了，店長根本不知道可以往右捲。

實際改法

規則、讀憑證、查詢條件，三個地方一起改

1. 菜單管理只放店長進來

在「一律放行」之前加一條規則。注意 GET 也要擋，因為後台清單包含已下架的品項和停用的分類：

// 菜單管理（分類、品項、選項群組）：所有動詞都要店長，包含 GET
authorize.requestMatchers("/api/order/admin/**").hasRole("MANAGER");
// 菜單圖片的簽發、確認上傳也只給店長，拿掉匿名開關
authorize.requestMatchers(HttpMethod.POST,
        "/api/uploads/presign", "/api/uploads/complete").hasRole("MANAGER");

StaffJwtFilter 改成看一份路徑前綴清單：/api/admin/、/api/order/admin/、/api/uploads/。程式註解提醒之後的人：新增需要員工登入的路徑群組時，這份清單也要一起加。

  • 沒登入（沒帶憑證、過期、被竄改）→ 401 UNAUTHORIZED。前端看到 401 會清掉憑證，導回登入頁。
  • 登入了但角色不對（例如櫃檯）→ 403 FORBIDDEN。前端只顯示「權限不足」，不會把人踢回登入頁。
  • 選項群組頁改用會自動帶員工憑證的 employeeClient。

顧客端的 /api/order/category、/api/order/items 不在 /api/order/admin/ 底下，仍然公開，客人不用登入就能看菜單。

2. 顧客只看得到「品項上架、分類也啟用」的東西

分類查詢改成只拿啟用的、依排序值排列（findByActiveTrueOrderBySortOrderAscIdAsc）。品項清單、搜尋、品項詳情的查詢都 JOIN 分類，加上 category.active = true，並依「分類排序 → 品項排序 → id」排列，順序才會固定。

3. 有品項的分類不能刪，請改用停用

刪除前先問資料庫「這個分類底下還有沒有品項（含下架的）」。有的話回 409 CATEGORY_NOT_EMPTY，訊息寫「請先移走或刪除品項；暫時不賣可改為停用」。空的分類才真的刪除，回 204。

4. 錯誤格式統一

原本菜單相關的錯誤，有的回 Spring 預設格式，有的直接 500。這次 MenuController 加入全專案共用的錯誤處理 ApiExceptionAdvice，錯誤一律是 { code, message, details }，前端可以照錯誤碼顯示清楚的訊息。

補上的基本功能 · 整合成果

M1 規格要求、還沒做完的部分

  • 分類管理（1.1）：
    • 新分類排在最後。
    • 可以改名，重名回 409 CATEGORY_NAME_DUPLICATED。
    • 可以上移、下移：前端把全部分類的新順序送給後端。清單和資料庫對不上時（例如別人剛新增或刪除分類），回 409 CATEGORY_LIST_CHANGED，請前端重新整理，不猜著排。
    • 停用前會跳確認：「停用後，顧客端看不到這個分類和底下的所有品項」。
    • 操作列只在選取分類後出現，平板上用手指也點得到，不靠滑鼠移過去才出現。
  • 品項標示（1.6、1.9、1.10）：鍋底、免費續加、是否追蹤庫存、素食、含牛、辣度 0–3。後端會檢查：
    • 免費續加的價格必須是 0，而且不追蹤庫存。
    • 鍋底不能同時是免費續加。
    • 辣度只能 0–3。
    不合規則回 400 VALIDATION_FAILED，並說明原因，不會偷偷幫你改數字。舊的呼叫端沒有送這些欄位時，修改品項會維持原值，不會把標示洗掉。
  • 售完是算出來的（1.8）：只有「追蹤庫存而且庫存 ≤ 0」才算售完。免費續加這類不追蹤庫存的品項，庫存 0 也照樣可以點。
  • 掛選項群組（1.4）：optionGroupIds 有三種意思：
    • 省略：不動原本的關聯。
    • 空陣列：全部移除。
    • 有值：整批取代，陣列順序就是顧客端的顯示順序。
    更新時只刪掉不要的關聯、改留下來的順序、新增新的，不會「全刪再重建」。
  • 表格標示：鍋底、素食、辣度等做成品項名稱下方的小標籤，不另外加欄位，避免表格更寬。

審查後再修的地方

停用要真的停賣，兩位店長同時改也不能出錯

第一版（commit 528f45b）補好權限與功能後，安排一位沒參與實作的審查者看程式碼。結果沒有 P1，有一個 P2、幾個 P3；整合者自己在 1024px 畫面上又找到一個問題，跑測試時再抓到一個 500。這些都在第二個 commit 4b9a521 修好。

1. P2：停用分類只是「藏起來」，沒有「停止販售」

第一版讓顧客看不到停用的分類，但「加入購物車」和「送出點餐」只檢查品項本身有沒有上架，沒有看分類。所以只要客人在停用前就打開了菜單，或購物車裡已經有那道菜，照樣能點、廚房照樣收到單。偏偏系統自己的提示寫著「暫時不賣可改為停用」，店長會以為停用就是停賣。

  • 兩個加入購物車的入口、送單驗證都加上「分類要啟用」。不合格時回 409，送單沿用品項下架時的 ITEM_SOLD_OUT「○○ 已下架或售完」，不另外發明新錯誤碼。
  • 送單和停用要排隊：送單時對這幾個分類加共享鎖（LOCK IN SHARE MODE），後台停用時對分類加排他鎖（FOR UPDATE）。共享鎖之間不互相擋，所以很多桌同時點同一類的菜不會變慢；只有「停用」會和「送單」排隊。停用先到，後面的送單就看到已停用；送單先到，停用就等那張單做完。
  • 顧客菜單即時更新：分類的啟用狀態改變，交易提交後推 MENU_CATEGORY_CHANGED 到 /topic/menu，打開中的菜單頁會自己重抓。實測 49 毫秒內，分類就從客人的畫面上消失。

2. P3：兩位店長同時改分類

審查者推演出幾種情境：

  • 一位店長在排序、另一位剛好刪除分類 → Hibernate 丟出例外，回 500。
  • 排序會把整列寫回去，可能把別人剛改好的名稱或停用狀態蓋回舊值。
  • 按「停用」時，前端會把畫面上的舊名稱一起送出。如果另一位店長剛改過名字，就會被改回來。

修法：

  • 改名／停用、排序、刪除，都先用 SELECT … FOR UPDATE 鎖住分類列；多列一律照 id 由小到大鎖。鎖完才讀到的資料是最新的，所以不會寫回舊值。排序撞上刪除時，後到的那個看到清單已經變了，回 409 CATEGORY_LIST_CHANGED。
  • 更新分類時 name 可以省略。前端的停用／啟用只送 {"active": false}，不再帶畫面上的舊名稱。
  • 拿掉分類對品項的 cascade = ALL，以後不會不小心連品項一起刪。

3. 跑測試才抓到的 500：MySQL 5.7 不認得的語法

第一次加鎖用的是 JPA 的 @Lock(PESSIMISTIC_WRITE)。結果連最單純的「改名」都回 500，後端紀錄寫著 You have an error in your SQL syntax … near 'of mce1_0'。原因是 Hibernate 產生的 SQL 是 FOR UPDATE OF 別名，這是 MySQL 8 才有的語法，團隊用的 MySQL 5.7 不支援。改成跟專案其他 repository 一樣的原生 SQL：SELECT * FROM menu_category WHERE id = :id FOR UPDATE。

這件事教我們什麼

框架幫你產生的 SQL，不一定每個資料庫版本都能跑。測試一定要在團隊實際使用的資料庫版本上跑。只讀程式碼的審查看不出這種問題，要真的執行過才會發現。

4. 平板上看不到快速上下架開關

第一版只把「操作」欄用 sticky 釘在右邊，1024px 時「庫存」和「上架狀態」兩欄還是藏在捲軸後面。但 S-05 規格寫明「快速下架開關直接放在表格列上（店家最常用的操作）」。改成依寬度分兩種版面：

  • 1280px 以上：欄位和原本一樣。
  • 1024–1279px：
    • 縮圖變小，「分類」欄拿掉，改成品項名稱下方的「分類：鍋底」小字。
    • 上架欄只留開關，下架的品項在名稱旁加「已下架」標籤。
    整張表不用左右捲動，開關在 851–897px、編輯按鈕在 991px，都在畫面內。

遠端更新：全站隱藏捲軸（Clara 的 d34cb19）

整合期間，Clara 在遠端 develop 推了「隱藏全站滾軸」：在 base.css 對所有元素隱藏捲軸外觀，元件上原本各自加的 no-scrollbar 就拿掉了。合併時以她的寫法為主，沒有衝突。因為上面已經把 1024px 的表格改成不需要左右捲動，合併後重跑瀏覽器檢查，開關和編輯按鈕仍然都在畫面內。

要記得的是：捲軸藏起來之後，「這裡還能捲」的提示也跟著不見了。之後新增畫面時，重要的按鈕要在最小寬度下直接看得到，不能放在需要捲動才找得到的地方。

5. 其他小修

  • 選項群組頁：驗證失敗時顯示具體原因，例如「價差最多 8 位整數與 2 位小數」，不再只顯示「欄位格式不正確」。
  • 排序回 409 之後自動重抓分類清單，不會之後每移一次都撞 409。
  • 櫃檯人員打開菜單管理，畫面顯示「權限不足：菜單管理只有店長可以使用」，而不是一張空表格。
  • SecurityConfig 的註解改成符合實際行為：沒登入被擋的請求一律回 401。
  • 文件網站的 R2 上傳指南拿掉已經不存在的匿名開關。

已知限制（這次沒處理）

  • 兩位店長在同一瞬間新增同名分類，可能兩筆都成功，因為資料表沒有名稱唯一索引。 已在後續修正，見收尾後補完的三件事。
  • 排序只檢查「分類的成員一樣」，如果成員一樣、但你畫面上的順序是舊的，還是會蓋過別人剛排好的順序。 已在後續修正，見收尾後補完的三件事。
  • 品項改過「是否追蹤庫存」之後，再取消改之前的訂單，補庫存會依現在的設定判斷。 已在後續修正：訂單明細改成記下送單時有沒有扣庫存，取消時依這個紀錄補回，見 YiTing 點餐交易文章的後續修正。
  • 極少見的三方情境：品項剛被搬進一個正在停用的分類，同時又有人送單。MySQL 會偵測到死結，取消其中一個請求並回錯誤，不會卡住。
收尾後補完 · 整合成果

名稱真的不重複、排序擋舊畫面、出餐順序交給店長

上一節的已知限制，收尾時一起補完了（commit 93e3700），另外也把出菜看板「靠分類名稱判斷肉品」的問題從根本解掉。

1. 同名分類：讓資料庫當最後一道防線

修正前實測

兩位店長同時新增「同一個名字」的分類，3 輪都是兩個請求都回 201，資料庫裡真的有兩筆同名分類。

修正後

3 輪都是一個 201、一個 409 CATEGORY_NAME_DUPLICATED，資料庫只有一筆。

原本的檢查是「先查有沒有同名，沒有才新增」。兩個請求同時查，都看到「沒有」，就都新增了。只要是「先查再寫」，中間就可能被插隊。修法是在資料表加上唯一索引 uk_menu_category_name：第二筆寫進去時，資料庫直接拒絕，後端把這個錯誤轉成和平常一樣的 409。原本的「先查」還留著，因為它能給一般情況比較友善的訊息；唯一索引負責那極少數同時發生的情況。

2. 排序：帶上「我看到的順序」

修正前實測

店長 A 剛把前兩個分類對調；店長 B 的畫面還是舊順序，接著也排了一次。兩次都回 200，A 的結果被 B 蓋掉。

修正後

前端排序時多送 expectedCategoryIds（移動前畫面上的順序）。後端鎖住全部分類後比對，跟資料庫現在的順序不同就回 409 CATEGORY_LIST_CHANGED，畫面重新抓一次再讓店長調。

這種做法叫樂觀並發控制：不事先鎖住畫面，而是送出時附上「我是根據哪個版本改的」，版本不對就請你重來。沒帶這個欄位的舊呼叫端仍然照舊接受，不會一改就壞掉。

3. 出餐順序：從「看名字」改成「店長設定」

出菜看板原本用分類名稱是不是「肉品」來決定排在最後。菜單管理可以改分類名稱以後，這個判斷就不可靠了：修正前實測，把「肉品」改名後，牛五花就排到了蔬菜前面。

  • 每個分類多一個「出餐順序」欄位 cook_order，照 API 規格 §4.12 分六級：鍋底 1、菜盤 2、火鍋料 3、肉品 4、主食 5、飲料甜點 6。鍋底品項不管放在哪個分類都排 1。
  • 店長在分類操作列用下拉選單設定，前端只送 {"cookOrder": 3}；超出 1–6 回 400。
  • 看板依「出餐順序 → 點餐順序」排列，每道菜也帶 cookOrder。改名後順序不變；把肉品改成 2，就跟菜盤照點餐順序排。

升級腳本 migrate_menu_category_guards.sql

  • 先加 cook_order，依名稱回填既有分類（鍋底 1、蔬菜 2、海鮮 2、火鍋料 3、肉品 4、主食 5、飲料 6、酒類 6，其他 2），只回填還沒有值的列。
  • 再加唯一索引。如果資料庫裡已經有同名分類，這一步會停下來（實測錯誤是 ERROR 1062 Duplicate entry），腳本不刪任何資料；請先人工改名，再整份重跑。實測改名後重跑成功，第三次重跑什麼都沒改。

前輩回饋、報告與履歷

技術前輩的建議

寫後台 API 時，先問「這個網址誰打得到」，再寫功能。最好的習慣是預設拒絕、明確放行：新路徑沒寫規則時應該被擋下，而不是被放行。這個專案目前是反過來的（最後一條一律放行），所以每新增一組後台路徑，都要記得補規則。

測權限時，一定要拿「沒有憑證」和「角色不對」各打一次。只用店長帳號測，功能看起來全部正常，門沒鎖也看不出來。

「刪除」要特別小心：資料一旦被訂單引用，就應該改成「停用」，而不是真的刪掉。cascade = ALL 很方便，但它會在你沒注意的時候，連別的資料一起刪。

這個功能用到的技術

  • Spring Security 規則順序、hasRole、401 與 403 的分工
  • JWT 員工憑證與自訂過濾器（OncePerRequestFilter）
  • Spring Data JPA 查詢方法命名、JPQL JOIN 條件與排序
  • JPA cascade 的風險、用 409 擋下不該刪的資料
  • Bean Validation 與統一錯誤格式
  • React 表格 sticky 欄位、平板寬度的版面

專題報告與履歷可以這樣寫

報告：先用修正前的版本示範「沒登入也能刪菜單」（用 curl 或 Postman 打一次），再展示修正後同一個請求回 401、櫃檯帳號回 403。接著示範停用分類後，顧客端立刻看不到；最後展示平板寬度的菜單管理畫面。

新手名詞表

API（Application Programming Interface，應用程式介面）
前端和後端溝通的窗口，例如 POST /api/order/admin/categories 是「新增分類」。
認證（authentication）與授權（authorization）
認證是確認「你是誰」，授權是確認「你能不能做這件事」。登入解決認證，角色規則解決授權。
JWT（JSON Web Token，JSON 網頁權杖）
登入後拿到的憑證，裡面記著員工編號、角色和過期時間，並有簽章防止竄改。
Spring Security
Spring 的安全框架，負責在請求進到程式之前，檢查有沒有登入、角色夠不夠。
過濾器（filter）
請求進到 controller 之前，先經過的一段程式。StaffJwtFilter 負責讀員工 JWT，告訴 Spring Security「這個人是誰、什麼角色」。
permitAll／hasRole
Spring Security 的規則寫法：permitAll 是誰都可以，hasRole("MANAGER") 是只有店長可以。
HTTP 401 與 403
HTTP 是 Hypertext Transfer Protocol（超文字傳輸協定）。401 是「沒登入」，前端會導回登入頁；403 是「登入了但權限不夠」，前端只顯示權限不足。
HTTP 409 Conflict（衝突）
請求本身沒錯，但跟目前資料狀態衝突，例如分類底下還有品項不能刪、分類清單已經被別人改過。
JPA（Jakarta Persistence API）與 Hibernate
JPA 是 Java 操作資料庫的標準寫法，Hibernate 是本專案用的實作。它讓我們用物件存取資料表。
cascade（連帶操作）
JPA 設定：對父資料（分類）做的操作，也自動套到子資料（品項）。CascadeType.ALL 包含刪除，所以刪分類會連品項一起刪。
DTO（Data Transfer Object，資料傳輸物件）
專門用來裝「API 要收或要回的資料」的物件，例如 SaveMenuItemRequest。
sticky（黏住）
CSS 的定位方式：表格左右捲動時，被設成 sticky 的欄位會一直黏在畫面邊緣。
R2 與預簽網址（presigned URL）
R2 是 Cloudflare 的檔案儲存服務。預簽網址是後端簽發、有時效的上傳網址，前端拿到後直接把圖片傳上去。
MANAGER／COUNTER／KITCHEN
員工角色：店長、櫃檯、廚房。
M1／S-05
M1 是「菜單與品項」模組規格；S-05 是 UI（User Interface，使用者介面）規格裡「菜單管理」畫面的編號。
SHA／Git commit
SHA 是 Secure Hash Algorithm（安全雜湊演算法）；Git 用它幫每個版本（commit）產生識別碼。
