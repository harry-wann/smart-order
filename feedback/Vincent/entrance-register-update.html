Vincent 的修正 1

新會員第一次驗證，為什麼會失敗？

新客人輸入手機、收到驗證碼、按下驗證，後端會發現「這支電話還沒有會員」，於是新增一筆會員資料。修正前，這一步回 409，後端紀錄寫著：

Column 'created_at' cannot be null

原因

資料表的 created_at 是「不可為空，預設值是現在時間」。但程式新增會員時沒有設定建立時間，JPA（Java 持久化 API）仍然把這個欄位寫進 INSERT，值是 NULL。資料庫的預設值只有在 INSERT 完全沒寫這個欄位時才會套用；明確寫了 NULL，就會被「不可為空」擋下。

Vincent 的修法

在 MemberEntity.createdAt 加上 @Column(updatable = false, insertable = false)：新增時不寫這個欄位，讓資料庫自己填「現在時間」；之後更新會員資料也不會動到它。專案裡訂位、員工、用餐紀錄的建立時間本來就是這樣寫，所以這個修法和既有慣例一致。

修正後實測：新電話第一次驗證回 200、newMember=true，會員中心讀得到建立時間；同一支電話第二次登入找到同一位會員，資料庫裡剛好一筆。

延伸觀察：資料庫的「現在時間」是哪一區的時間？

實測時會員的建立時間顯示 11:09，當時台北時間是 19:09，差了 8 小時。原因是團隊的 backend/compose.yaml 沒有設定 MySQL 時區，資料庫預設用 UTC（協調世界時）；用資料庫預設值填的時間，都會比台北時間早 8 小時。程式自己寫入的時間（例如候位、付款）則是台北時間，兩邊不一致。

這不是 Vincent 這次修正造成的，專案裡所有用資料庫預設值的建立時間都有一樣的情況。會員中心目前只顯示「某年某月加入」，影響很小；這個時區一致性問題會在 Harry 的共用技術地基（L0）整理中統一處理。

Vincent 的修正 2

「我的預約」應該連到哪裡？

首頁的「我的預約」原本連到 /member，也就是會員登入頁；沒有會員的客人想查自己的訂位，會被要求先登入。改成 /member/reservations 之後，這頁會同時處理兩種人：用這支手機匿名訂過位的客人直接看到自己的訂位，有會員身分的人看到會員的訂位。這個修正讓首頁卡片的文字「查看或取消訂位」和實際行為一致，實測點下去會正確打開預約清單。

整合時找到的問題

點一下提示，就從 A02 被帶到 A03

首頁下方有一個提示框：「已經坐在店裡了？掃桌上的 QR code 就直接開始點餐」。遠端更新讓這個提示框可以點，點了會固定前往 /order/checkin/A03，也就是 A03 桌的報到頁。推測是為了 demo 時方便進入點餐流程。

問題在報到頁（C-01）有一段合理的保護：如果這支手機手上已經有用餐身分，但屬於別張桌，就先把它清掉（leaveTable()），因為掃到新桌的 QR 代表客人換桌了。兩段程式單獨看都沒錯，合在一起就出事：

  1. 客人坐在 A02，已經掃碼加入、正在點餐。

  2. 他回到首頁，看到「已經坐在店裡了？」，以為是說明，點了一下。

  3. 畫面跳到 A03 的報到頁。報到頁發現他的身分屬於 A02、不是 A03，於是把 A02 的身分清掉。

  4. 結果：他回不去 A02 的購物車；如果再按「開始點餐」，還會加入 A03 那桌別人的帳單。

實測：修正前

A02 的客人點提示後，網址變成 /order/checkin/A03，手機上 A02 的用餐憑證被清掉。

修正後

提示框回到單純的說明，不能點；客人留在首頁，A02 的用餐憑證保留。真正的入口仍是桌上的 QR（每張桌一個網址），掃哪張桌就進哪張桌。

demo 時如果需要進入點餐流程，可以用座位管理列印出來的桌位 QR，或直接在網址列輸入 /order/checkin/桌號，不需要讓所有客人都看得到的首頁帶固定桌號。

  • frontend/src/features/customer/Entrance.jsx：「我的預約」連結（Vincent 的修正，保留）；QR 提示框改為不可點的說明（這次修正）。
  • frontend/src/features/customer/order/CheckIn.jsx：報到頁遇到別桌身分會先清掉，這段保護本身是對的，沒有修改。
手把手驗收 · 請在本機隔離資料庫

你可以照著做一次

  1. 重現註冊問題。在合併前的版本，用一支資料庫裡沒有的手機號碼呼叫 POST /api/member/otp，從測試資料庫的 verification_code 表讀出驗證碼，再呼叫 POST /api/member/verify：會得到 409，後端紀錄出現 Column 'created_at' cannot be null，會員表沒有新增資料。

  2. 確認註冊修正。換到合併後的版本重做一次：回 200、newMember 是 true；用拿到的會員憑證呼叫 GET /api/member/me，createdAt 有值。再用同一支電話登入一次，newMember 變成 false，會員表仍只有一筆。

  3. 重現帶錯桌。先讓測試手機加入一張用餐中的桌（例如 A02），打開首頁、點「已經坐在店裡了？」：修正前會跳到 A03 報到頁，瀏覽器 localStorage 裡的 customer.sessionToken 被清空。

  4. 確認修正。同樣的步驟在修正後：網址維持在首頁，用餐憑證和原本一樣。再點「我的預約」，確認打開 /member/reservations。

  5. 回歸檢查。合併後重跑既有的 36 項 HTTP 基線與 15 條頁面路由，確認其他功能沒有被影響。

前輩回饋、報告與履歷

技術前輩的建議

註冊這個修正抓得很準：看懂錯誤訊息、找到「預設值只在沒寫欄位時才生效」這個關鍵，並且用專案既有的寫法解決。下次可以再多問一句：「資料庫的現在時間和程式的現在時間是同一個時區嗎？」時間欄位在跨時區的部署裡很容易出錯。

入口頁的問題提醒我們：為了 demo 方便寫死的值（例如固定桌號），一旦放在每個客人都看得到的頁面，就會變成真的行為。demo 捷徑最好放在只有開發者用得到的地方，或在提交前拿掉。另外，改一個連結時，也要看一下連過去的那一頁會做什麼事。

這次用到的技術

  • JPA 欄位設定 insertable／updatable，與資料庫預設值的關係
  • MySQL 的 NOT NULL 約束、CURRENT_TIMESTAMP 預設值與伺服器時區
  • 手機驗證碼（OTP）登入與首次登入自動建立會員
  • 單頁應用程式（SPA）的路由，以及存在瀏覽器 localStorage 的用餐憑證
  • 修正前後對照的實測方式：同一份測試腳本先重現問題、再證明修好

專題報告與履歷可以這樣寫

報告：用「新會員第一次驗證就失敗」當除錯案例，展示錯誤訊息 → 找到 NULL 與預設值的關係 → 一行設定修好 → 修正前後對照。這類「從錯誤訊息推回原因」的過程，評審通常很有興趣。

履歷：「負責餐廳系統的顧客入口與會員手機驗證登入；排除新會員註冊時建立時間欄位寫入 NULL 導致的失敗，並修正首頁入口連結。」入口頁帶錯桌是整合時一起修的，可以在面試時當作「demo 捷徑變成正式行為」的經驗分享，履歷上不用另外列。

新手名詞表

遠端分支（remote branch）／合併（merge）
遠端分支是放在 GitHub 上、大家共用的版本；合併是把別人的更新和自己的版本整合在一起。
SHA／Git commit
SHA 是 Secure Hash Algorithm（安全雜湊演算法）；Git 用它幫每個版本（commit）產生識別碼，本文列的是短識別碼。
API（Application Programming Interface，應用程式介面）
前端向後端讀資料、送出操作的一組網址與規則。
HTTP 狀態碼 200／409
HTTP 是 Hypertext Transfer Protocol（超文字傳輸協定）。200 代表成功；409 代表和資料庫目前的資料或規則衝突，這裡是寫入違反「不可為空」。
OTP（One-Time Password，一次性密碼）
手機收到的 6 位數驗證碼，只能用一次、有期限。
JPA（Java Persistence API，Java 持久化 API）
Java 用物件讀寫資料庫的標準介面。@Column(insertable = false) 表示新增時不寫這個欄位，updatable = false 表示更新時不改它。
NOT NULL 與預設值（DEFAULT）
NOT NULL 是「這個欄位不能是空的」；DEFAULT 是「新增時沒提供這欄，就用這個值」。明確寫入 NULL 不算「沒提供」，所以不會套用預設值。
INSERT
SQL（Structured Query Language，結構化查詢語言）新增資料的指令。
UTC（Coordinated Universal Time，協調世界時）
國際標準時間。台北時間是 UTC+8，所以 UTC 的 11:09 等於台北的 19:09。
L0（Level 0，共用技術地基）
專案裡全隊共用的基礎設定，例如登入驗證、資料庫連線與時區設定，由 Harry 負責整理。
SPA（Single-Page Application，單頁應用程式）
切換畫面時不重新載入整個網頁，只換內容；網址的變化由前端路由處理。
localStorage
瀏覽器替每個網站保存資料的空間。本案把顧客的用餐憑證存在這裡，關掉頁面再打開仍在同一桌。
用餐憑證（session token）
客人掃碼加入某張桌後拿到的一串識別碼，之後點餐、看帳單都靠它證明「我是這桌的人」。
QR（Quick Response，快速反應碼）
手機相機可以快速讀取的方形圖碼；本案每張桌一個，內容是該桌的報到網址。
C-00／C-01
UI（User Interface，使用者介面）規格裡的畫面編號：C-00 是顧客首頁，C-01 是掃碼後的桌位報到頁。
demo（展示）捷徑
為了展示方便暫時寫死的值或入口。放在正式頁面上，就會被真正的使用者用到。
