技術亮點、報告與履歷

用到的技術與設計模式

全隊共用的技術

  • 後端：Java 21、Spring Boot 4.1（Spring MVC REST API：用網址和 HTTP（Hypertext Transfer Protocol，超文字傳輸協定）方法讓前端讀寫資料，例如 MemberAuthController）
  • Spring Data JPA／Hibernate 7（用 Java 物件存取資料庫，例如 MemberEntity）、MySQL 5.7
  • Bean Validation（請求欄位驗證，例如 SendCodeRequest 的手機格式）
  • Lombok（自動產生 getter／setter）、Maven（Java 專案建置工具）
  • 統一錯誤格式：ApiException、@RestControllerAdvice（驗證碼限流的 429 回應）
  • 前端：React 19、React Router 8（換頁，例如 RequireEmployee.tsx）、Vite 8（建置工具）、Tailwind CSS 4（用 class 名稱寫樣式）
  • TanStack Query 5（伺服器資料快取，checkoutApi.js 的帳單查詢）、axios（customerClient）
  • JavaScript／TypeScript 混用（.jsx 與 .ts）
  • 工具：Git 分支與 merge、oxlint（JavaScript 程式碼檢查）

這個工作包特有的

  • Spring Security＋JWT（JSON Web Token，jjwt）：SessionTokenFilter 驗證顧客的兩個 token；會員 7 天、員工 12 小時的有效期
  • Spring WebSocket／STOMP（Simple Text Oriented Messaging Protocol，簡單文字導向訊息協定） 即時推播（@stomp/stompjs）：連線只驗 session token，付款完成後通知同桌 SESSION_CLOSED
  • 綠界金流整合（ECPay）：產生付款表單、驗證回呼的 CheckMacValue（EcpayService）；本機測試，未實際扣款
  • @Scheduled 排程：VerificationCodeScheduler 每 10 分鐘清理過期驗證碼
  • SecureRandom 產生亂數 token、SHA-256 雜湊儲存（GuestToken.java）
  • JPA 原生 SQL 查詢（@Query(nativeQuery = true)）：鎖定手機鎖表、INSERT … ON DUPLICATE KEY UPDATE
  • 資料庫升級腳本：migrate_guest_token.sql、migrate_member_otp.sql
  • 瀏覽器 API：AbortController 取消舊請求、sessionStorage 與 localStorage 保存憑證

設計模式

  • 分層架構（Controller–Service–Repository）：MemberAuthController、MemberAuthService、VerificationCodeRepository
  • DTO（Data Transfer Object，資料傳輸物件）：SendCodeRequest、VerifyCodeRequest
  • 悲觀鎖（SELECT … FOR UPDATE）與固定鎖順序：每支手機一把鎖；付款回呼依場次、付款紀錄、桌位的順序上鎖
  • 樂觀並發控制（帶預期值）：付款時帶 expectedTotal，金額變了就回 409 BILL_CHANGED
  • 冪等（同一個請求做幾次結果都一樣）：付款通知重送只造成一次結果
  • 單一真相來源：線上與櫃檯結帳共用 BillingCalculator
  • 交易提交後才發布事件（afterCommit）：MenuCheckoutNotifier 發出 SESSION_CLOSED
  • 限流：同一支手機 10 分鐘最多要 3 次碼，超過回 429 與 Retry-After
  • 路由守門：RequireEmployee 沒員工憑證就導回登入頁（真正權限仍由後端檢查）
  • 憑證只存雜湊：guest token 在資料庫只留 SHA-256 指紋
  • 忽略過期回應：付款結果查詢確認回應仍屬目前交易

報告與履歷

  • 報告：示範帳單顯示 528 元後，另一位同桌客人加點使帳單成為 1,056 元；用舊金額付款收到 409，重新載入確認新總額再繼續；接著展示本機簽章回呼，以及第二位客人收到全桌結帳通知（154 項 HTTP 與資料庫檢查、31 項瀏覽器案例）。說明這是本機測試，沒有向綠界送出表單或實際扣款。
  • 報告：先用修正前版本示範「知道別人的裝置 ID 就能改他的購物車」，再說明識別碼與憑證的差別，最後示範同樣步驟被擋下（38 項身分專項、12 項瀏覽器檢查）。
  • 報告：先示範「同一組驗證碼同時送兩次，兩個都登入成功」，再示範加鎖後只有一個成功，並展示倒數畫面與「10 分鐘最多 3 次」（39 項專項、15 項瀏覽器檢查）。
  • 履歷（工作包 A）：「參與餐廳系統顧客入口與會員流程：驗證碼登入以每支手機一把資料列鎖處理並發問題；參與同桌身分改寫，以伺服器簽發的隨機 token（僅存 SHA-256 雜湊）取代可偽造的裝置識別碼，並以 HTTP 與瀏覽器測試驗證。」
  • 履歷（付款，建議與上面分開寫）：「參與跨包手機付款整合，補上預期金額核對、待確認付款保護與付款結果身分驗證，並以本機回呼及瀏覽器案例驗證同桌結帳同步。」付款與同桌身分都是跨工作包的整合，請寫「參與」，不要寫成獨立完成或已上線營運。
