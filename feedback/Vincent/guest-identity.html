工作包 A（顧客入口與掃碼進入）同桌身分已驗證

Vincent｜「識別碼」不是「密碼」：誰才是購物車裡的這位客人？

同一桌好幾支手機一起點餐，每支手機都要被認出來是「哪一位客人」。這篇說明原本為什麼只要知道別人的裝置 ID 就能冒充他，以及怎麼改成由伺服器發一把只有本人拿得到的鑰匙。

本篇範圍

一個安全問題、兩個小錯誤

  • P1 冒用身分：只要知道同桌別人的裝置 ID，就能拿到他的身分、改他的購物車、用他的名義送單。
  • 裝置 ID 長度：超過資料表欄位長度時變成資料庫錯誤，而不是清楚的「資料格式不對」。
  • 掃碼頁假資料：每張桌都顯示寫死的「2 大 1 小 18:32 入座」。
  • 依據：API 規格 §1.4／§4.2 早已定好正確設計（伺服器簽發的 guest token、資料庫只存雜湊、裝置 ID 只當提示），這次讓程式跟上規格。

這個修正同時碰到入桌（工作包 A）、購物車與送單（工作包 C）和共用驗證（L0），所以放在同一支分支一起改、一起驗收。

情境 · 同一桌的三支手機

系統要怎麼知道「這筆是誰點的」？

A03 桌有三位客人，各自用手機掃同一張 QR 加入。購物車是全桌共用的：大家都看得到彼此加了什麼，但只有本人能改、刪、送出自己的品項。所以每個請求進來，後端都要回答：「這是哪一位客人？」

原本的答案是看手機自己帶來的 X-Device-Id（裝置 ID）。它是前端第一次開網頁時隨機產生、存在瀏覽器裡的一串 UUID。

識別碼（identifier）

用來「指出是誰」，像座號、學號。別人知道也沒關係，因為它本來就不是用來證明身分的。裝置 ID 就是這種。

憑證（credential）

用來「證明是本人」，像密碼、門禁卡。只有本人拿得到，伺服器也不能把它原樣存起來。guest token 是這種。

原本的問題，就是把識別碼當成憑證在用。

原本哪裡會錯

裝置 ID 可以被看到、被偽造，卻被拿來認人

API 規格寫得很清楚：「X-Device-Id 客戶端提供，可偽造；只供顯示／診斷，不參與 guest 查找、身分驗證或授權」。但原本的程式在好幾個地方都拿它認人：

  • 查桌況（公開、不用登入）：GET /api/tables/A03/status 帶上某個裝置 ID，如果這個 ID 已經加入過，回應裡就直接附上那位客人的 token。
  • 加入用餐：同一個裝置 ID 再加入一次，就拿回同一位客人的身分。
  • 購物車、送單、WebSocket 連線、付款收據：都用「token 裡的裝置 ID 等於 header 的裝置 ID」或「用裝置 ID 查客人」來判斷身分。

那別人怎麼會知道我的裝置 ID？同桌的購物車即時通知裡就帶著「是哪個裝置 ID 加的」，所以同桌任何一支手機都收得到其他人的裝置 ID。拿到之後：

  1. 用對方的裝置 ID 呼叫公開的查桌況 API，拿到對方的 token。

  2. 帶著 token 和對方的裝置 ID 呼叫購物車 API，後端就當成是對方。

  3. 修改、刪除對方的品項，或用對方的名義送單。

另外兩個小問題：加入用餐只擋「超過 128 字」的裝置 ID，但資料表欄位只有 36 字，37～128 字會變成資料庫錯誤；掃碼頁的「2 大 1 小 18:32 入座」是寫死的展示文字，每一桌都一樣。

實際改法

由伺服器發一把鑰匙，資料庫只留指紋

1. 加入用餐時發 guest token

客人加入時，後端用 SecureRandom（密碼學等級的亂數）產生 32 bytes、也就是 256 位元的隨機值，編碼成文字後回給前端，這就是 guestToken。前端把它和原本的 sessionToken 一起存起來。

資料庫不存 guest token 本身，只存它的 SHA-256 雜湊（可以想成「指紋」）：同一個 token 算出來的指紋永遠一樣，但從指紋推不回 token。這樣就算資料庫外洩，別人也拿不到可以用的 token。因為 token 本身是 256 位元的亂數，不像人設的密碼容易被猜，所以用 SHA-256 就夠了。

2. 每個請求都要「兩把鑰匙」對得上

  • X-Session-Token：原本的 JWT，裡面寫著「哪一次用餐、哪一位客人」。不再比對裝置 ID。
  • X-Guest-Token：新發的鑰匙。後端把它算成指紋，到資料庫找客人，這位客人必須屬於 JWT 裡的那次用餐、而且就是 JWT 裡的那位客人。
  • 任何一個缺少或對不上，回 401 INVALID_GUEST_TOKEN。只有兩個都驗過之後，才會告訴對方「這桌已經結帳」（PAID）之類的狀態，避免拿假 token 探測別桌狀況。
  • 購物車服務改成直接用驗證過的客人 ID，不再用裝置 ID 查人。付款收據查詢也改成驗 guest token。

3. WebSocket 只用 session token

規格規定 guest token 只用在一般的 HTTP 請求，不放進 WebSocket。即時推播的連線只驗 X-Session-Token，確認這位客人屬於這次用餐、用餐還在進行中。推播本身只是通知，所有真正改資料的動作都還是走需要兩把鑰匙的 HTTP API。

4. 重新進入：兩把鑰匙都對才認回同一位

客人關掉網頁再掃同一張 QR，前端會帶著手上的兩個 token 加入；兩個都屬於這桌目前的用餐，才恢復成同一位客人（購物車裡自己的品項還能改）。否則一律建立新的客人，就算裝置 ID 一模一樣也一樣。所以資料表原本「同一次用餐、同一個裝置 ID 只能有一位客人」的唯一索引，改成一般索引。

5. 其他

  • 公開的查桌況 API 只回「桌號、有沒有開桌」，不再回任何 token。
  • 裝置 ID 變成選填，有帶的話最多 36 字，超過回 400 VALIDATION_FAILED。
  • 掃碼頁拿掉寫死的人數與時間。
  • 資料庫新增 guest_token_hash 欄位，附一支不改舊資料的升級腳本；舊資料的客人沒有指紋，重新掃碼會成為新客人。

獨立審查找到的回歸

掃錯桌，就回不去原本的自己

審查發現掃碼頁有一行舊程式：如果手機手上的身分屬於別桌，就先把 token 全部清掉。以前這沒關係，因為回原桌時後端會用裝置 ID 找回同一位客人。但現在 token 是唯一能證明身分的東西：

  1. 客人在 A 桌，購物車裡有還沒送出的品項。

  2. 不小心掃到 B 桌的 QR（還沒按「開始點餐」），兩個 token 就被清掉了。

  3. 回 A 桌重新掃碼，只能成為新的客人；原本那些品項沒有人能改、刪或送出。

修法：掃到別桌時先保留 token，只記住「手上的 token 是別桌的」；真的按下「開始點餐」加入 B 桌時，不帶 A 桌的 token，加入成功後才換成 B 桌的。這也提醒我們：改掉一個安全機制時，要回頭檢查原本依賴它的程式。

手把手驗收 · 請在本機隔離資料庫

你可以照著做一次

  1. 重現原本的攻擊。手機 A 加入 A03 並加一個品項。用 A 的裝置 ID 呼叫查桌況：回應只有 {"tableNo","open"}，沒有 token。再用 A 的裝置 ID 加入：拿到的是另一位客人。用這位「冒充者」去改、刪 A 的品項都回 403，送單回 409 CART_EMPTY（他自己沒有品項）。A 自己仍然可以修改。

  2. 各種 header 組合。只帶 session token → 401 INVALID_GUEST_TOKEN；自己的 session token 配別人的 guest token → 401；亂打的 guest token → 401；不帶裝置 ID 也能正常使用；換一個裝置 ID 不會變成別人。

  3. 重新進入。帶自己的兩個 token 再加入：同一位客人、同一把 guest token。帶別桌的 token 加入：在這桌建立新客人。只帶 session token：建立新客人。

  4. 裝置 ID 與儲存。37 字回 400；36 字或不帶都可以。資料庫裡存的是 token 的 SHA-256 指紋，找不到 token 原文；同一個裝置 ID 在同一次用餐可以有多位客人。

  5. 回歸測試。個人購物車、訂單一致性、結帳、代客點餐、付款這幾組原本的 HTTP 測試，全部改成帶兩個 token 後重跑，確認都正常。

  6. 瀏覽器（手機 390 像素寬）。兩支手機故意用同一個裝置 ID 掃碼加入：拿到不同的 guest token。A 加品項，B 的購物車頁不用重新整理就看到（WebSocket 只帶 session token）。只剩舊 token 的手機會被清掉 token、回到首頁。已加入的手機掃自己那桌，直接回菜單；掃到別桌再回來，仍是原本那位客人。

前輩回饋、報告與履歷

技術前輩的建議

看到一個欄位要被拿來「認人」時，先問：「誰能產生它？誰能看到它？」如果客戶端可以自己產生、或其他人看得到，它就只能當識別碼，不能當憑證。裝置 ID 兩個條件都不符合。

憑證要由伺服器產生、只交給本人、資料庫只存雜湊，這是密碼、API key、重設密碼連結都會用到的同一套原則。學會一次，以後很多地方都用得上。

這個功能用到的技術

  • 識別碼與憑證的區分、威脅建模（誰能看到、誰能偽造）
  • SecureRandom 產生高熵 token、SHA-256 雜湊儲存
  • JWT 與資料庫雙重驗證、Servlet Filter、Spring WebSocket（STOMP）CONNECT 驗證
  • 資料庫唯一索引調整與不改舊資料的升級腳本
  • 前端 token 保存與 401 處理、跨模組回歸測試

專題報告與履歷可以這樣寫

報告：先示範「知道別人的裝置 ID 就能改他的購物車」（用修正前的版本），再解釋識別碼和憑證的差別，最後示範同樣的步驟現在被擋下。評審通常對「自己找到並修好安全問題」很有印象。

履歷：「參與多人同桌點餐的身分驗證改寫：以伺服器簽發的隨機 token（僅存 SHA-256 雜湊）取代可偽造的裝置識別碼，修正可冒用他人購物車的安全問題，並以 HTTP 與多裝置瀏覽器測試驗證。」請寫「參與」，這是跨工作包的整合修正。

新手名詞表

識別碼（identifier）與憑證（credential）
識別碼只說「是誰」，別人知道也無妨；憑證用來證明「是本人」，只能本人持有。
X-Device-Id（裝置 ID）
前端隨機產生、存在瀏覽器的一串 ID，用來顯示或除錯；因為客戶端可以任意修改，不能用來認人。
token（權杖）
一段代表「你已經通過驗證」的文字，之後每個請求都帶著它。本案有 session token 與 guest token 兩種。
JWT（JSON Web Token，JSON 網頁權杖）
一種帶有簽章的 token，內容（例如用餐 ID、客人 ID）可以被讀出來，但沒有金鑰就無法偽造或竄改。
JSON（JavaScript Object Notation，JavaScript 物件表示法）
API 傳資料用的文字格式。
SecureRandom
Java 提供的密碼學等級亂數產生器，產生的值無法被預測，適合用來做 token。
SHA-256 與雜湊（hash）
SHA 是 Secure Hash Algorithm（安全雜湊演算法）。雜湊把任意資料算成固定長度的「指紋」，同樣的輸入得到同樣的指紋，但無法從指紋反推原文。
熵（entropy）
衡量一個值有多難猜。256 位元的亂數有 2256 種可能，實務上猜不到。
API（Application Programming Interface，應用程式介面）
前端呼叫後端功能的網址與規則。
HTTP 狀態碼 400／401／403／409
HTTP 是 Hypertext Transfer Protocol（超文字傳輸協定）。400 資料格式不對；401 沒有通過身分驗證；403 身分正確但沒有權限；409 跟目前資料狀態衝突。
Filter（過濾器）
請求進到各個 API 之前先經過的關卡，這裡統一檢查兩個 token。
WebSocket 與 STOMP
WebSocket 是保持開著的連線，伺服器可以主動推訊息；STOMP（Simple Text Oriented Messaging Protocol，簡單文字導向訊息協定）在連線一開始的 CONNECT 步驟驗證身分。
唯一索引（UNIQUE index）
資料庫規則：某些欄位的組合不能重複。這次拿掉「同一次用餐、同一個裝置 ID 只能一位客人」的限制。
migration（資料庫升級腳本）
把正在使用的資料庫從舊結構升級成新結構的一次性腳本，本案不刪、不改舊資料。
回歸（regression）
改了某處之後，原本正常的功能壞掉。所以修改後要重跑原本的測試。
L0（Level 0，共用技術地基）
全隊共用的基礎設定，例如驗證、金鑰與時區，由 Harry 負責整理。
SHA／Git commit
Git 用 SHA 幫每個版本（commit）產生識別碼，本文列的是短識別碼。
