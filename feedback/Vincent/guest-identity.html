工作包 A（顧客入口與掃碼進入）同桌身分已驗證

Vincent｜「識別碼」不是「密碼」：誰才是購物車裡的這位客人？

同一桌好幾支手機一起點餐，每支手機都要被認出是「哪一位客人」。原本只要知道別人的裝置 ID 就能冒充他；這篇說明為什麼，以及怎麼改成由伺服器發一把只有本人拿得到的鑰匙。API（Application Programming Interface，應用程式介面）規格 §1.4／§4.2 早已定好這個設計，這次讓程式跟上。

01 · 哪裡錯

把識別碼當成憑證在用

識別碼（identifier）

用來「指出是誰」，像座號、學號，別人知道也沒關係。裝置 ID 就是這種。

憑證（credential）

用來「證明是本人」，像密碼、門禁卡，只有本人拿得到，伺服器也不能原樣存起來。guest token 是這種。

P1 冒用身分。同桌購物車是共用的，大家看得到彼此的品項，但只有本人能改、刪、送出自己的品項，所以後端每次都要回答「這是哪一位客人」。原本的答案是看手機帶來的 X-Device-Id（前端第一次開網頁隨機產生、存在瀏覽器的 UUID，Universally Unique Identifier，通用唯一識別碼）。但規格明寫它「客戶端提供，可偽造；只供顯示／診斷，不參與 guest 查找、身分驗證或授權」。程式卻在好幾處拿它認人：公開、不用登入的 GET /api/tables/A03/status 帶上已加入過的裝置 ID，回應就附上那位客人的 token；加入用餐用同一個裝置 ID 會拿回同一位客人；購物車、送單、WebSocket、付款收據也都靠裝置 ID 判斷。

別人怎麼知道我的裝置 ID？同桌購物車的即時通知帶著「哪個裝置 ID 加的」，同桌任何一支手機都收得到。於是：拿對方的裝置 ID 查桌況取得 token → 帶 token 與對方裝置 ID 呼叫購物車 API，後端當成對方 → 改、刪對方的品項，或用對方名義送單。

兩個小錯誤。加入用餐只擋超過 128 字的裝置 ID，但資料表欄位只有 36 字，37～128 字會變成資料庫錯誤，而不是清楚的「資料格式不對」；掃碼頁的「2 大 1 小 18:32 入座」是寫死的展示文字，每桌都一樣。

審查找到的回歸（改完之後新出現的錯）。掃碼頁有一行舊程式：手機手上的身分若屬於別桌，就先把 token 全部清掉。以前沒關係，因為回原桌時後端會用裝置 ID 找回同一位客人；但現在 token 是唯一能證明身分的東西。客人在 A 桌有還沒送出的品項，不小心掃到 B 桌的 QR（Quick Response，快速反應碼）圖碼（還沒按「開始點餐」），兩個 token 就被清掉，回 A 桌重新掃碼只能成為新客人，原本那些品項沒人能改、刪或送出。

02 · 怎麼修

伺服器發一把鑰匙，資料庫只留指紋

  • 加入用餐時發 guest token：後端用 SecureRandom（密碼學等級亂數）產生 32 bytes（256 位元）隨機值，編碼後回給前端，前端與原本的 sessionToken 一起存。資料庫不存 token 本身，只存它的 SHA-256 雜湊（可想成指紋：同一個 token 指紋永遠一樣，但推不回 token）。為什麼：資料庫外洩也拿不到可用的 token；256 位元亂數不像人設的密碼容易被猜，用 SHA-256 就夠。
  • 每個請求要「兩把鑰匙」對得上：X-Session-Token（原本的 JWT，JSON Web Token，寫著哪次用餐、哪位客人，不再比對裝置 ID）加 X-Guest-Token（後端算成指紋到資料庫找客人，這位客人必須屬於 JWT 那次用餐、就是 JWT 那位客人）。缺一個或對不上，回 401 INVALID_GUEST_TOKEN；兩個都驗過，才會告訴對方「這桌已結帳」之類的狀態，避免拿假 token 探測別桌。購物車直接用驗證過的客人 ID；付款收據查詢也改驗 guest token。
  • WebSocket 只用 session token：規格規定 guest token 只用在一般 HTTP（Hypertext Transfer Protocol，超文字傳輸協定）請求。即時推播連線只驗 X-Session-Token；推播只是通知，真正改資料的動作都還是走兩把鑰匙的 HTTP API。
  • 重新進入：客人關掉網頁再掃同一張 QR，帶著手上的兩個 token 加入，兩個都屬於這桌目前的用餐，才認回同一位客人；否則一律建立新客人，連裝置 ID 一模一樣也一樣。所以「同一次用餐、同一個裝置 ID 只能一位客人」的唯一索引改成一般索引。
  • 其他：公開的查桌況 API 只回桌號與有沒有開桌，不再回任何 token；裝置 ID 變選填，最多 36 字，超過回 400 VALIDATION_FAILED；掃碼頁拿掉寫死的人數與時間；資料庫新增 guest_token_hash 欄位，附不改舊資料的升級腳本（舊客人沒有指紋，重新掃碼會成為新客人）。
  • 修回歸：掃到別桌時先保留 token，只記住「手上的 token 是別桌的」；真的按下「開始點餐」加入 B 桌時，不帶 A 桌的 token，加入成功後才換成 B 桌的。為什麼：改掉一個安全機制時，要回頭檢查原本依賴它的程式。
03 · 驗證

程式版本 dcbba26

  • HTTP 與資料庫檢查：身分專項 38 項全過（含原本的冒用情境），基線 36 項，回歸測試個人購物車 56、訂單一致性 200、結帳 156、代客點餐 108、付款 127 全過。升級腳本在舊結構（108 位既有客人）上套用成功，舊資料不變。完整 HTTP 紀錄
  • 重點檢查：用 A 的裝置 ID 查桌況沒有 token；用它加入只會拿到另一位客人，改、刪 A 的品項回 403，送單回 409 CART_EMPTY；缺 guest token、別人的或亂打的都是 401；37 字裝置 ID 回 400；資料庫裡找不到 token 原文。
  • 瀏覽器（手機 390 像素寬）12 項全過：兩支手機故意用同一個裝置 ID 掃碼，拿到不同的 guest token；A 加品項，B 的購物車不用重新整理就看到；只剩舊 token 的手機被清掉 token、回到首頁；掃到別桌再回原桌，仍是原本那位客人。完整瀏覽器紀錄
  • 還沒處理：JWT 簽章金鑰寫死在程式碼裡（屬 Harry 的共用技術地基 L0，Level 0；WebSocket 只靠 JWT，要優先修）；同桌通知仍帶裝置 ID，前端用它判斷「是不是自己剛做的」，只影響要不要跳通知，不影響權限。
04 · 用到的技術與設計模式

本篇真的用到的

  • SecureRandom 加 SHA-256 雜湊儲存：GuestToken.java 產生亂數 token 與指紋。
  • JWT（jjwt）加資料庫雙重驗證、Servlet Filter（請求進 API 前先經過的關卡）：SessionTokenFilter 統一檢查兩個 token。
  • Spring WebSocket／STOMP（Simple Text Oriented Messaging Protocol，簡單文字導向訊息協定）：連線的 CONNECT 步驟只驗 session token（WebSocketConfig）。
  • 資料庫唯一索引調整與升級腳本：schema.sql、migrate_guest_token.sql（不改舊資料）。
  • 前端 token 保存與 401 處理：tokenStore.ts、customerClient.ts、CheckIn.jsx。
  • 學到什麼：看到一個欄位要拿來認人，先問「誰能產生它？誰能看到它？」；憑證由伺服器產生、只交給本人、資料庫只存雜湊，這套原則也適用於密碼、API key、重設密碼連結。
05 · 名詞說明

新手名詞表

X-Device-Id（裝置 ID）
前端隨機產生、存在瀏覽器的一串 ID，只供顯示或除錯；客戶端能任意修改，不能用來認人。
token（權杖）
一段代表「你已通過驗證」的文字，之後每個請求都帶著。本案有 session token 與 guest token 兩種。
JWT（JSON Web Token，JSON 網頁權杖）
帶簽章的 token，內容（用餐 ID、客人 ID）能被讀出，但沒有金鑰就無法偽造或竄改。
SecureRandom
Java 的密碼學等級亂數產生器；256 位元亂數有 2256 種可能，實務上猜不到。
SHA-256／雜湊（hash）
SHA 是 Secure Hash Algorithm（安全雜湊演算法）。把任意資料算成固定長度的「指紋」，同輸入同指紋，但無法反推原文。
HTTP 狀態碼 400／401／403／409
400 資料格式不對；401 沒通過身分驗證；403 身分正確但沒有權限；409 跟目前資料狀態衝突。
WebSocket 與 STOMP
WebSocket 是保持開著的連線，伺服器可主動推訊息；STOMP（Simple Text Oriented Messaging Protocol，簡單文字導向訊息協定）在連線開始的 CONNECT 步驟驗證身分。
唯一索引／migration
某些欄位組合不能重複的資料庫規則／把使用中的資料庫升級成新結構的一次性腳本。
回歸（regression）
改了某處之後，原本正常的功能壞掉；所以修改後要重跑原本的測試。
