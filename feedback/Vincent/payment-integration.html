線上付款與全桌結清的一致性

Vincent · 結帳模組 M6指定案例已驗證修正提交 97391a4

付款頁能開啟，只代表畫面接上了。這篇用「金額相同、只收一次、結果屬於誰、付款後大家看到什麼」四個問題，說明九個已確認的錯誤與修法。

01 · 哪裡錯

九個錯誤，圍繞四個問題

付款路徑：客人確認總額 → 伺服器核對金額、建立「待確認」付款並給前往綠界測試頁的表單 → 綠界用「回呼」（系統主動通知另一個系統）告知結果，客人返回商店頁不代表付款成功 → 通知通過檢查、金額吻合，才保存成功、結束用餐、清購物車並通知同桌。

  1. 同一桌兩種應付金額（問題一）：小計 105 元，10% 服務費應是 10.50 元、總額 115.50 元（櫃檯算法）。線上帳單的 BillService 自己算、保留 0 位小數，得到 11 元、總額 116 元，轉給綠界時又取整數。畫面、付款與保存的金額沒有共同規則。
  2. 待確認期間仍能再收一次（問題二、三）：手機建立待確認付款後，櫃檯仍能結清，同桌也能加點或取消。舊金額的付款通知抵達時，原程式先寫成功才發現場次已結束，可能留下兩筆成功付款，或用舊金額結掉新帳單。且只擋最近 3 分鐘的待確認付款，過了就能建第二張表單，第一張沒失效，兩張都可能付款成功。
  3. 知道交易編號就能查付款結果（問題四）：GET /api/payments/{transactionNo} 不驗用餐身分，交易編號由時間戳加 3 位隨機數組成，別人能猜到附近編號，看到付款金額、桌號與人數。
  4. 付清後只有資料庫關帳（問題五）：線上付款只把用餐改為已付款、桌位改待清潔，沒清掉手機未送出的餐點，也沒發同桌結束通知，其他手機仍停在可點餐的畫面。
  5. 換桌後先顯示上一桌帳單（問題六）：所有帳單共用查詢名稱 ['customer','bill']，查詢工具會暫存結果，短時間換桌就顯示上一桌的結果，付款請求卻用目前桌的憑證：看 A 桌金額、操作 B 桌。
  6. 遲到的回應與未知的結果（問題七至九）：只取消下一次計時，已發出的 A 交易查詢切到 B 後才回來，仍會改畫面並繼續排 A 的查詢；連查多次仍待確認就顯示失敗並讓人重付，但沒收到成功通知不代表沒扣款；直接開付款完成網址沒帶 no 參數，會引用不存在的 DEMO_RESULT 而崩潰。

02 · 怎麼修

每一項修法與為什麼

  • 金額只有一套規則（問題一）：線上與櫃檯結帳共用 BillingCalculator.fromSubtotal()，用 BigDecimal 精確表示十進位金額，HALF_UP 四捨五入到小數第二位。送出付款時帶 expectedTotal（客人剛確認的總額），不同就回 409 BILL_CHANGED（資料狀態衝突），重抓帳單再確認。綠界只收正整數台幣，零元、負數、含小數或超出範圍的帳單回 ECPAY_AMOUNT_UNSUPPORTED 並引導到櫃檯，不默默進位或少收（綠界官方付款參數文件）。
  • 一次只處理一筆（問題二、三）：相關操作先取得同一場次的資料列鎖（暫時鎖住一筆資料讓同時操作排隊）；PendingPaymentGuard 發現有待確認或需人工確認的付款，送單、取消、櫃檯結帳就回 PAYMENT_PENDING，手機未送出的購物車仍可編輯。再次開啟重用原交易編號，收到明確的失敗通知才允許新付款。為什麼：「還沒收到結果」不等於「可以再收一次」，不能靠時間經過來判斷。
  • 回呼要驗、要冪等（問題二、三）：回呼依固定順序先鎖場次、再鎖付款紀錄、最後處理桌位。核對檢查碼 CheckMacValue、商店編號、金額與成功狀態；重複通知只確認同一結果、不再次收尾；金額或本地狀態衝突改為需人工確認。SimulatePaid=1 是測試通知，不據此關桌（綠界官方付款結果通知）。
  • 查結果也要驗身分（問題四）：查詢需要原用餐憑證（JWT，JSON Web Token）與裝置識別（X-Device-Id），後端檢查簽章、期限、客人資料，以及付款是否屬同一場次，不同桌查不到。交易編號改安全隨機，但不能取代身分檢查。付款後場次雖已關閉，此入口仍讓原客人讀結果（點餐入口仍拒絕）；前端把發起付款時的憑證暫存在該分頁的 sessionStorage，避免結束通知清掉點餐憑證後看不到結果。
  • 全桌一起收尾（問題五）：付款成功時核對場次、付款、桌位，再更新用餐狀態；MenuCheckoutNotifier.completeAfterCommit() 清除全桌未送餐點與選項，並在交易提交後發 SESSION_CLOSED。事件只綁定該場次，舊付款重送不能關掉下一組客人的新場次。
  • 前端不信暫存與舊回應（問題六至九）：checkoutApi.js 的查詢名稱含目前用餐身分，舊身分的資料套不到新身分；暫存只是加快畫面，不能決定該收多少錢。交易編號改變就清舊狀態、取消舊請求，回應與計時器要確認仍屬目前查詢；待確認逾時顯示「仍待確認」，不引導新交易，真正失敗才開放重試；缺少交易編號顯示明確訊息。
  • 整合審查補上，不算原作者的缺失：分頁儲存檢查。建立交易前先確認能保存原用餐憑證，保存失敗就不發起付款；收到交易回應後確認實際保存成功才送出表單；交易已建立後才發生儲存異常，提示仍待確認，不自動放行另一筆收款。

03 · 驗證

提交與證據

  • 程式提交 97391a4：154 項 HTTP（Hypertext Transfer Protocol，超文字傳輸協定）與資料庫檢查、31 項瀏覽器案例通過；後端清理後打包與前端建置通過；四份既有單元測試只編譯，未新增或執行。介面與資料庫紀錄 · 瀏覽器紀錄
  • 驗收重點：小計 15.05 元時服務費 1.51 元、總額 16.56 元，手機與櫃檯相同，且因含小數而引導到櫃檯付款，不會產生 17 元的付款；兩位同桌客人同時建立付款只有一筆待確認；不帶憑證查付款回 401（沒有有效身分），帶別桌憑證回 404（找不到）；付款成功後兩個隔離瀏覽器都顯示已結帳。
  • 範圍：只在本機以隔離資料庫驗證，未向綠界送出表單、未實際扣款，也不是正式金流上線驗證。綠界必要設定由執行環境提供，缺少時線上付款顯示不可用，櫃檯流程仍可操作。

04 · 用到的技術與設計模式

本篇真的用到的

  • 綠界金流整合：產生付款表單、驗證回呼檢查碼（EcpayService）。
  • 悲觀鎖（SELECT … FOR UPDATE）與固定鎖順序：場次 → 付款紀錄 → 桌位（PaymentRepository、DiningSessionRepository）。
  • 冪等：相同的成功通知重送多次，只造成一次結果。
  • 狀態推導：付款狀態分 PENDING（待確認）／SUCCESS／FAILED／REQUIRES_REVIEW（需人工確認），逾時與失敗不能混為一談。
  • 交易提交後才發布事件（afterCommit）＋WebSocket：通知同桌 SESSION_CLOSED（MenuCheckoutNotifier）。
  • 單一真相來源：金額一律由 BillingCalculator 計算；BigDecimal 加 HALF_UP。
  • 前端：TanStack Query 的查詢名稱含身分、AbortController 取消舊請求、sessionStorage 暫存憑證，見checkoutApi.js、PayFinsh.jsx、paymentCredentials.js。
  • 學到什麼：先列出每個狀態允許做什麼，程式和畫面才會用同一套規則；第三方只收整數時，要先明說產品政策，不能在轉型別時偷偷改金額。

05 · 名詞表

新手名詞表

用餐場次
一組客人從入座到離開的一次用餐。桌號會重用，場次編號用來分辨不同組客人。
回呼（callback）／冪等（idempotency）
付款系統主動送結果給本系統／相同通知重複處理，仍只造成一次業務結果。
BigDecimal／HALF_UP
Java 的十進位精確數值型別／四捨五入規則；本案金額保留兩位小數。
交易（transaction）
把相關資料庫步驟當一組保存，失敗時回復，避免付款成功紀錄與場次收尾只完成一半。
JWT（JSON Web Token）
以 JSON（JavaScript Object Notation）承載身分資訊並帶簽章的憑證；伺服器還要檢查簽章、期限，以及客人所屬場次。
CheckMacValue／MAC（Message Authentication Code）
付款通知的檢查碼欄位／訊息鑑別碼。用約定的金鑰和內容計算，核對通知是否被改過。
sessionStorage／AbortController
瀏覽器以分頁為範圍的暫存空間（關閉分頁後通常清除）／取消已發出請求的工具；取消之外仍要檢查舊回應是否過期。
