工作包 E（訂位）訂位時間與提醒已驗證

Harry｜18:15 為什麼不能訂？提醒為什麼只能寄一次？

訂位模組已經有悲觀鎖、區間重疊檢查這些很扎實的設計。這篇處理兩件事：讓「任意時間」真的能訂，以及把只寫在 log 裡的訂位提醒，變成可以追蹤、不會重複寄的通知。

本篇範圍

一個規格不符、一個基本功能、一個版面問題

  • 規格不符：M7 7.1 寫「任意時間預約、非固定時段」，但建立訂位只接受半小時整點。
  • 補上的基本功能：M7 7.12「用餐前 2 小時發通知」原本只寫一行 log，沒有記錄、會重複。
  • 版面：店家的預約管理頁在 1024 像素寬時，整個後台被表格撐出橫向捲軸。
  • 沒有動的：建立訂位時鎖住候選桌、檢查時間區間重疊、還沒結帳的已入座也算佔用，這些原本就正確的設計全部保留。

提醒是規格裡有、原本只寫 log 的基本功能，這次補完屬於整合成果。規格文件（資料庫設計、API 規格、M7、UI 規格）也同步補上新的欄位與規則。

情境

客人想訂明天 18:15

一位客人下班 18:00，想訂明天 18:15，四個人。店裡那個時間有空桌，也沒有和別的訂位重疊。但送出後拿到 400 錯誤：系統只接受 11:30、12:00、12:30……這種半小時整點。

M7 第 116 行附近其實特別討論過「固定時段」的設計，而且是被否決的：固定時段會讓 18:15 想來的客人只能選 18:00 或 18:30。正確的模型是存「開始時間」與「結束時間」，用區間重疊判斷能不能訂。訂位模組的資料模型和重疊檢查都已經照這個做了，只剩建立訂位的檢查還在要求整點。

任意時間訂位

改的是「合法時間」的定義，不是重疊的算法

  • 可以訂的時間：最早開始到最晚開始（預設 11:30～20:00，頭尾都算）之間的任意一分鐘，例如 13:07、18:15。
  • 精確到分鐘：帶了秒或毫秒（例如 18:15:30）就拒絕，而不是默默改成 18:15。這樣存進去的值就是客人選的值。
  • 其他規則不變：只能訂明天起 30 天內、人數、區間重疊、悲觀鎖都照舊。
  • 錯誤訊息說清楚：「訂位開始時間須在 11:30 到 20:00 之間，請重新選擇」「訂位時間只能精確到分鐘，請重新選擇」，都是 400 VALIDATION_FAILED。
  • 選時間頁：可訂時段查詢仍提供半小時一格的「建議時段」。UI 規格的選時間頁只有時段按鈕、沒有自訂時間的設計，所以畫面維持按鈕；後端已經不再限制，之後要加自訂時間輸入時不必再改後端。
補上的基本功能 · 整合成果

提醒要「寄過就記下來」，而且只能寄一次

原本的提醒排程每 15 分鐘跑一次，找出接下來要開始的訂位，然後寫一行 log 就結束了：沒有記錄寄過沒有，所以下一次排程又會再寫一次；店長按手動觸發，回傳的數字也只是寫了幾行 log。

1. 用一個欄位記錄「什麼時候提醒過」

訂位表新增 reminder_sent_at。要提醒的條件：狀態是已確認、還沒提醒過、開始時間在「現在」到「現在＋2 小時」之間。

2. 用「條件式更新」搶，搶到的才寄

排程和店長的手動觸發可能同時跑。如果先查「還沒提醒的」再寄，兩邊都會查到同一筆、各寄一次。所以每一筆都先執行：

UPDATE reservation SET reminder_sent_at = 現在 WHERE id = ? AND status = 'CONFIRMED' AND reminder_sent_at IS NULL

資料庫一次只讓一個人改這一列：先改的那個看到「影響 1 列」，才真的寄；後到的看到「影響 0 列」，就跳過。剛好在這瞬間被取消的訂位，因為條件裡有 status = 'CONFIRMED'，也不會被寄到。實測兩個手動觸發同時送出，回傳 1 和 0，合計只提醒一次。

寄送的時機選在「搶到並存檔之後」。如果剛好在寄之前程式當掉，那筆就不會補寄。這是刻意的取捨：寧可漏寄一次，也不要重複寄，因為重複的提醒簡訊對客人更困擾。

3. 模擬簡訊，不真的發送

專題沒有串真的簡訊服務。比照會員驗證碼的「模擬簡訊」做法，提醒內容寫成一行 log：「訂位提醒（模擬簡訊，沒有真的發送）… → 0912***678：王小明 您好，提醒您 10/24 18:30 的訂位（4 位）……」，手機號碼中間遮起來。店家端預約管理頁在那筆訂位下方顯示「已提醒 18:32（模擬簡訊）」。

4. 取消時不能把提醒時間洗掉

取消、報到時，程式會把整筆訂位寫回資料庫。如果 reminderSentAt 也跟著被寫回，讀進來時的舊值（例如 NULL）可能蓋掉剛記下的提醒時間。所以這個欄位設定成「JPA 不寫入」，只由上面那句條件式更新負責。實測提醒後再取消，提醒時間仍然保留。

整合時順手修的版面

一個 min-w-0，修好整個後台在 1024 像素的橫向捲軸

店家端規格從 1024 像素寬開始支援。預約管理頁的表格比畫面寬，表格外面雖然包了「可以橫向捲動」的框，但整個後台還是被撐到 1219 像素。原因是後台的右側內容欄是 flex 子元素，flex 子元素預設不會縮到比裡面的內容還窄（最小寬度是 auto），所以內層的捲動框根本沒有機會發揮作用。

在共用的後台版型（DashboardLayout）內容欄加上 min-w-0 後，寬表格就在自己的框裡捲動。修完逐頁檢查 8 個後台頁面，在 1024 與 1440 像素都不再有整頁橫向捲軸。這是改動前就存在的問題，不是作者的缺失，但因為規格要求 1024 起，這次一起修。

手把手驗收 · 請在本機隔離資料庫

你可以照著做一次

  1. 任意時間。訂 3 天後的 18:15、11:30、20:00、13:07，都回 201，資料庫存的時間就是送出的時間（18:15:00）。

  2. 邊界。11:29、20:01、18:15:30（帶秒）、今天、31 天後，都回 400 VALIDATION_FAILED。可訂時段查詢仍然回 18 個建議時段。

  3. 提醒。用 SQL 放三筆訂位：90 分鐘後開始、180 分鐘後開始、60 分鐘後開始但已取消。同時送兩次手動提醒：合計只提醒 1 筆（就是 90 分鐘後那筆）；再送一次回 0。log 只有一行模擬簡訊，手機號碼有遮罩。管理端清單帶回提醒時間。櫃檯身分不能觸發提醒（403）。

  4. 取消後保留。把已提醒的那筆取消，提醒時間仍然在。

  5. 畫面（1024 像素寬）。預約管理頁顯示的「已提醒（模擬簡訊）」筆數，和 API 回傳的一致；8 個後台頁面在 1024 與 1440 都沒有整頁橫向捲軸。

  6. 升級腳本。在舊結構的資料庫（72 筆訂位）上執行，新欄位都是 NULL，舊資料不變。

前輩回饋、報告與履歷

技術前輩的建議

訂位模組的區間重疊與悲觀鎖寫得很好，這次只要放寬「合法時間」的檢查就能支援任意時間，證明當初的資料模型選對了。寫驗證規則時，可以回頭對照規格的每一句話（「非固定時段」），避免舊設計的痕跡留在檢查裡。

排程類功能先問：「跑兩次會不會重複？」用條件式 UPDATE 搶一列、看影響列數決定要不要做事，是讓排程冪等最簡單的方法；也要想清楚失敗時是「寧可漏」還是「寧可重複」。

這個功能用到的技術

  • 時間區間模型（開始／結束時間）與區間重疊檢查
  • 悲觀鎖（SELECT ... FOR UPDATE）防止同一張桌被重複訂
  • 條件式 UPDATE 做去重、影響列數判斷
  • Spring 排程、手動觸發 API、Clock 注入的業務時鐘
  • JPA 欄位 insertable/updatable=false 避免整列寫回覆蓋
  • CSS flex 的 min-width: auto 與 min-w-0

專題報告與履歷可以這樣寫

報告：用「固定時段 vs 時間區間」的比較圖開場，說明為什麼選區間模型；再展示同時建立兩筆訂位時悲觀鎖如何讓其中一筆失敗。最後 demo 手動觸發提醒、畫面出現「已提醒」，再觸發一次回 0。

履歷：「負責餐廳線上訂位模組：以時間區間與悲觀鎖實作任意時間訂位與防重複配桌，並以條件式更新實作只寄一次的訂位提醒排程（含模擬簡訊與管理端追蹤）。」

新手名詞表

區間重疊（interval overlap）
兩段時間只要「A 開始早於 B 結束，而且 B 開始早於 A 結束」就重疊。用它判斷同一張桌能不能再接一筆訂位。
悲觀鎖（pessimistic lock）
先假設會有人搶，所以讀資料時就鎖住（SELECT ... FOR UPDATE），其他人要等鎖放開才能動同一筆。
條件式更新（conditional update）
在 UPDATE 的 WHERE 裡寫上「必須還是某個狀態」，資料庫會告訴你改了幾列；改到 1 列代表你搶到了。
冪等（idempotent）
做一次或做很多次，結果都一樣。排程最好設計成冪等。
API（Application Programming Interface，應用程式介面）
前端或其他程式呼叫後端功能的網址與規則。
HTTP 狀態碼 201／400／403
HTTP 是 Hypertext Transfer Protocol（超文字傳輸協定）。201 建立成功；400 資料不合規則；403 角色沒有權限。
JPA（Java Persistence API，Java 持久化 API）
Java 用物件讀寫資料庫的標準介面。insertable/updatable=false 代表存檔時不寫這個欄位。
Clock（時鐘注入）
把「現在幾點」包成一個可以替換的物件，程式統一跟它問時間，時區一致，也方便測試。
migration（資料庫升級腳本）
把正在使用的資料庫升級成新結構的一次性腳本。
S-07
UI（User Interface，使用者介面）規格的畫面編號，S-07 是店家端預約管理頁。
flex 與 min-w-0
flex 是 CSS 的排版方式；flex 子元素預設最小寬度等於內容寬度，加上 Tailwind 的 min-w-0（min-width: 0）才允許它縮小，讓裡面的捲動框生效。
SHA／Git commit
SHA 是 Secure Hash Algorithm（安全雜湊演算法）；Git 用它幫每個版本（commit）產生識別碼。
