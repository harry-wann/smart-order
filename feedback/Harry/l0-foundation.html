哪裡錯

三個 P1（要先修的嚴重問題）加一次匿名介面盤點

1. 金鑰寫在程式碼裡

JWT（JSON Web Token，JSON 網頁權杖）的內容誰都讀得到，能當登入憑證是因為有簽章：只有知道金鑰的人算得出，伺服器重算對得上才相信。

修正前

會員與同桌點餐的 JWT 金鑰，是 JwtToken.java 裡的字串常數。專案放在 GitHub，看得到程式碼的人都能自簽「我是會員 1 號」。實測用舊金鑰自簽會員 token 呼叫 GET /api/member/me，回 200（成功）。

修正後

同樣的偽造 token，不管有沒有加類型標記 typ，都回 401（沒有通過身分驗證）；真的登入拿到的 token 仍可用。

2. 同一個「現在」，程式和資料庫各說各話

修正前

客人送單後馬上出餐，出餐時間卻比下單時間早 28,799 秒（約 8 小時）。程式用 LocalDateTime.now() 寫 placed_at，是台北時間 20:30；資料庫用 CURRENT_TIMESTAMP 寫 served_at，compose 裡的 MySQL 沒設時區、預設 UTC（Coordinated Universal Time，協調世界時），是 12:30。新會員建立時間也早 28,800 秒。

修正後

出餐與下單時間相差 0 秒；新會員建立時間與台北現在時間相差 0 秒。

原因是 DATETIME 欄位只存「幾點幾分」、不存時區，兩個數字被當成同一個時區直接相減；所有用 DEFAULT CURRENT_TIMESTAMP 填的建立時間也都早 8 小時。每個人的環境都會遇到，所以屬於共用地基。

3. 誰都能聽櫃檯的即時推播

修正前

櫃檯畫面靠 WebSocket 的 /topic/counter 頻道即時收到桌況、候位、提醒、服務鈴，但它被寫成公開推播。實測匿名 STOMP（Simple Text Oriented Messaging Protocol，簡單文字導向訊息協定）連線訂閱它，伺服器回 CONNECTED，沒有拒絕。

修正後

匿名訂閱收到 ERROR；只有帶員工 JWT、角色是 COUNTER（櫃檯）或 MANAGER（店長）的人才能訂閱。

順便發現：櫃檯桌位詳情頁訂閱的 /topic/billing 沒列進允許清單，員工訂閱一律被拒，前端每 5 秒重連、每次又重抓帳單。這是結帳整合時漏掉的，整合時一併補上，不算 L0 原作者的缺失。

4. 匿名 API（Application Programming Interface，應用程式介面）盤點

Spring Security 的最後一條規則是「其他 /api/** 都放行」，新 API 只要忘了加規則就變成匿名可用。逐一盤點：

  • 客人用的（掃碼、菜單、會員 OTP（One-Time Password，一次性驗證碼）、訂位）合理公開，需要身分的另有 token 保護；/api/admin/** 每支都有角色規則。
  • 不合理的是 /api/order/admin/**（菜單管理）：匿名可以新增、修改、刪除菜單。前端選項群組頁用不帶員工憑證的方式呼叫，要和前端一起改，交由 Clara 的菜單管理分支處理。建議之後加一條「/api/admin/** 至少要登入」當最後防線，讓忘了加規則的新 API 預設是關的。
怎麼修

照專案裡已經做對的寫法，並說清楚為什麼

金鑰：改由設定讀取，設錯就起不來

員工登入的 StaffJwtProvider 早就是正確做法，這次讓 JwtToken.java 跟上：

  • 金鑰從設定 app.customer-jwt.secret 讀，正式環境用環境變數 CUSTOMER_JWT_SECRET 提供，.env.example 只放說明；金鑰就不會跟著程式碼被上傳。
  • 本機開發可用 repo 裡的預設值，但伺服器不是只聽本機卻還在用預設值，就拒絕啟動；金鑰短於 32 bytes 也在啟動時擋下。這叫 fail fast（及早失敗）：寧可起不來，也不要悄悄用公開的金鑰上線。
  • 會員與同桌 token 加上類型標記 typ（member／guest），各自只接受自己那一種，加上原本的 staff，三種 token 不能互相冒用。

時區：程式和資料庫都固定成台北

  • 資料庫連線：smartorder 這組連線每次建立時執行 SET time_zone = '+08:00'（HikariCP 的 connectionInitSql）。只影響這個專案的連線，不改 MySQL 全域設定。用 '+08:00' 而非 'Asia/Taipei'，因為後者要 MySQL 先載入時區資料表，台灣也沒有日光節約時間。
  • 程式：SmartOrderApplication 一啟動就把 JVM（Java Virtual Machine，Java 虛擬機）預設時區設成 Asia/Taipei，不依賴部署機器。
  • 為什麼兩邊都要：只設程式，SQL（Structured Query Language，結構化查詢語言）寫的時間還是 UTC；只設資料庫，程式部署到 UTC 的伺服器時又會錯。

推播權限：訂閱時檢查「你能不能聽這個頻道」

  • WebSocketConfig.java 在 STOMP 訂閱時檢查：/topic/counter 和 /topic/billing 只限帶員工 JWT 的 COUNTER 與 MANAGER。前端櫃檯的推播本來就帶員工 token，畫面不受影響。
  • 審查提醒：廚房帳號登入後原本進桌況總覽，現在訂閱被拒、每 5 秒重連，所以登入後改成依角色導頁，廚房帳號直接進出菜看板。
驗證

修正前後對照

  • 回歸：JWT 用法改了，所以重跑會員 OTP 75、同桌身分 74、個人購物車 56、結帳 156 項 HTTP，以及候位＋15 條頁面路由共 41 項、提醒 12 項瀏覽器測試，全部通過。完整瀏覽器紀錄。
  • 獨立高風險審查沒有 P1／P2：金鑰注入沒有遺漏的呼叫端、三種 token 不能互用、DATETIME 不會因改連線時區而位移、前端訂閱的頻道都在允許清單內。提醒：伺服器只聽本機時開發預設金鑰仍會被接受，部署清單必須設定 CUSTOMER_JWT_SECRET；修正前寫進資料庫的舊時間不會被回頭校正。
用到的技術與設計模式

本篇真的用到的

  • JWT 簽章（jjwt）、金鑰管理與 token 類型區分（typ）：環境變數加啟動時檢查，JwtToken.java。
  • HikariCP connectionInitSql、JVM 預設時區：SmartOrderDataSourceConfig.java、SmartOrderApplication.java。
  • Spring WebSocket（STOMP）訂閱授權：在 ChannelInterceptor 的 preSend 檢查，WebSocketConfig.java。
  • Spring Security 路徑規則盤點：SecurityConfig.java。
  • 學到什麼：金鑰、密碼不進版本控制；欄位不帶時區，就要決定全系統用哪個時區，並故意比較兩個由不同地方寫入的時間來驗證。
名詞表

新手名詞表

JWT 與簽章
內容誰都能讀；簽章只有持有金鑰的伺服器算得出來，所以能證明 token 沒被偽造。
環境變數（environment variable）
在程式外面設定的值，例如 CUSTOMER_JWT_SECRET，金鑰放這裡就不會被上傳到 GitHub。
UTC
國際標準時間；台北時間是 UTC+8。
DATETIME 與 CURRENT_TIMESTAMP
DATETIME 只存日期與時間、不存時區；CURRENT_TIMESTAMP 是資料庫依「目前連線的時區」給的現在時間。
HikariCP 與 connectionInitSql
HikariCP 是 Spring Boot 預設的資料庫連線池；connectionInitSql 是每條連線建立時先執行的一句 SQL。
WebSocket 與 STOMP
WebSocket 是保持開著的連線；STOMP 讓客戶端「訂閱」頻道，伺服器可以在訂閱時檢查權限。
