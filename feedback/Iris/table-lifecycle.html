Iris｜一張桌何時能開？從預約保留到清潔完成

本篇範圍

讓現場開桌、預約保留和清潔流程看見同一份桌況

  • 原本開桌已有桌位資料列鎖；這次讓清潔完成也使用同一把鎖，並在鎖內重驗狀態。
  • 後端檢查桌位是否啟用、是否已有用餐紀錄、目前是否被預約保留，以及人數是否符合容量。
  • 桌況總覽顯示實體狀態與預約保留；開桌頁等真實桌位和開桌選項載入後才允許操作。
  • 店員 API 權限、預約取消／報到後的桌況通知，以及需登入載入的桌位 QR（Quick Response，快速反應碼）列印一併接好。

這是 D、E 功能的整合成果。原審查列出的開桌保留競態、清潔覆寫、人數驗證和 D API 權限，是本篇追溯的原始問題；桌位設定讀取權限及開桌頁晚到回應，則是整合審查後補上的回歸修正。

情境一 · 同一張桌有兩種用途

客人到了，畫面上的「空桌」就能直接開嗎？

假設 A08 是四人桌，晚上 18:00 有一組四人預約。系統設定的保留時段若是預約前 30 分鐘到後 10 分鐘，17:45 時這張桌已經要留給預約客人。可是資料庫裡的實體桌況仍可能是 AVAILABLE，因為它還沒有任何人坐下。

如果櫃檯只看「實體狀態是空桌」，就可能讓現場客人或候位組先入座。預約客人到店時，桌子已被占用；櫃檯畫面和預約規則看起來各自合理，實際上卻爭用了同一張桌。

只看桌子狀態

資料庫記錄 status=AVAILABLE，開桌程式就建立用餐紀錄。它不知道這張桌目前由訂位保留。

同時看桌況與保留

保留資料指出 A08 屬於某筆訂位。畫面顯示「預約保留」；現場與候位開桌收到 409 TABLE_RESERVED，該筆訂位的客人仍可走報到流程。

情境二 · 找出錯誤在哪一層

為什麼光在畫面停用按鈕還不夠？

同一個開桌動作有不同入口：櫃檯按鈕、候位報到、預約報到，也可能有人直接呼叫伺服器。瀏覽器只是其中一個入口，資料正確與否仍要由後端在保存前決定。

保留與清潔競態

開桌只檢查實體狀態，可能占用仍在保留窗內的桌。清潔完成又用一般讀取；若它先讀到舊的 CLEANING，之後可能把另一個請求已經開好的桌改回空桌。

沒有服務端人數界線

畫面上硬寫容量，或只顯示「可能要加椅子」，不能阻止直接送來負數、空值、零人或超過桌位容量的請求。若用 32 位整數直接相加，極大數值還可能溢位。

員工操作路徑未完整保護

寬鬆的通用 API 規則若先放行，未登入的人也可能呼叫開桌、清桌或候位操作。光把按鈕藏起來，並不會替伺服器驗證員工身分。

整合時序帶來的額外回修

整合審查另發現，若 COUNTER 讀取桌位設定也被限制成店長專用，既有預約畫面的桌數會消失；開桌請求若在切換桌號後才回來，舊回應也可能把新頁面導走或顯示到錯桌。

實際改法

把「檢查、寫入、通知」放在正確的時間點

1. 清潔也使用開桌原有的桌位鎖

開桌流程原本就會先對桌位資料取得資料列鎖（row lock）；原問題是鎖內還沒檢查預約保留、容量與既有用餐紀錄。這次補上這些檢查條件。清潔完成原先沒有共用這把鎖，現在也先鎖定同一筆桌位，再確認桌子仍在清潔、沒有未結束的用餐紀錄。需要同一把鎖的交易會排隊，拿到鎖後重新讀取最新狀態；舊的清潔請求就不能把另一個請求新開的桌改回空桌。

候位報到的外層交易使用 READ_COMMITTED（讀取已提交資料）隔離層級，讓等待桌位鎖之後的狀態判斷看得到已提交的更新。

2. 同時保留實體狀態與畫面狀態

後端仍把桌子的真實 status 保留為 AVAILABLE；若保留窗內有訂位，桌況回應另外把 displayStatus 設為 RESERVED，並帶上 heldFor（被哪筆訂位保留）。這樣畫面可以顯示保留人、時間與人數，程式也不必把「預約保留」誤當成桌子已被入座。

同一份保留快照用在整張桌況總覽，避免每一桌各自查一次。預約報到可以使用自己的訂位；保留時段外、但 115 分鐘內即將開始的訂位只顯示提醒，櫃檯確認後仍可開桌。此提醒規則不會把「即將有訂位」錯當成「已進保留窗」。

3. 以伺服器規則檢查人數

成人與兒童人數都必須有值且不小於零；總人數至少一位，並且不能超過該桌座位數。計算總和時先轉成較大的整數型別，避免兩個輸入相加時先溢位。瀏覽器也使用真實桌位容量限制步進器、按鈕與候位清單，但後端仍會再檢查一次。

4. 把權限切在 API 路徑與 HTTP 方法上

桌況、開桌、清潔和候位操作只允許 COUNTER（櫃檯）或 MANAGER（店長）。桌位設定的讀取允許 COUNTER 與 MANAGER，新增或修改則只允許 MANAGER。這讓櫃檯能讀取預約頁與開桌頁所需資料，同時保留設定變更權限。

員工登入後，桌位 QR 圖片改由員工 API 取得檔案資料，再放入列印頁；列印完會釋放暫存圖片網址。不能再依賴未帶員工憑證的普通圖片網址。

5. 只讓仍屬於目前桌號的請求更新畫面

開桌頁為每次操作記錄桌號與請求世代。若櫃檯切到另一桌，舊請求即使之後成功或失敗，回應也不會導航或覆寫新桌的訊息。頁面還要等桌況與開桌選項 API（open-options）成功回來，才顯示可操作的現場／候位選項；人數容量、被保留的訂位，以及尚未進保留窗的提醒都取自伺服器資料。

桌況總覽每 60 秒重抓一次，並每分鐘更新用餐時間；所以保留窗開始或結束、用餐超過 100 分鐘時，不必等櫃檯手動重整。待報到數由今天的訂位資料計算，不再顯示固定假數字。取消訂位與預約報到的桌況通知則等交易提交後才發出，通知帶的是提交後重讀的實體狀態、畫面狀態與保留資訊。

本次店家端版面依使用者介面（UI）規格，以 1024 像素寬作為桌機／平板驗收起點。390 像素只檢查開桌頁內容區塊本身是否溢出：內容寬 266 像素且能放入容器；共用後台頁面的文件寬度仍是 474 像素，所以不宣稱整個店家後台支援手機寬度。

手把手驗收 · 請在本機隔離資料

逐項確認伺服器拒絕錯誤操作、畫面呈現真資料

本次在隔離資料庫與本機瀏覽器完成了下列對應驗收。HTTP 紀錄 101 項全通過；瀏覽器紀錄 36 項全通過。操作前會建立隔離測試資料，不使用正式店家桌位。

  1. 先看權限。不帶員工憑證呼叫 /api/admin/tables 與 /api/admin/waitlist，確認回 401；用 COUNTER 和 MANAGER 讀桌況、候位與桌位設定，確認可讀。再用 COUNTER 嘗試修改桌位設定，應回 403；同一操作由 MANAGER 執行應依設定成功。401 表示尚未通過身分驗證，403 表示已辨識身分但角色不能做這件事。

  2. 建立一筆現在正在保留的預約。讓測試訂位落在保留時間內、桌子實體狀態仍是空桌。讀取桌況，確認 status 是 AVAILABLE、displayStatus 是 RESERVED，而 heldFor 有訂位資訊。從開桌頁嘗試現場開桌，確認不會送出；直接呼叫開桌 API 則確認回 409，錯誤代碼是 TABLE_RESERVED。用該筆預約執行報到，再確認流程可繼續。

  3. 送出不合法人數。在本機 API 請求中分別送成人或兒童欄位缺值、負數、兩者都是零，以及總人數大於座位數的資料；每筆應回 400，資料庫不能多出用餐紀錄。再送很大的整數，確認總和仍被正確判定超容量，不會變成負數或小於實際值。

  4. 交錯清潔與開桌。用兩個本機請求在同一張待清潔桌上協調執行：讓第二個清潔請求等待第一個完成，再讓桌位開桌。確認等待中的清潔請求讀到最新狀態後遭拒；最後桌況是用餐中，且只有一筆未結束的用餐紀錄。也確認失敗的清潔沒有送出「已清潔」通知。

  5. 確認時間與櫃檯統計。瀏覽器測試把用餐時間控制前進 61 秒，再實際重抓桌況；用餐時間從 102 變成 103 分鐘，超過 100 分鐘後顯示紅框。頁首時鐘也從 17:00 更新到 17:01。另核對待報到數來自今天的真實訂位，櫃檯預約頁的可預約比例為 72%（13／18 桌）。桌況的 60 秒輪詢負責刷新時間會變動的保留資訊；本次紀錄沒有把等到保留邊界跨越當成一項瀏覽器驗收。

  6. 確認晚到的真實開桌成功不會帶走新桌頁。先在隔離資料庫準備桌位與員工資料，瀏覽器送出 A 桌真實開桌 POST，後端成功提交並回應 200；測試流程用 route.fetch 暫緩這個真實 HTTP 回應，先在單頁應用程式（SPA）切到 B 桌，再放回 A 的成功回應。確認頁面仍停留在 B 桌、沒有把 B 桌操作鎖住。這次只對真實成功回應做了執行期驗收；錯誤回應分支由獨立靜態審查確認有桌號與請求世代檢查，沒有宣稱也做過錯誤回應的執行期案例。fixture 在此指預先準備的隔離測試資料，不是假造成功的回應。

  7. 核對整合通知與 QR 列印。測試訂位取消或報到提交後，查看桌況通知中的狀態和保留資訊；以登入員工身分開啟 QR 列印頁，確認圖片載入、列印，關閉或列印完成後暫存網址會清除。

前輩回饋、報告亮點與履歷

技術前輩的建議

把「空桌」拆成實體狀態和能否供現場使用，是很好的狀態建模練習。接著可把每種操作整理成一張小表：誰可以做、必須先滿足什麼、失敗回哪個狀態碼、成功後什麼時候發通知。這張表能同時檢查 API、畫面和驗收案例有沒有說同一件事。

併發問題不要只用「按鈕有 loading」解釋。清楚指出誰先鎖哪一筆資料、等待後重新檢查什麼，並以最終資料庫狀態作證，會更能說明修正有效。

技術報告可以展示

  • 說明原本已有的開桌資料列鎖，以及這次讓清潔完成共用該鎖、取得鎖後重驗狀態的修正。
  • 說明預約保留快照如何產生 displayStatus 與 heldFor，並區分「現在保留」和「稍後提醒」。
  • 展示成人、兒童、缺值、總人數、容量及整數溢位的服務端界線。
  • 說明員工角色如何依 API 路徑及讀寫方法授權，並示範 QR 圖片如何用員工身分載入。
  • 交代整合回修：COUNTER 可讀桌位設定、舊桌號請求不能改寫新頁面，以及提交後才發桌況通知。
  • 用 101 項 HTTP 回應、並行後的資料狀態與 36 項瀏覽器操作紀錄相互核對。

履歷句建議

「參與餐飲訂位與候位流程整合，修正同桌開桌／清潔競態與預約保留衝突，加入服務端人數容量驗證和櫃檯角色授權；協作接上桌況即時呈現、預約異動通知及員工 QR 列印，並以 101 項 HTTP 與 36 項瀏覽器驗收確認。」

面試時可以挑「清潔請求拿著舊資料，晚一步把新開桌改回空桌」來說明：先畫出交錯順序，再解釋這次如何讓清潔也取得原本開桌使用的資料列鎖，最後指出資料庫最終狀態和驗收紀錄。履歷請保留「參與、協作」的範圍，不寫成獨立完成整個 D/E 模組或已上線營運；候位與座位設定仍在各自的整理範圍內。

新手名詞表

前端／後端
前端是店員在瀏覽器操作的畫面；後端是在伺服器檢查資料、權限並和資料庫互動的程式。
API（Application Programming Interface，應用程式介面）
前端或其他程式用來向後端讀取資料、提出操作的一組網址和規則。
HTTP（Hypertext Transfer Protocol，超文字傳輸協定）
瀏覽器和伺服器常用的通訊規則。GET 通常讀資料，POST 通常送出資料或操作。
HTML（HyperText Markup Language，超文字標記語言）
用標籤描述網頁標題、段落、連結與內容結構的格式；本篇文章就是 HTML 文件。
HTTP 狀態碼 400／401／403／409
400 是請求資料不合規則；401 是沒有通過登入驗證；403 是已辨識使用者但權限不足；409 是目前資料狀態與這項操作衝突。
DTO（Data Transfer Object，資料傳輸物件）
專門把資料欄位整理成 API 回應或請求格式的物件；例如桌況回應可包含實體狀態、畫面狀態與保留資訊。
QR（Quick Response，快速反應碼）
可由手機相機快速讀取的方形圖碼。本案桌位 QR 連到該桌的點餐入口。
SQL（Structured Query Language，結構化查詢語言）
用來查詢和更新資料庫資料的語言。資料列鎖會讓同一筆資料的特定更新依序進行。
JPA（Java Persistence API，Java 持久化 API）
Java 程式以物件讀寫資料庫的標準介面；專案的 repository（資料存取元件）透過它查桌位及取得鎖。
資料列鎖（row lock）
交易要修改某筆資料時取得的鎖。其他需要同一筆鎖的操作會等候，之後再檢查已更新的資料。
交易（transaction）
把一組資料庫讀寫視為一次完整操作；如果其中一步失敗，不應留下只做了一半的狀態。
READ_COMMITTED（讀取已提交資料）
一種資料庫隔離層級。查詢可讀取其他交易已完成提交的結果；候位報到在取得桌位鎖後需要判斷最新桌況。
保留快照（hold snapshot）
在同一個時間點整理當下有效的訂位資料，供桌況總覽與開桌檢查共用，避免不同畫面各算出不同保留結果。
afterCommit（提交後回呼）
資料庫交易成功保存後才執行的程式。本案用它發送桌況通知，避免通知先於資料寫入成功。
Blob（Binary Large Object，二進位大型物件）／URL（Uniform Resource Locator，統一資源定位符）
Blob 是瀏覽器中的二進位檔案資料；Object URL 是頁面暫時讀取這份資料的網址，列印結束後應釋放。
SHA／Git commit（版本提交）
SHA 是 Secure Hash Algorithm（安全雜湊演算法）的縮寫；Git 用它產生版本提交的識別碼。commit 是把一組程式變更保存成版本；本篇列出已完成整合的短識別碼。
競態（race condition）
兩個操作的執行順序互相交錯，造成單獨看每個操作都合理、合在一起卻寫錯資料的情況。
fixture（隔離測試資料）
為一次測試預先準備的桌位、訂位、員工等資料。本次晚到回應案例使用真實資料與真實開桌請求，fixture 不代表假造 HTTP 回應。
route.fetch
瀏覽器自動化工具在攔截請求時，仍將該請求送到真正後端並取回回應的方法；本次先讓資料庫真的完成開桌，再延後瀏覽器收到成功回應的時間。
SPA（Single-Page Application，單頁應用程式）
切換畫面時可只改變目前頁面內容，不必重新載入整份網頁的應用程式形式；本次用它驗證切到 B 桌後，A 桌的晚到回應不會帶走新頁面。
UI（User Interface，使用者介面）
使用者實際看見並操作的畫面、按鈕、文字和狀態提示。
RWD（Responsive Web Design，回應式網頁設計）
讓網頁依不同螢幕寬度調整排版。本次沒有把 390 像素觀察說成整個後台的 RWD 驗收。
loading（載入中）
資料尚未準備好時的等待狀態。按鈕顯示 loading 能避免重複點擊，但資料仍需由後端鎖定與重新檢查。
COUNTER／MANAGER
店員角色名稱：COUNTER 是櫃檯，MANAGER 是店長。API 依角色和讀取／修改操作限制權限。
