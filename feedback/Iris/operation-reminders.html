哪裡錯

M2 規格裡兩個還沒做的排程

週五晚上 19:30，店裡規定一組客人用餐約 100 分鐘、清桌約 15 分鐘。A01 已經吃了 101 分鐘，該去提醒客人最後加點、準備結帳；A06 在 16 分鐘前就結帳了，卻忙到沒人收，桌況一直是「待清理」，候位客人還在門口等。桌況總覽雖顯示用餐分鐘數，但十幾張桌的小字，店員在尖峰時不可能一直盯著看，系統應該主動告訴店員。

M2 規格與 API 規格的排程表有這兩個排程（用餐超時每分鐘一次、待清理每 5 分鐘一次），但原本還沒實作，整合時補齊，不算原作者的缺失。審查另外找到兩個問題：

100 分鐘的邊界不一致

原本後端「滿 100 分鐘」就推提醒，畫面卻要「超過 100 分鐘」才讓桌格變紅，中間有一分鐘提醒說超時、桌格卻還沒紅。

推播比桌況重抓晚到

推播晚於桌況重抓抵達時，那張桌其實已經不是用餐中，卻殘留一則舊提醒。

怎麼做

排程只負責「找」和「通知」，不改任何資料

另一種做法：資料庫存「已提醒」

在用餐紀錄加「已通知超時」欄位，推過就標記。缺點是要改資料表，而且店員剛好沒看到，就再也不會出現。

這次的做法：每次重新掃描

每次都從目前的資料重算「哪些桌超時」，推出去就結束，不寫資料庫；重複推播由畫面合併。沒有要同步的狀態，重新整理頁面後下一次推播就補回。

這種「重跑幾次結果都一樣、也不改變資料」的性質叫冪等（idempotent）。排程最怕「跑兩次就出事」，所以優先設計成冪等。

  • 找出超時的桌：用餐紀錄是 OPEN、超過 100 分鐘（分鐘數無條件捨去後大於 100，也就是滿 101 分鐘）、桌位啟用中。這條線和桌格變紅的條件完全一致，修掉上面的一分鐘空窗。資料庫沒擋同一桌兩筆 OPEN，所以依桌分組、取最早開的那筆，一桌只推一則。
  • 找出待清理的桌：桌況是 CLEANING，取最後一筆已結帳（PAID）紀錄的結帳時間 closed_at 當起算點，超過 15 分鐘才推（結帳時寫入 closed_at 和桌子改成待清理在同一個交易裡完成）。篩選與分組由資料庫做，不把所有紀錄載入記憶體。
  • 排程與手動共用同一段程式：排程方法只負責「時間到了呼叫 Service、記 log」，真正的查詢與推播都在 Service 裡；POST /api/admin/scheduler/check-overtime 與 /remind-cleaning 呼叫同一個 Service，只有 MANAGER 能用，回傳 {"job": "...", "affected": 推了幾桌}。規格強調：「你不可能在 demo 時等到晚上 11:30」，每個排程都要有手動入口，手動測到的就是排程實際會做的事。
  • 排程寫法：Spring 的 @Scheduled 用 cron 描述時間（0 * * * * * 每分鐘、0 */5 * * * * 每 5 分鐘），都指定 Asia/Taipei。排程裡的例外只記錄、不往外丟，否則一次錯誤可能讓之後的排程都停掉。
  • 推播：推到櫃檯頻道 /topic/counter，格式 {"type":"TABLE_OVERTIME","tableId":1,"tableNo":"A01","minutes":101}（API 規格 §3.4 已定義）與 TABLE_CLEANING_OVERDUE（規格的事件表沒列，這次依同格式新增）。查詢在唯讀交易裡完成，交易結束後才逐桌推播，推播期間不占資料庫連線（候位文章的「連線池用光」就是反例）；某一桌推播失敗只記錄、繼續下一桌，API 也不會因此回 500。
  • 前端：提醒列用「桌號＋種類」當識別，新推播只更新分鐘數，同一桌只顯示一筆；點超時提醒進入桌位詳情，點待清理提醒打開「清潔完成了嗎？」確認框，確認後提醒自動消失；按 × 後同一次超時不會再跳回來，等狀態變了（例如結帳）才會重新出現。收到推播時若目前桌況已對不上就不加入，修掉殘留的舊提醒。桌格分鐘數閃爍加上 motion-safe:，使用者開了系統「減少動態效果」就不閃（無障礙設計）。

用到的技術與設計模式

本篇真的用到的

  • Spring @Scheduled 與 6 欄位 cron、時區設定：TableReminderScheduler.java。
  • JPQL 分組查詢（GROUP BY／HAVING）與投影介面：DiningSessionRepository.java。
  • 唯讀交易、推播不放在交易裡：TableReminderService.java。
  • 冪等設計：每次重算、不存提醒狀態；排程與手動 API 共用同一個 Service（手動入口在 TableSchedulerController.java）。
  • WebSocket（STOMP）推播到櫃檯頻道；前端提醒合併、去重與 motion-safe：useTableStatusSocket.js、TableOverview.jsx。
  • 學到什麼：寫排程前先問「跑兩次會不會出事」「demo 時怎麼立刻看到效果」，答案就是冪等加上排程與手動 API 共用 Service；提醒要醒目但不吵，同一件事只提醒一次、能關掉、處理完自動消失，店員才不會開始無視提醒。
名詞表

新手名詞表

排程（scheduler）與 cron
排程是定時自動執行的程式；cron 描述「什麼時候執行」，Spring 用 6 個欄位：秒、分、時、日、月、星期。
冪等（idempotent）
同一件事做一次或很多次，結果都一樣。
JPQL 與 GROUP BY／HAVING
JPQL（Java Persistence Query Language，Java 持久化查詢語言）用 Java 物件名稱寫查詢，最後轉成 SQL；GROUP BY 把資料依欄位分組，HAVING 對分組後的結果再篩選。
唯讀交易
只讀不寫的交易。交易期間占用一條資料庫連線，所以不要在裡面做推播這種慢動作。
WebSocket 與 STOMP
WebSocket 是保持開著的連線，伺服器可主動推訊息；STOMP（Simple Text Oriented Messaging Protocol，簡單文字導向訊息協定）讓瀏覽器訂閱頻道，例如 /topic/counter。
COUNTER／MANAGER
店員角色：COUNTER 是櫃檯，MANAGER 是店長；手動觸發排程只限 MANAGER。
M2 規格與 API
M2 是專案規格文件的第 2 個模組「桌位、開桌與候位」；API（Application Programming Interface，應用程式介面）是前端呼叫後端功能的網址與規則。
motion-safe
Tailwind 的前綴，代表「只有使用者沒有要求減少動態效果時才套用」，閃爍效果加在這裡。
