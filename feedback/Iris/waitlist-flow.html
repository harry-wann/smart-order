哪裡錯

四個錯誤，都是「先查再做」中間被插隊

候位的狀態：WAITING（等待中）叫號後變 CALLED（已叫號）；已叫號未滿 10 分鐘可報到變 SEATED（已入座），滿 10 分鐘由排程標成 EXPIRED（已過號）；也能放棄變 ABANDONED。後三者是終態，不能再改。程式先「查」再「做」，中間只差幾毫秒，兩台櫃檯同時操作時另一個請求就可能改掉資料，這叫競態（race condition）。

錯誤 1：同一組客人入座了兩張桌

修正前

入座用一般的 findById 讀候位。櫃檯 A 選 A05、櫃檯 B 選 B02，幾乎同時送出，兩邊都讀到 A13 是 CALLED，各自鎖住不同的桌、誰也不用等誰，結果一組客人兩張桌、兩筆用餐紀錄。

同類漏洞

叫號、放棄、過號排程沒共用同一把鎖，可能把「已入座」改成「已過號」；WAITING 也能直接入座，跳過叫號。

錯誤 2：登記資料沒在伺服器檢查

畫面有擋，但 API（Application Programming Interface，應用程式介面）收到什麼就存什麼：空白姓名、電話不是四碼數字、人數 0／負數／21 人以上。畫面只是入口之一，規則一定要在後端再檢查一次。

錯誤 3：兩台櫃檯同時取號，拿到同一個號碼

原本找「最後一筆候位」的號碼 A14 再加一。兩台同時取號都讀到 A14、都發出 A15，號碼欄位又沒有「不可重複」的限制，兩筆 A15 都存進去。

錯誤 4：「今日過號」和「平均等待」永遠是 0

候位清單 API 只回傳等待中與已叫號的客人（這是對的），畫面卻拿同一份清單算過號與已入座的平均等待，這些客人根本不在清單裡。

整合時另外找到的兩個問題

A：20 人同時取號，請求卡 30 秒

後端紀錄寫著 Connection is not available (total=10, active=10 ...)。連線池（HikariCP，Spring Boot 預設）事先開好 10 條資料庫連線輪流借用，像只有 10 個車位的停車場。原本的推播在「交易提交後」還要讀一次資料庫，得再借一條，但原本那條還沒歸還：10 個請求各占 1 格、都在等第 2 格，卡到逾時。

B：S-10 在 1024 像素寬被撐破

側欄占 208 像素後，登記表單加候位表格放不下，出現橫向捲軸，狀態標籤被擠成直排的「已／叫／號」。改動前就有，因為改的正是這頁所以一起修：未滿 1280 像素時表單放上方、表格在下。

怎麼修

讓「查」和「做」變成不能被插隊的一步

  • 狀態改變排同一條隊：叫號、放棄、入座、過號第一步都用 SELECT ... FOR UPDATE 讀這筆候位，加上資料列鎖：誰先拿到誰先做，後來的要等，拿到後重讀就是最新狀態。櫃檯 B 這次會等 A 存檔，讀到 SEATED，收到 409 WAITLIST_STATUS，B02 沒被動到。入座先鎖候位、再鎖桌位，順序固定，否則兩個請求各拿一把互等會變死結（deadlock）。規則都在鎖裡檢查，開桌失敗整個交易取消，候位仍是 CALLED。最後防線是 dining_session.waitlist_id 的唯一索引，資料庫不收兩筆用餐紀錄指向同一組候位。
  • 取號改用「只有一個把手的抽號機」：新增只有一列的序號表 waitlist_ticket_counter，取號時先鎖這一列、拿號碼、加一再新增候位；waitlist.ticket_no 也加唯一索引。
  • 登記資料在伺服器檢查：姓名去空白後不為空、至多 50 字，電話剛好 4 個數字，人數 1 到 20；不合規則回 400 VALIDATION_FAILED，而且不會用掉號碼（檢查在拿號碼之前）。
  • 10 分鐘期限，兩處剛好互補：入座與再叫一次要「現在 < 叫號時間＋10 分鐘」，否則 409 WAITLIST_EXPIRED；排程要「現在 ≥ 叫號時間＋10 分鐘」才標 EXPIRED，不重疊、不留空隙。「再叫一次」不改叫號時間，否則一直按就永遠不過號。
  • 今日統計改由後端算：新增 GET /api/admin/waitlist/today-summary，以台北的「今天」回傳各狀態組數與平均等待，畫面改讀它。
  • 連線池卡死：提交後不在原請求裡讀資料，而是把「讀資料＋推播」交給單一背景執行緒排隊：請求先歸還連線，背景再借一條，單一執行緒也讓推播照提交順序送出。推播失敗只記錄，不讓已成功的取號回錯誤，否則店員以為失敗再按就多一筆重複候位。桌況推播（TableStatusNotifier）寫法相同，一併修正。

補上的基本功能（整合時補上，不算原作者的缺失）

M2 規格要求叫號用 WebSocket 推到候位螢幕、過號排程附手動觸發 API，但原本叫號只改資料庫，「再叫一次」只在瀏覽器主控台印一行字。補上：

  • 即時推播：叫號推 WAITLIST_CALLED，任何變動推 WAITLIST_UPDATED 到 /topic/waitlist 與 /topic/counter，只有櫃檯與店長能訂閱。一律在交易提交之後才送，不會「螢幕叫號了但資料沒存」。
  • 候位叫號螢幕：新頁面 /admin/waitlist/display，從 S-10 開在另一個視窗，可拖到門口螢幕，叫號時大字顯示 8 秒，沒有後台側欄。「再叫一次」改為真的呼叫後端。
  • 店長手動過號：POST /api/admin/scheduler/expire-waitlist 只限 MANAGER（COUNTER 得 403），與每分鐘排程呼叫同一段程式，demo 不必等 10 分鐘。
  • 審查的改進：選桌失敗後對話框重抓空桌清單並清空選取，讓店員自己重選，不默默換桌。

用到的技術與設計模式

本篇真的用到的

  • 悲觀鎖加固定鎖順序、唯一索引當最後防線：WaitlistService.java、WaitlistRepository.java、schema.sql。
  • Spring @Transactional（READ_COMMITTED：每次查詢都讀得到別人已提交的結果）與狀態機終態保護：WaitlistService.java。
  • Spring @Scheduled 排程（cron 加台北時區）與手動觸發 API：WaitlistScheduler.java、WaitlistSchedulerController.java。
  • WebSocket＋STOMP 推播、交易提交後才發布（afterCommit）、單一背景執行緒：WaitlistNotifier.java、useWaitlistSocket.ts（@stomp/stompjs）。
  • 前端防連點、TanStack Query 讓快取失效後重抓：WaitlistManagement.jsx、WaitlistSeatDialog.jsx；驗證用 Python 同時送請求加 Playwright（用程式控制瀏覽器）多視窗測試。
  • 學到什麼：寫狀態機前先畫「狀態 × 動作 → 新狀態」表，每個改狀態的方法第一行就鎖資料；問「兩個請求同時走到這行會怎樣」，並真的同時送出去看。提交後的程式還占著連線，裡面不能再借連線。
名詞表

新手名詞表

HTTP 狀態碼 200／400／403／409／500
200 成功；400 資料不合規則；403 角色沒有權限；409 與目前資料狀態衝突；500 伺服器內部出錯（5xx 泛指 500 開頭的伺服器錯誤）。
S-10／M2 規格
S-10 是 UI（User Interface，使用者介面）規格的候位管理頁編號；M2 規格是專案規格文件的第 2 個模組「桌位、開桌與候位」。
資料列鎖與死結
資料列鎖讓同一筆資料的操作排隊；死結是兩個請求各拿一把鎖又等對方那把，誰都動不了。
唯一索引（UNIQUE index）
資料庫層的規則：某欄位的值不能重複，程式寫錯時資料庫仍會拒絕。
afterCommit（提交後回呼）
交易成功存檔之後才執行的程式，用它發推播就不會「螢幕叫號了、資料卻沒存成功」。
WebSocket 與 STOMP
WebSocket 是保持開著的連線，伺服器可主動推訊息；STOMP（Simple Text Oriented Messaging Protocol，簡單文字導向訊息協定）讓瀏覽器訂閱頻道，例如 /topic/waitlist。
